# 乐影（SFC）同种券「一票多张」出票与报价设计

- 日期：2026-10-30
- 范围：`src/common/autoTicket/buyTicket/sfc/**`（SFC / 乐影系列）
- 配置粒度：**报价规则级（ruleId）**，默认 1 张/票，未配置的规则行为零变化
- 依据：Charles 抓包 `无标题2.har`（场次 668235，2 张票用 4 张券，实付 0 元）

## 一、背景与问题

业务诉求：乐影某些影院的特殊厅晚场，需要用**同一种券的 2 张抵 1 张票**来出票（捡漏场景），要求机器出票与报价都能识别这个口径。

现有实现是「一票一券」硬口径：

- 报价：券成本按**单张** `quan_cost` 计，规则库存门槛 `quan_stock >= ticket_num`；
- 出票：`useQuans = quanList.filter((item, index) => index < ticket_num)`，只用 `ticket_num` 张；
- 库存：出票成功后按 `ticket_num` 扣减。

### 抓包结论（本次需求的可行性依据）

1. 多券是接口原生能力：`price/calculate` 的 `quan_code` 与 `order/ng-create` 的 `coupon` 都是**逗号分隔的券码串**，抓包一次传了 4 个券码；
2. 抓包为 **2 票 4 券（每票 2 张）**，`total_price` 收口到 `0.00`，`ng-create` 成功，证明平台接受「券数 = 票数 × 2」；
3. 挂券后**票价基座会变**：无券时 `ticket_price=202`，挂券后抬到 `240`（券可兑票价 120/张）。因此**券没覆盖满反而更贵**（只用 1 张时代付 211 > 204）。这决定了出票必须强校验「实付 ≤ 手续费合计」；
4. `handle_fee` 不稳定（2 券 1.00、4 券 0.00），一切以 `price/calculate` 返回金额为准。

## 二、目标与非目标

### 目标

- 对**指定报价规则**，一张票使用同一券类型的 N 张券（本次 N=2）：
  - 报价：券成本 = `quan_cost × N`，规则券库存门槛 = `ticket_num × N`；
  - 出票：取 `ticket_num × N` 张券，券码串原样交给 `price/calculate` 与 `ng-create`；
  - 利润、手续费、出票后库存扣减均按 N 倍口径。
- 未配置的规则（含其他全部影院系列）行为完全不变。

### 非目标（本次不做）

- 不支持一张票混用**多种**券类型（抓包虽是同名券，但本需求已确认为同种券多张）；
- 不改数据库表结构、不改 auto-ticket-service、不改规则弹窗 UI；
- 不改共享模块 `commonQuanStock.js`（猎人规则同步的库存收缩口径保持现状）；
- 不改「多用券数量与票数不一致」等平台报错的换券重试机制。

## 三、术语与口径

| 术语 | 含义 |
|---|---|
| `quan_per_ticket` | 每票券张数，默认 1；本次目标规则配置为 2 |
| 张 | 券的物理单位，`quan_stock` / `quan_stock_list` 均为张数 |
| 票 | 订单票数 `ticket_num` |
| 需求券数 | `ticket_num × quan_per_ticket` |

**成本口径**：`quan_cost` 为**每张**券的成本，故每票券成本 = `quan_cost × quan_per_ticket`。
**库存口径**：库存为张数，「还能出几张票」= `quan_stock ÷ quan_per_ticket`。

## 四、配置设计

`src/common/constant.js` 新增一张默认空的映射表（客户端常量，零后端改动）：

```js
// 乐影：规则级「每票券张数」配置（默认 1；未配置的规则走原有"一票一券"逻辑）
// key = 报价规则 id；value = 每票使用的券张数（同一券类型的 N 张抵 1 张票）
export const SFC_QUAN_PER_TICKET = {
  // 4501: 2
};
```

解析函数（新增 `src/common/autoTicket/buyTicket/sfc/quanPerTicket.js`，纯函数、可单测）：

```js
getQuanPerTicket(offerRule) =>
  Number(SFC_QUAN_PER_TICKET[offerRule?.offer_rule_id ?? offerRule?.id] ?? 1) || 1;
```

- 取不到配置 → 返回 `1`，所有调用点与现状等价；
- 非正整数（脏配置）→ 归一为 `1`，避免 0 张/负数造成除零与空券串；
- 规则 id 在测试库/生产库不同，需各自配置一份（已在设计中确认接受）。

## 五、行为规格

### 5.1 报价

| 环节 | 现状 | N>1 时 |
|---|---|---|
| 券成本 | `getQuanInfo(quanValue)?.quan_cost`（多类型取 min） | 单类型：`quan_cost × N`；多类型（规则多选了候选券类型）：`min(quan_costs) × N`（与现状"取最优候选"语义一致）；**两种情形都不写入 `this.quanInfoList`**，避免基类 `maxCostPrice` 过滤把券类型裁掉 |
| 规则库存过滤 | `itemA.quan_stock >= order.ticket_num` | `itemA.quan_stock >= order.ticket_num × N` |
| 利润校验 | `报价 - (券成本 + 手续费)` | 券成本已提升为 N 倍，校验逻辑不变 |

实现方式：在 `sfc/offerManage.js` 覆写 `getCostPrice(offerRule)`（只在 N>1 时接管，N=1 时 `super`），并调整固定报价规则的库存过滤条件。基类 `BaseOfferPrice` 零改动。

### 5.2 出票（选券）

- 券数量门槛：`quanList.length < ticket_num × N` 即判「券不足」，走既有换号 / 转单 / 灵活用券兜底，**不允许半量下单**；
- 规则多选券类型时的候选收敛：现有逻辑按「该类型 `quan_stock >= ticket_num` 且库存最高」收敛为一个类型，N>1 时门槛改为 `quan_stock >= ticket_num × N`（收敛后仍只用一个类型，本次不做多类型混用）；
- 会员赠券分组：`groupList.find(group => group.length >= ticket_num × N)`；
- 绑定补券差额：`diffNum = ticket_num × N − 已有券数`；
- 选券：`useQuans = quanList.filter((item, index) => index < ticket_num × N)`；
- 券码串：`quan_code / coupon_nums` 仍为 `useQuans.map(...).join()`，天然支持 N 张，**不新增字段**。

### 5.3 出票（利润、手续费、校验）

- 利润：`profit = (supplier_end_price − quan_cost × N − 手续费) × ticket_num`；
  负利润判断沿用现状（`TEST_NEW_PLAT_LIST` 除外）。
- 手续费：`quan_fee_total = quan_fee × ticket_num × N`；
  实现上复用 `validateCouponPrice`，调用时把票数实参传成 `ticket_num × N`，**基类零改动**。
- 价格强校验（关键）：`pay_money > quan_fee_total` 即判失败并转单。
  依据抓包第 3 条——挂券后票价基座抬升，券未覆盖满会亏；该断言保证「券必须覆盖完实付」。

### 5.4 出票后库存与快照

- 库存扣减：`quan_stock = quanStock − ticket_num × N`（`quanStock` 为张数）；
- 出票前写回库存仍按张数口径，`_getQuanListForPay` 的 `quanStockNum / realStockNum` 语义不变；
- `ticket_record.coupons` 快照沿用现有 `coupon_nums` 拆分逻辑，无表结构变更（注意 `slice(0, 10)` 上限，N=2 时最多覆盖 5 张票的快照）。

## 七、兼容与回退

- **默认关闭**：映射表为空时 `getQuanPerTicket` 恒返回 1，所有分支与现状字节级等价；
- **回退方式**：删除对应规则条目即可，无需发版回滚；
- **作用域隔离**：只在 SFC 系列的选券/算价路径读取配置，其他系列不引用该函数。

## 八、风险

| 风险 | 评估 | 缓解 |
|---|---|---|
| 平台是否接受「券数 > 票数」 | 中低：抓包 2 票 4 券已证明 2:1 比例可用；1 票 2 券仍建议手工验一次 | 上线前用 1 张票 + 2 张券手工下单验证 `total_price=0` 且 `ng-create` 成功 |
| 手续费按张还是按单收 | 中：抓包 `handle_fee` 在 2 券/4 券时不同 | 出票只信 `price/calculate` 返回的 `total_price`；卡余额校验按 N 倍偏保守（多要余额，不会错买） |
| 券后价基座抬升导致部分覆盖亏损 | 高（业务侧）：只用 1 张时实付 211 > 无券 204 | `validateCouponPrice` 强校验「实付 ≤ 手续费合计」，不满足直接转单并记 error 日志 |
| 库存临界时规则误保留 | 低：共享模块 `commonQuanStock.js` 的收缩口径未改，仍按 `ticket_num` 判断，偏宽松 | 本次接受；若出现「报价成功但券不足」告警密集，再单独立项调整规则同步口径 |
| 多票时券快照被截断 | 极低：`slice(0, 10)`，N=2 时 5 张票以上快照不全 | 快照仅用于排查展示，不影响出票与核销 |
| 配置规则 id 环境不一致 | 低：测试库/生产库 id 不同 | 配置项加注释要求「按环境各配一份」，未配一律按 1 张/票 |

## 九、测试计划

### 单元测试（新增 `src/common/tests/sfcQuanPerTicket.test.js`）

1. `getQuanPerTicket`：未配置 → 1；配置 2 → 2；脏值（0 / 负数 / 非数字）→ 1；
2. 报价成本：N=1 与 N=2 下 `getCostPrice` 返回值（mock `getQuanInfo`）；
3. 选券：`ticket_num=2, N=2` → 取 4 张；`quanList` 只有 3 张 → 判券不足返回空；
4. 利润：`supplier_end_price=101, quan_cost=40, N=2, ticket_num=2` → 利润为负时返回 `{profit:0,useQuans:[]}`；
5. 手续费校验：`pay_money=0` 通过、`pay_money=10` 拒绝。

### 联调验证（测试单，不购买）

`window.sfcTicketObj(order, true).singleTicket()` 跑到算价后取消，核对日志中：

- `计算订单价格参数` 的 `quan_code` 是否含 `ticket_num × N` 个券码；
- `创建订单参数` 的 `coupon` 券码数量一致、`pay_money` 为 `0`；
- `使用卡券成功` 的 `profit` 与手工计算一致。
