# 乐影（SFC）券兑换比例「N 张券 : 1 张票」设计

- 日期：2026-10-30（V4 修订：2026-11-13，采纳代码评审）
- 范围：`rule_record` 新字段 + auto-ticket-service 取数 + 规则弹窗 + SFC 报价/出票
- 依据：Charles 抓包 `无标题2.har`（场次 668235，2 张票用 4 张券，实付 0 元）
- 配套文档：`doc/changes/2026-10-30-乐影券兑换比例一票多张整改说明.md`（含逐段代码对照与评审修订记录）

## 一、背景与需求

乐影（SFC 系列）部分影院特殊厅晚场存在"用同一种券的 2 张抵 1 张票"的捡漏出票场景，需要机器报价与出票都按该比例执行。

**本次确定的五个口径**：

1. **规则级配置**：兑换比例是报价规则上的字段（不是客户端常量、不是券类型字段）；
2. **三重限定可配置**：乐影系列（`sfc_applet`）**且** 内部角色（`IN_RULE_LIST`）**且** 固定报价规则（`offerType === "1"`）；
3. **券库存口径不变**：`quan_stock` 仍是"张数"，不引入"可出票数"字段、不做 `stock ÷ N` 换算；只改消费方式——报价门槛、座位数收缩、出票选券/绑券；
4. **出票读规则当前值**（联表），不落快照；规则在客户端 store 的刷新链路已覆盖（登录 / 规则页保存 / 券库存同步）；
5. **该规则不同步猎人平台**（`isSyncPlat = 2`），全程机器本地报价 + 机器出票，不存在平台口径分裂。

### 抓包证据

1. 多券是接口原生能力：`price/calculate` 的 `quan_code`、`order/ng-create` 的 `coupon` 都是逗号分隔券码串；
2. **2 票 4 券（每票 2 张）**，`total_price=0.00`，`ng-create` 成功 → 平台接受「券数 = 票数 × 2」；
3. 挂券后**票价基座会变**：无券 202，挂券后 240（券可兑价 120/张）→ 券没覆盖满反而更贵（只用 1 张时实付 211 > 204）；
4. `handle_fee` 不稳定（2 券 1.00、4 券 0.00），金额一律以 `price/calculate` 返回为准。

## 二、目标与非目标

### 目标

- 固定报价规则新增「券兑换比例」（正整数：每票消耗券张数；空/NULL/1 = 一票一券）；
- 报价：库存门槛 `ticket_num × N`、券成本 `quan_cost × N`、座位数 `floor(maxQuanStock / N)`；
- 出票：取 `ticket_num × N` 张券，券码串原样交给 `price/calculate` 与 `ng-create`；
- 比例未配置时，所有链路与现状一致。

### 非目标

- 不改券库存存储口径；
- 不支持一张票混用多种券类型；
- 不落 `offer_record` 比例快照、不加成本一致性守卫、不加规则 TTL 刷新；
- 不把票数乘 N 用于 `daily_ticket_count`（单位是票）；
- 不修复「价格校验对所有 SFC 券单生效」这件事，仅对配了比例的规则启用（见 4.6）。

## 三、数据模型与取数

### 3.1 新字段

`rule_record.quanExchangeRatio`（`TINYINT UNSIGNED NULL DEFAULT NULL`）：

| 值 | 含义 |
|---|---|
| `NULL` / `1` | 一票一券 |
| `2` | 2 张券兑 1 张票 |

列名 camelCase 与 `quanValue` / `bWalletMarkup` 一致。后端 `ruleRecord.add/update` 是动态 SQL、`findRecordData` 是 `select *` → **后端规则接口无需改**。

### 3.2 取数键

| 阶段 | 来源 | 键 |
|---|---|---|
| 报价 | 本地 store（`offerRuleMatch` ← `offerRuleList` ← `queryRuleList`） | `quanExchangeRatio` |
| 出票 | `queryOfferInfo`（`offer_record` + 券类型 + 规则） | `quan_exchange_ratio` |

解析统一走 **`src/common/autoTicket/quanPerTicket.js`** → `getQuanPerTicket(rule)`，**所有消费点只经它取值，禁止直接读字段**（避免各点各写一套默认值）。

> 放 common 层而非 `buyTicket/sfc/`：`commonQuanStock.js` 也要用，避免 common 反向依赖 sfc。

#### 3.2.1 归一化规则（硬约定：取不到就是 1）

| 入参 | 结果 | 说明 |
|---|---|---|
| `2` / `"2"` | `2` | 正整数（含数字字符串） |
| `1` / `"1"` | `1` | 等于默认 |
| `null` | `1` | **老规则（DDL 前创建，列为 NULL）** |
| `undefined` | `1` | **取不到该键**：旧 store 缓存、接口未返回该列 |
| `""` / `" "` | `1` | 表单清空后落库前的空值 |
| `0` / `-1` | `1` | 非法值（0 张券无业务含义） |
| `2.5` / `"2.5"` | `1` | **非整数一律回退 1**（不猜意图，避免成本算错） |
| `NaN` / `"abc"` / `{}` / `true` | `1` | 脏数据 |

配套要求：

1. **默认值只在 `getQuanPerTicket` 一处兜底**，报价与出票的 18 个消费点全部调用它；
2. 命中非法值（非 1 的脏值）时打一次 `warn` 日志（含 rule id / 原值），便于发现脏配置；归一为 1 属于正常路径，不刷日志；
3. 所有换算都以 `ratio = getQuanPerTicket(...)` 为准，`ratio === 1` 时各消费点走原有分支，保证"老规则行为零变化"。

### 3.3 出票阶段取比例（LEFT JOIN）

主查询加联表别名即可，**一次查询拿全**：

```sql
SELECT offer_record.*, rule_record.quanExchangeRatio AS quan_exchange_ratio
FROM offer_record
LEFT JOIN rule_record ON offer_record.offer_rule_id = rule_record.id
WHERE offer_record.user_id = ? AND offer_record.app_name = ?
  AND offer_record.order_number = ? AND offer_record.plat_name = ?
LIMIT 1
```

| 场景 | 行为 |
|---|---|
| 老规则（`quanExchangeRatio` 为 NULL） | `quan_exchange_ratio: null` → 客户端归一为 1 |
| 老订单（`offer_rule_id` 为空） | JOIN 不上 → `null` → 1 |
| 规则行已配 2 | `quan_exchange_ratio: 2` |
| 非乐影系列 | 取值存在但不被任何代码读取，行为不变 |

WHERE 列名加 `offer_record.` 前缀消歧；`rule_record` 只取一列别名，不覆盖 `offer_record` 同名列。

> **前提**：本次 DDL（`rule_record.quanExchangeRatio`）必须先于后端发布执行。若列不存在，`queryOfferInfo` 会因 `Unknown column` 整体报错，而它被 `ticketRecord.js` 等多处复用 → 影响所有系列。
> 因此把"列是否存在"作为**发布前自检项**（`SHOW COLUMNS FROM rule_record LIKE 'quanExchangeRatio'`），而不是在运行时加 try/catch 兜底：那会为每单多一次往返、并可能把真实连接错误吞成"按 1 处理"，反而更难排查。

## 四、行为规格

### 4.1 规则表单（`RuleDialog.vue`）

显示条件（三条件同时满足）：

```js
const showQuanExchangeRatio = computed(() =>
  formData.offerType === "1" &&
  GET_APP_INFO(formData.shadowLineName)?.app_type_code === "sfc_applet" &&
  IN_RULE_LIST.includes(Number(rule))
);
```

- 需要新增 `IN_RULE_LIST` 与 `platTokens` 导入（当前文件未引入，直接粘贴会 ReferenceError）；
- 表单项：`type="number"`，提示「每张票消耗券张数，2 表示 2 张券兑 1 张票；留空即一票一券。报价成本 = 券库单张券成本 × 该比例」；
- 校验：留空或 1-20 的整数（`QUAN_RATIO_MAX`），否则提交前拦截；
- **额外两种规则保存时拦截并清空**（告警后阻断本次保存，字段置空）：
  - 已同步猎人平台（`platOfferList` 中 `lieren.isSyncPlat == 1`）——否则平台按 1:1 报价、本地按 N:1 出票；
  - 选择了多个券类型（`quanValue.length > 1`）——座位数收缩按单一券类型匹配，多值无法收缩；
- 编辑回填 `formInfo.quanExchangeRatio ?? ""`；新增/重置清空；
- `IN_RULE_LIST = [2]` 不含管理员（1）；若管理员要配，需显式并入。

### 4.2 规则保存（`views/offerRule/index.vue`）

- 判定统一走 `validateQuanRatioInput({ ratio, quanValueCount, isLierenSynced })`（与弹窗同一套口径）；
- **乐影内部角色一律写值或 `null`**：非固定报价 / 多券类型 / 已同步猎人 / 非法值 → 写 `null` 清除历史残留（否则固定报价切会员加价后，出票走灵活用券仍按 N 倍取券）；
- **只有外部角色 / 非乐影才 `delete` 字段**，避免把别人配的值抹掉；
- 纳入 `NEW_RULE_COLUMNS` 缺列兜底（`quanExchangeRatio` / label「券兑换比例」/ `isUnknownQuanExchangeRatioError`）；
- 比例上限 1-20（`TINYINT UNSIGNED` 上限 255，业务上 20 已远超实际，防止误填导致巨额取券）。

### 4.3 报价：券库存门槛（5 处，全部 ×N）

| # | 位置 | 判断 |
|---|---|---|
| 1 | `sfc/offerManage.getMinAmountOfferRule` | `itemA.quan_stock >= order.ticket_num` |
| 2 | `filterFixedRulesByDailyTicketCount` 过滤可用手机号 | `itemA.quan_stock < ticket_num` |
| 3 | 同函数，手机号二次判断 | `Number(p.quan_stock) >= ticket_num` |
| 4 | 同函数，过滤规则关联券类型 | `itemA.quan_stock >= ticket_num` |
| 5 | 同函数，按手机号循环 | `Number(p.quan_stock) < ticket_num` |

**不乘 N**：同函数内 `remaining >= ticket_num`（`daily_ticket_count` 后端按 `SUM(ticket_num)` 统计，单位是票）。平台实际限额是否按券张数计，见 R11/待确认。

### 4.4 报价：券成本（`getCostPrice` 覆写）

```js
async getCostPrice(offerRule) {
  const ratio = getQuanPerTicket(offerRule);
  if (offerRule.offerType !== "1" || ratio <= 1) return super.getCostPrice(offerRule);
  const quanInfo = await this.cardQuanManage.getQuanInfo(offerRule.quanValue, this.appFlag);
  const list = (Array.isArray(quanInfo) ? quanInfo : quanInfo ? [quanInfo] : []).filter(Boolean);
  if (!list.length) return null;
  this.quanInfoList = list.map(i => ({
    ...i,
    quan_cost: mulDecimal(Number(i.quan_cost || 0), ratio)
  }));
  return Math.min(...this.quanInfoList.map(i => Number(i.quan_cost || 0)));
}
```

- **必须带 `offerType !== "1"` 守卫**：基类对会员加价规则返回 `memberCostPrice`，否则会员价算价直接错；
- **空列表返回 `null`**：`Math.min()` 得 `Infinity` 会让基类误判有成本；
- **保留 `quanInfoList` 且预乘 N**：基类用它按 `maxCostPrice` 裁剪券类型，清空会让多券类型规则选到高成本券。

### 4.5 报价：座位数随券库存收缩

```js
const effStock = Math.floor(maxQuanStock / ratio);
let targetSeatNum = effStock >= 4 ? 4 : effStock;
let targetStatus = targetSeatNum == 0 ? "2" : "1";
```

现逻辑只匹配「固定报价 + 已同步猎人（`isSyncPlat === 1`）」，本次规则不同步平台，须追加 `|| ratio > 1` 才能生效；这类规则**只更新本地 `seatNum/status`，跳过 `lierenOfferRuleSyncPlat`**，日志 `trigger_source = quan_stock_update_local`。

效果：10 张 → 4（上限）、3 张 → 1、1 张 → 0 → 禁用。

### 4.6 出票：选券与异步绑券（14 处）

```js
const ratio = getQuanPerTicket(offerRule);
const needQuanNum = ticket_num * ratio;
```

| # | 位置 | 改后 |
|---|---|---|
| 1 | `buyTicket.getCinemaLoginInfo` 选号门槛 | 传 `needQuanNum` |
| 2 | `useQuanOrCard` 多券类型收敛库存 | `>= needQuanNum` |
| 3/4 | `useQuanOrCard` 券不足判断 + 补券差额 | `< needQuanNum` / `needQuanNum - 已有` |
| 5 | `useQuanOrCard` 券不足判断（主流程） | `< needQuanNum` |
| 6 | 手续费垫卡余额 | `quan_fee × needQuanNum` |
| 7 | `_getQuanListForPay` 赠券分组 | `>= needQuanNum` |
| 8 | `getNewQuan` 绑券后库存修正 | `quanStock - needQuanNum + 新增` |
| 9/10 | `useQuan` 触发阈值 / 补券数量 | `length - needQuanNum < 10` / `10 - (length - needQuanNum)`，下限 ≥1 |
| 11 | `useQuan` 取券上限 | `index < needQuanNum` |
| 12 | `useQuan` 利润 | `(卖价 − quan_cost × N − 手续费) × ticket_num` |
| 13 | `buyTicket` 价格校验 | 传 `needQuanNum` + 真实券列表（见 4.7） |
| 14 | `buyTicket` 出票后核销扣减 | `quanStock - needQuanNum` |

**注意**：E#1 的库存判断与 4.3 #5 是同一处表达式（`sortPhonesByQuanValueAndStock`），统计唯一处数时只算一次 → 报价 5 + 出票 14 − 共用 1 = **18 处**。

### 4.7 价格强校验（含现状缺陷修复）

**现状**：`buyTicket` 调 `validateCouponPrice({ useQuan: useRes?.useQuan || [] })`，而 `useQuanOrCard` 返回体没有 `useQuan` 字段 → 恒为空 → 基类 `!useQuan?.length` 直接放行，**该校验对所有 SFC 券单从未生效**。

修复（按比例规则限定，避免存量行为突变）：

```js
const usedCouponList = String(coupon_nums || quan_code || "").split(",").filter(Boolean);
const couponCheck = this.validateCouponPrice({
  offerRule,
  ticket_num: needQuanNum,
  paymentAmount: pay_money,
  useQuan: ratio > 1 ? usedCouponList : useRes?.useQuan || []
});
```

规则：`pay_money > 手续费合计（quan_fee × needQuanNum）` 即失败转单。依据抓包第 3 条——券未覆盖满时实付反而更贵。

### 4.8 其他

- 券码串 `quan_code / coupon_nums`、`ng-create` 的 `coupon`、黑名单、`ticket_record.coupons` 快照均不改；
- 出票后核销按 `needQuanNum` 扣减；`_getQuanListForPay` 写回库存仍按张数。

## 六、兼容与回退

- 默认关闭：NULL/1 时全部 ×1，与现状等价；
- 灰度：仅目标影院那一条固定报价规则填 2；
- 回退：清空该规则比例即可；
- 上线顺序：DDL（含表结构文档）→ 后端 → 客户端 → 配置规则 → 确认 `isSyncPlat = 2`；
- 客户端先行有缺列兜底。

## 七、风险

| # | 风险 | 评估 | 缓解 |
|---|---|---|---|
| R1 | 平台是否允许券数 > 票数 | 中低：2 票 4 券已验证，1 票 2 券未验证 | 上线前手工验 1 票 2 券 |
| R2 | 手续费按张还是按单 | 中 | 只信 `total_price`；垫卡余额按 N 倍偏保守 |
| R3 | 券后价基座抬升导致部分覆盖亏损 | 高 | 4.7 强校验（须先修空转） |
| R4 | 座位数收缩对未同步平台规则不生效 | 中 | 4.5 放宽作用域 |
| R5 | 编辑时残留或抹掉比例 | 中 | 4.2：乐影内部角色一律写值/`null`（含非固定报价清空），外部角色/非乐影才 `delete` |
| R6 | 利润二次放大 | 中 | 4.6 #12 |
| R7 | 券快照截断 | 极低：N=2 时 6 票起才不全（5 票正好 10 张） | 仅影响展示 |
| R8 | 单订单券数上限未知 | 低-中 | 灰度先用小票数 |
| R9 | 异步绑券库存修正漏改 | 中：库存虚高、持续超发 | 4.6 #8 + 单测 |
| R10 | 报价后改比例的口径漂移 | 中：出票按新值，该单可能被拦成转单（不亏钱） | 改配置避开待出票高峰；观察改配置后 10 分钟内的失败 |
| R11 | `daily_ticket_count` 限额口径未知（票 vs 券） | 低-中 | 先按票（与代码一致），确认后再定 |
| R12 | DDL 未执行就发后端 | 低：列不存在会让 `queryOfferInfo`（多系列复用）`Unknown column` 报错 | 发布前自检 `SHOW COLUMNS FROM rule_record LIKE 'quanExchangeRatio'`；DDL 必须先行；上线后用一条非乐影订单验证 `queryOfferInfo` |
| R13 | 老规则/老订单取不到比例 | 极低：JOIN 得 `null`，统一归一到 1，行为等价上线前 | 单测覆盖 NULL/undefined/空串/0/负数/小数 |
| R13 | 老规则/老订单取不到比例 | 极低：统一归一到 1，行为等价于上线前 | 单测覆盖 NULL/undefined/空串/0/负数/小数，见第八节 |

## 八、测试计划

单测（`src/common/tests/sfcQuanExchangeRatio.test.js`，19 项）：

1. **归一化**：`2/"2"` → 2；`null`、`undefined`、`""`、`" "`、`0`、`-1`、`2.5`、`NaN`、`"abc"`、`{}`、`true` → 1（逐项覆盖 3.2.1 表）；
2. 归一化：snake 键 `quan_exchange_ratio` 同样识别；两键同时存在时 camel 优先；
3. 成本：`offerType=1` 的 N=1 / N=2 / 多券类型；
4. 成本：`offerType=2` 必须走 `super`（不查券成本）；
5. 成本：`quanInfo` 为空返回 `null`；
6. 库存门槛 5 处 ×N（`stock=3/4` 对照）与日出票数**不乘**；
7. 选券：4 张 / 不足 3 张不半量下单；
8. 异步绑券：差 10 **不触发**、差 5 补 5、差 2 补 8；绑券后库存 `20−4+6=22`；
9. 座位数：`10/2→4`、`3/2→1`、`1/2→0 禁用`；
10. 利润：`quan_cost=60, N=2` 时负利润拒绝；N=1 对照不被放大；
11. 价格校验：`ratio>1` 时 `pay_money=0/10` 通过/拒绝；`ratio=1` 保持原行为。
