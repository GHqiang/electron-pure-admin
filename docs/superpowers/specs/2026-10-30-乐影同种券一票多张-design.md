# 乐影（SFC）券兑换比例「N 张券 : 1 张票」设计

- 日期：2026-10-30
- 版本：V3（V1 客户端常量、V2 出票取快照，均已废弃）
- 范围：`rule_record` 新字段 + auto-ticket-service 取数 + 规则弹窗 + SFC 报价/出票
- 依据：Charles 抓包 `无标题2.har`（场次 668235，2 张票用 4 张券，实付 0 元）

## 一、背景与需求

乐影（SFC 系列）部分影院特殊厅晚场存在"用同一种券的 2 张抵 1 张票"的捡漏出票场景，需要机器报价与出票都按该比例执行。

**本次确定的五个口径**：

1. **规则级配置**：兑换比例是报价规则上的字段（不是客户端常量、不是券类型字段）；
2. **仅乐影系列 + 内部角色**可配置该字段；
3. **券库存口径不变**：`quan_stock` 仍是"张数"，不引入"可出票数"字段、不做 `stock ÷ N` 换算；只改两处消费方式——**报价的库存门槛**与**出票的选券张数**；
4. **出票读取规则的当前值**（联表取 `rule_record`），不落快照；规则在客户端 store 的刷新链路已覆盖（登录 / 规则页保存 / 券库存同步），改完即生效；
5. **该规则不同步猎人平台**（`isSyncPlat = 2`），全程由机器本地报价 + 机器出票。因此不存在"平台按住 1:1 报价、机器按 2:1 出票"的口径分裂问题，本设计只需保证本地算价与本地出票同源。

### 抓包证据（可行性依据）

1. 多券是接口原生能力：`price/calculate` 的 `quan_code` 与 `order/ng-create` 的 `coupon` 都是**逗号分隔的券码串**；
2. 抓包为 **2 票 4 券（每票 2 张）**，`total_price` 收口到 `0.00`，`ng-create` 成功 → 平台接受「券数 = 票数 × 2」；
3. 挂券后**票价基座会变**：无券 `ticket_price=202`，挂券后 240（券可兑价 120/张），**券没覆盖满反而更贵**（只用 1 张时代付 211 > 204）；
4. `handle_fee` 不稳定（2 券 1.00、4 券 0.00），金额一律以 `price/calculate` 返回为准。

## 二、目标与非目标

### 目标

- 报价规则新增「券兑换比例」字段（正整数，语义：**每张票消耗券张数**；2 表示 2 张券兑 1 张票；空/NULL/1 表示一票一券）；
- 该字段仅在**乐影系列（`app_type_code === "sfc_applet"`）+ 内部角色（`IN_RULE_LIST`）**时展示与保存；
- 报价：命中比例的规则，券库存门槛按 `ticket_num × N`、券成本按 `quan_cost × N`；
- 出票：取 `ticket_num × N` 张券，券码串原样交给 `price/calculate` 与 `ng-create`；
- 比例未配置时，所有链路与现状一致。

### 非目标

- 不改券库存存储口径（仍为张数），不新增库存换算字段；
- 不支持一张票混用多种券类型（本需求是同一券类型的 N 张）；
- 不落 `offer_record` 比例快照、不加成本一致性守卫、不加规则 TTL 刷新（团队确认：跨机不同步的场景不存在，规则保存后本机 store 立即刷新）；
- 不改"按库存自动收缩规则座位数"的逻辑（见风险 R4）。

## 三、数据模型与取数路径

### 3.1 新字段

`rule_record.quanExchangeRatio`（`TINYINT UNSIGNED NULL DEFAULT NULL`）：

| 值 | 含义 |
|---|---|
| `NULL` / `1` | 一票一券（现状） |
| `2` | 2 张券兑 1 张票 |
| 其他正整数 | N 张券兑 1 张票 |

列名用 `camelCase`，与 `quanValue` / `bWalletMarkup` / `offerTppRange` 一致。后端 `ruleRecord.add/update` 是按 payload key 拼 SET 的**动态 SQL**，加列后无需改后端代码；`findRecordData` 为 `select *`，新列自动返回。

### 3.2 两个阶段的取数键

| 阶段 | 规则对象来源 | 字段键 |
|---|---|---|
| 报价 | 本地 store（`offerRuleMatch` ← `offerRuleList` ← `queryRuleList`） | `quanExchangeRatio` |
| 出票 | `queryOfferInfo` ← `offer_record` + 券类型合并 | `quan_exchange_ratio`（联表别名） |

客户端统一用 `getQuanPerTicket(rule)` 归一：`quanExchangeRatio ?? quan_exchange_ratio ?? 1`；非法值（0/负数/非数字）一律按 1。

### 3.3 出票阶段的比例来源（联表）

`queryOfferInfo` 目前只返回 `offer_record` 行 + `quan_type` 合并字段，没有 rule_record 字段。在其主查询上加联表别名：

```sql
SELECT offer_record.*, rule_record.quanExchangeRatio AS quan_exchange_ratio
FROM offer_record
LEFT JOIN rule_record ON offer_record.offer_rule_id = rule_record.id
WHERE offer_record.user_id = ? AND offer_record.app_name = ?
  AND offer_record.order_number = ? AND offer_record.plat_name = ?
LIMIT 1
```

- `offer_record.offer_rule_id` 在报价落库时写入（`BaseOfferQueue`）；
- `queryOfferInfo` 被 `ticketRecord.js` 复用，多一列不影响既有调用方；
- 语义为"规则当前值"：规则改完即对后续出票生效（与报价侧 store 刷新链路一致）。

### 3.4 规则可见性判定

- 乐影：`GET_APP_INFO(formData.shadowLineName)?.app_type_code === "sfc_applet"`（`RuleDialog` 已有同款判定 `isShowOfferFlag`）；
- 内部角色：`IN_RULE_LIST.includes(Number(rule))`，`rule` 取自 `platTokens().userInfo.rule`；
- **注意**：`IN_RULE_LIST = [2]` 不含管理员（1）。若管理员也需配置，需显式把 1 并入判定（本次按"仅内部角色"实现，不改常量）。

## 四、行为规格

### 4.1 规则表单（`RuleDialog.vue`）

- 新增表单项「券兑换比例」，位置在用券类型之后，`type="number"`，提示文案：「每张票消耗券张数，2 表示 2 张券兑 1 张票；留空即一票一券。报价成本 = 券库单张券成本 × 该比例」；
- 显示条件见 3.4；
- 校验：留空 = 未配置；填写时必须为正整数（≥1），否则提交前拦截；
- 编辑回填 `formData.quanExchangeRatio = formInfo.quanExchangeRatio ?? ""`；新增/重置时清空。

### 4.2 规则保存（`views/offerRule/index.vue`）

- 空值转 `null`（避免 TINYINT 收到空串），非空转 `Number`；
- **非内部角色不得提交该字段**：`if (!IN_RULE_LIST.includes(Number(rule))) delete ruleInfo.quanExchangeRatio;`
  —— 外部角色看不到该字段，若照常提交空值会把内部角色已配的比例抹成 `NULL`，必须防；
- 纳入缺列兜底 `NEW_RULE_COLUMNS`（列 `quanExchangeRatio`、label「券兑换比例」、判定 `isUnknownQuanExchangeRatioError`），保证"客户端先发版、DDL 后执行"窗口期规则仍可保存；
- 保存后 `searchData()` 会刷新本地 store，报价立即使用新值（无需额外刷新机制）；
- 列表展示（可选）：内部角色 + 乐影规则在「用券类型」列后追加 `2:1` 徽标。

### 4.3 报价

| 环节 | 现状 | N>1 |
|---|---|---|
| 固定报价规则库存门槛（`sfc/offerManage.getMinAmountOfferRule`） | `itemA.quan_stock >= order.ticket_num` | `>= order.ticket_num × N`（N 取该规则的 `quanExchangeRatio`） |
| 券成本（`getCostPrice`） | 单张 `quan_cost`（多类型取 min） | `min(quan_cost) × N`，且 `this.quanInfoList` 保留、每项 `quan_cost` 预乘 N |
| 日出票数过滤（`commonQuanStock.filterFixedRulesByDailyTicketCount`） | 见下 | **只有券库存类判断 ×N**，日出票数判断**不乘** |
| 按券库存排序手机号（出票侧，见 4.4） | `quan_stock >= ticket_num` | `>= needQuanNum` |

`filterFixedRulesByDailyTicketCount` 内 `ticket_num` 有两类语义，必须分别处理：

- **券库存门槛**（`itemA.quan_stock` / `p.quan_stock` 共 4 处）→ 乘 N；
- **日出票数**（`remaining >= ticket_num`，单位是"票"）→ **保持乘 1**，乘 N 会导致超限接单。

### 4.4 出票

统一计算：

```js
const ratio = getQuanPerTicket(offerRule);   // 1 | 2 ...
const needQuanNum = ticket_num * ratio;       // 本次订单需要消耗的券张数
```

| 环节 | 位置 | 现状 | N>1 |
|---|---|---|---|
| 按券库存排序手机号 | `sfc/buyTicket.getCinemaLoginInfo` | `getSortPhoneByQuanTypeList(..., ticket_num)` | 传 `needQuanNum` |
| 多券类型收敛库存判断 | `cardQuanManage.useQuanOrCard` | `quan_stock >= ticket_num` | `>= needQuanNum` |
| 券不足判断（2 处） | 同上 | `quanList.length < ticket_num` | `< needQuanNum` |
| 服务端补券差额 | 同上 | `diffNum = ticket_num - 已有` | `needQuanNum - 已有` |
| 会员赠券分组 | `_getQuanListForPay` | `group.length >= ticket_num` | `>= needQuanNum` |
| 手续费垫卡余额 | `useQuanOrCard` | `quan_fee × ticket_num` | `quan_fee × needQuanNum` |
| 取券上限 | `useQuan` | `index < ticket_num` | `index < needQuanNum` |
| 利润 | `useQuan` | `(卖价 − quan_cost − 手续费) × useQuans.length` | `(卖价 − quan_cost × N − 手续费) × ticket_num`（**不能再乘 `useQuans.length`，否则二次放大**） |
| 异步绑券阈值 | `useQuan` | `length - ticket_num < 10` | `length - needQuanNum < 10` |
| 用券价格校验 | `sfc/buyTicket` | `validateCouponPrice(ticket_num)` | 传 `needQuanNum` |
| 出票后核销扣减 | `sfc/buyTicket` | `quanStock − ticket_num` | `quanStock − needQuanNum` |

券码串（`quan_code` / `coupon_nums`）、`ng-create` 的 `coupon`、黑名单、`ticket_record.coupons` 快照**全部不改**——本来就是逗号串。

### 4.5 必须保留的强校验

`pay_money > 手续费合计` 即判失败并转单（现有 `validateCouponPrice` 承担，票数实参换成 `needQuanNum`）。
依据抓包第 3 条：券没覆盖满时实付反而高于无券，等于直接亏损。此校验是"比例配错/券不够"的最后一道闸。

## 六、兼容、灰度与回退

- **默认关闭**：`quanExchangeRatio` 为 NULL/1 时所有换算等于 ×1，与现状等价；
- **灰度**：只给目标影院的那条规则填 2，其余规则不填；
- **回退**：把该规则比例清空保存即可，无需发版；
- **上线顺序**：先执行 DDL → 再发客户端/后端。客户端有缺列兜底（保存不报错、仅提示"未包含券兑换比例"）；后端只多一列，旧客户端不受影响；
- **生效时机**：规则页保存后 `searchData()` 刷新本地 store，报价立即使用新比例；出票侧联表读同一规则，两者同源。

## 七、风险

| 编号 | 风险 | 评估 | 缓解 |
|---|---|---|---|
| R1 | 平台是否允许「券数 > 票数」 | 中低：抓包 2 票 4 券已证明 2:1 可用；1 票 2 券仍建议手工验一次 | 上线前用 1 张票 + 2 张券手工下单，确认 `total_price=0` 且 `ng-create` 成功 |
| R2 | 手续费按张还是按单收 | 中：抓包 `handle_fee` 在 2 券/4 券时不同 | 只信 `price/calculate` 的 `total_price`；垫卡余额按 N 倍偏保守（多要余额，不会错买） |
| R3 | 券后价基座抬升造成部分覆盖亏损 | 高（业务侧） | 4.5 的强校验，不满足直接转单 + error 日志 |
| R4 | 本地"规则座位数随库存自动收缩"的逻辑未按比例换算（共享模块按 `ticket_num` 判断） | 中低：库存以 N 倍速度消耗，收缩判断偏乐观，可能出现"本地报价接单但券不足"。因该规则不同步平台，影响仅限本地报价成功率，不涉及平台侧口径 | 本次不改；观察「券不足」告警，必要时后续在同一算式处补 N |
| R5 | 外部角色保存规则把比例抹成 NULL | 中：看不到字段却照常提交 | 4.2 的 `delete ruleInfo.quanExchangeRatio` 防护（必做） |
| R6 | 利润二次放大 | 中：`useQuan` 现按 `useQuans.length` 乘利润，N>1 时会乘成 2 倍票数 | 4.4 明确改为乘 `ticket_num`，单测覆盖 |
| R7 | 券快照截断 | 极低：`slice(0, 10)`，N=2 时 5 张票以上不全 | 仅影响排查展示，不影响出票与核销 |
| R8 | 单订单券数上限未知 | 低-中：4 券已验证，更大票数（如 5 票 10 券）未验证 | 灰度期先用小票数订单，观察 `ng-create` 返回 |

## 八、测试计划

### 单元测试（新增 `src/common/tests/sfcQuanExchangeRatio.test.js`）

1. `getQuanPerTicket`：未配置/1 → 1；2 → 2；0/负数/非数字 → 1；snake 键同样识别；
2. 报价成本：N=1 → `quan_cost`；N=2 → `quan_cost × 2`；多券类型 N=2 → `min(quan_cost) × 2`，且 `quanInfoList` 已按 N 预乘；
3. 报价库存门槛：`ticket_num=2, N=2, stock=3` → 规则被过滤；`stock=4` → 保留；
4. 日出票数过滤：确认 `remaining >= ticket_num` 未被乘 N；
5. 出票选券：`ticket_num=2, N=2` → 取 4 张；`quanList=3` → 判券不足、返回空（不半量下单）；
6. 利润：`supplier_end_price=101, quan_cost=40, N=2, ticket_num=2` → 利润为负 → `{profit:0, useQuans:[]}`；N=1 同参数对照不被二次放大；
7. 价格校验：`pay_money=0` 通过；`pay_money=10` 拒绝。

### 联调验证（测试单，不购买）

`window.sfcTicketObj(order, true).singleTicket()`，核对日志：

- 「计算订单价格参数」`quan_code` 含 `ticket_num × N` 个券码；
- 「创建订单参数」`coupon` 券码数一致、`pay_money` 为 `0`；
- 「使用卡券成功」`profit` 与手工计算一致（重点核对未被二次放大）；
- 出票后券库存减少 `ticket_num × N`。

- 其他系列：`commonQuanStock.js` 改动对其等价于 ×1，需回归其单测。
