# 渲染进程崩溃自愈与队列自动恢复方案

> 日期：2026-08-07
> 状态：**待评审**
> 关联问题：6.6.8 用户 1 天内连续 2 次白屏（8/6 23:40 前后、8/7 12:25 前后），白屏期间报价/出票队列完全停摆，需手动重启程序恢复。
>
> 设计目标：**渲染进程崩溃后窗口自动恢复（无需人工重启），且自动拉起崩溃前正在运行的报价/拉单/出票队列；连续崩溃时停止自动恢复，避免无限重启循环。**

---

## 一、问题背景与现状诊断

### 1.1 白屏现象（用户反馈）

| 项 | 第一次 | 第二次 |
|----|--------|--------|
| 白屏区间 | 8/6 23:40:57 → 8/7 07:09:39 | 8/7 12:25:00 → 13:44:25 |
| 白屏前最后订单 | mahua/ume_h5/wanxiangh5 报价，1465ms | haha/ume_h5/wanxiangh5 报价，94ms |
| 白屏期间 | 完全无订单（报价+出票队列全停） | 同左 |
| 恢复方式 | 用户手动重启程序 | 同左 |

### 1.2 根因方向（已排查结论）

- 白屏 = **渲染进程崩溃/无响应**（render-process-gone）。6.6.8 代码无死循环、无无限递归（已逐文件排查）；崩溃与具体订单无强因果，更可能是**渲染进程内存持续增长（队列级 logger 的 logList 在上传失败时不清理、长时间运行累积）→ OOM** 或 GPU/环境因素。
- **关键缺陷**：主进程 `electron/main/index.ts` **没有任何 `render-process-gone` / `unresponsive` 监听与自动恢复逻辑**，渲染进程一崩，窗口永久白屏，只能手动重启。
- 即使只做"自动 reload"，**报价/拉单/出票队列实例全部挂在 window 上（内存对象），reload 后全部丢失**，需手动到队列管理页重新"一键启动"。

### 1.3 现状机制确认

| 状态 | 存储位置 | reload 后 |
|------|----------|-----------|
| 登录信息 `userInfo` / 各平台 token | localStorage（`auth.ts:37`、`platTokens.js:3`） | ✅ 保留，无需重新登录 |
| 影院登录信息 `loginInfoList` | localStorage（`utils.js:502`） | ✅ 保留 |
| 报价队列 `window.offerQueueObj` | 内存（`queueManage/index.vue:296`） | ❌ 丢失 |
| 拉单队列 `window.platFetchOrderQueueObj` | 内存（同上 :302） | ❌ 丢失 |
| 出票队列 `window.appTicketQueueObj` | 内存（同上 :309，底层 registry 也在 window） | ❌ 丢失 |
| 队列启动状态 isRunning/isStart | 内存 | ❌ 丢失 |

---

## 二、设计目标

1. **P0 自愈**：渲染进程崩溃/无响应后，主进程自动 reload 窗口，白屏可自愈，无需人工重启。
2. **P0 防循环**：短时间内连续崩溃（如 5 分钟内 ≥2 次）则**停止自动恢复**，保留白屏并提示人工介入，防止"崩溃→恢复→处理同批数据又崩"死循环。
3. **P1 队列自动恢复**：reload 后自动重新拉起崩溃前正在运行的报价/拉单/出票队列，用户无感恢复出票业务。
4. **P1 取证**：崩溃时自动记录崩溃原因（reason/exitCode/时间），reload 后上传后端，为根因定位提供数据。
5. **P2 止血（可选）**：`logUpload` 失败时 logList 增加上限保护，阻断"日志上传失败→内存无限累积→OOM"链路。

## 四、详细设计

### 4.1 P0：主进程崩溃自愈（`electron/main/index.ts`）

**改动点 1：崩溃监听与自动恢复**

```ts
// 崩溃自愈配置
const CRASH_GUARD = {
  WINDOW_MS: 5 * 60 * 1000,   // 防循环时间窗：5 分钟
  MAX_CRASH: 2,               // 窗口内最大允许崩溃次数
  RECOVERY_KEY: "__crashRecovery" // 通知渲染层"本次为崩溃恢复"的标记 key
};

function setupCrashRecovery(win: BrowserWindow) {
  const crashTimes: number[] = [];

  const handleCrash = (reason: string, exitCode?: number) => {
    const now = Date.now();
    crashTimes.push(now);
    // 只保留时间窗内的崩溃记录
    while (crashTimes.length && now - crashTimes[0] > CRASH_GUARD.WINDOW_MS) {
      crashTimes.shift();
    }

    // 崩溃取证：记录崩溃信息供 reload 后上传
    const crashInfo = {
      reason,              // crashed | oom | killed | launch-failed | ...
      exitCode: exitCode ?? null,
      time: new Date().toLocaleString(),
      count: crashTimes.length
    };
    try {
      localStorage.setItem("__crashInfo", JSON.stringify(crashInfo));
    } catch {}

    if (crashTimes.length >= CRASH_GUARD.MAX_CRASH) {
      // 连续崩溃：停止自动恢复，提示人工介入
      console.error("[崩溃自愈] 连续崩溃次数超限，停止自动恢复", crashInfo);
      dialog.showMessageBox(win!, {
        type: "error",
        title: "程序连续崩溃",
        message: `程序 5 分钟内连续崩溃 ${crashTimes.length} 次，已停止自动恢复。\n` +
                 `崩溃原因：${reason}${exitCode ? ` (exitCode=${exitCode})` : ""}\n` +
                 "请截图本提示并联系技术支持。"
      });
      return;
    }

    // 单次崩溃：自动 reload 恢复（登录信息在 localStorage，不丢）
    console.warn("[崩溃自愈] 渲染进程崩溃，自动恢复中", crashInfo);
    try {
      localStorage.setItem(CRASH_GUARD.RECOVERY_KEY, "1");
    } catch {}
    win?.webContents.reload();
  };

  win.webContents.on("render-process-gone", (_e, details) => {
    handleCrash(details.reason, details.exitCode);
  });

  // 渲染进程无响应 15 秒后强制 reload（弹窗提示由主进程统一处理）
  win.webContents.on("unresponsive", () => {
    console.warn("[崩溃自愈] 渲染进程无响应，15 秒后强制恢复");
    setTimeout(() => {
      if (win?.webContents.isCrashed() || !win.webContents.isLoading()) {
        win?.webContents.reload();
      }
    }, 15 * 1000);
  });

  // reload 完成后清除恢复标记（供渲染层一次性消费）
  win.webContents.on("did-finish-load", () => {
    try {
      localStorage.removeItem(CRASH_GUARD.RECOVERY_KEY);
    } catch {}
  });
}
```

> 说明：
> - 主进程无法直接访问渲染层的 localStorage，需要**预加载脚本（preload）桥接**，或在渲染层通过 `ipcRenderer` 读取。本项目 `contextIsolation: false`、`nodeIntegration: true`，渲染层可直接 `require("electron").ipcRenderer` 或经 preload 暴露的桥读取。
> - **推荐实现**：预加载脚本暴露 `window.__crashBridge = { getCrashInfo(), consumeRecoveryFlag() }`，主进程在崩溃时用 `win.webContents.executeJavaScript` 或经桥写入 localStorage；更简单的替代：崩溃时主进程把恢复标记写入**主进程侧文件或 query**，reload 时通过 `loadFile(indexHtml, { query: { crashRecovery: "1" } })` 传给渲染层（reload 方法不支持 query，需改用 `loadFile` 重载）。**采用后者**：自愈时统一走 `win.loadFile(indexHtml, { query: { crashRecovery: "1", crashReason: reason } })`，渲染层在 `main.ts` 挂载后解析 `location.search` 消费标记。

**改动点 2：原加载逻辑抽成可复用函数**

```ts
async function loadWindow(win: BrowserWindow) {
  if (process.env.VITE_DEV_SERVER_URL) {
    await win.loadURL(process.env.VITE_DEV_SERVER_URL);
  } else {
    await win.loadFile(join(process.env.DIST, "index.html"));
  }
}
```

### 4.2 P1：队列自动恢复（渲染层）

**改动点 3：队列启动快照持久化（`src/views/queueManage/index.vue`）**

在现有 `oneClickStart` 成功路径（已调用 `svApi.updateUser` 上报 `plat_offer_queue` / `app_ticket_queue`）旁，同步写本地快照：

```js
// oneClickStart 成功分支内追加：
const queueSnapshot = {
  platOfferQueue: platQueueList.value
    .filter(item => item.platToken)
    .map(item => item.platName),
  appTicketQueue: Object.keys(appTicketQueueObj),
  time: getCurrentTime()
};
localStorage.setItem("__queueSnapshot", JSON.stringify(queueSnapshot));
```

**改动点 4：渲染层消费恢复标记并自动拉起队列（`src/main.ts` 或 `App.vue`）**

```js
// main.ts 挂载后：
const isCrashRecovery = new URLSearchParams(location.search).get("crashRecovery") === "1";
if (isCrashRecovery) {
  autoRestoreQueues().catch(e => console.error("崩溃恢复自动拉起队列失败", e));
}

// 自动恢复：复用 queueManage 的工厂与启动逻辑（抽成公共函数，避免页面耦合）
async function autoRestoreQueues() {
  const snapshot = JSON.parse(localStorage.getItem("__queueSnapshot") || "{}");
  if (!snapshot.platOfferQueue?.length && !snapshot.appTicketQueue?.length) return;
  // 依赖窗口工厂：platOfferQueueObj / platFetchOrderQueueObj / appTicketQueueObj
  // 1) 重建出票队列实例：getTicketQueue(app_name) + start()
  // 2) 重建报价/拉单队列：offerQueueFactory.getOfferQueue(plat_name) + start()
  // 3) 平台 token：从 localStorage 读取（platTokens store 已持久化），无需重新登录
  // 4) 恢复后清除快照中的"待恢复"标记，避免下次正常启动重复拉起
}
```

> 设计约束：
> - 自动恢复**只重建并启动快照中记录的队列**，不触发 `svApi.updateUser` 重复上报（避免副作用）。
> - 队列启动依赖登录信息 `loginInfoList`（localStorage 保留）与平台 token（localStorage 保留），**无需重新登录**。
> - 抽公共函数放 `src/common/queueRestore.js`，`queueManage/index.vue` 与 `main.ts` 共用，保证"一键启动"与"自动恢复"逻辑同源。

### 4.3 P1：崩溃取证上传

**改动点 5：恢复后上报崩溃信息**

```js
// autoRestoreQueues 或 main.ts 中：
const crashInfo = localStorage.getItem("__crashInfo");
if (crashInfo && isCrashRecovery) {
  logUpload({ plat_name: "", type: 1 }, [{
    opera_time: getCurrentTime(),
    des: "渲染进程崩溃自愈",
    level: "error",
    info: JSON.parse(crashInfo)
  }]);
  localStorage.removeItem("__crashInfo");
}
```

→ 后端日志可查：`des=渲染进程崩溃自愈`，info 含 reason/exitCode/count，用于根因统计（OOM vs crashed vs killed）。

### 4.4 P2（可选）：logList 内存上限保护（`src/common/logger.js`）

```js
// _addToLogList 增加上限保护：
const MAX_LOG_LIST = 500; // 与 handledOrdersCapacity 同量级，字典可配
_addToLogList(item) {
  this.logList.push(item);
  if (this.logList.length > MAX_LOG_LIST) {
    this.logList.splice(0, this.logList.length - MAX_LOG_LIST); // 丢弃最旧
  }
}
```

> 说明：队列级 logger（`BaseTicketQueue.this.logger`）长期存活，`logUpload` 上传失败时 logList 不清空（`utils.js:1780` break），是渲染进程内存增长的主要嫌疑点。上限保护可阻断该链路，属低成本高收益止血。

## 六、验证方案

### 6.1 自愈功能验证（开发环境 / 生产 exe 均可）

1. **模拟崩溃**：渲染进程 DevTools 执行 `window.ipcRenderer.invoke("crash-test")`（主进程注册的崩溃测试通道，调用 Electron 官方 API `forcefullyCrashRenderer()`；`index.html` 覆盖了 `window.process`，故 `process.crash()` 不可用）→ 观察窗口自动恢复，登录态保留。生产环境同样可测（通道已去除环境限制，随时注册）。
2. **模拟无响应**：渲染层执行 `while(true){}` → 15 秒后自动 reload。
3. **验证防循环**：连续触发 2 次崩溃（5 分钟内）→ 第 2 次不再自动恢复，弹出人工介入提示。
4. **验证队列恢复**：崩溃前在队列管理页一键启动 → 崩溃恢复后，检查报价/拉单/出票队列自动 start，日志出现"渲染进程崩溃自愈"记录，后端可查。

### 6.2 回归验证

- 正常启动、正常关闭不受影响（无崩溃标记时不触发恢复逻辑）。
- 一键启动/停止、队列管理页原有功能不受影响（公共函数抽取后走同一套逻辑）。
- 崩溃恢复后不重复上报 `svApi.updateUser`（快照消费后清除）。

### 6.3 用户侧验证（6.6.9 或 6.6.10 发布后观察）

- 观察 3~7 天：是否再次白屏；若再白屏，是否自动恢复、队列是否自动拉起；后端日志中"渲染进程崩溃自愈"记录的 reason/exitCode 分布（OOM 占比）。

## 七、风险与回滚

| 风险 | 说明 | 缓解 |
|------|------|------|
| 崩溃根因未消除，reload 后再次崩溃 | 若崩溃由特定数据/状态触发，恢复后可能复现 | 防循环机制：5 分钟 2 次后停止自愈并人工介入 |
| 队列自动恢复时序问题 | reload 后登录/字典/规则数据未就绪就拉起队列 | 恢复逻辑放在 `router.isReady()` 之后，并加 2~3 秒延时兜底；失败仅记日志不影响页面 |
| 快照过期 | 快照可能包含已失效平台 | 恢复时校验 `loginInfoList`/token 存在性（同 oneClickStart 的过滤逻辑），无效的跳过 |
| loadFile query 与 dev 模式差异 | 开发环境走 VITE_DEV_SERVER_URL | 恢复标记仅在自愈路径写入，dev 下同样可用 `loadURL(url + "?crashRecovery=1")` |

**回滚**：主进程改动集中在 `setupCrashRecovery` 一个函数内，出现异常时注释调用即可整体回退；渲染层改动集中在 `queueRestore.js`，不调用即无副作用。
