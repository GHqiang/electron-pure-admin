# h5ume 用券创建订单异常换券重试方案

> 状态:已实施
> 创建日期:2026-08-07
> 实施日期:2026-08-07

## 1. 背景与目标

### 1.1 问题现象
h5ume 系列在用券出票场景下,创建订单接口偶发返回以下两类异常,当前主链路直接走转单,导致本可出票的订单被浪费:

1. **优惠券优惠计算异常**(`bizCode: PROMOCOUPON_CAL_ERROR`)
   - 多为单张券在 UME 服务端核算异常(坏券),换一张券即可成功
2. **券数量和票数量不一致**(`bizCode: COUPONCOUNT_TICKET_NOT_SAME`)
   - 所选券在竞态间隔内被其他渠道用掉,换券后可继续

### 1.2 目标
在创建订单命中上述两类异常时,从备选券池中换券重试,提升用券出票成功率,同时通过次数上限控制出票耗时,避免在不可恢复的失败上浪费时间。

### 1.3 非目标
- 不改造卡支付场景的创建订单重试(现有超时重试逻辑保留)
- 不对失败券做持久化标记(仅本次出票内跳过)
- 不改用券选券主逻辑(`useQuanOrCard` 仅追加返回备选券池)

## 2. 现状分析

### 2.1 关键链路
- [h5ume/cardQuanManage.js](../../src/common/autoTicket/buyTicket/h5ume/cardQuanManage.js) `useQuanOrCard`:
  - 按到期时间升序从 `targetQuanList` 取前 `ticket_num` 张作为 `useQuan`
  - 返回 `{ card_id, cardNum, profit, useQuan, quanStock }`,**未返回备选券池**
- [h5ume/orderManage.js](../../src/common/autoTicket/buyTicket/h5ume/orderManage.js) `createOrder`:
  - 成功返回 `res.bizValue`(含 `orderId`)
  - 失败仅对"超时 + 用卡"重试,用券异常直接返回 `undefined`
- [h5ume/buyTicket.js](../../src/common/autoTicket/buyTicket/h5ume/buyTicket.js) 主链路:
  - `orderId = createOrderRes?.orderId`,拿不到即走 `transferOrder`

### 2.2 问题根因
- `createOrder` 失败信息未透出,主链路无法区分"券异常"与其他失败
- 无备选券池可用,即使想换券也没有候选
- 多座位时 UME 不告知具体哪张券坏,需要定位策略

## 3. 设计方案

### 3.1 触发条件
同时满足以下条件才进入换券重试:

1. **用券场景**:`offerRule.offer_type == "1" && useQuan?.length`
2. **错误命中**(匹配 `formatErrInfo(error)` 字符串,命中其一即可):
   - `PROMOCOUPON_CAL_ERROR` 或 `优惠券优惠计算异常`
   - `COUPONCOUNT_TICKET_NOT_SAME` 或 `券数量和票数量不一致`

### 3.2 换券策略:自适应、不切换

每次重试前**实时判断备选池剩余量**,据此选择替换方式,**全程不切换策略**:

| 备选池剩余量 | 替换方式 | 次数上限 |
|------------|---------|---------|
| ≥ `ticket_num` | **全量替换**:取下一批 `ticket_num` 张整批替换 `workingUseQuan` | `COUPON_RETRY_LIMIT`(默认 2) |
| `> 0` 且 `< ticket_num` | **逐个替换**:从备选池取下一张替换 `workingUseQuan[swapPos]`,`swapPos = retryInx % ticket_num` | `COUPON_SINGLE_RETRY_LIMIT`(默认 5) |
| `= 0` | 停止重试,走转单 | — |

说明:
- 单座位时两种方式等价(都是换一张)
- 多座位且备选充足时走全量,一次调用验证整批,高效
- 备选紧张时退化为逐个,不浪费候选
- **全量替换第一次仍失败时,继续按同一策略取下一批,不切到逐个定位;若下一批数量不足票数,直接停止走转单**(不退化到逐个)
- 逐个替换采用累积替换(保留已替换位置),每次只新增替换一个位置
- **连续相同错误提前停止**:换券后仍返回相同错误(bizCode/错误关键词一致)时,说明非单券问题,连续 2 次即停止走转单,避免无效重试浪费时间

### 3.3 券核销查询
换券重试时**所有券均重跑 `checkQuan` 核销查询**(不再仅限 COMMON 类型券),确保换入券在 UME 侧核销状态最新。checkQuan 内部有 try-catch,异常不会中断重试流程。

### 3.4 模块改动

#### 3.4.1 cardQuanManage.js `useQuanOrCard`
返回值新增 `remainQuanList`:
```js
return {
  profit,
  card_id,
  useQuan,
  quanStock: targetQuanList.length,
  remainQuanList: targetQuanList.slice(ticket_num)  // 新增:备选券池
};
```

#### 3.4.2 orderManage.js(换券重试逻辑下沉于此)
拆分为三个方法,职责分离:

- `createOrderOnce`:单次调用创建订单接口,成功返回 `res.bizValue`(含 orderId),失败返回 `{ error }`
- `createOrder`:编排方法,负责超时重试 + 场景判断
  1. 调 `createOrderOnce`,成功直接返回
  2. **超时**:用卡时内部重试一次(原逻辑),失败直接 `return`(undefined)——超时非券类问题,不触发换券重试
  3. **非超时 + 非用券场景**:`return { error }`
  4. **非超时 + 用券场景 + 可重试错误**:委托 `retryCreateOrderWithCouponSwap`
  5. **非超时 + 用券场景 + 非可重试错误**:`return { error }`
- `retryCreateOrderWithCouponSwap`:用券场景换券重试独立方法
  - 自适应全量/逐个替换策略,成功返回 `{ ...res, finalUseQuan }`,耗尽返回 undefined
  - 全量下一批不足票数时直接停止走转单(不退化到逐个)
- 辅助函数 `isCouponRetryableError`/`buildCouponPayments` 同文件顶部模块级定义
- 换券重试所需参数由主链路传入:`useQuan`、`remainQuanList`、`seatIds`、`quan_fee`、`ticket_num`、`isUseQuanScene`

#### 3.4.3 buyTicket.js 主链路(简化为单次调用 + 结果替换)
创建订单段简化为:
```js
const createOrderRes = await this.orderManage.createOrder({
  cinemaLinkId, scheduleId, scheduleKey, lockOrderId,
  tickets, totalPrice: total_price || areaTotalPrice,
  payAmount, payments, card_id,
  // 用券场景换券重试所需参数
  useQuan, remainQuanList,
  seatIds: seatIds.map(item => item.seatId).join("|"),
  quan_fee: offerRule.quan_fee || 0,
  ticket_num, isUseQuanScene
});
orderId = createOrderRes?.orderId;
// 换券重试成功时，用最终生效券替换外层 useQuan / quan_code
if (orderId && createOrderRes?.finalUseQuan) {
  useQuan = createOrderRes.finalUseQuan;
  quan_code = useQuan.map(item => item.couponCode).join();
}
```
主链路不再包含换券循环、辅助函数,职责清晰。

#### 3.4.4 retryConfig.js 新增配置
```js
// 用券创建订单异常换券重试配置
export const COUPON_RETRY_LIMIT = 2;        // 全量替换重试上限(每批已整批验证,2 次足够)
export const COUPON_SINGLE_RETRY_LIMIT = 5; // 逐个替换重试上限(需覆盖多座位多坏券场景,可按实际座位数调整)
```

### 3.5 日志规范
遵循项目日志规范(前缀 `[出票]创建订单-`):

| 事件 | 级别 | 内容 |
|------|------|------|
| 每次换券 | `infoSave` | `创建订单优惠券异常,换券重试`,带 `retryInx`、`swapMode`、新券码、触发错误 |
| 重试耗尽 | `errorSave` | `换券重试耗尽,走转单`,带已试券码列表、备选池剩余量 |
| 全量后备选不足 | `errorSave` | `全量换券后备选不足票数,走转单`,带券码列表、剩余量、票数 |
| 连续2次相同错误 | `errorSave` | `连续2次相同错误,换券无效,走转单`,带 `errorKey`、已试券码列表 |
| 非可重试错误 | `errorSave` | `创建订单异常(非券类错误),走转单`,带 error |

## 4. 影响范围

### 4.1 改动文件
| 文件 | 改动 |
|------|------|
| [h5ume/cardQuanManage.js](../../src/common/autoTicket/buyTicket/h5ume/cardQuanManage.js) | `useQuanOrCard` 返回值追加 `remainQuanList` |
| [h5ume/orderManage.js](../../src/common/autoTicket/buyTicket/h5ume/orderManage.js) | 拆分 `createOrderOnce`/`createOrder`/`retryCreateOrderWithCouponSwap` 三方法,换券重试逻辑下沉 |
| [h5ume/buyTicket.js](../../src/common/autoTicket/buyTicket/h5ume/buyTicket.js) | 创建订单段简化为单次调用 + `finalUseQuan` 结果替换 |
| [common/retryConfig.js](../../src/common/autoTicket/buyTicket/common/retryConfig.js) | 新增 `COUPON_RETRY_LIMIT`、`COUPON_SINGLE_RETRY_LIMIT` |

### 4.2 兼容性
- `createOrder` 成功返回结构不变,仅失败时新增 `{ error }`,现有 `orderId = res?.orderId` 判断兼容
- `useQuanOrCard` 仅追加返回字段,不影响现有解构
- 仅 h5ume 系列改动,其他系列不受影响

### 4.3 风险
- **耗时增加**:最坏情况重试 `COUPON_RETRY_LIMIT` 次(全量,默认 2)或 `COUPON_SINGLE_RETRY_LIMIT` 次(逐个,默认 5),每次约一次 createOrder 耗时。逐个替换默认 5 次以覆盖多座位多坏券定位需求,可按实际座位数场景下调
- **备选券耗尽**:备选池空时立即停止,不会无限重试
- **多座位多坏券**:逐个替换受 `COUPON_SINGLE_RETRY_LIMIT` 限制,默认 5 可覆盖 5 座位以内的坏券定位;座位更多时可按需上调

## 5. 验收要点
- [ ] 单座位 + PROMOCOUPON_CAL_ERROR:换下一张备选券成功
- [ ] 单座位 + COUPONCOUNT_TICKET_NOT_SAME:换下一张备选券成功
- [ ] 多座位 + 备选充足:全量替换一批成功
- [ ] 多座位 + 备选不足:逐个替换定位坏券
- [ ] 备选池耗尽:停止走转单,不报错
- [ ] 非券类错误(如网络异常):不触发换券,直接走原转单
- [ ] 连续2次相同错误:提前停止走转单
- [ ] 换券重试时所有券均重跑 checkQuan 核销查询
- [ ] 重试次数受配置上限控制
- [ ] 日志含券码、重试序号、触发错误
- [ ] 卡支付场景不受影响(现有超时重试保留)
