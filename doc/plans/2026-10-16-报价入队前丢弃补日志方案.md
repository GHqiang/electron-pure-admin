## 一、现象与目标

**现象**：同一角色、同一平台下，某订单在一个用户上有报价记录，在另一个用户上**什么都查不到**——UI 的「未报价记录」页没有、L1 操作日志没有、`offer_record_fail` 没有、L2 明细 trace 也没有。用户因此怀疑「程序有问题，有的单没记到自己名下」。

**本案例**：订单 `2026101512355077473`（lieren / 速铂 subojinsong）：user 10 有完整报价链路（`offer_record` 成功 1 条 + L2「新的待报价订单」），user 9 侧四类记录全空。分析报告给出两种可能：A＝拉到了但在入队前被丢弃（较可能）；B＝该客户端根本没拉到（水位线/时机错过、平台未返回或请求失败）。

**目标（本次整改后应达到）**：

1. **A 场景**：该单在任何一个拉到了它的用户客户端上若被丢弃，「未报价记录」页能直接看到一行（含丢弃原因），无需登录服务器、无需查日志文件；
2. **B 场景**：该单若根本没被该客户端拉到，也能给出**正向证据**——「该轮是否拉到 / 拉到了哪些单 / 拉单循环当时是否连续」，而不是像现在只能从「全空」反推；
3. 原始事实（平台返回了什么、哪一步丢的）可在 L2 明细中逐单回溯；
4. **不改动任何报价/入队行为**，只增加记录、日志与证据采集；
5. 记录/日志/请求量可控，不污染「真实报价失败」的统计口径；
6. **用户/客服不依赖命令行**：逐单定位在 UI 内完成（「未报价记录」页 + 「订单排查」页），统计在「统计分析」页内直观可见；`prod-query.js` 仅作开发兜底（见 §十四）。

### 2.2 报价入队前的静默丢弃路径（4 处，全部无记录）

订单要先通过下列检查，才会写 L2「新的待报价订单」（`BaseOfferQueue.js` L570）并进入报价流程：

| # | 位置 | 条件 | 现状 |
|---|------|------|------|
| ① | `LierenOfferQueue.fetchOrders` L61-L71（`.filter`） | `getCinemaFlag(item)` 返回空 **或** `getCinemaLoginInfoList()` 找不到匹配登录 | 静默 `filter` 掉，**记录/日志全无** |
| ② | `LierenOfferQueue.fetchOrders` L90-L92（`.filter`） | `handledOrders` 命中（此前已投递过） | 静默过滤，**无记录** |
| ③ | `BaseOfferQueue.handleNewOrder` L536-L544 | `offer_end_time - now <= dictStore.dictInfo.minOfferQueueEndTime`（现网配 3000ms） | 直接 `return`，**记录/日志全无** |
| ④ | `BaseOfferQueue.handleNewOrder` L546-L554 | `handledOrders` 命中 / 已在队列中 | 直接 `return`，**无记录** |

补充事实：

- `lieren` **未配置** `features.skipOfferEndTimeCheck`（`_shouldSkipOfferEndTimeCheck` 读 `platformAdapter.config.features`，`BaseOfferQueue.js` L393-L397），所以 lieren 确实走 ③；全仓仅 `mayi` 在 `platform-config.js` L210 配了 `true`（无子类覆盖）。
- `getCinemaFlag`（`src/utils/utils.js` L427-L463）返回空有 **4 种不同成因**：①影院识别不出（`newGetCinemaFlagFun` 空）②`disableAppTypeList` 手动禁用了该系列 ③内部角色影院禁用（`GET_USABLE_APP_LIST` 无该影院）④`isLoginByAppName` 未登录。
- lieren 的过滤器**还有第 5 种**：`getCinemaLoginInfoList().find(...)` 要求 `mobile && session_id`，因此「登录条目存在但缺 `mobile`/`session_id`」或「登录 `link_user_id` 不属于当前用户」也会被过滤；`getCinemaFlag` 内部只查 app_name 是否存在，区分不了。**本次归入 `17 无可用登录`，细分写 `err_msg`**（见 §5.3）。
- 同款「过滤即静默」逻辑还存在于另外 **10 个报价队列**：haha（L83-L94）、mangguo、mahua、sheng、shoutu、yangcong、yinghuasuan、piaosheng、shangzhan、mayi；`HahaOfferQueue.js` L106 另有一条 `filter(item => item.cinema_code)` 也无记录。
- 猎人拉单为 timestamp 水位线增量（仅 -2s 重叠缓冲），**某轮错过即不再重拉**（`LierenOfferQueue.js` L129-L171）。

### 2.3 拉单证据现状（B 场景，v3 新增核实）

| 事实 | 代码位置 | 结论 |
|------|----------|------|
| 成功拉单只打 `console.log`（返回条数、params、下一水位线） | `LierenOfferQueue.js` L142-L145 | **不持久化**，事后无法回答「这一轮返回了哪些单」 |
| 拉单失败写 L1 `errorSave` + `logUpload`，带 `lastFetchTimestamp` 与 `params` | `LierenOfferQueue.js` L147-L170 | 失败有据；但**成功轮次没有留痕** |
| 拉单心跳告警只在「5 分钟无拉单」时触发 | `fetchAlarmMonitor.js` L15-L20 | 抓不到 80 秒窗口内的空窗/水位线跳变 |
| 每次成功拉单刷新 `lastFetchTime`，失败也刷新 | `BaseOfferQueue.js` L146-L168 | 心跳只代表「循环在跑」，不代表「这一单被返回过」 |

→ 所以现在 B 场景只能靠「trace 为空」反推，无法区分「平台没返回」「客户端漏了一轮」「请求失败」「证据上传失败」。**v3 必须补正向证据链。**

### 2.4 L2 明细（trace）的查询约束

- 存储：`logs/trace/{userId}/{date}/shard-{hash(order_number)%128}.log`；查询三要素 `userId + order_number + date` 必填。
- 行级过滤：`upload_order !== order_number` 的行**直接跳过**；`upload_user_id` 必须等于入参 `userId`（`auto-ticket-service/api/traceFile.js` L276-L279）。
- 写入侧的 `user_id` 由后端从 JWT 覆盖（`routes/trace.js` L14-L28），归属可信。
- 分片超容量上限时**只写 error 行**，`info/warn` 被丢弃（`traceFile.js` L199-L205）。

**结论：trace 里查不到某单 ⇒ 该用户端对该单没有留下任何 L2 明细**；但**必须限定在「该系列已启用 L2」的前提下**——不在 `log_v3_enabled_series` 白名单的系列，`traceEnabled=false`，正常报价链路同样没有 L2。因此 v3 的逐单证据（C1/B）走「直传 L2」，不依赖字典（见 §七）；C2 摘要走 L1（见 §7.2）。同时：**丢弃日志必须绑定具体 `order_number`**，否则行级过滤会把它过滤掉。

### 2.5 日志通道的开关事实（v3 修正 v2 误判）

`Logger`（`src/common/logger.js`）的落盘行为由每个实例的 `v3Mode`（L1 收窄）与 `traceEnabled`（L2 采集）两个标志决定：

| 情形 | `v3Mode` / `traceEnabled` | `infoSave/warnSave` 实际去向 |
|------|---------------------------|------------------------------|
| 系列**在**白名单 | `true` / `true` | **不进 L1**（L95-L97 收窄），**进 L2**（L122-L129） |
| 系列**不在**白名单 | `false` / `false` | **进 L1**（不收窄，L111-L119 → `logUpload`）,**不进 L2** |
| 未调 `logUpload()` 就早退 | 任意 | **L1/L2 都不落**（最容易踩） |

现网字典（2026-10-16 只读查得）：`log_v3_enabled_series = chenxing_applet,fenghuang_applet,ume_applet,ume_h5,jinyi_applet,lma_applet,sfc_applet,wanda_applet`；`trace_max_size_mb = 20480`、`trace_retain_days = 7`。

**v2 的「不在白名单 ⇒ L1/L2 都不落，等于什么都没记」是错的**：`v3Mode=false` 时 L1 不收窄，`warnSave` 照常进 `opera_record`。真正会「补了却不落盘」的是**早退分支没有调用 `logUpload()`**——`handleNewOrder` 里 Logger 在 L567 才创建、L623 才上传，截止分支在 L542 就 `return` 了。

→ 结论修正：日志方案不是「不能绑字典」，而是「**绑了字典会让证据分散在 L1/L2 两处，且明细弹框只查 L2**」。v3 的 C1/B 统一用 **`traceUpload()` 直传 L2**（绕开 Logger 字典），C2 摘要走 L1（`logUpload` 有重试 + 本地兜底），页面记录仍为主要抓手；早退分支必须显式上传。

## 四、调整方案总览（三通道）

```
拉单成功 ──► [C1] 每单「拉单返回」直传 L2（正向证据）
   │
   ├─► [能否登录/识别] ──► [是否重复投递] ──► [距截止是否足够]
   │         │ 丢弃                │ 丢弃(不记录)       │ 丢弃
   │         ▼                    ✗                   ▼
   │    [A] 未报价记录页      （不补，此前已记录）   [A] 未报价记录页
   │    + [B] L2 丢弃明细                          + [B] L2 丢弃明细
   └─► （每轮）[C2] 5 分钟「拉单摘要」写 L1（循环是否连续 / 返回/过滤/入队计数）
```

- **通道 A = 页面记录（主）**：用户/客服日常可见，A 场景的落点；
- **通道 B = L2 丢弃明细（辅）**：保留原始字段（水位线、返回条数、剩余 ms、阈值、细分原因），供开发回溯「丢在哪一步」；
- **通道 C = 拉单证据（B 场景）**：C1 回答「这一单是否曾返回给该客户端」，C2 回答「该时段拉单循环是否连续、返回/过滤/入队各多少」；
- 重复投递（②④）**仍然不记录**：此前必然已留过记录/日志，补了只会刷屏。

### 5.2 落库字段要求（关键：不满足会静默失败）

`offer_record_fail` 现有 **13 个 NOT NULL 且无默认值**的列（2026-10-16 只读查得表结构；与 `addOrderHandleRecord` 必写字段一致）：

```
user_id, plat_name, app_name, order_status, ticket_num, order_number,
processing_time, city_name, cinema_addr, cinema_name, hall_name, film_name, show_time
```

- 写入必须**逐字段兜底**（缺值给 `""`/`0`），不能依赖「缺字段就少写」——`addRecordData` 是动态拼列的 INSERT（`api/offerRecord.js` L427-L455）；缺必填列是否直接报错取决于 MySQL `sql_mode`，不能赌；
- `rule` 必须带上（后端按 `rule` 过滤，不带则同角色用户查不到；报价链路里取 `tokens.userInfo.rule`，见 `BaseOfferQueue.js` L1246）；`rule` 取不到时**不要写**（写了也没人查得到）并 `errorSave` 留痕；
- `user_id` **不要前端传**（后端 JWT 覆盖）；
- 只使用 `addOrderHandleRecord` 已用过、确认存在的列（不要新增列）；
- 建议抽一个 `_addOfferDiscardRecord(item, { reason, errType, errMsg, extra })` 私有方法，字段组装对齐 `addOrderHandleRecord`（`BaseOfferQueue.js` L1216-L1294）但只取可用字段；
- **写入失败必须留痕**（`logger.errorSave("丢弃记录入库异常", ...)`），否则「入库失败」又变成新的静默丢弃；
- 测试订单（`this.isTestOrder`）不写，沿用 `addOrderHandleRecord` 的 `shouldSave` 语义；
- 写入走**串行队列、最多 1~2 并发**，不 `await` 在过滤器/`handleNewOrder` 里，避免拖慢拉单与报价节奏；队列积压上限建议 200，超出丢弃并计数（计入 §7.2 摘要）；
- 可选：给 `svApi.addOfferRecord` 增加 `{ silent: true }`，由 `sv-request` 拦截器识别后不弹 `ElMessage`（丢弃记录写入失败时避免弹窗风暴）；该标记仅用于丢弃记录调用。

| 编号 | 文案 | 是否记录 | 触发点 / 条件 | `err_msg` 细分 |
|------|------|----------|----------------|----------------|
| 16 | 入队前丢弃-距报价截止不足 | ✅ A+B 逐单 | `handleNewOrder` L536-L544 | 剩余 ms + 阈值（`minOfferQueueEndTime`） |
| 17 | 入队前丢弃-无可用登录 | ✅ **仅同角色有人有登录时** | 当前客户端无登录/登录不完整，但 `hasAnyRoleLogin(app_name)` 为 true | `未登录`、`缺 mobile 或 session_id`、`link_user_id 不匹配` |
| 18 | 入队前丢弃-系列或影院被禁用 | ❌ **跳过（不写库/日志）** | `disableAppTypeList` 命中 / 影院未对当前用户开放 | 仅保留枚举兼容，不再产生新行 |
| 19 | 入队前丢弃-影院未识别 | ❌ **跳过（不写库/日志）** | `newGetCinemaFlagFun` 为空 / 映射表无该 code | 仅保留枚举兼容，不再产生新行 |

**第 5 种登录成因（有登录条目但缺 `mobile`/`session_id`，或登录不属于当前用户）归入 `17`**：对用户而言补救动作相同（重新登录/补全登录态），单独开编号只会让下拉框更碎；`err_type` 保持用户可读的粗粒度，细分信息进 `err_msg` 与 §六 的 `reason_detail`。

**无关订单判定（v5）**：
- `hasAnyRoleLogin(app_name)` 读 `loginInfoList`（登录页按当前 `rule` 拉取的全角色列表，含 `link_user_id`），只要同角色**任一**用户有 `mobile` + `session_id` 就算「有人能报」；
- 若同角色所有用户都没有该影院登录 → 该订单对当前角色无意义，**不写 A/B/C1/C2**；
- 18/19 同样视为无关订单，**不写 A/B/C1/C2**；
- 因此 `offer_record_fail` 的 16-19 实际只会出现 **16** 和 **17（同角色有人有登录）**；18/19 的枚举保留只为兼容历史/下拉展示。

前端下拉与表格**自动展示**（遍历枚举），无需改 `.vue`。

**注意**：这会让 `offer_record_fail` 出现「非真实报价失败」的行，凡按该表总数/原因的报表需同步排除 `err_type >= 16`（见 §九 D2，改动点见 §十二）。

### 5.4 粒度与去重

- **粒度（待确认 D1）**：
  - A1（推荐）＝**各客户端只写自己一行**：`user_id` 由自己的 token 决定。同角色 N 个用户都丢弃则 N 行，页面上用「报价人」区分；
  - A2 ＝ 在一个客户端里为「同角色全部有登录的用户」各写一行（行数 × 同角色用户数）。
- **去重（A1 必做）**：进程内按 `${plat_name}_${order_number}` 记录已写过的单，**同一单只写一次**，防止 `-2s` 重叠窗口/多轮投递重复写行；容量取 `handledOrdersCapacity` 同量级（默认 500）、FIFO 淘汰，`start()` 时重置。
- **说明**：粒度是 A1 时，Vue 侧分页天然不会再重复；A2 需评估同角色用户数上限。
- **页面噪音提示（v5）**：18/19/同角色全无登录已**不写库/日志**；①分支只剩「同角色有人有登录、当前客户端无登录」的 17 会写行，量已大幅下降。每日上限仍保留兜底（见 D8）：每个平台队列实例每日最多写 2000 行，超出只计数不写行，计数进 §7.2 摘要。

## 七、通道 C：拉单证据（B 场景，v3 新增）

### 7.1 C1：每单「拉单返回」直传 L2

**目的**：把「这一单是否曾返给该客户端」变成**可按订单号查询的正向证据**。

- 位置：`LierenOfferQueue.fetchOrders` 拿到 `stayList` 后，**先跳过无关订单（19/18/同角色全无登录），再对相关订单逐单直传 L2**（`traceUpload`，`type=1`）；
- 文案：`报价队列-拉单返回`；`info` 带 `order_number`、`plat_name`、`app_name`、`cinema_code`、`cinema_name`、`offer_end_time`、`round_ts`、`fetch_timestamp`（本轮 `params.timestamp`）、`returned_count`（本轮返回总条数）、`filter_reason`（`""` 可报价 / `not_login` 当前客户端无登录）、`reason_detail`；
- **无关订单不写 C1**（19/18/同角色全无登录），避免无意义日志；
- 去重：按 `${plat_name}_${order_number}` 只记首次返回（容量 1000、FIFO、`start()` 重置），避免 `-2s` 重叠重复；
- 失败/积压：`try/catch` 计数 `trace_fail`；积压上限 200，超出 `evidence_dropped++`；
- 测试订单不写；
- **不改后端**：按订单逐条 `traceUpload`，复用现有 `/svpi/log/trace` 与查询三要素，无版本兼容问题；
- 量级：约「每用户每日拉到的**相关**订单数」条（无关订单已跳过；lieren 一个用户约 600~700 条/日，单条 ~300B → ~200KB/日，7 天 <1.5MB/用户）。

> 为什么不批量：`traceFile.writeTrace` 按**请求级 `order_number`** 决定分片，一次请求只能落一个订单的分片；要批量需改后端契约（老客户端/新服务端、新客户端/老服务端都有兼容问题）。逐条 + 串行更稳，量级也足够小。

### 7.2 C2：5 分钟「拉单摘要」写 L1

**目的**：回答「该时段拉单循环是否连续、这一轮到底拉到了多少」。C1 只能证明「某单返回过」，证明不了「某个时段客户端在正常拉单」。

- 位置：`BaseOfferQueue._startFetchLoop` 的 `finally`（L146-L168）里累加，**不新增定时器**；
- **开关**：基类加 `this._pullSummaryEnabled = this.platName === "lieren"`（或由子类覆盖），一期只对 lieren 生效，避免 11 个队列同时各写 288 行/日；铺开时再逐个打开；
- 触发：距上次 flush ≥5 分钟时，直接调用 `logUpload`（`src/utils/utils.js` L1953）写 1 条 L1，`order_number=""`、`type=1`、`app_name=""`、`des="报价队列-拉单摘要"`；
- `info` 字段：`from`/`to`、`rounds`、`ok_rounds`、`fail_rounds`、`returned`、`filtered`（仅**相关**过滤丢弃：17 且同角色有人有登录）、`enqueued`、`last_fetch_timestamp`、`max_round_gap_ms`、`trace_fail`、`evidence_dropped`、`discard_record_fail`、`discard_record_dropped`；
- 子类只需在 `fetchOrders` 的 `finally` 里把本轮统计挂到 `this._lastFetchStats = { returned, filtered, enqueued }`（lieren 先接；其余队列不接也能记录轮次/失败）；
- 失败轮次判定复用 `countFetchFailLogs` 的 `failLogsBefore/After`（L142-L155）；
- 量级：288 行/日/用户（5 分钟一条），单条约 0.3KB → ~86KB/日；这是 L1 的**有意例外**（V3 后 L1 只收 error），需在 D9 确认；
- 查询：`scripts/prod-query.js` 新增只读子命令 `pull-summary --user-id <uid> --date YYYYMMDD [--platform lieren]`，SQL 为 `SELECT opera_time, info FROM opera_record WHERE user_id=? AND des='报价队列-拉单摘要' AND opera_time BETWEEN ? AND ?`；不新增后端接口。
- **展示位置**：C2 只用于支持/开发排查（`pull-summary`），**不出现在「未报价记录」页**；用户在页面上看到的仍是通道 A。

### 7.3 判定矩阵（把「全空」变成可定性结论）

查询顺序：先查该用户「未报价记录」页/A 行，再查 `trace`（C1/B），最后查 `pull-summary`（C2）。同订单号、同日、同 `userId`。

| C1 拉单返回 | B 丢弃明细 | A 页面记录 | 入队日志（白名单系列看 L2；非白名单系列看 L1） | 结论 |
|---|---|---|---|---|
| 有 | 有 | 有 | 无 | **拉到但入队前丢弃**，原因见 `err_msg`（16/17/18/19） |
| 有 | 无 | 无 | 有 | **已正常入队**（后续成功/失败看 `offer_record`/`offer_record_fail`） |
| 有 | 无 | 无 | 无 | **异常缺口**（拉到后既未丢弃也未入队），按代码缺陷排查 |
| 无 | 无 | 无 | 无 | **该客户端未拉到**：查 C2 对应时段的 `rounds`/`max_round_gap_ms`/`trace_fail`；有 `获取待报价列表异常` L1 则请求失败；循环连续且无失败 ⇒ 平台该轮未返回 |
| 无 | 有 | 有 | — | 理论矛盾（B/A 只在拿到订单后写）→ 查 C2 的 `trace_fail`，判断是否 C1 上传失败 |
| 无 | 任意 | 任意 | — | 若 C2 显示该时段 `rounds=0`/大 gap/失败轮次多 ⇒ 客户端当时没有正常拉单 |

> 说明：C2 的 `from/to` 是 5 分钟窗口；订单时间可用订单号前 14 位（本案例 `20261015123550...` = 下单时间）对照，再结合 `offer_end_time` 定位窗口。

## 十三、文档同步（拟新增到 `doc/常见问题排查.md`）

> **N. 某用户对某单「完全没有记录」**
>
> **第 1 步（UI，用户/客服日常路径，见 §十四）**
> 1. 打开「未报价记录」→ 订单号筛选 → 看「失败类型 / 失败原因 / 报价人」：有 `入队前丢弃-*` ⇒ 该用户客户端**已拉到**、入队前丢弃，原因直接可见（`17` 的「缺 session_id / 登录不属于当前用户」在失败原因列）；
> 2. 没有行 ⇒ 打开「订单排查」→ 订单号（日期自动带出）+ 选择用户 → 页面直接给结论条：
>    - 已正常入队 / 异常缺口 / 未拉到（平台未返回 / 客户端未正常拉单 / 证据上传失败）。
>
> **第 2 步（CLI，开发兜底，可选）**
> - 明细：`node scripts/prod-query.js trace <订单号> --user-id <该用户> --date <YYYYMMDD>`（三要素必填）：
>   - 有 `报价队列-拉单返回` + `报价队列-订单丢弃-*` ⇒ 同第 1 步 1（页面记录缺失时用它定位）；
>   - 有 `报价队列-拉单返回`、无丢弃明细、且能看到「新的待报价订单」（白名单系列在 L2；非白名单系列在 L1）⇒ 正常入队，缺失是「多用户同单各自报」；
>   - 有「拉单返回」、既无丢弃也无入队 ⇒ 异常缺口，按代码缺陷排查；
>   - **完全没有 `拉单返回`** ⇒ 该客户端未拉到该单，进入下一条；
> - 摘要：`node scripts/prod-query.js pull-summary --user-id <该用户> --date <YYYYMMDD>`，对照订单时间（订单号前 14 位）看该时段：
>   - `rounds` 正常、`max_round_gap_ms` 正常、`trace_fail=0` ⇒ 平台该轮未返回给该用户；
>   - `rounds=0` / `max_round_gap_ms` 很大 / `fail_rounds>0` ⇒ 客户端当时未正常拉单（网络/停机/水位线跳变），结合 L1 `获取待报价列表异常` 的 `params`/`lastFetchTimestamp` 定位；
>   - `trace_fail>0` / `evidence_dropped>0` ⇒ 证据上传失败或积压，不能凭 C1 为空下结论；
>
> **第 3 步：注意** V3 后**白名单系列**的 L1 `opera_record` 只收 `errorSave`，正常链路明细只落 L2——**L1 为空是正常现象**；非白名单系列相反（正常链路明细在 L1、无 L2）。本方案的 **C1/B 无论系列一律直传 L2**，**C2 一律写 L1**，均绕过该开关。

> v3 的 C1/B/C2 只有 `prod-query.js` 能查，**不满足「方便」**。v4 补两个 UI 入口；`prod-query.js` 降级为开发兜底。

### 14.1 「订单排查」页（回答：是否拉到 / 是否无可用登录没报）

**入口**：设置 → 订单排查（`/set/orderDiagnosis`，新增菜单）；「未报价记录」「报价记录」页顶部加「排查此单」按钮（可选快捷入口）。

**输入**：

| 字段 | 说明 |
|------|------|
| 订单号 | 必填；输入后自动按前 14 位（`yyyyMMddHHmmss`，本案例订单号即此规则）带出日期 |
| 日期 | 默认按订单号解析，可手改（trace 三要素之一） |
| 用户 | 外部角色固定本人；内部/管理员可选（用于查「哪个用户客户端」） |

**查询与展示（全部复用现有接口，不改后端）**：

| 区块 | 接口 | 展示 |
|------|------|------|
| 同角色记录 | `svApi.queryOfferList`（`order_status=2`/`1` + `order_number` + 日期范围，**不传 user_id**） | 同角色所有未报价/成功记录，标注「目标用户/其他用户」，直接对照谁有、谁没有 |
| 本机配置对照 | 前端 `getCinemaFlagDetail` + `hasAnyRoleLogin`（用对照记录的 cinema_code/名称 + 本机映射/登录/禁用状态） | 本机若拉到会走 19/18/17 还是可报价；不写库/日志 |
| L2 明细 | `svApi.queryLogTrace`（`order_number` + `date` + `userId` + `type=1`） | `拉单返回`（C1）、`订单丢弃-*`（B）、`新的待报价订单` |
| L1 日志 | `svApi.queryLogRecord`（`order_number` + `user_id` + `type=1`） | 非白名单系列的入队日志、拉单失败日志 |
| 拉单摘要 | `svApi.queryLogRecord`（`user_id` + `des='报价队列-拉单摘要'` + `opera_time_start/end` + `page_size`） | 该时段 `rounds / returned / max_round_gap_ms / trace_fail` |

**结论条（前端按优先级计算，直接给一句话）**：

| 证据组合 | 结论文案 |
|----------|----------|
| 目标用户 A 行 `err_type` 16/17 | 「目标用户已拉到，入队前丢弃：`<原因>`」 |
| 无 A 行 + 有 C1 + 有入队日志 | 「目标用户已拉到并**正常入队**」 |
| 无 A 行 + 有 C1 + 无入队/丢弃 | 「目标用户已拉到，但未发现丢弃/入队记录 → **异常缺口**」 |
| **同角色其他用户有记录、目标用户无记录 + 本机配置命中 19/18/17** | 「同角色其他用户有记录，目标用户未记录：**本机（当前页面）配置原因**」——用 `getCinemaFlagDetail` 结果说明 |
| **同角色其他用户有记录、目标用户无记录 + 本机配置可报价** | 「**本机配置正常，疑似未拉到**」——看 C2 |
| 无 C1 + C2 `trace_fail>0` | 「**证据上传失败**，无法判断」 |
| 无 C1 + C2 `rounds=0` / `max_round_gap_ms` 过大 / `fail_rounds>0` | 「**未拉到**：目标用户客户端当时未正常拉单」 |
| 无 C1 + C2 正常 | 「**未拉到**：平台该轮未返回给目标用户」 |

> 本机配置对照只代表**当前打开页面的这台机器**；查用户 B 请到 B 的客户端打开。映射/登录/禁用状态可解释 19/18/17 这类“无关订单”为什么没有记录，但不需要为它们逐单写库/日志。

> 关键区分：**「未拉到」不是「无可用登录」**——前者是平台/水位线/网络问题，页面不会出现 17 行；后者是拉到了、被过滤器挡下，页面会出现 17 行（仅同角色有人有登录时）。19/18/同角色全无登录属于无关订单，不写 C1/B/A，排查页会给出「未记录」提示，不能据此判平台未返回。
>
> **平台范围**：C1 本期只接 lieren（D4a）。非 lieren 平台尚未接入拉单证据，排查页对这些平台显示「该平台暂未接入拉单证据，不能判定是否拉到」，**不能**给出「未拉到」结论；A 行（是否丢弃）仍然可用。

**权限**：外部角色只能查本人（用户选择器禁用）；内部/管理员可选任意用户。A 行查询本身受后端 `rule` 过滤，不会越权。

### 14.2 「统计分析」页新增「拉单与入队前丢弃」模块（**v6 已下线**）

> 2026-10-19 按用户要求，本模块及 `/discard`、`/pull`、`aggregateDiscard`/`aggregatePull` **已全部下线**；本节仅作设计记录。逐单排查以 §14.1「订单排查」页为准；C2 的 `returned` 只计「影院映射存在 + 同角色有登录」的可纳入订单（§7.2）。

**入口**：现有「统计分析」页（`/set/todayStatistics`）KPI 行下方新增模块（KPI 卡 + 堆叠柱 + 排行表），可下钻到「未报价记录」并自动带上 `err_type` 过滤。

**指标与交互**：

- KPI：入队前丢弃总数、丢弃率（丢弃/拉取）、**16/17 两类原因**各多少（18/19 及同角色全无登录按无关订单不记录，恒为 0）；
- 堆叠柱：按日 × 原因（16 截止不足 / 17 无可用登录；18/19 不记录）；
- 排行表：按用户 / 平台 / 影线，展示丢弃数、拉取数、过滤数、入队数、丢弃率；点用户行 → 未报价记录（带 `user_id` + `err_type` + 日期）；
- 时间范围：**默认「今日 / 近 7 天」**，不与页面主查询的 30 天混用（原因见 14.3）。
- 平台范围：C2 一期只对 lieren 开启（§7.2），因此「拉取/过滤/入队/丢弃率」暂为 lieren；丢弃原因（A 行）按已接入的平台展示。

**数据源与保留期（必须先知道，否则统计会“看起来少”）**：

| 数据 | 来源 | 现状保留期 | 代码位置 |
|------|------|------------|----------|
| 丢弃行（按原因/用户/平台） | `offer_record_fail`（`err_type>=16`） | **7 天** | `cron/index.js` L206 `clearNoOfferRecord(7)` |
| 拉单摘要（拉取/过滤/入队） | C2：`opera_record`（`des='报价队列-拉单摘要'`） | **保留 8 天，查询接口上限 7 天** | `cron/index.js` L236 `clearOperaRecord(8)`；`api/operaRecord.js` L17 把起点钳到 7 天前 |
| 历史失败/成功聚合 | `stat_daily_record` | 永久 | 按 `(stat_date, app_name, plat_name, rule)` 聚合，**无 user_id 维度** |

**两个可选方案**：

- **S1（v6 已下线，仅设计记录）**：新增两个只读聚合接口 `statisticalAnalysis/discard`（近 7 天，按日/原因/用户/平台）与 `statisticalAnalysis/pull`（近 7 天，读 C2 聚合）；模块上明确标注「丢弃统计近 7 天 / 拉单统计近 7 天」。已把 `clearNoOfferRecord(3)` 调到 **7**（一行保留期参数，不动表结构）——见 D10。
- **S2（30 天，需加列）**：`stat_daily_record` 增加 4 个丢弃原因计数列（`discard_deadline_num` / `discard_login_num` / `discard_disabled_num` / `discard_unknown_num`），`aggregateDaily` 日聚合时写入；30 天只能做**平台/影线/原因**维度——预聚合表没有 `user_id`，按用户 30 天需要改唯一键，成本更高（不建议本期）。

### 14.3 为什么统计不能和主页面一样直接 30 天

- `offer_record_fail` 每晚 23:35 清理 7 天前数据（`cron/index.js` L206），**丢弃行保留 7 天**；
- C2 在 `opera_record`，每晚 23:50 清理 8 天前数据（L236），但查询接口把起点钳到 **7 天前**（`api/operaRecord.js` L17）→ **拉单摘要实际可查 7 天**；
- `stat_daily_record` 永久，但没有 `user_id` 维度，且现有 `aggregateDaily` 不会写丢弃原因列。
- 因此：**S1 的 3/7 天是“零 DDL 能做到的上限”**；要 30 天趋势必须选 S2（且按用户维度另说）。
