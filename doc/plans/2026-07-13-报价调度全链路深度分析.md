## 一、调度链路全景

```
┌─ start() 拉单循环 ──────────────────────────────────────────────────┐
│ while(isRunning) {                                                   │
│   fetchDelay = await getFetchInterval()  // 返回间隔 2-5s（仅取值） │
│   await fetchOrders(fetchDelay)  // 调平台 API，内部 mockDelay 睡眠 │
│     ↓                                                                │
│   handleNewOrder(item)  ← 逐个新单入队                              │
│     │                                                                 │
│     ├─ minOfferQueueEndTime 过滤 ← 截止<3s不入队                    │
│     ├─ handledOrders Map 去重 ← 容量字典可配                        │
│     ├─ insertOrderIntoQueue ← O(n) 线性插入                         │
│     ├─ 调度器运行时: 本系列畅通 → 立即派出                           │
│     └─ 调度器空闲: startProcessingQueue()                            │
│ }                                                                     │
└──────────────────────────────────────────────────────────────────────┘
                                    ↓
┌─ startProcessingQueue() 调度器 ──────────────────────────────────────┐
│ isOfferRunning = true                                                │
│ runningCountBySeries.clear()                                         │
│ _offerConcurrencyPerSeries = await getOfferConcurrencyPerSeries()    │
│                                                                       │
│ tryStartOne() 同步 while 循环:                                        │
│   while(isRunning) {                                                  │
│     next = findNextOrderToRun()  ← O(n) 全队列扫描                   │
│     if (!next) break  ← 无可执行订单则退出循环                       │
│     queue.splice(index, 1)     ← O(n) 从队列移除                     │
│     runningCountBySeries.set(sk, count+1)                            │
│     orderHandle(order).finally(() => { count-1; tryStartOne() })     │
│   }                                                                    │
│   if (allIdle) isOfferRunning = false                                │
└──────────────────────────────────────────────────────────────────────┘
                                    ↓
┌─ orderHandle() 单订单执行 ───────────────────────────────────────────┐
│ offerHandleTimeout 超时保护                                           │
│ minOfferHandleEndTime 截止检查 ← 距截止<3s不报价（蚂蚁平台跳过）     │
│ _checkPlatformAlreadyQuoted ← 猎人平台已报价跳过                     │
│ singleOffer:                                                          │
│   getEndOfferPrice → 规则匹配+成本+查询链                            │
│   dynamicPrice → 动态调价                                             │
│   submitOffer → 提交报价                                              │
│ addOrderHandleRecord → 写 offer_duration + queue_wait_ms             │
└──────────────────────────────────────────────────────────────────────┘
```

## 二、字典配置详解

> 下表"生产配置值"为线上字典表实际下发值。除 `handledOrdersCapacity` 外，其余配置在代码中无硬编码默认值，完全依赖后端字典下发；若字典缺失则按各配置的代码兜底逻辑处理（见末尾"代码兜底差异"说明）。

| dict_type                         | 说明                     | 生产配置值                    | 影响范围                                                     |
| --------------------------------- | ------------------------ | ----------------------------- | ------------------------------------------------------------ |
| `minOfferHandleEndTime`           | 报价执行最小剩余时间(ms) | 3000                          | `orderHandle`：距截止 <3s 的订单不报价（蚂蚁平台例外，跳过此检查） |
| `minOfferQueueEndTime`            | 入队最小剩余时间(ms)     | 3000                          | `handleNewOrder`：距截止 <3s 的订单不入队                    |
| `offerConcurrencySeriesKey`       | 系列分组 key             | `app_name`                    | 决定同系列并发以什么维度划分（影院 or 系列类型）             |
| `offerConcurrencyPerSeries`       | 每系列并发上限           | 1                             | 全局默认值，`app_name` 模式下=1 意味着每个影院一次只能报一单 |
| `offerHandleTimeout`              | 报价超时(ms)             | 30000                         | `orderHandle` 整体超时，超时后释放队列位                     |
| `fixedOfferToPlatList`            | 走平台报价的平台列表     | `lieren`                      | `_checkPlatformAlreadyQuoted` 判断是否启用平台检查           |
| `lierenFixedOfferToPlatTimeRange` | 猎人平台报价时间范围     | `9-23`                        | 非此时间段猎人仍走机器报价                                   |
| `bigChainSeriesConcurrency`       | 大连锁专属并发           | `{"wanda":1,"sfc":1,"ume":1}` | 可单独为热门系列调大并发                                     |
| `handledOrdersCapacity`           | 去重 Map 容量            | 500                           | 防止大单量时旧条目被淘汰导致重复入队                         |

### 代码兜底差异（字典缺失时）

| 配置项                       | 生产配置值 | 代码兜底值 | 说明                                                                                     |
| ---------------------------- | ---------- | ---------- | ---------------------------------------------------------------------------------------- |
| `offerConcurrencyPerSeries`  | 1          | **2**      | `BaseOfferQueue.js` 中 `\|\| 2` / `?? 2` 兜底；生产字典显式配 1，故实际生效 1            |
| `offerHandleTimeout`         | 30000      | **15000**  | `BaseOfferQueue.js` 中 `15 * 1000` 兜底；生产字典显式配 30000，故实际生效 30000          |
| `handledOrdersCapacity`      | 500        | 500        | 代码兜底与生产配置一致                                                                   |
| 其余 6 项                    | 见上表     | 无兜底     | 字典缺失时为 `undefined`，可能导致比较失效（如截止检查失效）或回退默认行为（如 sk 取 app_name） |

> **注意**：麻花平台通过 `platform-config.js` 的 features 单独覆盖 `offerHandleTimeout = 120000`（120s），优先级高于字典。

### 字典联动关系

```
订单入队路径:
  minOfferQueueEndTime → handledOrdersCapacity → insertOrderIntoQueue
  → [调度器空闲] startProcessingQueue
  → [调度器运行] 立即派出 or 排队

调度器:
  offerConcurrencySeriesKey → 决定 sk 值
  → offerConcurrencyPerSeries / bigChainSeriesConcurrency → 决定 seriesLimit
  → findNextOrderToRun 按 sk+limit 找可执行订单

执行:
  minOfferHandleEndTime → 截止检查
  → fixedOfferToPlatList → 平台已报价检查(仅配置的平台)
  → lierenFixedOfferToPlatTimeRange → 时间范围判断(仅猎人)
  → offerHandleTimeout → 超时保护
```

## 三、瓶颈深度分析

### 瓶颈①：拉单阻塞式循环

```
时间线:
  T+0s: fetchOrders 开始（调平台API）
  T+2s: fetchOrders 返回 10 个新订单
  T+2s: handleNewOrder ×10 → 入队
  T+2s: 调度器空闲 → startProcessingQueue → 批量派出
  T+2s: 全部派出完毕，调度器再次空闲
  T+2s~T+7s: getFetchInterval 等待 + 下一轮拉单...（调度器空闲空转！）
```

**问题**：`start()` 的 `while` 循环是 `await fetchDelay → await fetchOrders` 严格串行。`fetchOrders` 本身耗时就占用了调度器的"新单窗口期"。调度器可能在 T+2s 就已经把所有订单跑完了，但得等到 T+7s 才有下一批新单。

**影响量化**：按 5s 拉单间隔、2s 拉单耗时算，调度器每 7s 才有 1 批新单，其余时间空转。实际吞吐 = 理论吞吐 × (2/7) ≈ 30%。

### 瓶颈②：tryStartOne 一次性派完退出

```js
const tryStartOne = () => {
  while (this.isRunning) {
    if (!findNextOrderToRun()) break; // 派完了，退出
    // 派出订单...
  }
};
```

同步 `while` 循环一次性把所有符合条件的全派出去，然后退出。之后的新订单只能等某个正在跑的订单 `finally` 里回调 `tryStartOne`。

**问题**：如果 10 个订单都是不同系列的（互不阻塞），一次全派出去了，队列清空，循环退出。此时如果有 10 个订单正在跑，没有新单进来，调度器"休眠"，`isOfferRunning=true`。之后新单来了——`handleNewOrder` 的立即派出能救一部分（最近加的优化），但只派当前这一单，不会触发批量调度。

### 瓶颈③：findNextOrderToRun O(n) 全队列扫描

```
队列: [wanda_A, wanda_B, wanda_C, sfc_A, ume_A, ...]
        ↑         ↑         ↑
        skipped  skipped  skipped (wanda系列满员)
```

当 wanda 系列并发满员时，`findNextOrderToRun` 每调用一次都要跳过前面 N 个 wanda 订单才能找到 sfc_A。如果队列积压 50 个 wanda 订单，每次 `tryStartOne` 调用都要跳过 50 次。

### 瓶颈④：handleNewOrder 立即派出后不触发批量调度

当前优化让 `handleNewOrder` 在调度器运行且**本系列畅通**时立即派出当前订单。每个新单独立判断，若该单所属系列未达并发上限则立即派出；**本系列已达上限的单**才会进队列等 `tryStartOne` 唤醒。

**问题**：立即派出只处理当前这一单，派完后**不触发批量调度**。若一轮拉单返回 10 个新单，其中前几个在调度器空闲期已通过 `startProcessingQueue` 批量派出，后续到达的单虽能各自立即派出，但一旦遇到本系列阻塞（如 wanda 已有 1 单在跑），就静默进队列。此时只能等某个在跑订单 `finally` 回调 `tryStartOne` 才会扫描队列——而 `tryStartOne` 只派下一单，非批量。若阻塞期间又有其他系列的新单入队，这些新单不会被主动唤醒，直到下一轮 `finally` 回调。

## 四、优化方案

### 方案 A（高收益）：拉单与调度解耦

**现状**：`start()` 阻塞式循环

**改造**：

```js
async start() {
    this.isRunning = true;
    // 拉单独立定时器，不阻塞调度
    this._fetchTimer = setInterval(async () => {
        try { await this.fetchOrders(); } catch (e) { /* log */ }
    }, (await this.getFetchInterval()) * 1000);
    // 调度器持续运行
    this.startProcessingQueue();
}
```

**收益**：拉单与调度并行，调度器永不休眠，新单一到立即处理。理论吞吐提升 3 倍。

**风险**：需确保 `fetchOrders` 不会并发执行（用 `isFetching` 标志防重入）。

---

### 方案 B（中收益）：handleNewOrder 触发批量调度

**现状**：立即派出只处理当前一单

**改造**：立即派出后，调用一次 `_dispatchBatch()` 把队列里所有畅通的订单一起派出：

```js
if (running < limit) {
  // 立即派出当前单...
  // 然后批量扫队列，把所有畅通的一起派
  this._dispatchAllEligible();
}
```

**收益**：一轮拉单的所有畅通订单全部 0 延迟派出。

---

### 方案 C（中收益）：findNextOrderToRun 加系列跳过标记

**现状**：每次全队列扫描，重复判断同系列阻塞

**改造**：维护一个 `Set` 记录当前已达上限的系列，`findNextOrderToRun` 遇到这些系列直接 `continue`，不需要每单都检查 `runningCountBySeries`。

**收益**：避免重复 map 查找，队列积压时提升明显。

---

### 方案 D（低收益，顺手改）：insertOrderIntoQueue 二分插入

**现状**：`findIndex` + `splice` 都是 O(n)

**改造**：二分查找插入位置（队列已按 `offer_end_time` 升序）：

```js
insertOrderIntoQueue(order) {
    let lo = 0, hi = this.queue.length;
    while (lo < hi) {
        const mid = (lo + hi) >> 1;
        if (order.offer_end_time < this.queue[mid].offer_end_time) hi = mid;
        else lo = mid + 1;
    }
    this.queue.splice(lo, 0, order);
}
```

## 六、字典调优建议

基于线上 `queue_wait_ms` 数据（`offer_duration` 字段上线后可见），可按以下策略调整：

| 观察指标                                          | 诊断                  | 调整                                                            |
| ------------------------------------------------- | --------------------- | --------------------------------------------------------------- |
| `queue_wait_ms` 普遍 > 3s                         | 并发上限太低          | 调大 `offerConcurrencyPerSeries` 或 `bigChainSeriesConcurrency` |
| `offer_duration` 普遍 > 5s                        | 报价查询慢/缓存未命中 | 检查缓存命中率，或调大 `offerHandleTimeout`                     |
| `offerConcurrencySeriesKey=app_name` 时某系列积压 | 每个影院只能跑 1 单   | 切到 `app_type_code` 模式可调大并发                             |
| 距截止 <3s 大量订单被过滤                         | 入队/执行阈值太保守   | 调小 `minOfferQueueEndTime` / `minOfferHandleEndTime`           |
| 猎人订单仍走机器报价（非 9-23 时段）              | 时间范围外            | 调整 `lierenFixedOfferToPlatTimeRange`                          |
