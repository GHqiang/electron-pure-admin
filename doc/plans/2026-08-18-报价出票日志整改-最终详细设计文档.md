## 一、需求分析

### 1.1 背景与问题（现状痛点，均有代码证据，见 §二）

1. **日志量爆炸**：单个订单（报价+出票）入库 110~140 条（报价 55~75 + 出票 50~65）；报价是入库大头（日 2000 单 → 12 万+ 条/天）；
2. **单条体积大**：整单/整接口响应/整列表直接作为 meta 入库（单条 2~5KB，大对象 10~100KB），每单持久化 300~500KB；
3. **出票被日志阻塞**：出票队列串行 while 循环中 `await logger.logUpload()`，日志上传慢会拖住锁座出票（时效敏感）；
4. **console 生产不可见**：中间过程日志"仅 console"等于生产环境看不到（devtools 不常开）；
5. **排查靠翻日志表**：用户反馈"金额不对/出票异常"时，开发需在 opera_record 里人工拼接时间线，字段散、量多；
6. **崩溃丢日志**：logList 在内存，渲染进程崩溃自愈重启后日志丢失。

### 1.2 干系人与诉求（三个消费者）

| 消费者 | 核心诉求 | 粒度 | 频率 |
|--------|---------|------|------|
| 用户（运营/客服/财务） | 这单怎么算的、结果对不对（命中规则、会员价、最终报价、用券用卡、实付、手机号） | 每单一组字段 | 按需查单 |
| 开发（日常排查） | 金额不对/出票异常时，能定位"哪层算错、哪步挂的" | 每单结果+异常现场 | 接到反馈时 |
| 开发（疑难深挖） | 接口原始往返、中间计算全过程 | 全量 | 极少 |

### 1.3 需求清单与裁定

| # | 原始需求 | 裁定 | 落地位置 |
|---|---------|------|---------|
| R1 | 不需要统一前缀，有 type 区分即可 | 采纳：不引入 `[报价]/[出票]` 前缀机制，`logger.type`（1=报价/3=出票）承担流程区分（现状机制）；des 统一文案（`环节-结果`）仍保留 | §2.1（type 现状）+ §4.2.3（des 前缀约束） |
| R2 | 日志能看到关键信息：会员价怎么算、命中哪条规则、最终报价、用的什么券/卡、付了多少、哪个手机号 | 采纳并升级：这些字段**进业务表+详情页**（L0），不依赖日志；会员价三层（真实价/折扣/成本价）、券卡明细、实付金额均为独立列 | §4.1 |
| R3 | 日志不要太多，但要清晰看到环节执行结果，可参考抽象归类环节 | 采纳：**量随异常走**——正常订单入库 ≈0 条；环节"结果"由 calc_path/use_path 一句话路径 + 详情页字段承载；过程全量进文件（L2） | §4.1/§4.3 |
| R4 | 辅助操作（更新券库存、同步会员卡余额）日志也要控制 | 采纳：辅助操作成功仅 console（入 L2 文件）、失败才 `辅助-` 前缀 errorSave 入库且不污染根因 | §4.2.3 |
| R5 | 成功/失败流程日志不入库、只落本地文件是否可行 | 可行（本地写盘链路已存在）。裁定**分层**：摘要/异常入库（检索统计）+ 全量明细落后端文件（开发主入口）+ 本地文件兜底；失败根因 err_msg 仍随业务数据入库（出票记录/转单推送依赖） | §4.3/§4.4 |

### 1.4 排查场景需求（设计倒推依据）

**场景 A：用户反馈某订单报价金额不对**
```
① L0 详情页/offer_record：命中规则、会员价三层、最终报价构成、calc_path —— 字段级定位（哪层算错）
② L1 opera_record：失败现场（失败单才有）
③ L2 后端 trace 文件 grep order_number：取价接口原始返回、计算全过程
```
**场景 B：用户反馈某订单出票异常/金额异常**
```
① L0 ticket_record：手机号/卡/余额/券明细/实付/use_path + err_msg（根因）
② L1：失败现场（哪步挂的、入参/出参/error）+ 降级-XX（补救动作）
③ L2：支付/取码接口往返
```

### 1.5 设计目标（可度量）

| 指标 | 现状 | 目标 |
|------|------|------|
| 正常订单入库日志 | 110~140 条/单 | **≈0 条**（业务字段进业务表，异常才入日志表） |
| 异常订单入库日志 | 110~140 条/单 | **≤5 条**（设计目标值，叠加场景受 §4.2.1 计数兜底约束） |
| 每单新增持久化数据（日志部分） | 300~500KB | **正常 ≈0KB；异常 ≤2.5KB**（5 条×0.5KB；业务表行宽增加 ~0.5KB 另计） |
| 用户查单 | 找开发翻日志 | **详情页直接可读** |
| 开发排查 | 翻 opera_record 拼时间线 | **L0 字段 → L1 现场 → L2 文件 grep** |
| 全量明细 | 无 | **后端 trace 文件分片落盘（L2）**（保留 7 天；~~本地双写~~ 已停用 2026-08-20，客户端不写日志） |
| 出票耗时 | 含日志上传等待 | 不含（fire-and-forget + 全局串行链） |

## 二、现状诊断（代码级证据）

### 2.1 日志写入链路（现状）

```
渲染进程 Logger（src/common/logger.js，260 行，V3 扩展后）
  ├─ type 已有：1-报价队列 2-获取待出票队列 3-出票队列 4-凤凰sid续期 5-帮助锁座 6-h5ume-sid续期
  ├─ logList 内存攒批（MAX_LOG_LIST=500，超出丢最旧）
  ├─ isPrint=true：每条日志同时 console 输出
  ├─ logUpload()（utils.js:1751）：每批 ≤50 条 → POST /svpi/operaRecord/addList，重试 3 次
  │    └─ 上传失败 → 本地兜底 userData/logs/logUploadFail-日期.log（localFailLog.js 经 ipc 写盘）+ 微信告警
  └─ 网络错误走 networkErrorBatcher 攒批（30s/20 条）→ 同样 addList 入库
后端 auto-ticket-service
  ├─ opera_record 逐条 INSERT（api/operaRecord.js addRecordData，动态 INSERT：obj 键即列名）
  ├─ offer_record/offer_record_fail/ticket_record 同样动态 INSERT（obj 键即列名）
  └─ routes/opera_record.js:23 整批 payload console.log（待清理）
```

**关键技术事实（设计依据）**：
- **动态 INSERT**：`addRecordData` 用 `Object.keys(obj)` 拼列名（offerRecord.js:324-334、ticketRecord.js:172），前端传什么字段就插什么列 → 加列零侵入，但 **DDL 必须先于代码**（无列则报 Unknown column）；**值不能为 undefined**（mysql 驱动绑定参数报错）；
- **数据传递链**：报价 `offerRule`（各系列 offerManage 组装）→ `offerResult.offerRule` → `BaseOfferQueue.addOrderHandleRecord` serOrderInfo → addOfferRecord；出票 `ticketRes`（各系列 buyTicket return）→ `BaseTicketQueue.saveTicketRecord` serOrderInfo → addTicketRecord → 两条链均可**公共收口**；
- **查询默认 SELECT \***：offerRecord.js:122 `SELECT ${tableName}.*`、ticketRecord.js:91 `fields='*'` → 新列 DDL 后自动返回（列表查询显式字段为优化项）；
- **本地写盘链路已存在**：localFailLog.js → `ipcRenderer.invoke("save-fail-log")` → 主进程写 `userData/logs/`，支持自定义文件名前缀（注释已预留"整改 D3 复用"）；
- **字典白名单模式成熟**：`dictStore.dictInfo.supportChangeSeatPlatList.includes(plat_name)` 遍布代码（chenxing/buyTicket.js:189 等 20+ 处），按系列开关有现成范式；
- **logger 按实例创建**：每个 offerManage `new Logger({ logType: 1 })`、队列/出票各自实例 → 实例级开关可行。

## 三、总体架构：四层模型

```
┌─ L0 业务层（用户看）──────────────────────────────────────────────┐
│ offer_record/ticket_record 加列 + 订单详情页（命中规则/会员价三层/  │
│ 最终报价/券卡/实付/手机号/calc_path/use_path）                     │
├─ L1 索引层（DB opera_record，开发快速定位）────────────────────────┤
│ 只存异常：失败现场（errorSave 5W）+ 降级动作 + 关键异常             │
│ 正常订单入库 ≈0 条，异常订单 ≤5 条                                 │
├─ L2 明细层（后端日志文件，开发主入口）──────────────────────────────┤
│ 全量过程（console 级 + 接口往返），按日 JSON 行文件                 │
│ grep/查询接口按 order_number 取单                                   │
└─ L3 兜底层（本地 trace 文件，最后防线）─────────────────────────────┘
   与 L2 同源双写，打点即落盘（攒批 flush），崩溃/后端不可达不丢
```

**设计原则**：
1. **按消费者分通道**：业务结果→业务表；异常→日志表；过程→文件。一个通道只服务一类诉求；
2. **量随异常走**：入库日志量只与异常订单数挂钩，与业务量解耦（报价大头问题的根治）；
3. **全量永远可得**：console 不是日志通道（生产不可见），一切过程日志落文件（本地即时写 + 后端集中收）。

**防呆约束（必守）**：
1. **数值列与字符串列分流兜底**：`payment_amount`/`card_balance` 为 `DECIMAL(10,2)` 列，**必须兜底 `?? null`**（列 `DEFAULT NULL` 接收 NULL，mysql2 绑定 null 正常）；**绝不能兜底 `""`**——MySQL 严格模式（`STRICT_TRANS_TABLES`，8.0 默认，本项目 MySQL 8.0.24）下 DECIMAL 列插入 `''` 报 `ERROR 1366: Incorrect decimal value`，后端虽 catch 但**该单 ticket_record 整条丢失**（出票记录写不进、转单推送依赖的 err_msg 缺失）。字符串列（use_path/calc_path/hit_rule_name）保持 `?? ""`；coupons 用 `JSON.stringify(coupons ?? [])`；
   ```javascript
   // 收口代码（已实施）：
   payment_amount: paymentAmount ?? null,   // chenxing 采集侧同样 ?? null（"" 会绕过 ?? 兜底）
   card_balance: cardBalance ?? null,
   ```
2. **动态 INSERT 的值绝不能是 undefined**（mysql 驱动报 "Bind parameters must not contain undefined"）——null/""/JSON 均安全；
3. coupons 兼容数组（采集方传数组 → 自动序列化）与字符串（未采集系列默认 ""）；
4. 提前 return 路径（转单/换号/测试模式/异常）不采集 → 解构默认值兜底（数值列 null/字符串列 ""），不影响原逻辑；
5. 出票 `offer_type` 取值须在 useQuanOrCard 之后（灵活用券会将其改写为 "1"，chenxing/cardQuanManage.js:305-307）。

  - 按用户单日单文件：1G/文件，逐行 parse 查询极慢（10s+）；
  - 一订单一文件：几十万订单/天 → 几百万文件/15 天，**inode/目录遍历/清理全崩（不可行）**；
  - **分片 128**：单文件 ~8MB/天（最坏分片 ~16MB，hash 实测最大/平均 ≤2），订单查询 **O(1) 定位文件**（hash 同源），文件数 128×用户×天数（10 用户 15 天 = 1.9 万）可控，清理按 `{userId}/{date}` 目录级删除（一天=一个目录）；
- **容量控制（磁盘预算 45G 剩余，10G/天 全站）**：
  - 保留 `trace_retain_days`（默认 **7** 天）；明文活跃 `trace_active_days`（默认 **3**）天后 gzip 归档 `.log → .log.gz`（~5:1，查询自动解压）；预算：7G 明文 + 4G×归档 ≈ **38G 紧贴预算**（可调字典降保留或升归档压缩）；
  - 全站超 `trace_max_size_mb`（默认 2048）→ **降级为仅写 error 行**（保留失败现场，5 分钟容量检查缓存）；
  - 单条 ≤8KB 截断、单批 ≤200 条（原有）；
- **查询权限（目录 + 行级双层，2026-08-20 修订）**：外部角色（rule 3~7）**强制查自己目录**（路由层强制 userId=登录用户）；**内部角色（rule=2）与管理员不传 userId 时遍历全部用户目录**（满足"同角色可查其它用户日志、内部可查外部"；内部角色可显式传 userId 指定，行级过滤兜底）。行级：管理员全量 / 内部仅 IN_VIEW_RULE_LIST=[2,3,4,5,7] / 外部仅自己 rule；
- **`brief=1` 精简模式**：只返回 `{opera_time, des, level, upload_order, upload_type, upload_user_id}` 时间线，不含 info 大对象。**排查铁律：AI/人排查必须走查询接口（date+order_number+brief+分页），禁止直接读原始文件**；
- 保留策略：启动 + 每日 03:00 清理（删超期目录 + 归档超明文期文件，字典 `traceCleanEnabled` 开关）；
- 容量监控：每日统计目录大小（含 .gz），超阈值微信告警；
- 查询：订单定位单分片（O(1)）；无订单号按用户遍历当日分片；.gz 自动解压；逐行过滤 + brief + 分页，返回 `{code:1, data:{list,total}}`。

## 附录 A：排查 SOP（验收用，可直接执行；AI/人通用）

> **排查铁律（V4.5）**：明细一律走查询接口（date+order_number+brief+分页），**禁止直接读原始日志文件**——接口只返回目标行，token/流量只花在目标数据上。

**A.1 报价金额不对**：① 详情页/offer_record 看命中规则→会员价三层→最终报价→calc_path；② opera_record 失败现场；③ `GET /svpi/log/trace?date=...&order_number=X&brief=1` 看时间线 → 定位到具体 des 后去掉 brief 取该条 info（取价接口原始返回）。
**A.2 出票失败/异常**：① ticket_record 看用券用卡/实付/use_path + err_msg；② 失败现场（哪步挂的）；③ 降级-XX（补救动作）；④ 明细接口 brief 时间线 + 按需 info。
**A.3 系统级批量失败**：明细接口按 type/时间/用户目录统计分布 → 失败现场 err_msg 聚类 → 网络错误行（改道后）定位接口问题。
**A.4 多用户同订单**：管理员不传 userId 遍历全部用户目录查该订单全部用户日志；外部用户只能查自己目录（自己的行）。
