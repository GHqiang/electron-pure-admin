# 平台 × 系列单量分析页面设计文档

> 日期：2026-10-21
> 状态：**设计稿 v1（已与用户逐段确认，待评审）**
> 涉及仓库：`electron-pure-admin-fix`（前端新增页面）+ `auto-ticket-service`（后端新增 1 个聚合接口）
> 关联页面：新增 `src/views/dailyVolume/index.vue`，复用 `src/views/todayStatistics/detail.vue` 作下钻终点
> 关联接口：新增 `GET /statisticalAnalysis/cross`；前端 `svApi.queryAnalysisCross`
> 前置依赖：`stat_daily_record`（按日预聚合表，已存在）、`offer_record`、`offer_record_fail`、`ticket_record`、`cinema_record`
> 不改表结构，不改现有页面行为

---

## 1. 背景与目标

### 1.1 现状

现有「统计分析」页（`/set/todayStatistics`）围绕**利润、流水、成功率**做概览，平台维度只有一张"平台拆解"（按利润排序看各订单来源），影院维度只有一个下钻页「影线明细」（按 `app_name` 平铺全部指标）。它回答的是"赚没赚、成功率好不好"，**不回答"哪个系列 / 哪个影院 / 哪个平台单子多"**。

后端统计接口目前只有两种分组：按 `app_name`（`/query`）或按 `plat_name`（`/plat`），**没有 `app_name × plat_name` 交叉**，因此"平台 × 系列"单量矩阵无法从现有接口组合出来（组合调 `/query` 需按平台循环 10 次）。

### 1.2 目标

新增独立页面「单量分析」，用**订单笔数**回答三个问题：

1. 哪些**平台**单子多？（每个平台的报价量 / 出票量）
2. 哪些**系列**单子多？（同一平台下哪个系列贡献多）
3. 哪些**影院**单子多？（系列内部谁在出单）

信息结构：平台 × 系列交叉矩阵 + 系列排行 + 影院排行，三个视图共用一套指标切换。

### 1.3 已确认决策

| 决策点 | 结论 |
|--------|------|
| 页面位置 | **新建独立页面**「单量分析」（`/set/dailyVolume`），不改现有统计分析页 |
| 时间范围 | 默认**近 7 天**，可切「当天 / 近 7 天 / 近 30 天」，上限 31 天（沿用现有校验） |
| 页面布局 | **三视图**：Tab1 平台×系列交叉表、Tab2 系列排行、Tab3 影院排行；平台排行由 Tab1 列合计呈现，不单开 Tab |
| 计量口径 | **按订单笔数**（不乘票数），与现有统计页口径一致，可对账 |
| 实现路径 | **方案 A**：后端只加一个"影院×平台"聚合接口，前端做三视图聚合与系列映射 |
| 指标切换 | 顶部一个分段切换器，三个 Tab 共用，切换只重算不发请求 |

## 2. 口径定义

全部为**订单笔数**，统一在 `(app_name, plat_name)` 粒度取原始计数后再向上聚合。

| 指标 | 定义 | 历史段（`stat_daily_record`） | 今天段（实时表） |
|------|------|------------------------------|------------------|
| 报价量 `offerTotalNum` | 报价成功 + 报价失败 | `SUM(offer_success_num + offer_fail_num)` | `offer_record` 行数 + `offer_record_fail` 行数 |
| 报价成功量 `offerSuccessNum` | 报价成功笔数 | `SUM(offer_success_num)` | `offer_record` 行数 |
| 出票量 `ticketTotalNum` | 出票记录笔数（含失败、转单） | `SUM(ticket_total_num)` | `ticket_record` 行数 |
| 出票成功量 `ticketSuccessNum` | `order_status='1'` 笔数 | `SUM(ticket_success_num)` | `ticket_record` 中 `order_status='1'` 行数 |
| 报价成功率 | `offerSuccessNum / offerTotalNum` | 派生 | 派生 |
| 出票成功率 | `ticketSuccessNum / ticketTotalNum` | 派生 | 派生 |

**失败口径**：报价失败**排除"入队前丢弃"**（`err_type >= 16`），复用 `api/statisticalAnalysis.js` 已有的 `REAL_FAIL_FILTER` / `withRealFailFilter`。这样与本页对账的「统计分析」页数字完全一致。

**分母为 0 时**成功率显示 `--`，不显示 `0%`（避免"没单"和"全失败"混淆）。

## 3. 数据来源与查询策略

### 3.1 历史 + 今天拆分

沿用现有 `aggregatePlat` 的成熟模式：

1. **历史段**：`stat_date ∈ [startDate, min(endDate, 昨天)]`，读 `stat_daily_record`，`GROUP BY app_name, plat_name`。
2. **今天段**：`realtimeRange()` 裁剪出落在今天的时间窗，三张实时表并行 `GROUP BY app_name, plat_name`。
3. **合并**：复用 `mergeAgg()`（按 `g` 键累加，这里 `g` 用 `app_name + '\u0001' + plat_name` 复合键）。
4. **兜底**：历史段为空且 `dailyRangeEmpty()` 为真（预聚合未跑）→ 按现有方式**回退全实时**。

### 3.2 系列映射（前端完成，不改后端）

系列 = `app_type_code`，映射来源是登录后已加载的影院列表：

- `GET_ALL_APP_TYPE_LIST()` / `allAppList` 中每项含 `app_name` 与 `app_type_code`，构建 `appName → appTypeCode` 字典。
- 系列显示名取 `APP_TYPE_OBJ`：`sfc_applet` 乐影、`ume_applet` 凤凰云智小程序、`ume_h5` 凤凰云智 H5、`fenghuang_applet` 凤凰云智新版小程序、`lma_applet` 卢米埃、`chenxing_applet` 辰星、`jinyi_applet` 金逸、`wanda_applet` 万达小程序。
- **未匹配到系列的影院归入「未分类」**，页面顶部给出灰字提示"N 家影院未匹配到系列"，不静默丢数据。
- 若 `allAppList` 为空（影院列表尚未加载），系列列只显示「未分类」并提示"影院列表未加载，系列维度暂不可用"，不抛错。
- 系列筛选 → 先算出该系列下的 `app_name` 集合，再按集合过滤前端聚合结果（下拉数据即来自 `allAppList`，天然受 `rule` 权限约束）。

### 3.3 时间范围

- 默认：近 7 天 = `[今天-6 天 00:00:00, 明天 00:00:00)`，与现有页面 `getDayStart()` 语义一致。
- 快捷：当天 / 近 7 天 / 近 30 天，选中态高亮；手动改时间后清除选中态。
- 上限 31 天：沿用 `confirmQueryRange()` 的提示文案（实时表留 30 天，第 31 天由预聚合表兜底）。

## 4. 后端设计

### 4.1 接口契约

`GET /statisticalAnalysis/cross`（前端经 `/svpi` 前缀访问，`sv-request` 会去掉前缀）

| 入参 | 必填 | 说明 |
|------|------|------|
| `start_time` / `end_time` | 是 | `YYYY-MM-DD HH:mm:ss`，≤31 天，缺失或超限返回 `failRes` |
| `plat_name` | 否 | 等值过滤 |
| `app_name` | 否 | 等值过滤（单影院下钻用，页面暂不用） |
| `user_id` | 否 | 等值过滤 |
| `rule` | 否 | 角色数据过滤，沿用现有页面传参 |

响应：

```json
{
  "code": 1,
  "data": {
    "list": [
      {
        "app_name": "sfc001",
        "plat_name": "lieren",
        "offer_success_num": 1200,
        "offer_fail_num": 300,
        "ticket_total_num": 800,
        "ticket_success_num": 780
      }
    ]
  }
}
```

### 4.2 实现要点

- `api/statisticalAnalysis.js` 新增 `aggregateCross(obj)`：
  - 历史：`SELECT app_name, plat_name, SUM(offer_success_num) …, SUM(ticket_success_num) … FROM stat_daily_record<dailyWhere> GROUP BY app_name, plat_name`
  - 今天：`offer_record` / `offer_record_fail`（带 `REAL_FAIL_FILTER`）/ `ticket_record` 三查并行，均 `GROUP BY app_name, plat_name`，各自 `COUNT(*)` / `SUM(CASE WHEN order_status='1' …)`
  - 合并：本地 `Map` 复合键合并（`mergeAgg` 只保留分组键，无法同时保留 `app_name` / `plat_name`），字段集合 `FIELDS = ["offer_success_num","offer_fail_num","ticket_total_num","ticket_success_num"]`
  - 回退分支与现有 `aggregatePlat` 完全同构（历史为空 → 全实时）
- `routes/statistical_analysis.js` 新增 `GET /cross`：
  - `validateTimeRange(params)` 校验 → 失败 `failRes(null, msg)`
  - `cacheKey("cross", params)` + 5 分钟 `resultCache` 复用
  - 异常走 `console.warn` + `failRes(null, error?.message)`
- **依赖确认**：实现前先 `SHOW CREATE TABLE stat_daily_record` 确认唯一键为 `(stat_date, app_name, plat_name, rule)` 且 `stat_date` 上有可用的范围扫描索引。若唯一键不含 `rule`，本设计的"按 rule 求和"仍然正确（同组只有一行），无需改表。

### 4.3 为什么不需要改表

`stat_daily_record` 已按 `(stat_date, app_name, plat_name, rule)` 聚合，`app_name × plat_name` 的交叉只是换一个 `GROUP BY`，不新增维度、不需要新表、不需要回填。

### 4.4 报文规模

行数上界 ≈ 周期内有数据的 `app_name` 数 × 平台数（实际远小于笛卡尔积，通常几百行，极端 < 3000 行），单行 6 个数字 + 2 个短字符串，估算 < 300KB，桌面端可接受；后续若变慢，可在接口加 `group=series` 由后端直接汇总（本期不做）。

### 5.3 组件职责

**`utils/aggregate.js`（纯函数，无 Vue 依赖）**

- `buildSeriesIndex(cinemaList)`：`app_name → { appTypeCode, appTypeName }`，未知归 `UNKNOWN_SERIES`。
- `buildCrossView(rows, { metric, seriesIndex, platOrder })`：输出 `{ rows: [系列行], cols: [平台], rowTotals, colTotals, grandTotal, unmatchedCount }`。
- `buildSeriesRank(rows, { metric, seriesIndex })`：输出按指标降序的系列数组，含 4 指标 + 双成功率 + 占比。
- `buildCinemaRank(rows, { metric, seriesIndex, limit })`：影院级聚合，含所属系列名、按指标降序，`limit` 为空表示全部。
- 所有函数对空数组、缺字段（`undefined`/`null`）返回 0，不抛错。

**`CrossTable.vue`**：`props: { rowData, metric }`；渲染固定列（系列 + 合计）+ 动态平台列；单元格背景按**该列最大值**做透明度梯度；点击列头按该平台数值排序（再次点击反转）；行尾/表尾合计；平台列显示名走 `ORDER_FORM`，未知平台原样显示 code。

**`SeriesRank.vue`**：`props: { data, metric }`；每行 = 条形（相对最大值）+ 系列名 + 4 指标 + 报价成功率 + 出票成功率 + 占比；`emit('select', appTypeCode)` 由父级切 Tab 并带筛选。

**`CinemaBoard.vue`**：`props: { data, metric, total }`；`el-table` 渲染排名/影院/系列/当前指标/4 指标/双成功率；默认截断 20 行，底部「显示全部 / 收起」；点击行 `router.push({ path: "/set/todayStatistics/detail", query: { app_name } })`。

### 5.4 交互约定

- 指标切换为**本地计算**：只有筛选条件变化才请求接口。
- 平台多选、系列多选为空 = 全部；平台过滤在前端做（后端已支持 `plat_name` 等值，多选时前端过滤，避免多次请求）。
- 时间快捷按钮点击即查询；手改时间后清除高亮，点「搜索」才查。
- Tab2 点行 → `activeTab = 'cinema'` 且 `selectedSeries = 该系列`，CinemaBoard 只显示该系列的影院。
- 下钻复用现有「影线明细」页，不新写明细页。

### 5.5 状态处理

- loading：`ElLoading.service({ lock: true, text: "Loading" })`，与现有页面一致。
- 空数据：`el-empty`「当前条件下没有报价/出票数据」。
- 失败：顶部 `el-alert` 错误条 + 「重试」按钮；清空三视图数据，避免展示上一次的旧数据。
- 竞态：`AbortController` + `reqSeq` 序号守卫（照搬 `todayStatistics/index.vue` 的写法），被取代的响应直接丢弃。
- `keepAlive` 下首次进入才加载，切回不重复请求。

## 6. 权限与安全

- 后端沿用 `rule` 等值过滤（与现有统计接口同款），SQL 全部走 `buildWhere` 参数化占位符，**禁止拼接**。
- 前端系列/影院下拉只取当前用户可见影院列表，不额外暴露数据。
- 前端不做任何越权兜底判断——数据边界由后端保证。

## 7. 边界与异常

| 场景 | 处理 |
|------|------|
| 影院未匹配到系列 | 归「未分类」，顶部灰字提示数量，数据保留 |
| `app_name` 已调整/已删除 | 显示 `code-已调整`（沿用 `detail.vue` 写法） |
| 预聚合表未跑（历史为空） | 回退全实时，与现有接口行为一致 |
| 时间范围超 31 天 | 弹出提示并中止查询（沿用 `ElMessageBox.alert`） |
| 平台枚举新增但 `ORDER_FORM` 未登记 | 原样显示 `plat_name` |
| 接口返回空 `list` | 三视图空态，不报错 |
| 分母为 0 | 成功率显示 `--` |

## 11. 方案选型回顾

| 方案 | 内容 | 取舍 |
|------|------|------|
| **A（选定）** | 后端单接口按 `(app_name, plat_name)` 聚合，前端二次聚合 + 系列映射 | 改动最小、口径与现有页一致；报文稍大、前端多一次 reduce |
| B | 后端 JOIN `cinema_record` 直接输出平台/系列/影院三段汇总 | 前端零计算、报文小；后端改动与测试面大，系列口径被固化到后端 |
| C | 纯前端循环调 `/query`（每平台一次） | 零后端改动；10 次大查询，首屏慢，不可接受 |

## 12. 风险与应对
