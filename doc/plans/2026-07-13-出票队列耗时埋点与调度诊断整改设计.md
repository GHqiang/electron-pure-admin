# 出票队列耗时埋点与调度诊断整改设计

> 日期：2026-07-13
> 对比参照：[2026-07-13-报价调度全链路深度分析.md](./2026-07-13-报价调度全链路深度分析.md)
> 整改范围：出票队列基类 `BaseTicketQueue.js`（不含拉单方 `BaseOrderFetcher`）

---

## 一、现状分析

### 1.1 架构总览

出票侧采用**拉单/出票分离**架构，与报价侧的"拉单+调度合一"不同：

| 组件 | 文件 | 职责 |
|------|------|------|
| 拉单方 `BaseOrderFetcher` | [BaseOrderFetcher.js](file:///d:/Electron/electron-pure-admin-fix/src/common/core/BaseOrderFetcher.js) | 阻塞 while 循环拉单，`window.dispatchEvent` 派发 `newOrder_${appFlag}` 事件 |
| 出票队列 `BaseTicketQueue` | [BaseTicketQueue.js](file:///d:/Electron/electron-pure-admin-fix/src/common/core/BaseTicketQueue.js) | 监听事件，FIFO 入队，**串行 await** 出票 |

调用链路：

```
BaseOrderFetcher.start()                     // 阻塞 while 循环
  └─ await mockDelay(5)                      // 固定 5s 间隔
  └─ await this.fetchOrders()                // 子类实现：调平台API + 查后端API
     └─ sendNewOrderMsg(order)               // dispatchEvent('newOrder_xxx')
        │
        ▼ 事件桥
BaseTicketQueue.handleNewOrder(event)        // 监听 newOrder_xxx
  ├─ dispatchEvent(ackEvent)                 // 先发 ACK，避免拉单方 5s 超时告警
  ├─ 去重检查（实例Map + 全局Map TTL 30min）
  ├─ 猎人固定报价补全
  ├─ this.queue.push(order)                  // FIFO 入队（无优先级、无时间戳）
  └─ if (!this.isRunning) startProcessingQueue()
                                            // 调度器空闲才启动；运行中只 push 不干预
BaseTicketQueue.startProcessingQueue()       // async while 串行循环
  └─ while (queue.length > 0 && isRunning)
     ├─ order = queue.shift()                // FIFO 出队
     ├─ await orderHandle(order, logger)     // ⚠️ 串行 await，阻塞等完成
     │  └─ StrategyFactory.createSeatStrategy(order)
     │     └─ buyTicket.singleTicket()       // 实际出票
     └─ await saveTicketRecord(order, res)   // 写后端出票记录
```

### 1.2 与报价队列的关键差异

| 维度 | 报价队列 `BaseOfferQueue` | 出票队列 `BaseTicketQueue` |
|------|--------------------------|---------------------------|
| 调度模型 | 按系列并发（`_dispatchBatch` 同步 while + `findNextOrderToRun`） | **全局串行**（`startProcessingQueue` async while + `await orderHandle`） |
| 并发控制 | `runningCountBySeries` + `offerConcurrencyPerSeries`（默认2） | **无**（天然并发=1） |
| 入队方式 | `insertOrderIntoQueue`（按 `offer_end_time` 二分插入） | `queue.push`（FIFO） |
| handleNewOrder 路径 | 三路径（①立即派出 ②本系列阻塞 ③触发调度器） | **单路径**（push + 空闲则启动） |
| 入队时间戳 | `_offerEnqueueAt = Date.now()` | **无** |
| 队列等待耗时 | `queue_wait_ms`（落库 + 日志） | **无** |
| 执行耗时 | `offer_duration` + `platformCheckDurationMs` + `singleOfferDurationMs` | **无** |
| 调度诊断日志 | "订单入队-调度诊断"（三路径全覆盖） | **无** |
| 超时保护 | `offerHandleTimeout`（默认15s，麻花120s） | **无** |
| 去重容量 | 实例 Map（容量500，字典可配） | 实例 Map（无淘汰）+ 全局 Map（TTL 30min） |

### 1.3 核心问题

1. **零耗时埋点**：无法回答"出票慢在哪"——是队列等待慢、还是 `singleTicket` 执行慢、还是 `saveTicketRecord` 落库慢
2. **零调度诊断**：订单入队后看不到"前面排了几单"、"预计等多久"，排查滞留只能靠猜
3. **无超时保护**：`singleTicket` 卡死会阻塞整个队列，后续订单全部饿死
4. **`saveTicketRecord` 耗时计入 `orderHandle`**：当前 `await orderHandle` 包含了落库时间，但落库慢≠出票慢，无法区分

## 二、整改目标

### 2.1 核心目标

| 目标 | 交付物 |
|------|--------|
| 入队耗时可见 | `_ticketEnqueueAt` 时间戳 + `ticket_queue_wait_ms` |
| 出票执行耗时可见 | `ticket_handle_duration_ms`（含 `singleTicket` 净耗时 + `saveTicketRecord` 落库耗时） |
| 调度诊断可见 | "出票订单入队-调度诊断"日志（队列长度、前方排队、预计等待） |
| 超时保护 | `ticketHandleTimeout`（默认 120s，字典可配） |

### 2.2 不做的事（避免过度设计）

- **不引入并发**：出票天然串行（同影院登录态互斥、座位锁互斥），保持并发=1
- **不引入系列分组**：出票无"系列"概念，不照搬 `runningCountBySeries`
- **不引入优先级排序**：出票无"截止时间"概念，保持 FIFO
- **不改拉单方 `BaseOrderFetcher`**：本次仅整改出票队列 `BaseTicketQueue`

#### 3.1.3 耗时拆分

在 `startProcessingQueue` 中把 `orderHandle` 和 `saveTicketRecord` 的耗时分开计量：

```js
async startProcessingQueue() {
  while (this.queue.length > 0 && this.isRunning) {
    const order = this.queue.shift();
    if (order) {
      const logger = new Logger({ logType: 3 });
      if (!order.isAgain && this.prevOrderNumber === order.order_number) {
        // 重复订单跳过
      } else {
        logger.init(order);
        const orderHandleStartAt = Date.now();
        const queueWaitMs = order._ticketEnqueueAt
          ? orderHandleStartAt - order._ticketEnqueueAt
          : null;

        const res = await this.orderHandle(order, logger);
        const ticketHandleDurationMs = Date.now() - orderHandleStartAt;
        this.prevOrderNumber = order.order_number;

        logger.infoSave(
          `单个订单自动出票结束，状态-${res?.submitRes ? "成功" : "失败"}`,
          { res }
        );

        // 耗时统计日志必须在 saveTicketRecord 之前输出
        // 因为 saveTicketRecord 的 finally 会执行 logUpload 上送日志
        logger.infoSave("出票链路耗时统计", {
          订单号: order.order_number,
          队列等待耗时ms: queueWaitMs,
          出票执行耗时ms: ticketHandleDurationMs,
          总耗时ms: queueWaitMs != null
            ? ticketHandleDurationMs + queueWaitMs
            : null
        });

        let saveRecordDurationMs = null;
        if (!this.isTestOrder) {
          const saveRecordStartAt = Date.now();
          await this.saveTicketRecord(order, res, logger, {
            ticket_queue_wait_ms: queueWaitMs,
            ticket_handle_duration_ms: ticketHandleDurationMs
          });
          saveRecordDurationMs = Date.now() - saveRecordStartAt;
        } else {
          await logger.logUpload();
        }
      }
    }
  }
  this.isRunning = false;
}
```

> **注意**：`出票链路耗时统计` 日志必须在 `saveTicketRecord` **之前** `infoSave`，否则 `saveTicketRecord` 的 `finally` 块里 `await logger.logUpload()` 会先上送日志缓冲，导致耗时统计日志被遗留到下一轮或丢失。`saveRecordDurationMs`（落库耗时）仅在日志可见，不落库。

### 3.4 超时提醒

**位置**：[BaseTicketQueue.js:424](file:///d:/Electron/electron-pure-admin-fix/src/common/core/BaseTicketQueue.js#L424) `orderHandle` 方法

#### 3.4.1 设计原则

**超时仅作提醒，不中断 `singleTicket`、不改变队列流程。** 原因：
- `Promise.race` 无法真正取消 `singleTicket`，中断后后台仍会继续执行
- 出票含登录态/座位锁，后台继续执行可能与下一单冲突
- 保持串行 await 原行为，最简单、最安全

#### 3.4.2 新增字典字段

| 字段名 | 兜底默认值 | 说明 |
|--------|-----------|------|
| `ticketHandleTimeout` | `0`（不启用） | 出票执行超时提醒阈值（ms），`> 0` 启用 |

#### 3.4.3 `orderHandle` 超时提醒实现

```js
async orderHandle(order, logger) {
  const ticketHandleStartAt = Date.now();
  const queueWaitMs = order._ticketEnqueueAt
    ? ticketHandleStartAt - order._ticketEnqueueAt
    : null;
  try {
    logger.infoSave(`订单开始出票`, {
      订单号: order.order_number,
      上个订单号: this.prevOrderNumber,
      队列等待耗时ms: queueWaitMs,
      队列前方剩余: this.queue.length
    });

    if (this.isRunning) {
      const buyTicket = StrategyFactory.createSeatStrategy(
        order, logger, this.isTestOrder
      );

      // 超时提醒：字典 ticketHandleTimeout > 0 时启用
      // 超时不中断 singleTicket，仅发微信告警提醒人工介入，队列继续等待结果
      const ticketHandleTimeout =
        Number(dictStore.dictInfo.ticketHandleTimeout) || 0;
      let timeoutTimer = null;
      if (ticketHandleTimeout > 0) {
        timeoutTimer = setTimeout(() => {
          logger.errorSave("订单出票超时提醒", {
            订单号: order.order_number,
            超时阈值ms: ticketHandleTimeout,
            已耗时ms: Date.now() - ticketHandleStartAt,
            影院: order.cinema_name
          });
          sendWxPusherMessage({
            orderInfo: order,
            failReason: `出票执行超时，已耗时${Date.now() - ticketHandleStartAt}ms（阈值${ticketHandleTimeout}ms）`,
            transferTip: "出票超时提醒，请人工核查该订单状态"
          }).catch(e => console.error("超时微信告警发送失败", e));
        }, ticketHandleTimeout);
      }

      const res = await buyTicket.singleTicket();
      if (timeoutTimer) clearTimeout(timeoutTimer);

      logger.infoSave("订单出票执行完成", {
        订单号: order.order_number,
        出票执行耗时ms: Date.now() - ticketHandleStartAt,
        是否成功: !res?.err_msg
      });
      return res;
    } else {
      logger.warn("订单出票队列已停止");
    }
  } catch (error) {
    logger.errorSave("订单执行出票异常", {
      订单号: order.order_number,
      错误: error.message,
      出票执行耗时ms: Date.now() - ticketHandleStartAt
    });
  }
}
```

**关键点**：
- `setTimeout` 到时发微信告警 + 错误日志，但 `singleTicket` 继续执行不受影响
- `singleTicket` 正常完成后 `clearTimeout` 取消未触发的定时器
- 若 `singleTicket` 在阈值后完成，定时器已触发，`clearTimeout` 无副作用
- 队列仍 `await buyTicket.singleTicket()`，等结果出来才取下一单，无并发风险

### 3.5 字段汇总

#### 3.5.1 日志字段

| 日志名 | 时机 | 关键字段 |
|--------|------|----------|
| `出票订单入队-调度诊断` | 入队后 | 订单号、调度路径、队列长度、队列位置、调度器是否运行、上一单订单号 |
| `订单开始出票` | `orderHandle` 开始 | 订单号、上个订单号、队列等待耗时ms、队列前方剩余 |
| `订单出票超时提醒` | 超时触发（仅 `ticketHandleTimeout > 0` 时） | 订单号、超时阈值ms、已耗时ms、影院 |
| `订单出票执行完成` | `singleTicket` 完成 | 订单号、出票执行耗时ms、是否成功 |
| `出票链路耗时统计` | `saveTicketRecord` 之前（确保随本轮 logUpload 上送） | 订单号、队列等待耗时ms、出票执行耗时ms、总耗时ms |

#### 3.5.2 落库字段（`serOrderInfo`）

| 字段名 | 来源 | 说明 |
|--------|------|------|
| `ticket_queue_wait_ms` | `orderHandleStartAt - _ticketEnqueueAt` | 入队到开始出票的等待时间 |
| `ticket_handle_duration_ms` | `singleTicket` 前后差 | 出票执行净耗时（含平台检查+买票，不含落库） |

> 落库耗时（`saveRecordDurationMs`）仅在日志中输出，**不落库**——因为它在 `saveTicketRecord` 返回后才能算出，无法写入自己执行的记录。

#### 3.5.3 字典字段

| 字段名 | 兜底默认值 | 说明 |
|--------|-----------|------|
| `ticketHandleTimeout` | `0`（不启用） | 出票执行超时提醒阈值（ms），`> 0` 启用，超时发微信告警 |

## 五、验收标准

### 5.1 功能验收

1. **入队耗时可见**：日志能看到 `队列等待耗时ms`，落库记录有 `ticket_queue_wait_ms`
2. **出票耗时可见**：日志能看到 `出票执行耗时ms`，落库记录有 `ticket_handle_duration_ms`

## 七、风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| 超时提醒改变原流程 | 低 | 超时仅 `setTimeout` 发告警，不 `Promise.race`、不中断 `singleTicket`，对原 `await` 流程零侵入 |
| 落库字段后端暂不支持 | 低 | 前端先写日志，落库字段先置 null，后端支持后再启用 |
| `Date.now()` 精度问题 | 低 | 毫秒级精度足够，无需 `performance.now()` |
| 日志量增加 | 低 | 出票单量远小于报价单量（串行处理），日志量可控 |
| `出票链路耗时统计` 日志被 `logUpload` 遗漏 | 中 | 日志必须在 `saveTicketRecord` 之前 `infoSave`，已在代码中保证顺序 |
