# 报价出票日志整改最终方案 V3（分层定稿版）

> 日期：2026-08-18
> 状态：**定稿（V3）**，取代 V2"业务快照版"（差异见附录 B）
> ⚠️ 2026-08-18 更新：**数据脱敏要求已作废**（日志按原始值记录与存储，不再打码），本文涉及脱敏（sanitize/LOG_LOCAL_PLAIN/安全验收等）的内容不再执行，以《2026-08-18-报价出票日志整改-最终详细设计文档.md》V4.1 为准。
> 前置文档：2026-08-06（根因追踪）、2026-08-18 体积整改方案、V1 合并定稿、V2 业务快照版
>
> **V3 范式转变（架构上升）**：V1/V2 的共同错位是**把"用户要看的业务字段"硬塞进"日志"里**——用户看不到（日志表不是界面），开发又嫌碎。V3 按消费者分四层：**用户看业务层（业务表加列 + 详情页）、开发查日志索引层（DB 只存异常）+ 明细层（后端日志文件）+ 兜底层（本地文件）**。日志量问题随之根治：**opera_record 入库量只随异常量走，正常订单入库 ≈ 0 条**。
>
> 设计目标：用户关心的字段（命中规则/会员价三层/最终报价/券卡/实付/手机号）在订单详情页直接可见；开发排查走"业务字段 → 失败现场 → 后端文件全量明细 → 本地兜底"四级链路，任何问题有迹可查；入库日志量与业务量解耦（只存异常）。

## 〇、一页读懂（四层架构）

```
┌─ L0 业务层（用户看）─────────────────────────────────────────────┐
│ offer_record / ticket_record 加列 + 订单详情页展示                │
│ 内容：命中规则、会员价三层、最终报价构成、券卡明细、实付、手机号    │
│ 权威来源：流程结束写一次，SQL 可统计                              │
├─ L1 索引层（DB opera_record，开发快速定位）───────────────────────┤
│ 只存异常：失败现场（errorSave）+ 降级动作 + 关键异常               │
│ 正常订单入库 ≈ 0 条；异常订单 ≤ 5 条                              │
├─ L2 明细层（后端日志文件，开发主入口）─────────────────────────────┤
│ 全量过程：console 级打点 + 接口往返（URL/入参/出参/耗时）          │
│ 按日分文件 JSON 行，grep order_number 即得全量时间线               │
└─ L3 兜底层（本地 trace 文件，最后防线）────────────────────────────┘
   与 L2 同内容双写，打点即落盘；渲染进程崩溃/后端不可达时不丢
```

| 消费者 | 看哪层 | 得到什么 |
|--------|--------|---------|
| 用户（运营/客服） | L0 | 这单怎么算的、结果对不对（界面直接看） |
| 开发（日常排查） | L0 + L1 | 结果字段定位 + 失败环节现场 |
| 开发（疑难深挖） | L2 + L3 | 接口原始往返、中间计算全过程 |

## 一、设计原则（上升后的三条）

1. **按消费者分通道，不混装**：业务结果 → 业务表（L0）；异常 → 日志表（L1）；过程 → 文件（L2/L3）。一个通道只服务一类诉求。
2. **量随异常走**：入库日志量只和异常订单数挂钩（正常订单 ≈ 0 条），与业务量（报价 2000 单/天）解耦——这是"报价是大头"问题的根治，而非压缩。
3. **全量永远可得**：console 不是日志通道（生产环境渲染进程 devtools 不可见），一切过程日志必须落文件（本地即时写 + 后端集中收），开发在任何条件下都能拿到全量。

## 二、L0 业务层：用户看的（业务表加列 + 详情页）

### 2.1 offer_record 新增列（报价记录表，DDL）

> 现状：`offer_record`（成功）/`offer_record_fail`（失败）分表，`addRecordData` 动态 insert（obj 键即列名，前端直传），`sync_offer_record` 供统计。新增列直接进 obj 即可入库。

```sql
ALTER TABLE offer_record ADD COLUMN
  hit_rule_id      BIGINT       COMMENT '命中规则ID',
  hit_rule_name    VARCHAR(100) COMMENT '命中规则名称',
  member_price     DECIMAL(10,2) COMMENT '平台真实会员价',
  discount         DECIMAL(6,3)  COMMENT '规则折扣',
  cost_price       DECIMAL(10,2) COMMENT '会员成本价(真实会员价×折扣)',
  final_price      DECIMAL(10,2) COMMENT '最终报价',
  strategy         VARCHAR(20)   COMMENT '策略: 会员价/固定价',
  limit_adjusted   TINYINT      COMMENT '是否限价调整 0/1',
  adjusted_price   DECIMAL(10,2) COMMENT '限价调整后价格',
  calc_path        VARCHAR(500)  COMMENT '一句话计算路径(匹配/过滤过程)',
  pay_mobile       VARCHAR(20)   COMMENT '取价手机号(脱敏后4位)';
-- offer_record_fail 同步加列（失败单同样要能看到算到哪一步）
```

### 2.2 ticket_record 新增列（出票记录表，DDL）

```sql
ALTER TABLE ticket_record ADD COLUMN

  pay_card_num     VARCHAR(50)   COMMENT '实际支付卡号(脱敏后4位)',
  card_balance     DECIMAL(10,2) COMMENT '支付前卡余额',

  payment_amount   DECIMAL(10,2) COMMENT '卡实际支付金额',
  coupon_deduct    DECIMAL(10,2) COMMENT '券抵扣合计',
  use_path         VARCHAR(500)  COMMENT '一句话用券用卡路径(换卡/抵扣过程)',

-- qrcode/ticket_no 若已有列则复用，不重复加
```

### 2.3 写入时机与代码落点

| 数据 | 写入点 | 时机 |
|------|--------|------|
| 报价字段（含 calc_path） | BaseOfferQueue 保存报价记录处（serOrderInfo 组装处）+ 各系列 offerManage 匹配终点拼装 calc_path | 报价流程结束（成功写 offer_record，失败写 offer_record_fail，均含算到哪一步） |
| 出票字段（含 use_path） | BaseTicketQueue.saveTicketRecord 处 + 各系列 buyTicket 用券用卡后拼装 use_path | 出票流程结束（成功/失败均写，失败含 failReason） |

### 2.4 详情页展示（用户直接看）

- `src/views/offerRecord/index.vue`、`src/views/offerFailRecord/index.vue` 列表行加"报价详情"抽屉/弹窗：
  - **命中规则**：规则名（ID）+ 类型 + 金额构成（offerAmount/addAmount/quanValue）
  - **会员价明细**：真实会员价 × 折扣 = 会员成本价（手机号后 4 位）
  - **最终报价**：价格 + 策略 + 加价 + 是否限价调整（调整后价格）
  - **计算路径**：calc_path 原文
- `src/views/ticketRecord/index.vue` 列表行加"出票详情"抽屉：
  - **用券用卡**：手机号后 4 位、卡号后 4 位 + 支付前余额、券明细（类型/面额/张数）
  - **支付**：券抵扣合计 + 卡实付金额 + 取票码
  - **结果**：利润、失败原因、补救动作（转单/换号）
- 展示字段即 L0 列，前后端打通零额外成本；**客服/运营不再依赖日志**。
- **查询性能注意（配合附录 C-1）**：列表查询走 `queryFields` 显式字段（不含 coupons 等 TEXT 大字段），详情弹窗才查全字段；现有 `HistoryOfferRecord.vue`/`HistoryTicketRecord.vue` 的"查询日志"弹框保留并复用（L1 异常入口）。

### 2.5 统计口径（可选，延后）

todayStatistics 可加"命中规则分布 / 报价构成 / 实付金额核对"维度，SQL 直接基于新列（现有 statisticalAnalysis.js 的 WHERE 拼装机制天然支持新字段过滤）。

## 三、L1 索引层：DB 日志只存异常

### 3.1 入库清单（opera_record 仅收以下）

| des 模式 | 级别 | meta | 说明 |
|---------|------|------|------|
| `XX-失败-现场` | errorSave | { params摘要, res摘要, error } | 各环节失败处（5W：环节/入参/出参/错误/补救） |
| `降级-XX-进入` / `-成功` / `-失败` | errorSave/infoSave | {原因}/{手续费}/{error} | 降级动作，`降级-` 开头不覆盖根因 |
| `辅助-XX-异常` | errorSave | { error } | 券库存/余额同步等辅助操作失败 |
| 关键异常（超时/吞异常补记） | errorSave | { error } | 08-06 P0 清单中补的空 catch |

**正常订单入库 ≈ 0 条**；异常订单 ≤ 5 条。

### 3.2 明确不入库清单（全部转入 L2 文件）

- 一切 infoSave/warnSave（环节过程、快照摘要）——业务结果字段已进 L0，过程进 L2；
- 队列/调度诊断日志（BaseOfferQueue 入队/出队/竞速）——仅 L2；
- 辅助操作成功——仅 console/L2；
- 网络错误日志——改道 L2（见 4.4）；
- 轮询中间迭代——仅 L2。

### 3.3 根因缓存与 err_msg（保留，机制不变）

- `_rootErrCache` + `降级-`/`辅助-` 关键词排除 + 成功终态重置（V1 §3.2 原样）；
- `getLastErrMsgAndInfo` 优先根因 → 写入 offer_record_fail/ticket_record 的 err_msg/err_info（L0 业务表，**不依赖日志表**）。

## 四、L2 明细层：后端日志文件（开发主入口）

### 4.1 通道设计

```
渲染进程 Logger
  ├─ logList（仅 errorSave 等入库级）→ POST /svpi/operaRecord/addList → opera_record（L1）
  └─ traceBuffer（全部过程：console 级 + 接口往返 + 快照）→ POST /svpi/log/trace
       → 后端落文件 logs/trace/YYYY-MM-DD.log（L2，不入库）
       └─ 上传失败 → 本地兜底（L3 已有，不重复告警）
```

- 后端新增路由 `POST /svpi/log/trace`（body: `{ plat_name, app_name, order_number, type, lines: [] }`，lines 为脱敏后 JSON 行），**只写文件不查库**；
- 上传策略：fire-and-forget + 全局串行链（`window.__logUploadChain`，任意时刻在途 ≤1），出票队列不阻塞；
- 批大小沿用 100；`traceBuffer` 内存上限 500（超出丢最旧，本地 L3 已即时落盘兜底）。

### 4.2 内容与文件格式

- 覆盖：**所有** console 级过程（含 info/warn/error 不入库的）+ 接口往返（URL、入参摘要、出参摘要、耗时）+ L1 同款行；
- 格式：每行一个 JSON 对象（与 localFailLog.js 现有一致）：
  `{"local_save_time":"2026-08-18 15:30:00","order_number":"X","type":1,"des":"取会员价-返回","level":"info","info":{...}}`
- 按日单文件 `trace-YYYYMMDD.log`，开发排查：`grep 'order_number":"X"' trace-20260818.log` 即得该订单全量时间线（含接口原始返回）。

### 4.3 保留与容量

| 项 | 值 |
|----|----|
| 单条体积 | 0.3~1KB（接口往返截断后，脱敏） |
| 日容量估算 | 2000 单 × 60 条 × 0.5KB ≈ 60MB/天（保守按 100MB/天） |
| 保留策略 | 15 天（≈1.5GB，实测服务器剩余 ~45GB，占比 ~3%），后端定时清理（参照现有 opera_record 分区清理 cron） |
| 容量监控 | 每日统计 trace 目录大小，超阈值（如 2GB）微信告警 |
| 降级开关 | 字典可配 `trace_upload_enabled`（默认开；关闭时仅错误行上传，本地 L3 仍全量） |

### 4.4 明细查询方式（开发/半技术人员）

```
① L1 异常日志（已有界面）：HistoryOfferRecord / HistoryTicketRecord 的"查询日志"弹框
   （现状即按 order_number 查 opera_record，V3 沿用）
② L2 明细文件（推荐新增）：GET /svpi/log/trace?order_number=X&date=YYYY-MM-DD
   后端读文件过滤返回；前端在现有"查询日志"弹框加"明细"Tab（开发量小）
③ 命令行兜底（零开发）：SSH 服务器 → grep '"order_number":"X"' logs/trace/2026-08-18.log
④ 本地文件：userData/logs/trace-YYYYMMDD.log 编辑器搜索订单号
```

> 原则：**每层都有界面/命令入口，不让任何人去翻原始文件**；文件按日单文件 + 行 JSON，grep 即查。当日文件过大（>500MB）再考虑订单号行索引，YAGNI 暂不做。

### 4.5 网络错误日志并入（推荐，可延后）

`networkErrorBatcher.js` 的上传目标由 addList（入库）改为 `/svpi/log/trace`（文件），D3 本地 `network-error-*.log` 兜底不变。理由：网络错误对排查接口问题价值高、入库无检索价值，归入明细层最合理。

## 五、L3 兜底层：本地文件打点即写

- 复用现有 `localFailLog.js` ipc 写盘链路（`userData/logs/`，已核实可用）；
- **打点即写**：Logger 每次入 logList / traceBuffer 时，追加写本地 `trace-YYYYMMDD.log`（攒批高频 flush：满 50 条或 2 秒，fire-and-forget）——对抗渲染进程崩溃（崩溃自愈已存在，日志不能再丢）；
- 内容与 L2 一致（同源双写）；写盘前脱敏（session/token/password 打码，mobile/card 后 4 位；`LOG_LOCAL_PLAIN=1` 显式开启才明文）；
- 保留 7 天，主进程启动清理（与现有 logUploadFail 清理合并实现）。

## 八、实施阶段与系列对照

### 8.1 示范机制（不影响现有的关键设计）

**实例级开关 v3Mode**：`new Logger({ logType, isPrint, v3Mode })`——v3Mode=true 走新链路（L1 收窄 + trace 双通道 + 本地即时写），false 完全走现状代码路径。公共文件（logger.js/BaseOfferQueue/BaseTicketQueue）的改造点全部按 v3Mode 分支，**非示范系列行为逐字节不变**。

**开关来源（字典白名单，与现有 `supportChangeSeatPlatList.includes()` 同一模式）**：

```javascript
// 字典表新增：log_v3_enabled_series = "chenxing"（后台可改，渲染进程重启生效；置空即全量回退）
const v3Mode = dictStore.dictInfo.log_v3_enabled_series?.split(",").includes(plat_name);
```

**两步走示范**：

| 步骤 | 内容 | 行为变化 | 回退 |
|------|------|---------|------|
| 示范第一步（纯增量） | chenxing 采集字段写新列 + calc_path/use_path + trace 双写 + 详情页 + 失败现场 5W | 零变化（现有日志照常入库，只是多字段/多文件/多页面） | 删除新代码即回退 |
| 示范第二步（行为切换） | 字典开启 chenxing 的 L1 收窄（infoSave 不入库） | 仅 chenxing 变 | 字典置空即回退 |

**后端/DB 零影响**：`/svpi/log/trace` 为新增接口；DDL 为新增列（动态 insert 不破坏现有请求）；addList/现有查询不动。

### 8.2 阶段划分（每阶段先 chenxing 示范，评审通过再推广）

- **阶段一（框架通道）**：logger 双通道（v3Mode 分支）+ trace 接口 + 本地即时写 + logTrim/脱敏 + 根因缓存 + 全局串行链 + 出票不阻塞 + 后端清理
- **阶段二（止血）**：P0 bug 10 处（08-06 §4.1）+ console 清理（08-06 §4.2）
- **阶段三（L0 业务层，示范第一步）**：DDL 加列 → chenxing 字段写入 + calc_path/use_path 拼装 → 详情页展示（评审：真实问题单反测字段够用）
- **阶段四（L1 收窄 + L2 切换，示范第二步）**：字典开启 chenxing 收窄（依赖阶段三完成）；网络错误改道 L2
- **阶段五（推广）**：chenxing 两步验收通过后，按系列对照表逐系列推广（每系列独立提交、独立验收）

**chenxing 示范验收点**：
- [ ] chenxing 跑真实报价 + 出票各数单：详情页字段正确、trace 文件全量、第二步后 opera_record 仅异常（≤5 条/失败单、正常单 0 条）
- [ ] 对照系列（wanda）跑一单：日志行为与改造前一致（diff 验证），证明不影响现有

## 九、验收标准（总）

1. **用户侧（L0）**：报价详情/出票详情页可见全部字段（命中规则、会员价三层、最终报价构成、券卡明细、实付、手机号后4位、calc_path/use_path）；SQL 可按新列统计
2. **排查链路**：按附录 A SOP，任选历史订单走通"业务字段 → 失败现场 → 后端文件 → 本地兜底"四级定位
3. **量级**：opera_record 正常订单 0 条、异常订单 ≤5 条；后端 trace 文件按日生成、容量在预算内；入库总量与异常量挂钩（抽样对比验证）
4. **全量可得**：后端 `logs/trace/YYYY-MM-DD.log` 当日存在且 grep order_number 可得全量时间线（含接口往返）；本地 trace 文件同内容兜底
5. **崩溃不丢**：渲染进程崩溃场景（可模拟）最后 2 秒内日志已在本地文件
6. **根因**：ticket_record/offer_record_fail 的 err_msg 为真实失败原因（非降级/辅助动作）
7. **安全**：库、后端文件、本地文件均无 session_id/token/password 明文；mobile/card 仅后 4 位（明文需显式开关）
8. **性能**：出票不等待日志上传；全局在途上传 ≤1；上传失败本地兜底 + 微信告警不破坏
9. 无手写 `[报价]/[出票]` 前缀；后端控制台无整批 payload 打印；eslint 通过

## 附录 A：排查 SOP（升级版，四级链路）

### A.1 报价金额不对（用户反馈）

```
1. L0：订单详情页/offer_record 查该单
   - hit_rule_name/offerAmount → 命中规则是否符合预期（不对 → 查规则配置）
   - member_price/discount/cost_price → 会员价三层哪层错
   - final_price/strategy/limit_adjusted → 最终报价构成
   - calc_path → 匹配/过滤路径是否符合预期
2. L1：opera_record 该单有无失败现场（失败单才有）
3. L2：后端 logs/trace/YYYY-MM-DD.log grep order_number
   → 取价接口原始返回（rawPrice 是接口给的还是算错的）、中间计算全过程
4. L3：机器本地 trace 文件（后端不可达时）
```

### A.2 出票失败/金额异常（用户反馈）

```
1. L0：ticket_record 该单
   - pay_mobile/pay_card_num/card_balance/coupons/payment_amount → 用的号/卡/券/金额是否符合预期
   - use_path → 换卡/抵扣路径
   - err_msg/failReason → 失败根因
2. L1：失败现场（哪一步挂的、入参/出参/error）+ 降级-XX（补救动作）
3. L2：grep order_number → 支付/取码接口往返原始数据
4. L3：本地兜底
```

### A.3 系统级问题（批量失败、无单量）

```
1. L2：按 type/时间段 grep 文件 → 分布与共性（某平台/某接口集中失败）
2. L1：异常订单失败现场聚类（err_msg 统计）
3. 网络错误：L2 network-error 行（改道后）→ 接口不可达/超时定位
```

## 附录 C：加列与文件存储 FAQ（量化分析）

### C-1 业务表加列会影响查询效率吗？

**结论：不会产生可感知影响（<1% 量级）。**

| 查询场景 | 走什么路径 | 加列影响 |
|---------|-----------|---------|
| 按订单查详情 | order_number 索引点查 | 无（只读 1~2 页） |
| 列表页查询 | ORDER BY processing_time + LIMIT 分页 | 无（有 LIMIT，只扫少量行） |
| 统计分析 | sync_offer_record 预聚合表 + 按日聚合 | 无（预聚合由定时任务维护） |
| 行数规模 | offer_record 已有定时清理（processing_time < N 天） | 行数有上限 |

- 物理层面：InnoDB 16KB/页，行宽 ~600B → ~1KB（coupons TEXT 溢出页存储、不占主行），每页行数 25 → 15，仅全表扫描场景翻倍——**系统无全表扫描场景**；
- 写入侧：每单 INSERT 多写 ~1KB，相对业务网络耗时可忽略；
- **两个注意点（改造时做掉）**：
  1. `offerRecord.js:122` 默认 `SELECT ${tableName}.*` 会把 TEXT 大字段带进列表 → 列表查询改显式字段（`queryFields` 已支持），详情弹窗才查全字段；
  2. 新列一律不加索引（按订单走 order_number）——零索引维护成本；
- 退路（YAGNI 不做）：实测异常时快照字段拆独立表。

### C-2 过程写文件有什么影响？磁盘够吗？

**性能：无影响。** 本地写盘 = 攒批（50 条/2 秒）+ ipc 异步 + 失败静默，单次写 ~25KB（顺序追加，磁盘 MB/s 级）；上传后端 = fire-and-forget + 全局串行链，业务不等待。服务器实测：负载 0.45、CPU 3.5%、磁盘已用 57%。

**容量（实测依据）：**

| 位置 | 估算 | 实测空间 | 占比 |
|------|------|---------|------|
| 后端 trace 15 天 | ~1.5GB | 服务器剩余 **~45GB**（总 105GB） | ~3% |
| 本地 trace 7 天 | ~0.4~0.7GB | 用户机磁盘常规容量 | 可忽略 |

保险：每日容量统计 + 超阈值微信告警；超期自动清理；`trace_upload_enabled` 可降级为仅错误行。

### C-3 过程日志怎么查？

```
① L1 异常：HistoryOfferRecord/HistoryTicketRecord"查询日志"弹框（已有，沿用）
② L2 明细：GET /svpi/log/trace?order_number=X&date=... + 弹框"明细"Tab（新增，推荐）
③ 命令行：SSH 服务器 grep '"order_number":"X"' logs/trace/YYYY-MM-DD.log
④ 本地：userData/logs/trace-YYYYMMDD.log 编辑器搜索订单号
```

### C-4 文件查询性能（文件变大后）

- 按日单文件 + 行 JSON，单日 ~100MB，grep 秒级返回；
- 查询接口限定 date + order_number 双条件，只读单文件；
- 单文件 >500MB 时再引入"订单号 → 行号"索引或按订单分文件（YAGNI，暂不做）。
