# 报价出票日志写入体积整改方案

> 日期：2026-08-18
> 状态：**待评审**
> 关联：《2026-08-06-报价出票日志追踪整改细化设计方案.md》聚焦日志**可读性与根因追踪**（des 统一、自动前缀、根因缓存、轮询收敛），本方案聚焦日志**写入体积与写入量**（单条 payload 瘦身、去重减噪、上传不阻塞业务）。两份方案互补：前者解决"日志看得懂"，后者解决"日志写得太多太大"；共用 `logTrim.js` 裁剪函数、des 统一字典等基础设施，阶段划分对齐，建议联动实施。
>
> 设计目标：单个订单（报价 + 出票）的日志**条数与单条体积**降到可接受量级（预估每单持久化数据缩减 80%~90%），日志上传不阻塞出票业务，敏感字段不入库，后端存储与控制台不再被日志撑爆。

## 一、现状诊断摘要

### 1.1 日志写入链路（当前实现）

```
渲染进程 Logger（src/common/logger.js）
  ├─ logList 内存攒批（上限 500 条，超出丢最旧）
  ├─ isPrint=true：每条日志同时 console 输出
  └─ logUpload()（src/utils/utils.js:1751）
       ├─ 每批 ≤ 50 条（LOG_UPLOAD_CONFIG.BATCH_SIZE）
       ├─ 超时重试 3 次（1s/2s/4s 指数退避）
       ├─ POST /svpi/operaRecord/addList
       └─ 上传失败 → 本地兜底 userData/logs/logUploadFail-*.log + 微信告警
后端 auto-ticket-service
  ├─ api/operaRecord.js addRecordData：log_list 逐条 INSERT，每条一行 opera_record
  ├─ routes/opera_record.js:18：每个请求 console.log(JSON.stringify(params)) 整批打印
  └─ 查询接口 console.log('mainRows:'/'partitionRows:') 全量结果打印
```

网络错误日志已走 `networkErrorBatcher` 攒批上传（正例，不在本方案范围）。

### 1.2 核心数据：一单写多少

**条数**（仅计 `infoSave/warnSave/errorSave`，即入 logList 持久化的）：

| 流程 | 条数估算 | 来源 |
|------|---------|------|
| 报价侧（队列层 + offerManage） | 55~75 条/单 | 队列层约 15 条（入队/调度诊断/竞速/记录），offerManage 23~59 条（h5ume 最多 59） |
| 出票侧（队列层 + buyTicket） | 50~65 条/单 | 队列层约 10 条，buyTicket 28~46 条 |
| **合计** | **约 110~140 条/单** | 后端 opera_record 每单 110~140 行 |

**体积**（量级估算，单条含大对象时）：

| 单条类型 | 体积 | 占比 |
|---------|------|------|
| 纯文本 des | ~0.2 KB | 约 40% |
| 带订单/响应摘要 | ~0.5~2 KB | 约 40% |
| 带完整对象（order/res/规则） | ~2~10 KB | 约 15% |
| 带列表（卡列表/座位/登录信息/规则列表） | ~10~100 KB | 约 5% |

> 按每单 120 条估算：现状每单约 **300~500 KB** 持久化数据；瘦身后（全量对象改摘要）约 **30~60 KB**，缩减 **80%~90%**。若单条混入全量卡列表/座位列表，单条可达 100 KB 以上，单日多平台累计可达数十 MB。

### 1.4 条数过多

- 全量打点：各平台 `offerManage` 23~59 条 + `buyTicket` 28~46 条 + 队列层 20~30 条 ≈ 每单 110~140 条。
- **中途多次上传**：`buyTicket` 目录下 49 处 `logger.logUpload()`（如 chenxing/orderManage.js:571/591/594），一批 120 条按 50 条/批拆成 3 个请求。
- 轮询循环未收敛：`getPayResult` 等轮询每次迭代都 infoSave（07-06 方案已要求收敛为 wanda 模式，见 08-06 文档 5.2.3，尚未全系列落地）。

### 1.5 冗余双写

- `Logger.isPrint` 默认 true：每条日志 console 一遍 + 上传一遍。
- 正常流程用 `console.warn`：BaseOfferQueue.js:513「新的待报价订单」、BaseTicketQueue.js:199 等（语义应为 info，且与 infoSave 重复）。
- **BaseBuyTicket.js:126 `console.warn("单个订单出票流程结束", this.logger.logList)`：每单结束时把整个 logList 全量打到 console**，单笔最大的一次 console 输出。

### 1.6 出票队列被日志上传阻塞（性能隐患，需优先修复）

```
BaseTicketQueue.startProcessingQueue（串行 while 循环）
  → await this.saveTicketRecord(...)          （BaseTicketQueue.js:494）
      → finally { await logger.logUpload() }  （BaseTicketQueue.js:765）
```

出票队列**串行**：下一单必须等上一单日志批次上传完成。批次大（100 条×大 payload）、网络慢、超时重试（最多 3 次，1s/2s/4s 退避）叠加时，出票会被日志拖住数十秒——对时效敏感的锁座出票是实打实的业务风险。报价侧所有 `logUpload()` 均为 fire-and-forget（不 await），无此问题。

### 1.7 后端存储与控制台

- `opera_record` **逐条一行**，`info` 字段 `JSON.stringify` 入库，无长度上限。
- `routes/opera_record.js:18` 每个 addList 请求 `console.log(JSON.stringify(params))`，整个批次 payload 打到后端控制台。
- `api/operaRecord.js` 查询接口 `console.log('mainRows:'/'partitionRows:')` 全量结果打印。
- 查询侧已有 15 天限制与 `opera_record_partitioned` 分区表（保留）。

## 二、总体策略：三阶段渐进式

```
阶段一：Logger 框架能力增强（基础先行，一次性完成）
  └─ logTrim 裁剪 + 敏感字段脱敏 + 上传前统一 summarize（内存/上传同步瘦身）
         ↓
阶段二：止血整改（大 payload 打点改摘要 + console 去重 + 出票不阻塞）
  └─ Top 清单逐项整改 + 出票队列 logUpload 改 fire-and-forget + 后端控制台清理
         ↓
阶段三：写入规范推广（新打点审查规范 + 系列对照表验收）
  └─ 打点 Checklist 固化 + 各系列按对照表逐项消除
```

**关键原则**：
1. 阶段一不依赖系列改造，可独立完成并验证（与 08-06 文档阶段一联动，共用 logTrim.js）。
2. 阶段二优先修「出票阻塞」与「敏感字段入库」两处风险点，再逐项瘦身。
3. 阶段三以打点 Checklist + 对照表固化标准，新代码评审强制走查。

## 三、阶段一：Logger 框架能力增强

> 改造范围：`src/common/logger.js` + 新建 `src/common/autoTicket/common/logTrim.js` + `src/utils/utils.js` 的 `sanitizeLogInfoForUpload` 增强。

### 3.1 大对象裁剪（logTrim.js）

> 08-06 文档 3.1.7 已设计 `trimRuleForLog`（11 字段）/`trimCardForLog`（4 字段），本方案**复用并扩展**通用裁剪器：

```javascript
// 通用摘要：深度 5 / 数组 ≤10 项 / 字符串 ≤200 字符 / 敏感 key 打码
const summarizeForLog = (obj, options = {}) => { /* ... */ };

// 订单摘要：只留业务定位字段（serOrderInfo 字段集是现成模板）
const trimOrderForLog = order => ({
  order_number: order.order_number,
  plat_name: order.plat_name,
  app_name: order.app_name,
  cinema_name: order.cinema_name,
  hall_name: order.hall_name,
  film_name: order.film_name,
  show_time: order.show_time,
  ticket_num: order.ticket_num,
  tpp_price: order.tpp_price,
  supplier_end_price: order.supplier_end_price,
  lockseat: order.lockseat,
  offer_end_time: order.offer_end_time
});

// 接口响应摘要：只留结果判定字段
const trimResForLog = res => ({
  success: res?.success,
  msg: res?.msg,
  order_status: res?.order_status,
  quote_id: res?.data?.quote_id,
  qrcode: res?.qrcode,
  profit: res?.profit,
  card_id: res?.card_id
});

export { summarizeForLog, trimOrderForLog, trimResForLog, trimRuleForLog, trimCardForLog };
```

### 3.2 Logger 入列前统一瘦身（内存 + 上传同步降）

- 新增 `Logger.levels` 之上的一层：`infoSave/warnSave/errorSave` 在 `_addToLogList` 前对 meta 统一 `summarizeForLog(meta)`，**入内存即瘦身**（当前只在上传前 sanitize，内存和 logList 仍占全量）。
- 上传侧 `sanitizeLogInfoForUpload` 增强：
  - **敏感字段 denylist**：`session_id`、`sessionId`、`token`、`cookie`、`password`、`mobile`（如非业务必需）→ 打码 `[MASKED]` 或保留后 4 位；
  - 数组截断：≤10 项（`[...slice(0,10), "…共N项"]`）；
  - 字符串截断：≤500 字符；
  - 嵌套深度：40 → 10。
- 提供 `logger.infoLocal(msg, meta)`：仅 console 不入 logList（供调试性日志使用，如测试模式参数、轮询中间过程）。

### 3.3 上传条数控制

- `LOG_UPLOAD_CONFIG.BATCH_SIZE` 50 → 100（瘦身后单条变小，可减少请求次数）。
- 上传前按 level 过滤做成**字典可配开关**：`uploadInfoLevel`（默认保留 info，保证 08-06 文档的环节时间线完整；如需止血可配成只传 warn/error）。

### 3.4 阶段一验收点

- [ ] 敏感字段（session_id/token/mobile）入库前已打码

### 4.4 出票队列 logUpload 不阻塞改造（风险优先）

```javascript
// 改造前（BaseTicketQueue.js:765）：阻塞串行出票队列
} finally {
  await logger.logUpload();
}

// 改造后：fire-and-forget + 全局串行上传，双保险
} finally {
  // 上传失败已由 utils.logUpload 本地兜底 + 微信告警，业务不等日志
  logger.logUpload().catch(() => {});
}
```

> **并发控制**：出票队列串行处理时改为不 await 后，连续订单的上传可能重叠。为避免并发 HTTP 堆积（历史教训：占连接池放大排队），将 `logUpload` 的串行化从"每实例链"升级为**全局共享链**（`window.__logUploadChain`），保证任意时刻全局最多一个日志上传批次在途。报价侧保持 fire-and-forget 不变，同样受益于全局串行。

## 六、验收标准（总）

1. 单个订单（报价+出票）持久化日志条数 ≤ 80 条，单条 meta 均为摘要（无全量对象）
2. 任选订单按 `order_number` 过滤，时间线完整可读（联动 08-06 文档标准）
3. 日志/数据库抽样确认无 session_id、token 等敏感字段
4. 出票队列一单接一单连续处理时，出票耗时不含日志上传等待
5. 全局任意时刻日志上传批次在途 ≤ 1
6. 上传失败仍走本地兜底 + 微信告警（不被本次改造破坏）
7. 后端控制台无整批 payload/全量结果打印
8. 新打点全部通过 5.1 Checklist
9. 每单持久化数据量较整改前下降 80% 以上（抽样对比）

---

## 七、已确认决策

1. **瘦身优先于删日志**：保留环节时间线（08-06 文档的根因），通过内容摘要 + 条数控制降体积，不做"砍 info"式粗暴删减
2. **入列即瘦身**：meta 在入 logList 前统一 `summarizeForLog`，内存与上传同步降（不只是上传前兜底）
3. **敏感字段绝不入库**：session_id/token/mobile 默认打码，白名单例外需评审
4. **出票不阻塞**：logUpload 改 fire-and-forget，串行化升级为全局共享链防并发堆积
5. **上传批次 50→100**：瘦身后减小请求次数
6. **裁剪函数与 08-06 文档共用**：`trimRuleForLog`/`trimCardForLog` 在 logTrim.js 统一实现，两个方案不重复造
7. **后端联动**：opera_record 入库前截断、路由/查询 console.log 收敛

## 八、风险与控制

| 风险 | 控制 |
|------|------|
| 裁剪后字段不足导致排查困难 | 裁剪字段集 = serOrderInfo/出票记录字段集，保证业务定位字段齐全；摘要字段集评审确认 |
| 全局串行上传成为新瓶颈 | 上传批次增大（50→100）+ 本地兜底不丢日志；串行链失败恢复逻辑沿用现有实现 |
| 敏感字段脱敏误伤排查 | 白名单外一律打码；如需明文排查走本地 fail log（不上传） |
| 瘦身后环节不完整 | 仅裁剪 meta 内容，不删环节打点；条数控制靠轮询收敛与去重，不动主链路 |
| 与 08-06 文档改造面重叠 | 两个方案阶段对齐、共用 logTrim.js 与 des 字典；评审时合并验收避免重复改动 |
| 后端截断丢失长错误栈 | 截断阈值（100KB）远大于正常错误栈，仅兜底异常大对象 |
