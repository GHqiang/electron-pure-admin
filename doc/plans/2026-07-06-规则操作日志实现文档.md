# 规则操作日志系统 — 实现完整文档

> 创建日期：2026-07-04  
> 最后更新：2026-07-06

---

## 一、概述

为追踪 SV 数据库规则状态变更和猎人平台同步操作，建立了一套完整的操作日志系统。日志写入后端 `rule_operation_log` 表，前端在 7 个位置埋点，覆盖所有规则状态变化和同步操作。

---

## 二、数据库

### 2.1 表结构

```sql
CREATE TABLE IF NOT EXISTS rule_operation_log (
    id INT AUTO_INCREMENT PRIMARY KEY,
    rule_id INT COMMENT '关联的规则ID',
    rule_name VARCHAR(255) COMMENT '规则名称（冗余，便于查询）',
    shadow_line_name VARCHAR(100) COMMENT '影线名称',
    operation_type VARCHAR(50) NOT NULL COMMENT '操作类型',
    old_status VARCHAR(10) COMMENT '变更前状态',
    new_status VARCHAR(10) COMMENT '变更后状态',
    old_seat_num VARCHAR(10) COMMENT '变更前座位数',
    new_seat_num VARCHAR(10) COMMENT '变更后座位数',
    plat_name VARCHAR(50) DEFAULT 'lieren' COMMENT '目标平台',
    trigger_source VARCHAR(100) COMMENT '触发来源',
    change_reason VARCHAR(500) COMMENT '变更原因说明',
    success TINYINT DEFAULT 1 COMMENT '操作是否成功 1-成功 0-失败',
    error_msg TEXT COMMENT '失败时的错误信息',
    operator VARCHAR(100) COMMENT '操作人',
    ext_data TEXT COMMENT '扩展数据(JSON)',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    INDEX idx_rule_id (rule_id),
    INDEX idx_operation_type (operation_type),
    INDEX idx_trigger_source (trigger_source),
    INDEX idx_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
COMMENT='规则操作日志表：记录规则状态变更及猎人平台同步操作';
```

### 2.2 字段枚举

**operation_type**：

| 值                        | 含义                    | 使用场景                            |
| ------------------------- | ----------------------- | ----------------------------------- |
| `status_change`           | 仅状态字段变化          | 手动切换开关                        |
| `quan_stock_change`       | 券库存触发状态/座位变化 | 券库存更新后自动检查                |
| `allow_offer_time_change` | 允许报价时间变更        | "当日不报"操作                      |
| `rule_create`             | 规则新增                | 用户新增保存规则                    |
| `rule_update`             | 规则编辑                | 用户编辑保存规则                    |
| `sync_add_update`         | 同步规则到平台          | `lierenOfferRuleSyncPlat`           |
| `sync_status`             | 同步状态到平台          | `lierenOfferRuleEditStatusPlat`     |
| `sync_delete`             | 从平台删除规则          | `lierenOfferRuleDelPlat`            |
| `sync_bidirectional`      | 双向同步修复            | `checkAndUpdateLierenRuleState`     |
| `getRuleIdByPlat`         | 获取平台规则ID          | `usesMachineBaseFun` 会员价规则新增 |

**trigger_source**：

| 值                      | 含义                      |
| ----------------------- | ------------------------- |
| `manual_toggle`         | 用户手动切换启用/禁用开关 |
| `form_save`             | 用户通过表单保存规则      |
| `quan_stock_zero`       | 券库存归零自动禁用        |
| `quan_stock_update`     | 券库存变化更新座位数      |
| `time_change`           | "当日不报"等时间字段变更  |
| `login_sync`            | 登录时双向同步检查        |
| `manual_fix`            | 点击"规则同步修复"按钮    |
| `rule_edit_save`        | 编辑规则保存时同步        |
| `rule_add_save`         | 新增规则保存时同步        |
| `rule_delete`           | 删除规则时同步删除        |
| `no_offer_today`        | "当日不报"操作            |
| `add_member_price_rule` | 新增会员价规则            |

### A — 手动切换开关

**文件**：`src/views/offerRule/index.vue` → `editStatus()`

触发时机：用户在规则列表页点击启用/禁用 el-switch

**old_status 推算**：el-switch 的 `v-model` 在 `@change` 之前已改 `row.status`，翻转推算：当前 `"2"` → 旧值 `"1"`，当前 `"1"` → 旧值 `"2"`。

```javascript
svApi
  .addRuleOperationLog({
    rule_id: row.id,
    rule_name: row.ruleName,
    shadow_line_name: row.shadowLineName,
    operation_type: "status_change",
    old_status: row.status === "1" ? "2" : "1",
    new_status: row.status,
    trigger_source: "manual_toggle",
    change_reason: "用户手动切换规则状态",
    success: 1,
    operator: name
  })
  .catch(() => {});
```

> **注意**：`rules.offerRuleList` 只缓存启用/仅报价的规则（status=1/3）。如果从禁用切到启用，old_status 会是 null。

| 文件                           | 取值方式                        | 来源                                          |

| `useLierenOfferRuleSyncFun.js` | `tokens.userInfo?.name \|\| ""` | 每次调用动态读取 Pinia store                  |

## 七、注意事项

1. **日志写入不阻塞主流程**：所有 `addRuleOperationLog` / `batchAddRuleOperationLog` 调用都加了 `.catch(() => {})` 兜底
2. **编码安全**：文件编辑使用 UTF-8 编码，不要用 PowerShell `Set-Content` 默认编码
3. **变量遮蔽**：`lierenOfferRuleSyncPlat` 中查询旧状态的 `const listRes` 不能叫 `res`，会覆盖外层 `ruleAdd` 的返回值
4. **platRuleId 判空**：查询旧状态前检查 `lierenOfferRule.platRuleId` 是否存在
5. **批量场景**：`platOnlyRules` 用 `batchAddRuleOperationLog` 减少 HTTP 请求
6. **日志保留**：暂不自动清理，后续可视数据量增加定时清理

## 十、优化记录

### 2026-07-06 — 消除 `manual_toggle` 重复日志

**问题**：用户手动切换规则开关时，`editStatus()` 同时写入 `status_change` 和 `sync_status` 两条日志，实际是一条用户操作。

**根因**：`editStatus()` 无条件写 `status_change` 日志，随后 `editRuleStatusSyncToPlat()` → `lierenOfferRuleEditStatusPlat()` 又写了 `sync_status` 日志。

**修复**：`editStatus()` 中先执行同步，再判断是否实际走了平台同步。若已同步（`sync_status` 日志已覆盖），跳过 `status_change` 日志；若未同步（非固定报价规则 / 未配置猎人同步），保留 `status_change` 日志。

**判断条件**（与 `editRuleStatusSyncToPlat` 一致）：

1. `dictStore.dictInfo.fixedOfferToPlatList` 非空
2. `row.offerType == 1`（固定报价）
3. `platOfferList` 中有 `platName === "lieren"` 且 `isSyncPlat == 1` 的项

**影响范围**：仅 `src/views/offerRule/index.vue` → `editStatus()`，不影响其他埋点。
