# 原价（tpp_price）不报 详细设计

> 日期：2026-10-11
> 需求：报价前按订单原价过滤规则 —— **原价超过 xx，或落在 xx 区间内，则不报**；原价字段取 `order.tpp_price`。
> 关联：《2026-09-30-猎人B钱包加价报价整改说明.md》（规则级新增字段的落库/回显/兜底先例）、《2026-06-04-报价失败原因分类.md》（`OFFER_FAIL_TYPE` 枚举）、《2026-08-18-V3-字段采集与打点详细设计方案.md》（`offer_record.tpp_price` 已有列）。
> 状态：设计已评审确认（2026-10-11），**待实施**。

---

## 一、需求与已确认决策

### 1.1 需求

运营需要「按订单原价（`tpp_price`）决定某些规则不报价」：例如原价超过 50 元的场次不参与某条规则，或原价落在 30~80 元区间内的场次不报。原价字段统一用 `tpp_price`（订单对象已有，见 §2.2）。

### 1.2 已确认决策（2026-10-11 评审）

| # | 决策点 | 结论 |
| - | ------ | ---- |
| 1 | 不报粒度 | **规则级过滤**：命中条件的规则从候选里剔除，其它规则照常报；全部被剔除时按既有「规则为空」链路写失败报价记录 |
| 2 | 配置形式 | **结构化输入 + 表达式落库**：DB 一列 `noOfferTppRule`，与"灵活加价"同族的「一列 + 分号分隔多条件」形态；规则弹框用条件行（下拉 + 数字）编辑，也允许直接写表达式 |
| 3 | 已同步猎人平台的固定价规则 | **跳过过滤**（与 B钱包加价同口径）：这类规则由平台报价、本地不参与算价，本地过滤拦不住，跳过可避免"本地记录规则为空、平台照报"的错位与统计噪音 |
| 4 | 「是否由平台报价」判定 | 抽成公共纯函数 `isPlatQuotedRule`，报价守卫与本次过滤**共用一份判定**（防两处条件漂移） |
| 5 | 解析器 | **不复用 `calculateMarkup`**，新写纯函数（原因见 §2.4） |

### 2.4 为什么"和灵活加价保持一致"但不复用它的解析器

"灵活加价"= 报价类型 `offerType=2`（会员价加价）的加价金额表达式：`rule_record.addAmount`，形如 `30;>=+2;<+1`，由 `calculateMarkup(comparePrice, memberPrice, ruleList)`（`src/utils/utils.js:2286`）解析。

**该函数与"不报"语义不匹配，且区间操作符实现是坏的**（`src/utils/utils.js:2318-2337`）：

```js
case "<>":  if (memberPrice >= qujianPrice[0] || memberPrice <= qujianPrice[1]) // 对任意数恒真
case "!<>": if (memberPrice <  qujianPrice[0] || memberPrice >  qujianPrice[1]) // 实际等于"区间外"
```

即 `<>`（应当"区间内"）恒真、`!<>` 语义与命名相反。**本次不修复该函数**（它服务加价链路，改动面与风险都不属于本需求），改为新写独立解析器；代价是"不报"的表达式语法与加价表达式**同族但不完全相同**（见 §4）。

## 三、数据模型

### 3.1 DDL（需先于客户端发版执行）

```sql
ALTER TABLE rule_record
  ADD COLUMN noOfferTppRule VARCHAR(255) NULL DEFAULT NULL
  COMMENT '原价(tpp_price)不报条件：分号分隔多条，命中任一即不报。>50 超过50；>=50 不低于50；<30 低于30；<=30 不高于30；30-80 区间内(闭区间)；!30-80 区间外';
```

- 命名沿用表内驼峰风格（`bWalletMarkup`/`shadowLineName`/`offerType`）。

### 3.2 兼容性

- 后端 `ruleRecord.js` 为 `Object.keys(obj)` 动态拼 SQL，**无需改后端代码**。
- 客户端先发版、DDL 后执行的窗口期：保存链路有缺列兜底（§6.3），报价侧读不到该字段即等价于"未配置"（放行），不会造成停报。

## 四、表达式语法与解析器

### 4.1 语法（v1）

分号 `;` 分隔多条，**命中任一即不报**；条内允许空格；空串/`NULL` = 不启用。

| 写法 | 语义 |
| ---- | ---- |
| `>50` | 原价 > 50 → 不报（"超过xx"） |
| `>=50` | 原价 ≥ 50 → 不报 |
| `<30` | 原价 < 30 → 不报 |
| `<=30` | 原价 ≤ 30 → 不报 |
| `30-80` | 30 ≤ 原价 ≤ 80 → 不报（"区间内"，**闭区间**） |
| `!30-80` | 原价 < 30 或 > 80 → 不报（"区间外"） |

组合示例：`>50;30-40` = 原价超 50 或落在 30~40（含端点）都不报。

### 4.2 新模块 `src/utils/tppPriceRule.js`（纯函数、无 store 依赖）

| 导出 | 签名 | 说明 |
| ---- | ---- | ---- |
| `parseNoOfferTppRule` | `(ruleStr) => { conditions, invalid }` | `conditions` 形如 `[{op:'gt',value:50},{op:'between',min:30,max:80}]`；`invalid` 收集无法识别的原文片段 |
| `isTppPriceNoOffer` | `(tppPrice, ruleStr) => boolean` | 判定是否命中"不报"；`tppPrice` 缺失/非数值/≤0 → **false（放行）** |
| `formatNoOfferTppRule` | `(ruleStr) => string` | 人话回显，如 `原价>50；原价30~80`；空值返回 `""` |
| `validateNoOfferTppRule` | `(ruleStr) => { ok, msg }` | 保存前校验：`invalid` 非空 → `ok:false` 并给出片段与原因；区间 `min > max` 亦视为非法 |

解析规则：
1. `String(ruleStr).split(";")` → trim → 丢弃空片段；
2. `^(>=|<=|>|<)\s*(-?\d+(\.\d+)?)$` → 比较条件；
3. `^!?\s*(\d+(\.\d+)?)\s*-\s*(\d+(\.\d+)?)$` → 区间条件（`!` 前缀 = 区间外）；要求 `min ≤ max`；
4. 其余 → 进 `invalid`。

判定规则（按顺序命中即返回 `true`）：`gt: num > value`、`gte: num >= value`、`lt: num < value`、`lte: num <= value`、`between: num >= min && num <= max`、`notBetween: num < min || num > max`。

### 4.3 为什么不复用 `calculateMarkup`

除 §2.4 的缺陷外，另有两点：加价表达式以"首段比较价 + `条件+金额`"为单位（每段必须带金额），不报没有金额；且加价是**算价**语义、不报是**过滤**语义，混用会让后续维护者误改一处影响两条链路。**保持形态一致、实现独立**是本方案的取舍。

## 五、报价侧改造

### 5.1 新增过滤（`src/utils/utils.js` `offerRuleMatch` 末尾）

放在**会员日过滤之后、`return` 之前**。放末尾的理由：只影响"本来能匹配到规则"的订单，不改变现有「按城市/影院/影厅/座位数筛选为空」的统计口径。

```js
// 11、匹配原价（tpp_price）不报条件：命中的规则剔除（放最后，不影响既有失败原因口径）
// 时段布尔量与 BaseOfferPrice.js:66-75 保持同一写法（判定条件必须逐项一致）
const lierenFixedOfferToPlatTimeRange =
  dictStore.dictInfo.lierenFixedOfferToPlatTimeRange?.split(",");
const offerToPlatTimeOk =
  plat_name == "lieren"
    ? isCurrentTimeInRange(
        lierenFixedOfferToPlatTimeRange[0],
        lierenFixedOfferToPlatTimeRange[1]
      )
    : true;
const tppPriceRuleList = memberDayRuleList.filter(item => {
  if (!item.noOfferTppRule) return true; // 未配置：存量规则直接放行
  // 由平台报价的规则本地不参与算价，过滤无效：跳过（与 B钱包加价同口径）
  if (
    isPlatQuotedRule({
      plat_name,
      offerRule: item,
      dictInfo: dictStore.dictInfo,
      offerToPlatTimeOk
    })
  ) {
    return true;
  }
  const { invalid } = parseNoOfferTppRule(item.noOfferTppRule);
  if (invalid.length) {
    // 配置错误不应导致全量停报：记日志后，无法识别的片段忽略、其余条件照常判定
    logger.errorSave("原价不报条件无法识别，已忽略该片段", {
      noOfferTppRule: item.noOfferTppRule,
      invalid,
      ruleId: item.id
    });
  }
  const hit = isTppPriceNoOffer(order.tpp_price, item.noOfferTppRule);
  if (hit) {
    logger.infoSave("原价命中不报条件", {
      tpp_price: order.tpp_price,
      noOfferTppRule: item.noOfferTppRule,
      ruleId: item.id
    });
  }
  return !hit;
});
if (!tppPriceRuleList.length) {
  logger.errorSave("按原价筛选后，报价规则为空");
  return;
}
return {
  matchRuleList: tppPriceRuleList
};
```

要点：
- 未配置该字段的规则**第一个判断就放行**，存量行为零变化；
- 命中只写 `info` 级日志（日报价量级大，不进 `error`）；配置错误与"全空"才写 `error`；
- `return` 语句由 `memberDayRuleList` 换成 `tppPriceRuleList`（易漏，实施时以 diff 复核）。

### 5.2 抽取 `isPlatQuotedRule`（方案决策 4）

```js
export const isPlatQuotedRule = ({ plat_name, offerRule, dictInfo, offerToPlatTimeOk = true }) => {
```

- 保持与"灵活加价"一致的"一个输入框 + 分号多条件"手感，同时避免手写错误；
- **空表达式默认一行**（2026-10-11 追加）：打开弹框时若表达式为空（新增规则、复制/编辑未配置该条件的规则），自动呈现一行条件行，等价于已经点过一次「新增」——运营不必先找按钮。该行为在 `open()`（新增/编辑两个分支）与 `resetForm()` 三处通过 `ensureTppRuleRow()` 保证；新增场景同时把行状态清空，避免沿用上一次会话的残留行；
- **新增行默认「区间外」**（2026-10-11 追加）：点「新增」或自动补的那一行，下拉默认选中 `区间外`（`notBetween`），仍可切换为其它操作符。注意区间类条件需要上下限都填才会写入表达式（只填下限时表达式保持为空，属预期）。

## 七、边界与异常

| 场景 | 行为 | 理由 |
| ---- | ---- | ---- |
| `tpp_price` 为空 / `null` / 非数值 / ≤ 0 | **放行**（不拦）+ `info` 日志 | 平台字段缺失时宁可照报，避免全量不报价 |
| 表达式为空 / `NULL` | 不启用（放行） | 存量规则零影响 |
| 表达式有无法识别的片段 | 该片段忽略、其余条件照常判定；`errorSave` 提示；**保存时前端已阻断** | 不因配置错误停报 |
| 全条件都不命中 | 规则保留，正常报价 | — |
| 某规则命中但它是"平台报价规则" | 跳过过滤（规则保留，走平台报价既有分支） | 决策 3 |
| 平台报价时段外（如猎人 23:00-9:00） | 过滤**生效**（本地算价） | 决策 4 的核心：判定必须与守卫含同样的时段条件 |
| 测试单（`isTestOrder`） | 同样生效 | 口径一致，便于用测试单验证 |
| 出票链路 | **不改** | 出票按已选定的规则 id 取规则，不做二次过滤；规则变更不追溯已出票订单 |

## 十、已知限制与待确认

1. **平台报价的规则不受约束**（业务已知悉）：已同步猎人平台 + 固定价 + 字典开关 + 时段内的规则由平台报价，本地过滤跳过 → 该条件对这类规则**不生效**。若业务要求平台侧也生效，需平台侧支持（另行推进）。
2. **`tpp_price` 的平台口径差异**：各平台映射来源不同（守兔 `unitInitPrice`、商展 `price_ori`、芒果/麻花/哈哈/票生 `maoyan_price`…），配置阈值时需按平台分别评估；是否需要"按平台分别配置阈值"由业务确认（当前设计支持在规则里按平台规则分别配置，规则本身已按平台维度建）。
3. **不做"命中即整单不报"**：按决策 1，命中只剔除该条规则；如需"这类场次一律不碰"，应通过规则覆盖范围（影院/影片白名单）实现。
4. **表达式 v1 不支持枚举值**（如"原价等于 30/40/50 不报"）与"百分比条件"；如后续需要，在 `tppPriceRule.js` 扩展操作符并补测即可，不影响落库结构。
