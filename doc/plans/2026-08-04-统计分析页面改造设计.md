## 1. 背景与目标

### 1.1 现状问题

当前统计分析页(`今日统计`)是一个**扁平明细表**,按影线汇总今日的利润/流水/报价数/中标数等。用户看完只能得到"今天多少",无法回答"今天怎样、为什么、怎么办"。此前已完成后端"聚合下推"优化(查询不再拖垮服务),但**页面展示形式未变,信息价值仍偏低**。

### 1.2 改造目标

在保留原数据能力的前提下,把页面向"**运营决策辅助**"升级,让用户能够:

1. **一眼判断**今天赚没赚、趋势好不好(概览 + 环比 + 趋势图)
2. **定位好坏**哪个影线/平台贡献利润或拖后腿(平台拆解)
3. **理解原因**失败原因构成(堆叠柱·按日)
4. **获取行动**异常预警(待处理),把"用户找问题"变成"问题找用户"

### 1.3 设计要点(已与用户确认)

| 决策点 | 结论 |
|--------|------|
| 整体布局 | 上下分块,各模块**独占一排** |
| 诊断摘要条 | ② 与 ③ 之间加一条"一句话结论 + 建议动作"(v3 新增,见 §3.3) |
| 趋势图 | **五线双轴**,口径见 §3.4(v8 调整:在报价量/报价成功率/利润基础上增加中标率、出票成功率;中标率为按日出票口径,跨日错位仅供参考) |
| 失败原因构成 | **堆叠柱·按日**(规则为空/超成本/超限价/其他),数据并入 trend 接口(v3 合并) |
| 平台拆解 | 独占一排,各订单来源的利润/中标率/成功率 |
| 待处理 | 独占一排,异常预警卡片(v2 修正:真"激增"规则,见 §3.7) |
| 原影线明细表 | 保留,通过**独立路由**打开(原表并入新页面,以独立详情页呈现) |
| 时间概念 | **单一数据源**,查询区为唯一范围,趋势图跟随(v2 修正,见 §3.1/§3.4) |
| 独立容错 | trend/plat 任一失败不阻塞 KPI 与明细,图表空态显示"--"(v3 新增,见 §6) |
| 环比数据源 | 从 trend 取昨日值,与趋势图同源(M2 过渡期才用昨日 queryAnalysis 兜底) |

## 2. 页面结构总览

```
统计分析页(重写 /set/todayStatistics)
├── ① 查询区            (沿用现有 + 快捷:当天/近7天/近30天,唯一时间源)
├── ② KPI 概览          (5 张卡片:利润/流水/转单手续费/中标率/成功率,各带环比 vs 昨日 / 7日均)
├── ③ 诊断摘要条        (一句话结论 + 建议动作,v3 新增)
├── ④ 趋势曲线          (五线双轴:报价量(柱)/利润/报价成功率/中标率/出票成功率,跟随查询区时间)
├── ⑤ 失败原因构成      (堆叠柱·按日,数据并入 trend 接口)

```

每个模块独占一整行(横向铺满),自上而下从"看结果"到"看原因"再到"看行动"。

## 3. 模块详细设计

### 3.1 查询区(①)

沿用现有表单:订单来源、用户、影线级联、开始/结束时间、搜索按钮。

**新增**:时间范围快捷切换(**当天 / 近7天 / 近30天**,v8 增加"当天"tab 与选中态高亮),点击后自动回填 `start_time`/`end_time` 并触发查询;点"搜索"或手动改条件后清除选中态(视为自定义条件)。与后端 30 天硬限制对应。

> **查询上限 = 30 天(v6 实测依据)**:报价记录有定时清理任务([cron/index.js](file:///d:/Electron/electron-pure-admin-fix/auto-ticket-service/cron/index.js))——`offer_record` 保留 30 天 / `offer_record_fail` 保留 3 天 / `ticket_record` 永久。查超过 30 天的报价/失败数据已被清理,无统计意义。后端上限 90 天 → **30 天**,前端超过 30 天直接提示拦截(原 90 天快捷按钮移除,原 31 天确认改为 30 天直接拦截)。

> **时间单一数据源(v2 修正,解决 P2-4)**:查询区是**唯一**时间范围入口。趋势图(④)不再有独立的时间轴切换,其粒度与范围完全跟随查询区:
> - ≤7 天:按日
> - 8~30 天:按日
> (查询上限 30 天,无 31~90 天场景)
> 避免"查询区/趋势图两处时间"打架,用户只需理解一个时间范围。

### 3.2 KPI 概览(②)

5 张 KPI 卡片,数据来自 `queryAnalysis` 返回的 `list` 全量聚合(**对全部影线求和**):

| 卡片 | 计算口径 | 环比参照 |
|------|----------|----------|
| 利润总和 | `Σ profitTotal` | vs 昨日 / 7日均 |
| 流水 | `Σ supplier_end_price_total` | vs 昨日 / 7日均 |
| 转单手续费(v9 新增) | `Σ transferTotal`(转单记录手续费累加,全部订单状态) | vs 昨日 / 7日均 |
| 中标率 | `Σ ticketTotalNum / Σ offerSuccessNum` | vs 昨日 / 7日均 |
| 成功率 | `Σ ticketSuccessNum / Σ ticketTotalNum` | vs 昨日 / 7日均 |

**环比数据源(v2 修正,解决 P2-3;v4 补全实现)**:每张卡显示 `↑12% / ↓5%`。**最终口径** = 从 `trend` 接口返回的按日序列中取**昨日**与 **7 日均值**作为参照,与趋势图**同源、口径一致**,**不再额外发起第二次 `queryAnalysis`**。仅 M2 过渡期(trend 未实现)才退化为"昨日同条件 `queryAnalysis`"兜底。

> **v4 补全**:trend 接口除展示字段外,**同时返回按日 raw 计数**(`offer_success_num` / `offer_fail_num` / `ticket_success_num` / `ticket_total_num`,见 §3.4)。中标率/成功率环比 = 昨日 raw 之比(`昨日Σticket_total_num / 昨日Σoffer_success_num`、`昨日Σticket_success_num / 昨日Σticket_total_num`),**不需要 trend 返回跨表比率序列**——既满足"跨表比率不进趋势图",又让 KPI 环比有同源数据。

> 环比的意义:让"利润 1.2 万"从孤立数字变成"有参照系"的判断;"vs 昨日 / 7日均"双参照(v3 增量建议 2)让短期波动与长期趋势并置,孤立数字更可读。

### 3.3 诊断摘要条(③,v3 新增)

在 KPI 之后、趋势图之前,加一条**自动生成的一句话结论 + 建议动作**。这是"怎么办"最直接的载体,成本极低(前端基于 `list` + `trend` 规则拼接)。

**生成逻辑**(前端本地,规则可配置):
- 优先取待处理预警(§3.7)中最高级别的一条,转为结论:如 *"今日失败 152 次全部为规则为空,估算影响 -¥900,建议检查规则配置"* + 按钮"去检查规则"。
- 无预警时给出正向结论:如 *"今日利润 ¥1.2 万,环比 +12%,表现良好"*。
- 摘要条含一个"查看影线明细"兜底按钮(下钻到⑧)。

> **影响金额估算公式(v4 补充)**:影响金额 = 规则为空次数 × **近 7 日平均单笔利润**(= Σ前7日 `profit_total` / Σ前7日 `ticket_success_num`,trend 按日数据可得,见 §3.4)。先给默认口径,后续可按影线级细化。

### 3.4 趋势曲线(④,五线双轴)

**数据**:按日聚合的趋势数据。需要时间序列数据,当前 `queryAnalysis` 只返回按 `app_name` 聚合的汇总,**不返回按日维度**。因此**新增后端接口**支持按 `DATE(processing_time)` 分组返回趋势数据。

> **口径修正(v2/v8)**:跨表比率指标(中标率 = 出票量/报价成功数)分子来自 `ticket_record`(出票时间)、分母来自 `offer_record`(报价时间),**按日拆开后分子分母不在同一天**(8/1 报价 8/2 出票),趋势线会抖动失真。v2 曾将中标率排除出趋势图;v8 按产品要求加入,采用**按日出票口径**(当日 `ticket_total_num / offer_success_num`),并保留口径警示——该线为当日快照,跨日错位仅供参考;**出票成功率**(`ticket_success_num / ticket_total_num`)同表同日,口径可靠。
>
> 趋势五线:报价量(柱,左轴)、利润(虚线,左轴)、报价成功率(点线,右轴%)、中标率(实线,右轴%)、出票成功率(虚线,右轴%)。分母为 0 的日期显示断点(null)。

**推荐方式**:新增后端接口 `GET /svpi/statisticalAnalysis/trend`,参数 `{ start_time, end_time, user_id, plat_name, app_name, rule }`(**v4 补 rule**,与 query 口径一致,漏掉会混入其他 rule 数据),返回:

```json
[
  {
    "date": "2026-08-01",
    "offer_success_num": 120, "offer_fail_num": 30,
    "offer_total_num": 150, "offer_success_rate": 0.8,
    "profit_total": 1234.5, "supplier_end_price_total": 8800, "transfer_total": 12.5,
    "ticket_success_num": 25, "ticket_total_num": 28,
    "fail": { "规则为空": 50, "超成本": 20, "超限价": 10, "其他": 5 }
  },
  ...
]
```

> 字段说明(v3/v4):
> - `offer_success_num` / `offer_fail_num` / `ticket_success_num` / `ticket_total_num` 为**按日 raw 计数**(v4 新增),供 KPI 环比(②)与待处理激增(⑦)计算,**不画进趋势图**;
> - `offer_success_rate = offer_success_num / (offer_success_num + offer_fail_num)`(v4 写明公式),同日可比;
> - 原 `ticket_success_rate` 易被误读为"出票成功率",且本次趋势图已不含跨表中标率,故用 `offer_success_rate`(报价成功率)明确口径;
> - `fail` 子对象同时承载失败原因构成(⑤)数据,避免第二个接口。

> **按日口径与数据范围(v4 补充,实现要点)**:
> - 报价侧指标(`offer_success_num` / `offer_fail_num` / `fail`)取 `offer_record` + `offer_record_fail`(两表 `processing_time` 同义,同日可比);出票侧指标(`profit_total` / `supplier_end_price_total` / `ticket_*`)取 `ticket_record`(按出票日),与报价侧**口径不同日**,图例标注"按出票日"即可,这是业务真实(报价到出票有延迟);
> - **向前多取 8 天**:查询范围自动前移 8 天(供 KPI 环比"昨日/7日均"与待处理"激增"对比计算,范围不足 8 天时也有参照);前端图表展示时按查询范围截取(`date >= start_time` 日期),不展示扩展段;
> - `end_time` 为 `00:00:00` 时按**开区间**处理,序列不含 end 日(避免趋势图末端多一根 0 数据柱子)。

**图表**:ECharts 折线图
- 左 Y 轴:利润(元),报价量(次)用**柱状背景**(v4 量纲处理:报价量与利润共用左轴,量级悬殊时柱状在背景不影响折线可读性,单位按需换算 k 次 / k 元)
- 右 Y 轴:报价成功率 / 中标率 / 出票成功率(%)
- X 轴:日期
- 粒度跟随查询区(见 §3.1)

**五线**:报价量(柱,左轴)、利润(虚线,左轴)、报价成功率(点线,右轴%)、中标率(实线,右轴%)、出票成功率(虚线,右轴%)。双轴,量纲不同必须分开。分母为 0 的日期显示断点(null)。

### 3.5 失败原因构成(⑤,堆叠柱·按日)

**数据**:按日 + 失败原因分类的堆叠统计。**数据并入 trend 接口的 `fail` 子对象**(v3 增量建议 4,合并 trend 与 failTrend 为同一按日接口,同范围同分组,减少一次并发查询):

```json
"fail": { "规则为空": 50, "超成本": 20, "超限价": 10, "其他": 5 }
```

**err_msg 分类口径**(与后端聚合一致):
- `规则为空`:`err_msg LIKE '%规则为空%'`
- `超成本`:`err_msg LIKE '%低于真实成本%'`
- `超限价`:`err_msg LIKE '%超过平台限价%'`
- `其他`:`COUNT(*) - 上面三类之和`

**图表**:ECharts 堆叠柱状图,按日每根柱子,堆叠 4 个原因,既看每天失败总数趋势,也看各原因占比变化。

### 3.6 平台拆解(⑥)

**数据**:按 `plat_name`(订单来源)分组的利润/中标率/成功率。当前 `offer_record`、`ticket_record` 有 `plat_name` 字段,但 `queryAnalysis` 聚合按 `app_name` 分组,**不提供 plat_name 维度**。需新增后端能力。

**推荐方式**:新增后端接口 `GET /svpi/statisticalAnalysis/plat`,参数 `{ start_time, end_time, user_id, plat_name, app_name, rule }`(**v4 补 rule**),按 `plat_name` 分组返回:

```json
[
  { "plat_name": "某平台", "profit_total": 1234, "supplier_end_price_total": 8800, "offer_success_num": 100, "offer_fail_num": 20, "ticket_total_num": 30, "ticket_success_num": 28 },
  ...
]
```

> 字段命名(v3 增量建议 6):中标率/成功率等**比率由前端计算**(分母为 0 显示 `--`),后端只返回 raw 计数与金额;平台拆解的中标率口径用"成交率/中标率"(`ticket_total_num / offer_success_num`),避免与"出票成功率"混淆。plat 维度**不按日拆分**,跨表比率无错位问题。

**展示**:表格 + 条形图(可选)。重点:各平台利润对比 Top/Bottom,一眼定位"哪个平台赚钱/拖后腿"。

### 3.7 待处理(⑦,异常预警)

**数据**:基于聚合结果 + 简单规则计算预警。**前端本地计算**(不新增后端接口),规则可配置:

| 预警类型 | 规则(示例) | 级别 | 数据源 |
|----------|-----------|------|--------|
| 规则异常激增 | 今日总 `规则为空` 数 > 前 7 日均值 × 2 **且** 占当日 `offer_fail_num` 超 50% | 红 | trend 按日序列 |
| 中标率过低 | 某影线 `ticketTotalNum/offerSuccessNum` 低于 5%(且 **`offerSuccessNum > 100`**,v8 调整:分母样本需 >100 才可靠) | 黄 | query list |
| 成功率异常 | 某影线 `ticketSuccessNum/ticketTotalNum` 低于 20%(且 `ticketTotalNum > 0`) | 黄 | query list |
| 无数据 | 所有 KPI 为 0 | 提示 | query list |

> **规则语义修正(v2/v4)**:原"某影线 `offerRuleMatchEmptyNum` 占其 `offerFailNum` 超 50%"是**构成比**,不是"激增"。改为**真激增**:今日值 vs 前 7 日均值(`今日 > 7日均 × 2 且占比 > 50%` 才告警)。**数据源**用 `trend` 接口的按日序列(前 7 日取 `fail.规则为空`,今日取序列最后一天的 `fail.规则为空`)。"中标率过低/成功率异常"为**影线级阈值判断**(v4 改名,原"骤降"名实不符——影线级无按日数据,无法做对比,阈值即"过低"),基于 `query` 的 `list` 计算。预警卡上标注"异常"而非"激增"作为触发条件说明。

**展示**:预警卡片列表,红/黄/提示三色,每条含"影线名 + 指标 + 建议动作"。点击可跳转到对应影线明细(下钻到⑧)。最高级别预警同时用于 §3.3 诊断摘要条。

### 3.8 影线明细(⑧,独立路由)

**原明细表**完整保留,从主页面拆出,作为**独立路由**:

```
/set/todayStatistics/detail
```

**入口**:主页面顶部"查看影线明细"按钮 + ⑤⑥ 模块中点击下钻跳转。

**内容**:原 `todayStatistics/index.vue` 的表格(利润/流水/报价数/成功数/失败数/规则为空/超成本/超限价/中标数/中标率/出票数/成功率/失败数/转单数),保留排序、合计、成功专率计算等既有逻辑。

**复用**:原页面逻辑抽为 `src/views/todayStatistics/detail.vue`,`index.vue` 重写为可视化主页面。

> **必须原样保留的三项逻辑(v3 增量建议 5,避免抽离时丢失)**:抽离 detail.vue 时,原样保留已实施的——
> 1. **去 appList 传参**:后端不再传 `appList`,避免超长参数;
> 2. **本地补 0**:后端只返回有数据的影线,前端按全量 `APP_LIST` 补 0 行(保持"全量展示"行为);
> 3. **30 天校验**:查询时间范围超过 30 天时直接拦截提示(与后端 `MAX_RANGE_DAYS = 30` 一致,报价记录仅保留 30 天)。

## 4. 数据来源与接口方案

### 4.1 现有接口(复用)

`GET /svpi/statisticalAnalysis/query`(已聚合下推):
- 参数:`{ start_time, end_time, user_id, plat_name, app_name, rule }`
- 返回:`{ list: [{ app_name, profitTotal, supplier_end_price_total, transferTotal, offerTotalNum, offerSuccessNum, offerFailNum, offerRuleMatchEmptyNum, offerExceedLimitedPriceNum, offerExceedLimitedMaxPriceNum, ticketTotalNum, ticketSuccessNum, ticketNum, ticketFailNum, ticketTransferNum }] }`
- 用途:KPI 概览(②)、影线明细(⑧)、平台拆解(若前端按 plat 重新聚合则不需要新接口)

### 4.2 新增后端接口(2 个)

| 接口 | 用途 | 分组 |
|------|------|------|
| `GET /svpi/statisticalAnalysis/trend` | 趋势曲线(④)+ 失败原因构成(⑤)+ 环比参照(②) | `DATE(processing_time)` + `fail` 子对象分类 |
| `GET /svpi/statisticalAnalysis/plat` | 平台拆解(⑥) | `plat_name` |

> **重要决策点**:这 2 个接口的后端聚合是实现的关键。当前后端 `api/statisticalAnalysis.js` 已有 `aggregateOfferSuccess/aggregateOfferFail/aggregateTicket` 三个聚合方法,可在此基础**扩展**或**新增**按日期/按平台分组的聚合方法。
>
> **统一约定(v4 补充,v6 修正)**:新接口沿用 `/query` 的**时间必填 + 30 天硬限制**校验与**等值过滤约定**(含 `rule`),参数构建复用 `buildWhere`,确保口径一致。
>
> **接口合并说明(v3 增量建议 4)**:原计划 `trend` 与 `failTrend` 两个按日接口合并为同一 `trend` 接口(返回 `fail` 子对象),同范围、同分组、同一批查询,前端并发从 4 次降到 3 次(query + trend + plat)。

### 4.3 前端 sv-api 扩展

`src/api/sv-api.js` 新增:
- `queryAnalysisTrend(params)` → `/svpi/statisticalAnalysis/trend`
- `queryAnalysisPlat(params)` → `/svpi/statisticalAnalysis/plat`

### 4.4 预聚合表与缓存(v7 实施)

**预聚合表 `stat_daily_record`**:每日 00:05 由 cron 聚合昨日数据(`aggregateDaily`),按 `(stat_date, app_name, plat_name, rule)` 汇总 offer/ticket 各指标。query/trend/plat 三接口查询拆"历史读预聚合表 + 今天实时聚合"合并返回;预聚合表为空(任务未跑)时回退全实时,保证功能正确。首次上线用 `days=30` 回填历史。

**内存结果缓存**:query/trend/plat 三接口均有 5 分钟 TTL 的内存缓存(`resultCache`),同一查询条件 5 分钟内直接复用聚合结果,防并发重复查询;超 500 条自动清理过期项。

## 6. 交互与状态

- **查询联动**:更换查询区条件 → 重新 `loadData`,同时刷新 KPI(含环比)、诊断摘要、趋势、失败原因、平台拆解、待处理。
- **请求竞态**:引入 `AbortController`,切换条件时取消上一次未完成请求(参考 `doc/综合优化改造设计方案.md` §4.4)。
- **独立容错(v3 增量建议 3)**:`trend` / `plat` 任一失败**不阻塞** KPI 与明细(这两者只依赖 `query`)。各模块独立 loading 与错误态:
  - 图表请求失败 → 该模块显示空态占位,数值显示 `--`;
  - 比率分母为 0(如 `offerSuccessNum=0`、`ticketTotalNum=0`)→ 显示 `--` 而非 `0%` 或报错;
  - 避免"4 个请求并发,一个挂全页空白"。
- **下钻**:⑤平台拆解点击某平台 → 跳转⑧;⑦待处理点击某影线 → 跳转⑧(带 app_name 参数);③诊断摘要动作按钮 → 按需跳转⑧或规则配置。
- **loading**:主页面统一 `ElLoading`,各图表独立加载态。

## 8. 风险与注意事项

| # | 风险 | 缓解 |
|---|------|------|
| 1 | 环比需昨日数据,可能增加接口调用 | 环比从 trend 序列取昨日值,与主查询共用一次 trend,不额外查昨日 queryAnalysis(M2 过渡期才兜底);不阻塞主渲染 |

| 6 | 原明细表复用 | 直接抽离为 detail.vue,不重写逻辑;明确保留"去 appList + 本地补 0 + 30 天校验"三项,降低回归风险 |
