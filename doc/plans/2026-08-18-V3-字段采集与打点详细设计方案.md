# V3 报价出票日志整改：字段采集与打点详细设计方案

> 日期：2026-08-18
> ⚠️ 2026-08-18 更新：**数据脱敏要求已作废**（日志按原始值记录与存储，不再打码），本文涉及脱敏的内容不再执行，以《2026-08-18-报价出票日志整改-最终详细设计文档.md》V4.1 为准。
> 关联：V3 分层定稿（四层架构：L0 业务层 / L1 索引层 / L2 明细层 / L3 兜底层）。本文是 V3 的**字段级详细设计**：调研各系列报价/出票流程（重点：用券、用卡场景）的现状日志打点与记录表字段，给出 L0 加列的**最小集**、字段采集点、calc_path/use_path 拼装设计、以及各系列打点改造清单。
>
> **核心调研结论先行**：现有 `offer_record`/`ticket_record` 已覆盖用户关心的 90% 字段（会员价三层、最终报价、券码、卡号、手机号、利润、取票码均已入库），**真正缺口仅 6 个字段**（报价侧 1~2 个、出票侧 4~5 个）+ 两个"一句话路径"字段。改造量远小于预期。

## 一、现有字段盘点（已核实，代码级）

### 1.1 offer_record 现有字段（BaseOfferQueue.js:1184-1247 serOrderInfo）

| 类别 | 字段 | 来源 |
|------|------|------|
| 订单信息 | plat_name / app_name / order_id / order_number / tpp_price / supplier_max_price / city_name / cinema_addr / ticket_num / cinema_name / hall_name / film_name / show_time / cinema_code / cinema_group | order |
| **报价结果** | **offer_type**（规则类型 1固定/2加价/3会员日）、rule_status、**offer_end_amount（最终报价）**、**member_price（会员成本价）**、**real_member_price（真实会员价）**、**member_discount（折扣）**、quan_value、offer_rule_id、adjust_price（限价调整）、price_spread | offerRule |
| 结果判定 | order_status（1成功/2失败）、err_msg、err_info、err_type、rewards、fee_rate、rule、offer_from、offer_duration、queue_wait_ms、third_party_ids、cache_hit、plat_rule_id、app_type | 组装 |
| 规则名 | **无独立字段**，查询时 LEFT JOIN rule_record（offerRecord.js:139 `rule_record.ruleName AS rule_name`） | JOIN |

> **结论**：报价侧"会员价三层（真实价/折扣/成本价）+ 最终报价 + 策略类型 + 限价调整"**全部已入库**。唯一语义缺口：**calc_path（一句话匹配/计算路径）**——目前靠过程日志还原，无结构字段。规则名可 JOIN 得到，但规则删除后 JOIN 为 NULL，独立冗余存一份更稳（可选）。

### 1.2 ticket_record 现有字段（BaseTicketQueue.js:716-754 serOrderInfo）

| 类别 | 字段 | 来源 |
|------|------|------|
| 订单信息 | plat_name / app_name / order_id / plat_order_sn / order_number / tpp_price / supplier_end_price / supplier_max_price / city_name / cinema_addr / ticket_num / cinema_name / hall_name / film_name / lockseat / show_time / cinema_group / cinema_code | order |
| **用券用卡结果** | **quan_code（用券码）**、**card_id、card_num（支付卡）**、**mobile（出票手机号）**、quan_value、offer_type | ticketRes |
| 结果判定 | order_status（1成功/2失败/4规则禁用/9换座中）、**profit、qrcode**、err_msg、err_info、transfer_fee、rewards、rule、offer_from、rule_id、app_type、耗时字段 | ticketRes/logger |

> **结论**：出票侧"用券（quan_code）、用卡（card_id/card_num）、手机号、利润、取票码"**已入库**。缺口：**payment_amount（实付金额）、card_balance（支付前卡余额）、coupons 明细（券类型/面额/张数）、use_path（一句话用券用卡路径）**——这些数据在流程中均已计算（见 §2.2），只是没有传入 ticketRes 入库。

### 1.3 缺口汇总（L0 加列最小集）

| 表 | 新增列 | 类型 | 语义 | 优先级 |
|----|--------|------|------|--------|
| offer_record | `calc_path` | VARCHAR(500) | 一句话报价计算路径（规则过滤/会员价/策略/限价过程） | 必加 |
| offer_record | `hit_rule_name` | VARCHAR(100) | 命中规则名（冗余存，防规则删除后 JOIN 丢失） | 建议加 |
| ticket_record | `payment_amount` | DECIMAL(10,2) | 用户实付金额（卡支付额/券手续费合计） | 必加 |
| ticket_record | `card_balance` | DECIMAL(10,2) | 支付前卡余额（排查余额不足） | 必加 |
| ticket_record | `coupons` | TEXT(JSON) | 用券明细 `[{couponType,couponCode,couponName,quanValue}]`（≤10 条） | 必加 |
| ticket_record | `use_path` | VARCHAR(500) | 一句话用券用卡路径（换卡/灵活用券/券+卡组合过程） | 必加 |

> **不加的字段**：member_price/real_member_price/member_discount/offer_end_amount/offer_type/adjust_price/quan_value/quan_code/card_id/card_num/mobile/profit/qrcode（已有）；strategy、limit_adjusted（可由 offer_type/adjust_price 推导，YAGNI）。

## 二、字段采集设计（数据从哪来、怎么传）

### 2.1 报价侧：calc_path 采集链路（公共收口）

**关键设计：字段挂在 offerRule 上传递，基类统一入库——一次改基类，全系列受益。**

```
各系列 offerManage 匹配终点（getEndMatchOfferRule 返回前 / comparePricingStrategies 处）
  └─ offerRule.calc_path = "会员日未命中→券库存过滤剩3条→会员价95折最优(42.75+3=45.75)"
  └─ offerRule.hit_rule_name = rule.ruleName
        ↓（offerResult.offerRule 传回队列）
BaseOfferQueue.addOrderHandleRecord（公共，一次改造）
  └─ serOrderInfo.calc_path = offerResult?.offerRule?.calc_path ?? ""
  └─ serOrderInfo.hit_rule_name = offerResult?.offerRule?.ruleName ?? ""
        ↓
svApi.addOfferRecord → offer_record 新列
```

**calc_path 拼装点（按系列，chenxing 已确认）**：

| 环节 | chenxing 位置 | 拼装素材 |
|------|--------------|---------|
| 规则过滤过程 | offerManage.js:86-130（初始匹配/电影格式/券库存/日出票券数） | 各过滤步骤剩余条数（当前是分散 infoSave，改为在终点汇总） |
| 会员价 | offerManage.js:594-611 calculateBestDiscount 返回 | real_member_price/discount/member_price |
| 加价/策略 | offerManage.js:849-871 comparePricingStrategies | memberOfferAmount vs fixedOfferAmount、选择结果 |
| 限价调整 | offerManage.js:415-427 adjustToMaxPrice | 是否触发限价、调整后价格 |
| 最终报价 | BaseOfferQueue.js:962-967（offer_end_amount） | dynamicPrice 后最终价 |

拼装示例：`券库存过滤剩2条→固定价规则45.5最优（会员价路径42.75+3=45.75被固定价击败）` 或 `限价调整：最终报价48.5>平台限价45，下调至45`。

### 2.2 出票侧：实付/余额/券明细采集链路（公共收口）

**关键设计：各系列 buyTicket 把缺的字段挂到 ticketRes 返回对象，BaseTicketQueue.saveTicketRecord 统一入库。**

```
各系列 buyTicket 用券用卡决策处（chenxing:361-433 useQuanOrCard + priceCalculation 后）
  └─ ticketRes.paymentAmount = calcRes.priceDetail.totalRealPayAmount（实付）
  └─ ticketRes.cardBalance = useCardList.find(cardNo==cardNum)?.cardAmount（支付前余额）
  └─ ticketRes.coupons = useQuan.slice(0,10).map({couponType,couponCode,couponName,quanValue})
  └─ ticketRes.use_path = "灵活用券→券2张抵扣19.8→券手续费卡尾号1234支付3.96"（或"换卡1次→卡尾号5678支付36.6"）
        ↓（return 时带上）
BaseTicketQueue.saveTicketRecord（公共，一次改造，ticketRes 解构处）
  └─ serOrderInfo.payment_amount / card_balance / coupons / use_path
        ↓
svApi.addTicketRecord → ticket_record 新列
```

**用券 vs 用卡场景的数据点（chenxing 已确认，各系列差异待调研补全）**：

| 场景 | 判定 | 关键变量（chenxing） | 入库字段 |
|------|------|---------------------|---------|
| 用券（offer_type=1 或灵活用券） | cardQuanManage.js:149 | useQuan[{couponType,couponCode,couponName}]、quanStock、quan_fee、paymentAmount=券手续费合计 | coupons / payment_amount / quan_code |
| 券+卡（券手续费>0 需卡支付） | cardQuanManage.js:277-301 | useCardList（cardAmount 排序取最大余额）、quan_fee | payment_amount / card_balance |
| 用卡（offer_type=2/3） | useCardHandle | card_id/cardNum、cardBalance、paymentAmount | payment_amount / card_balance / card_id |
| 灵活用券转用卡 | cardQuanManage.js:229/267/291 | is_auto_use_quan 分支 | use_path 记录"灵活用券失败转用卡" |
