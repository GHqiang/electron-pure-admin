# 非猎人平台拉单证据（C1/C2）与猎人口径对齐设计

> 日期：2026-10-21
> 状态：设计待确认
> 关联排查：`reports/analyze-issue/2026-10-20-14点后用户9-10记录不对称.md`（本地，不入库）

## 一、背景与目标

14:00 后的排查确认：lieren 的 C1「拉单返回」、C2「拉单摘要」已经能解释“同角色同订单，一个有记录、一个没有”的大部分情况；其它平台目前没有 C1/C2，排查时只能看到 A/成功记录，无法判断另一侧是否拉单、为什么没记录。

目标：

1. 其它平台与 lieren **同口径**：C1 只记“可报价订单”（含同角色有登录、当前客户端无登录的 `not_login`），并写 A17/B；C2 的 returned/filtered/enqueued 与 lieren 一致。
2. 平台列表可配置：sys_dict `pullEvidencePlatList`，首期默认 Top5。
3. 订单排查页支持按订单平台查看 C1/C2，不在白名单时明确提示“未开启拉单证据”，不误判为丢单。

## 二、范围

### 支持平台

全部 10 个平台都已接入同一套 C1/A17/C2 两遍处理：

`lieren,haha,mahua,yinghuasuan,mayi,sheng,mangguo,shoutu,yangcong,piaosheng`

默认白名单（按 2026-10-20 报价量）：

`lieren,haha,mahua,yinghuasuan,mayi`

- 白名单可开启/关闭任意已接入平台；未写进白名单的平台只是不产生 C1/C2，报价和 A16/A17/B 不受影响。
- lieren 现有 C1/C2 逻辑保持不变，只接入统一 helper。
- 其余 9 个平台均复用同一套两遍处理；后续新增平台只需让该队列走同一 helper。

### 不做

- 不记录未映射影院、系列禁用、同角色全无登录的 C1（与 lieren 一致）。
- 不补历史数据。
- 不改变 A16（入队前截止时间丢弃）、A17/B 的现有语义。
- 不改变报价成功/失败判定。

## 三、配置

- sys_dict 新增 `pullEvidencePlatList`，逗号分隔；缺省或为空时用默认 Top5。
- 客户端用统一 helper 读取 `dictTable().dictInfo.pullEvidencePlatList`；C1/C2 在每次拉单/写摘要时判断，动态生效，无需重启。
- 支持列表：`lieren,haha,mahua,yinghuasuan,mayi,sheng,mangguo,shoutu,yangcong,piaosheng`；白名单可开启/关闭其中任意平台。
- **白名单只控制 C1/C2 拉单证据、登录列表刷新和排查页提示；不控制平台启停、报价、成功记录、A16、A17/B。** A17/B 属于业务记录，已接入队列按同角色逻辑照写。
- **有效白名单 = `pullEvidencePlatList` ∩ 已接入队列**；未知平台即使写进 sys_dict，也不写 C1/C2，页面提示“未接入”。
- 后端只加字典数据，不改表结构、不改接口。

## 四、C1 与 A17/B：与 lieren 同口径

### 4.1 两遍处理

每个白名单队列的 fetchOrders 按 lieren 的方式改成两遍：

1. **第一遍：筛可报价**
   - 把平台原始订单转换成统一订单对象（平台原有转换逻辑不变）。
   - 调 `getCinemaFlagDetail(order, { requireSession: true })`。
   - 跳过 `unknown_cinema`、`disabled_series`。
   - `not_login` 时，用 `hasAnyRoleLogin(app_name)` 判断：同角色全无登录 → 跳过；同角色有人有登录 → 进入 quoteable。
   - `quoteable.push({ order, detail })`。
2. **第二遍：写证据 + 入队**
   - 对每个 quoteable 调统一 `_recordPullEvidence(order, detail, returnedCount)`，写 C1。
   - `detail.reason` 非空（只剩 `not_login`）：`filtered++`，`_recordDiscard` 写 A17 + B，不进入报价。
   - 否则转换 app_name 等入队字段，交给 `handleNewOrder`。

### 4.2 C1 字段

与 lieren 完全一致：

`order_number / plat_name / app_name / cinema_code / cinema_name / offer_end_time / round_ts / fetch_timestamp / returned_count / filter_reason / reason_detail`

- `filter_reason`：`""` 可报价；`not_login` 同角色有登录但当前客户端无登录。
- `fetch_timestamp`：lieren 保持；其它平台无统一时间戳时写 null。
- 同一订单首次返回才写，去重 key `${platName}_${orderNumber}`。
- 测试单不写。

### 4.3 A17/B

- 复用 `BaseOfferQueue._recordDiscard`，errType=17，message 用与 lieren 相同的 `_buildDiscardMessage`。
- A17 受现有每日上限/队列/去重保护；C2 discard_record_fail/dropped 计数沿用。
- A16 仍由 base 的 `handleNewOrder` 截止时间检查覆盖所有平台。

## 五、C2 拉单摘要

- `BaseOfferQueue._pullSummaryEnabled` 从“仅 lieren”改为白名单判断。
- 白名单队列的 stats 与 lieren 一致：
  - `returned` = quoteable.length（含 not_login）
  - `filtered` = A17 数量
  - `enqueued` = 排除已处理后实际入队数
  - `failed` = 本轮处理异常
- 5 分钟窗口写 L1 `opera_record`：`报价队列-拉单摘要`；字段保持现有 `rounds/ok_rounds/fail_rounds/returned/filtered/enqueued/last_fetch_timestamp/max_round_gap_ms/trace_fail/evidence_dropped/discard_record_fail/discard_record_dropped`。
- 白名单之外的平台不写 C2。

## 六、代码结构

### BaseOfferQueue 新增/抽取

- `_collectQuoteableOrders(orders, { normalize })`：统一第一遍；返回 `{quoteable, rawCount}`。
- `_recordQuoteableEvidence(quoteable, returnedCount)`：统一写 C1 + A17/B；返回可入队列表与 filtered 数。
- `_buildDiscardMessage(detail, order)`：从 LierenOfferQueue 抽到 base，供所有白名单队列复用。
- `_refreshLoginInfoList()`：从 LierenOfferQueue 抽到 base；白名单队列在 `start()` 和每 5 分钟拉单时刷新 `loginInfoList`，保证 `hasAnyRoleLogin(app_name)` 与 lieren 同源。否则其它平台可能因为本地登录列表为空/过期，把本应记 `not_login` 的订单直接跳过。
- `_pullEvidenceEnabled` / `isPullEvidenceEnabled(platName)`：读 sys_dict 白名单，并与 `SUPPORTED_PULL_EVIDENCE_PLATS` 取交集。
- C2 `_pullSummaryEnabled` 改为有效白名单判断。

### 队列

- `LierenOfferQueue`：现有两遍逻辑改为调用 base helper，行为不变。
- `MayiOfferQueue`、`HahaOfferQueue`、`MahuaOfferQueue`、`YinghuasuanOfferQueue`：
  - 保留各自原始订单转换；
  - 把 `getCinemaFlag + 当前用户登录过滤` 改为 `getCinemaFlagDetail + 同角色登录` 两遍；
  - 写 C1/A17/B、C2 stats。
- 其它 5 个队列首期不动。

### 配置 helper

- `src/common/constant.js` 或 `src/utils/utils.js` 增加 `getPullEvidencePlatList()`，读 sys_dict，返回数组；默认 Top5。
- 页面和队列共用，避免口径不一致。

## 七、订单排查页

- 从 A/成功记录取订单 `plat_name`；无记录时从 C1 的 `info.plat_name` 取。
- C2 表按订单平台过滤，并增加「平台」列；订单平台未知时显示全部并标注。
- C1 明细仍按 order/user 查，不额外平台过滤。
- 订单平台不在白名单时：显示“该平台未开启拉单证据（当前白名单：...）”，不进入“未拉到/丢单”结论。
- 现有 lieren 结论逻辑保留，只扩大平台范围；补充平台列/白名单提示。

## 八、错误处理

- C1/A17/B 写入失败：沿用 trace_fail/evidence_dropped/discard_record_fail 计数，不阻断拉单/报价。
- C1 队列上限 200、A 每日上限 2000 等现有保护不变。
- 白名单为空/缺省：默认 Top5；若配置了未接入平台：不写 C1/A17/C2，页面提示“未接入”。
- 其它平台的 `loginInfoList` 刷新失败：与 lieren 一样，本轮 `hasAnyRoleLogin` 可能拿不到同角色登录，C1/A17 不写；C2 trace_fail 计数可见。不要在没有登录列表时把订单直接当“当前用户无登录”静默跳过。
- 测试单、重复单：不写 C1/A17。

## 九、测试

- 单测：
  - `getPullEvidencePlatList` 默认/解析/空值。
  - base `_collectQuoteableOrders` 的 unknown/disabled/not_login/同角色登录分支。
  - C1 去重、A17/B 写入、C2 stats（returned/filtered/enqueued）。
  - 页面平台过滤/白名单提示（如现有测试可覆盖）。
- 全量：前端 jest、后端 jest、`browser:build`。
- 手工：默认 Top5 各跑一单；切到 sheng/mangguo/shoutu/yangcong/piaosheng 各跑一单，确认 C1、A17、C2 记录与 lieren 同型。

## 十、体积与风险

- 默认 Top5 约 1.57 万单/天，C1 约 20–30MB/天，7 天 150–200MB；C2 MySQL 5 平台约 1440 行/天。全部 10 个平台开启约 2 万单/天，7 天 200–300MB。
- 风险：
  - 把其它队列的“当前用户登录过滤”改为“同角色登录过滤”会影响入队行为：同角色有登录、当前无登录的订单以前被静默过滤，现在会写 A17 并跳过，不会报价；这是与 lieren 对齐的预期变化。
  - C1 量增加；用首次去重和默认 Top5 控制，按需再开其它平台。
  - 未知/未接入平台写进白名单时无 C1；页面必须提示，避免误判。
- 需重新打 Electron/前端包；后端只加 sys_dict 配置。

## 十一、验收标准

1. 全部 10 个平台都能通过 sys_dict 白名单开启 C1/C2；默认 Top5 下可查到与 lieren 同字段的 C1，`not_login` 订单有 C1 + A17/B。
2. C2 的 returned/filtered/enqueued 与 lieren 口径一致。
3. sys_dict 增删白名单平台后，C1/C2 在下一轮拉单生效。
4. 订单排查页按平台显示 C1/C2；未接入平台有明确提示。
5. 全量测试/构建通过。
