> 文档状态：全部 8 个系列已落地（含报价+出票双流程缓存复用）
> 创建日期：2026-07-14

## 一、背景与目标

### 1.1 问题

当前报价/出票流程中，每个订单都要独立调用 `getBuyPrevCinemaInfo()` 解析影院/影片/场次信息，涉及 3-4 次第三方 API 调用：

- 同一影院同一场次的多个订单重复查询
- 报价阶段解析出的第三方 ID（city_id/cinema_id/film_id/show_id）用后即弃
- 直连系列（SFC/UME/金逸）不走后端代理，Redis 缓存方案无法覆盖

### 1.2 目标

| 指标 | 当前 | 目标 |
| ---- | ---- | ---- |
| 报价阶段第三方 API 调用 | 每单 3-4 次 | 命中缓存时 0-1 次 |
| 同影院同场次重复查询 | 每单都查 | 首单查，后续复用 |
| 直连系列优化 | 无 | 通过后端 ID 缓存覆盖 |
| 单次报价查询阶段耗时 | 2-4s（未命中 Redis）/ 0.3s（命中 Redis） | <50ms（命中 ID 缓存） |

### 1.4 各系列命中时减少的 API 调用数

缓存命中时跳过影院/影片级查询，仅场次实时查。各系列减少的第三方 API 调用数：

| 系列 | 完整查询链 API 数 | 命中时仍需调用 | 命中时减少 | 跳过的 API |
| ---- | ---------------- | ------------ | ---------- | ---------- |
| wanda | 4 | 1（场次） | **3 次** | 城市列表 + 影院列表 + 影片列表 |
| fenghuang | 3 | 1（场次） | **2 次** | 影院列表 + 影片列表 |
| chenxing | 3 | 1（场次） | **2 次** | 影院列表 + 影片列表 |
| jinyi | 3 | 1（场次） | **2 次** | 影院列表 + 影片列表 |
| ume | 4 | 1（场次时间） | **3 次** | 影院列表 + 影片列表 + 场次日期 |
| h5ume | 3 | 1（场次） | **2 次** | 影院列表 + 影片列表 |
| lma（完整版+） | 2 | 1（场次） | **1 次** | 影片列表（含 feature/language_type） |
| sfc（精简版） | 2 | 1（影片+场次） | **1 次** | 城市列表 + 影院列表 |

> 说明：
> - lma 完整版+ 缓存了影片级属性（feature/language_type），命中时连 getMoviePlayInfo 也跳过
> - sfc 精简版仅缓存影院级 ID，getMoviePlayInfo 一次调用即获影片+场次，所以仍需调用
> - ume 命中时跳过 getMoviePlayDate（场次日期列表），仅查 getMoviePlayTime（场次时间）

### 1.3 与 Redis 缓存方案的关系

| 方案 | 作用层 | 覆盖系列 | 命中后行为 |
| ---- | ------ | -------- | ---------- |
| Redis 缓存（2026-07-12 方案） | 代理转发层 | 5 个后端代理系列 | 跳过第三方调用，返回缓存响应 |
| **本方案（ID 缓存复用）** | 业务逻辑层 | **8 个系列（含直连）** | 跳过整个查询链，直接用已解析的 ID |

两者互补：
- Redis 缓存命中时仍需反序列化响应 + 匹配目标影院/影片/场次
- 本方案命中时直接拿到已匹配的 ID，省掉匹配逻辑
- 直连系列无 Redis 缓存，本方案是其唯一可行的查询优化手段

## 三、表结构设计

### 3.1 方案选择：在 offer_record 加列，不新建表

理由：
- offer_record 已有 `cinema_code`、`film_name`、`show_time`、`app_name` 字段，可直接作为匹配 key
- 新建表会增加 JOIN 和写入负担
- addOrderHandleRecord 的 INSERT 是动态拼字段（见 `api/offerRecord.js` 的 `addRecordData`），加列后自动支持

### 3.2 DDL

```sql
-- offer_record 新增第三方 ID 缓存列
ALTER TABLE offer_record 
  ADD COLUMN third_party_ids JSON DEFAULT NULL COMMENT '报价时解析的第三方ID集合（跨订单复用）';

-- offer_record 新增缓存命中标识列（0=未命中，1=本地命中，2=远端命中）
ALTER TABLE offer_record
  ADD COLUMN cache_hit TINYINT NOT NULL DEFAULT 0 COMMENT '报价时是否命中第三方ID缓存 0-未命中 1-本地命中 2-远端命中';

-- offer_record_fail 同步加列（失败单也可能已解析出部分 ID）
ALTER TABLE offer_record_fail
  ADD COLUMN third_party_ids JSON DEFAULT NULL COMMENT '报价时解析的第三方ID集合（跨订单复用）';

-- offer_record_fail 同步加 cache_hit 列
ALTER TABLE offer_record_fail
  ADD COLUMN cache_hit TINYINT NOT NULL DEFAULT 0 COMMENT '报价时是否命中第三方ID缓存 0-未命中 1-本地命中 2-远端命中';

-- 复用查询索引（app_name + cinema_code + film_name + show_time）
-- 注意：show_time 是字符串格式（如 "2026-07-14 14:30"），索引长度需控制
ALTER TABLE offer_record
  ADD INDEX idx_cache_lookup (app_name, cinema_code, film_name, show_time(30));

-- offer_record_fail 同步加复用查询索引（失败单也参与缓存复用，UNION ALL 查询需要索引避免全表扫描）
ALTER TABLE offer_record_fail
  ADD INDEX idx_cache_lookup_fail (app_name, cinema_code, film_name, show_time(30));
```

**cache_hit 字段说明**：
- `0` = 未命中缓存，走完整查询链（城市/影院/影片/场次查询）
- `1` = 本地缓存命中，跳过对后端的 HTTP 调用，直接从进程内 LRU 缓存读取
- `2` = 远端缓存命中，查后端 offer_record 表命中，跳过部分第三方查询
- 用于统计缓存命中率和优化效果评估，可通过 SQL 直接查询命中率，无需翻日志

### 4.3 extractThirdPartyIds 提取函数

新增工具函数（`src/common/core/extractThirdPartyIds.js`，纯函数独立文件便于单测），按 app_name 提取对应字段：

```javascript
// 各系列第三方 ID 字段映射（不缓存场次级字段，场次实时查）
const fieldMap = {
  wanda: ['city_id', 'cinema_id', 'film_id'],
  fenghuang: ['cinemaLinkId', 'filmId'],
  sfc: ['city_id', 'cinema_id'],
  chenxing: ['cinemaId', 'filmId'],
  jinyi: ['cinema_id', 'film_id'],
  lma: ['cinema_id', 'city_id', 'short_code', 'feature', 'language_type'],
  ume: ['cinemaCode', 'cinemaLinkId', 'filmUniqueId'],
  h5ume: ['cinemaLinkId', 'filmId']
};

// app_name（具体影院标识，如 hsmzyc/bona）→ 系列 key（如 h5ume/sfc）
// wanda 和 lma 的 app_name 恰好等于系列名，直接命中 fieldMap
function getSeriesKeyByAppName(appName) {
  if (!appName) return null;
  if (fieldMap[appName]) return appName;
  if (GET_UME_LIST().includes(appName)) return 'ume';
  if (GET_H5_UME_LIST().includes(appName)) return 'h5ume';
  if (GET_SFC_APP_LIST().includes(appName)) return 'sfc';
  if (GET_CHENXING_LIST().includes(appName)) return 'chenxing';
  if (GET_FENGHUANG_LIST().includes(appName)) return 'fenghuang';
  if (GET_JINYI_LIST().includes(appName)) return 'jinyi';
  return null;
}

/**
 * 按平台提取第三方 ID 集合（用于跨订单复用，写入 offer_record.third_party_ids）
 * @param {Object} cinemaInfo - 各系列 getBuyPrevCinemaInfo / getMovieInfo 返回的影院信息
 * @param {string} appName - 订单的 app_name（具体影院标识，如 hsmzyc/bona/wanda）
 * @returns {Object|null} 第三方 ID 集合；cinemaInfo 为空或无匹配字段时返回 null
 */
function extractThirdPartyIds(cinemaInfo, appName) {
  if (!cinemaInfo || !appName) return null;
  const seriesKey = getSeriesKeyByAppName(appName);
  const fields = seriesKey ? fieldMap[seriesKey] : null;
  if (!fields) return null;
  const result = {};
  let hasValue = false;
  for (const field of fields) {
    const v = cinemaInfo[field];
    if (v != null && v !== '') {
      result[field] = v;
      hasValue = true;
    }
  }
  return hasValue ? result : null;
}
```

> **关键设计**：app_name 是具体影院标识（如 `hsmzyc`/`bona`），不是系列名（如 `h5ume`/`sfc`）。必须通过 `getSeriesKeyByAppName` 映射到系列 key 后才能查 fieldMap，否则 h5ume/sfc/ume/chenxing/fenghuang/jinyi 的子系列全部匹配失败（P0 阻断问题，已在开发阶段发现并修复）。

### 5.2 查询 SQL

```sql
-- 同时查成功表和失败表，优先取成功表（src=0），同表取最新
-- 失败单的 third_party_ids 可能不完整（如只有 cinema_id 没有 film_id），下游 buildCinemaInfoFromCache 会做完整性校验
SELECT third_party_ids FROM (
    SELECT third_party_ids, processing_time, 0 AS src
    FROM offer_record
    WHERE app_name = ?
      AND cinema_code = ?
      AND film_name = ?
      AND show_time = ?
      AND third_party_ids IS NOT NULL
      AND processing_time >= DATE_SUB(NOW(), INTERVAL ? DAY)
    UNION ALL
    SELECT third_party_ids, processing_time, 1 AS src
    FROM offer_record_fail
    WHERE app_name = ?
      AND cinema_code = ?
      AND film_name = ?
      AND show_time = ?
      AND third_party_ids IS NOT NULL
      AND processing_time >= DATE_SUB(NOW(), INTERVAL ? DAY)
) t
ORDER BY src ASC, processing_time DESC
LIMIT 1;
```

约束：
- `processing_time >= NOW() - N DAY`：只信任 N 天内的缓存（场次时效性），N 由字典表 `offer_record_cache_ttl_days` 配置，默认 7 天
- TTL 从 24h 延长到 7 天（可配），覆盖提前一周排片场景；有降级兜底（场次匹配失败回退完整查询），即使缓存过期也不影响功能
- `UNION ALL` 查成功表 + 失败表：失败单也可能已解析出影院/影片 ID（如影院匹配成功但影片/规则/价格失败），复用可省第三方查询
- `ORDER BY src ASC, processing_time DESC`：优先取成功表（src=0），同表取最新
- `LIMIT 1`：只需一条
- `INTERVAL ? DAY` 用占位符传值，避免 SQL 注入

### 5.6 场次实时匹配（fillShowInfoFromApi）

场次 ID 时效性强（可能被影院调整），**命中缓存后仍需实时查询场次**，但可省掉城市/影院/影片 3 步：

```javascript
// wanda 示例：命中缓存后仅查场次，返回 boolean 供调用方判断是否回退
async fillShowInfoFromApi(cinemaInfo) {
  try {
    if (!cinemaInfo.cinema_id || !cinemaInfo.film_id) return false;
    const targetShow = await this.getTargetShow(cinemaInfo);
    if (!targetShow) return false;
    cinemaInfo.targetShow = targetShow;

    cinemaInfo.show_id = targetShow.showtimeId;
    cinemaInfo.member_price = targetShow.salesPrice;
    return true;
  } catch (error) {
    this.logger.errorSave("缓存命中后实时查询场次异常", {
      error: formatErrInfo(error)
    });
    return false;
  }
}
```

## 六、时效校验与降级

### 6.1 时效校验规则

| 字段类型 | 校验方式 | 失效处理 |
| -------- | -------- | -------- |
| city_id / cinema_id / film_id 等影院/影片级 ID | N 天内的报价记录（SQL `INTERVAL ? DAY`，N 由字典表 `offer_record_cache_ttl_days` 配置，默认 7 天） | 超时则不命中，走原逻辑 |
| 场次级 ID（show_id/schedule_id 等） | **不缓存，命中后仍实时查场次** | 实时查失败则回退完整查询 |

### 6.2 降级策略

```
查询 third_party_ids 缓存
├─ 命中 → 用缓存 ID 构造 cinemaInfo
│    ├─ fillShowInfoFromApi 成功 → 返回 cinemaInfo（省 3 步查询）
│    └─ fillShowInfoFromApi 失败 → 回退完整查询链（0 损失）
├─ 未命中 → 走原完整查询链（0 损失）
└─ 查询异常 → 走原完整查询链（try/catch 兜底，0 损失）
```

**核心原则**：缓存命中是优化，未命中或异常不影响原有流程。

### 6.3 数据一致性

- 同一影院同场次可能被多次报价，取最新一条（`ORDER BY processing_time DESC`）
- 第三方 API 变更导致 ID 规则变化（极少见）时，旧缓存失效 → fillShowInfoFromApi 失败 → 自动回退

```sql
  COUNT(*) as cnt
FROM offer_record
```

## 十、风险与约束

### 10.1 场次时效性（最关键）

- 场次可能被影院调整（改厅、改时间、取消）
- **对策**：命中缓存后仍实时查场次（fillShowInfoFromApi），失败则回退完整查询
- **TTL 兜底**：只查 7 天内的报价记录（覆盖提前一周排片场景，场次匹配失败时回退完整查询，不影响功能）

### 10.2 缓存污染

- 第三方某次返回错误数据，被解析后写入 third_party_ids
- **对策**：extractThirdPartyIds 只提取已成功匹配的字段（getBuyPrevCinemaInfo 成功返回的 cinemaInfo）

### 10.3 索引性能

- `idx_cache_lookup (app_name, cinema_code, film_name, show_time(30))` 索引
- show_time 取前 30 字符建索引，避免全长度索引过大
- 查询频率：每单 1 次，日均 3 万+ 次，有索引下 <5ms

### 10.4 h5ume 重构风险

- h5ume 已完成重构：cinemaManage 新增 `getBuyPrevCinemaInfo` 封装查询链，buyTicket 走统一入口

## 十一、后续可优化方向

### 11.1 卡券列表短期缓存

当前卡券可用性实时查（方案明确规定不走缓存）。可考虑同影院 5-10 分钟短期缓存，降低 SV 后端查询压力。需评估券库存超卖风险。

### 11.2 targetShow 整体缓存

当前场次实时查（fillShowInfoFromApi）。若观察发现场次变更频率极低，可考虑缓存 targetShow 整体对象，进一步省掉场次查询。需严格 TTL（如 5min）+ 失效降级。

### 11.3 跨平台影院映射

当前按 app_name 隔离，不同系列各自缓存。若影院映射表（cinema_code_match）完善，可考虑跨平台复用（如 wanda 的 cinema_id 映射到 fenghuang 的 cinemaLinkId），但收益有限且复杂度高。

### 12.3.3 失败单缓存复用扩展（2026-07-15）

原方案仅查成功表 offer_record，失败单不写 third_party_ids，导致失败率高的影院同场次订单反复重试第三方查询。本次扩展：

| # | 改动点 | 说明 |
| --- | --- | --- |
| 1 | `BaseOfferPrice.buildErrorResponse` 透传 `cinemaInfo` + `cacheHit` | 失败单若已解析出影院/影片 ID（如影院匹配成功但影片/规则/价格失败），也能写入 third_party_ids |
| 2 | `offerRecord.findCachedThirdPartyIds` SQL 改 `UNION ALL` | 同时查成功表 offer_record + 失败表 offer_record_fail，`ORDER BY src ASC` 优先取成功表 |
| 3 | `offer_record_fail` 加索引 `idx_cache_lookup_fail` | UNION ALL 查询需要索引避免失败表全表扫描 |
| 4 | `buildCinemaInfoFromCache` 完整性校验已有 | 失败单 third_party_ids 可能不完整（如只有 cinema_id 没有 film_id），下游 `if (!cachedIds?.cinema_id) return null` 自动回退完整查询链 |

**覆盖的失败类型**：类型 1（超限价）、4（券无库存）、5（无可用卡）、6（影厅未含规则）、9（座位数不符）、10（低于成本价）、11（张数超促销数）—— 这些失败发生在影院/影片查询之后，cinemaInfo 已有值。

**不覆盖的失败类型**：类型 7（官网拉取数据失败）—— 失败发生在第三方查询本身，cinemaInfo 为 null，无 ID 可缓存。后续可考虑方案 B（缓存"查询失败"标记）。

**安全性**：失败单 third_party_ids 不完整时，`extractThirdPartyIds` 只提取有值的字段，`buildCinemaInfoFromCache` 校验必填字段（如 cinema_id），不完整自动回退完整查询链，不会导致错误报价。

## 十四、进程内缓存控制（前端 LRU 缓存 + 字典配置化）

### 14.1 问题背景

每个订单报价/出票时都会调用 `tryGetCachedThirdPartyIds` 查后端缓存。同影院同场次的订单在短时间内（如批量报价）会重复调用后端接口，占用 HTTP 连接池和后端 DB 连接池。虽然单次查询只需 30-80ms，但高峰期同影院同场次几十单并发时，连接池压力较大。

**核心定位**：本地进程内缓存是后端缓存的"热数据子集"，**本地未命中仍需查后端**，不能替代后端缓存。

### 14.2 方案设计

在前端进程内增加 LRU 缓存层，缓存后端查询**命中**的结果：

```
订单 → tryGetCachedThirdPartyIds
        ├─ 1. 查本地 LRU 缓存（6 小时 TTL）
        │    ├─ 命中 → 直接返回（省掉 HTTP 调用，这是本地缓存的核心价值）
        │    └─ 未命中 → 2
        └─ 2. 调后端 /offer-record/cached-ids
             ├─ 后端命中 → 用 + 写入本地缓存（下次同参数省 HTTP）
             └─ 后端未命中 → 走完整查询链（null 不写本地缓存）
```

**关键设计决策**：

| 决策点 | 选择 | 理由 |
| ------ | ---- | ---- |
| null 是否缓存 | **不缓存** | 避免首单写入 third_party_ids 后被本地 null 缓存"挡住"，简单优先 |
| 本地未命中是否查后端 | **必须查** | 本地是后端的子集，不能替代后端（进程重启/其他客户端写入的数据本地没有）|
| 过期机制 | **逐条过期 + 惰性清理** | 每条各自 6 小时有效期，读取时判断过期，无定时器 |
| 淘汰策略 | **LRU** | 超容量淘汰最近最少访问的条目 |

### 14.3 字典配置化（sys_dict）

所有参数通过 `sys_dict` 字典表运行时配置，修改后无需重启服务：

| dict_type | dict_label | dict_value | 说明 |
| --------- | ---------- | ---------- | ---- |
| `third_party_ids_cache_ttl` | 第三方ID本地缓存有效期(毫秒) | `21600000` | 前端进程内 LRU 缓存有效期，默认 6 小时 |
| `third_party_ids_cache_size` | 第三方ID本地缓存最大条数 | `2000` | 前端进程内 LRU 缓存最大条数，超容量 LRU 淘汰 |
| `offer_record_cache_ttl_days` | 报价记录缓存有效期(天) | `7` | 后端查询第三方 ID 缓存的报价记录有效期 |

**生效时效**：
- 前端两个参数：60 秒内自动生效（字典配置缓存 TTL 60 秒，避免每单查字典接口）
- 后端有效期：立即生效（每次查询都读字典）
- 字典读取异常：前端回退默认值（6 小时/2000 条），后端回退默认值（7 天）

**SQL 初始化**：`doc/sql/2026-07-15-third-party-ids-cache-dict.sql`

### 14.5 关键代码

**thirdPartyIdsCache.js 核心流程**：

```javascript
// 缓存命中来源标识（写入 offer_record.cache_hit 字段）
// 0 = 未命中，1 = 本地缓存命中，2 = 远端缓存命中
const CACHE_SOURCE = {
  MISS: 0,
  LOCAL: 1,
  REMOTE: 2
};

async function getCachedThirdPartyIdsWithCache(params, fetcher) {
  const { app_name, cinema_code, film_name, show_time } = params;
  const key = buildCacheKey(app_name, cinema_code, film_name, show_time);
  const config = await getDictConfig();  // 60秒查一次字典

  // 1. 查本地缓存
  const cached = getFromCache(key, config);
  if (cached !== undefined) {
    return { ids: cached, source: CACHE_SOURCE.LOCAL };  // 本地命中
  }

  // 2. 本地未命中，查后端
  let result = null;
  try {
    const res = await fetcher();
    result = res?.data?.third_party_ids || null;
  } catch (error) {
    return { ids: null, source: CACHE_SOURCE.MISS };  // 异常不缓存
  }

  // 3. 只缓存命中结果（null 不缓存）
  if (result) {
    setToCache(key, result, config);
    return { ids: result, source: CACHE_SOURCE.REMOTE };  // 远端命中
  }
  return { ids: null, source: CACHE_SOURCE.MISS };
}
```

**后端 offerRecord.js 字典读取**：

```javascript
// 读取字典配置，异常回退默认值 7 天
let ttlDays = 7;
try {
```

**各系列接入方式（8 个系列统一）**：

```javascript
async tryGetCachedThirdPartyIds() {
  try {
    const { app_name, cinema_code, film_name, show_time } = this.order;
    const { ids, source } = await getCachedThirdPartyIdsWithCache(
      { app_name, cinema_code, film_name, show_time },
      () => svApi.getCachedThirdPartyIds({ app_name, cinema_code, film_name, show_time })
    );
    this.cacheSource = source; // 1=本地命中, 2=远端命中, 0=未命中
    return ids;
  } catch (error) {
    this.logger.errorSave("查询第三方ID缓存异常", { error: formatErrInfo(error) });
    this.cacheSource = 0;
    return null;
  }
}
```

> `tryGetCachedThirdPartyIds` 返回 `ids`，同时把 `source` 存到 `this.cacheSource`。各系列在缓存命中分支读取 `this.cacheSource` 赋给 `this.cacheHit`，经 `BaseOfferPrice.buildSuccessResponse` 透传（`?? 0` 兜底）写入 `offer_record.cache_hit`。

### 14.6 缓存层级关系

| 层级 | 位置 | TTL | 容量 | 作用 |
| ---- | ---- | --- | ---- | ---- |
| 第一层：后端 DB 缓存 | offer_record.third_party_ids | 7 天（字典可配）| 无限 | 跨订单复用第三方 ID，命中省 2-4 秒 |
| 第二层：前端本地缓存 | 进程内 Map | 6 小时（字典可配）| 2000 条（字典可配）| 减少对后端的重复查询，命中省 30-80ms + 连接池占用 |

**两层互补**：
- 本地缓存命中 → 直接返回，省掉 HTTP 调用（连接池/带宽收益）
- 本地缓存未命中 → 查后端，后端命中则写入本地缓存（下次同参数省 HTTP）
- 两层都未命中 → 走完整查询链，报价成功后写入后端缓存

### 14.7 风险评估

| 风险 | 影响 | 评估 |
| ---- | ---- | ---- |
| 进程重启本地缓存丢失 | 重启后首批订单需重新查后端 | **无影响**：降级为正常查后端，不报错 |
| 本地缓存数据偏旧（6 小时内影院换 ID）| 用偏旧的 ID 查场次失败 | **无影响**：fillShowInfoFromApi 失败后回退完整查询链 |
| 字典配置异常 | 参数无法动态调整 | **无影响**：前端/后端都有默认值兜底 |
| 字典配置被误改（如 TTL 设为 0）| 缓存立即过期或容量为 0 | **低风险**：parseInt 解析失败回退默认值；建议管理后台加校验 |

### 14.8 配置调整指南

| 场景 | 调整方式 |
| ---- | -------- |
| 本地缓存命中率低 | 调大 `third_party_ids_cache_ttl`（如 12 小时 = 43200000）|
| 本地内存占用高 | 调小 `third_party_ids_cache_size`（如 1000）|
| 后端缓存命中率低 | 调大 `offer_record_cache_ttl_days`（如 14 天）|
| 临时关闭本地缓存 | **当前无法通过字典完全关闭**：`parseInt("0") \|\| DEFAULT` 中 `0` 为 falsy 会回退默认值。如需完全关闭，需修改代码增加 `if (config.ttlMs === 0) return undefined` 开关判断 |

> 注意：调整字典配置后，前端参数 60 秒内生效，后端参数立即生效，无需重启服务。
