# 报价/出票全链路性能优化方案

> 文档状态：已批准，实现中
> 创建日期：2026-07-12
> 关联变更文档：`doc/changes/2026-07-12-报价出票全链路性能优化.md`
> 核心思路：**Redis 缓存扩展 + 串行→并行 + 并发控制优化 + 完整可观测性**
> 覆盖范围：5 个后端代理系列（fenghuang/h5ume/chenxing/lma/wanda）
> 会员卡、券列表实时查不走缓存；缓存命中日志受字典开关控制

---

## 一、问题与目标

### 1.1 核心问题

报价/出票流程中最耗时的环节是**影院第三方 API 查询链**——每个订单都要串行调用 3-4 个查询接口获取城市、影院、排期、场次信息，这些数据短时间内几乎不变，但每单都重新请求。

以 30 个影院、每分钟 10 单计算，每分钟产生 **40-60 次冗余第三方 API 调用**。

### 1.2 「报价已结束」问题

单子多时频繁出现报价时接口返回"报价已结束"。根因有二：

1. **报价本身慢**：缓存未命中 + 串行 4 次网络调用，单次报价 2-4s，卡住时长时间占用队列（当前 `offerHandleTimeout=60000` 即 60s，麻花平台单独 120s）
2. **队列堆积**：热门大连锁系列（如 wanda）占满并发上限 2，后续订单排队等待，等到开跑时已过截止时间

### 1.3 目标

| 指标                        |         当前         |            目标            |
| --------------------------- | :------------------: | :------------------------: |
| 报价查询阶段耗时            |        2-4 秒        | **< 0.3 秒**（缓存命中时） |
| 缓存命中率                  |         ~5%          |         **> 80%**          |
| offerHandleTimeout 内完成率 | 偶尔超时（当前 60s） |         接近 100%          |
| "报价已结束"发生频率        |      单多时频发      |          显著减少          |

**带宽压力分析**：4 用户 × 10 平台 = 40 个报价队列，每单 3-4 次第三方查询，每小时 ~1193 单 = 每小时约 4000-5000 次外网请求。20M 带宽不够用的根因是**大量重复请求**（同一影院列表被各用户各订单重复拉取）。缓存上线后命中部分不走外网，带宽消耗预计显著下降。

### 2.5 报价并发控制现状与「报价已结束」根因

深入阅读 `BaseOfferQueue.js` 和 `BaseOrderFetcher.js` 后定位到 4 个瓶颈：

**瓶颈①：拉单轮询是阻塞串行的**（`BaseOfferQueue.js:51-54`）

```js
while (this.isRunning) {
  const fetchDelay = await this.getFetchInterval(); // 默认 2-5 秒
  await this.fetchOrders(fetchDelay); // ← 阻塞！拉单本身要调第三方 API + 查后端
}
```

单量大时，`fetchOrders` 本身耗时数秒，实际拉单周期可能拉长到 10+ 秒，新单入队晚 → 距截止时间不足 → 被 `minOfferQueueEndTime` 过滤掉。

**瓶颈②：同系列并发上限默认 2**（`BaseOfferQueue.js:96-98, 364-381`）
热门大连锁系列（如 wanda）占满并发上限 2 后，同系列后续订单排队等待。`findNextOrderToRun()` 的 for 循环会 continue 跳过被阻塞的订单继续扫描——这部分逻辑是对的，能自动恢复。但当所有订单都被同系列阻塞时，调度器 break。

**瓶颈③：`offerHandleTimeout` 整体超时 60s（麻花 120s）**（`BaseOfferQueue.js:461-516`）
字典 `offerHandleTimeout=60000`，麻花平台在 `platform-config.js:485` 单独硬编码 120s。单次报价卡住时会长时间占用队列（尤其 `offerConcurrencyPerSeries=1` 时，一个卡住的订单阻塞整个系列 60s），后续订单排队等到过期。

**瓶颈④：`handledOrders` Map 容量 100**（`BaseOfferQueue.js:32, 316-321`）
单量大时 100 条容量很快填满，旧订单被淘汰后重复拉取重新入队，浪费调度资源。

**核心解法**：缓存让单次报价从 2-4s 降到 <0.5s → 队列不再堆积 → 同系列并发上限不再成为瓶颈 → 更多订单在截止前完成报价。"报价已结束"的根本解是**让报价变快**。

## 三、方案设计：四大支柱

### 支柱 A：Redis 缓存扩展 + 分级 TTL

#### A1. 扩展 CACHEABLE_ENDPOINTS（`auto-ticket-service/routes/cacheManager.js`）

从 4 个扩展到 15 个，覆盖 5 个系列的城市/影院/影片/场次列表：

- h5：`schedule.getschedules`（新增场次）
- 凤凰：`schedule.filmschedules.get`（新增场次）
- 辰星：`getCinemaList`、`getHitFilm`、`loadSchedule`
- 卢米埃：`film`、`sell_session`
- 万达：`homepage/city.api`、`by_locationid_v6_4.api`、`hot_coming_show.api`、`schedule_v6_4.api`

#### A2. 分级 TTL（替代统一 60min）

| 数据类型 | TTL   | 说明                 |
| -------- | ----- | -------------------- |
| 城市列表 | 24h   | 几乎不变             |
| 影院列表 | 4h    | 小时级变化           |
| 影片列表 | 30min | 30min 级变化         |
| 场次列表 | 15min | 最关键，原完全无缓存 |

#### A3. SimpleProxy 增加可选缓存（`proxyFactory.js`）

给 `createSimpleProxyMiddleware` 加 `cacheEnabled`/`cacheName` 参数，走标准 check→get→miss→fetch→set 流程。辰星、卢米埃开启 `cacheEnabled: true`。

#### A4. 万达独立代理接入缓存（`proxyWandaFilmApi.js`）

万达走的是独立的 WASM 签名代理（非 SimpleProxy/ComplexProxy），原本完全无缓存。单独接入缓存命中检查 + 分级 TTL 写入 + 字典控制日志。

- 万达的 `userToken`/`userIdentifier` 在请求头里、不在 URL 中，GET 请求缓存 key 只取 URL，所以城市/影院/影片/场次等全局数据可**跨用户共享缓存**，命中率较高。

**A1-A4 上线后，前端零改动即受益**——前端请求走后端代理，缓存命中在后端透明完成。

### 支柱 B：串行→并行（仅万达）

#### B1. 各系列查询链依赖分析

| 系列      | 查询链                                      | 能否并行                              |
| --------- | ------------------------------------------- | ------------------------------------- |
| fenghuang | 影院列表→cinemaLinkId→影片列表→filmId→场次  | ❌ 严格数据依赖                       |
| h5ume     | 同 fenghuang                                | ❌                                    |
| chenxing  | 同 fenghuang                                | ❌                                    |
| lma       | 影院列表→cinema_id→影片列表→short_code→场次 | ❌                                    |
| wanda     | 城市列表→city_id→{影院列表, 影片列表}→场次  | ✅ 影院列表与影片列表都只依赖 city_id |

**仅万达可并行**：影片列表按 `city_id` 查询，与影院列表（也按 `city_id`）无依赖，用 `Promise.all` 并行执行，节省 1 次网络往返（约 0.5-1s）。

#### B2. 缓存命中后串行已足够

fenghuang/h5ume/chenxing/lma 虽然串行，但缓存命中后每次查询 <50ms，3 次串行总耗时 <0.3s，已足够。强行并行化会引入回归风险，收益有限。

### 支柱 C：并发控制优化

#### C1. handledOrders 容量提升 + 字典可配

从硬编码 100 提升到字典 `handledOrdersCapacity`（默认 500），单量大时避免重复入队。

#### C1.5 handledOrders 去重增强（2026-07-12 线上日志验证）

**问题**：原始代码 `handledOrders.set()` 后无条件继续执行 `insertOrderIntoQueue()`——即使同一订单已在 Map 中，也会重新入队，并覆盖 `_offerEnqueueAt`。线上日志证实：订单 `7474786795111768064` 在 71 秒内重复入队 2 次。此问题与 Map 容量无关（线上容量 500 足够）。

**修复**：`set()` 前增加 `has()` 显式检查 + `return` 提前退出，同时 `queue.some()` 兜底（Map 淘汰后仍能拦住）。key 加上 `plat_name` 前缀避免跨平台订单号冲突。

```js
// 修复后
const orderKey = `${item.plat_name}_${item.order_number}`;
if (this.handledOrders.has(orderKey)) return; // Map 快速去重
if (this.queue.some(o => o.order_number === item.order_number)) return; // 队列兜底
this.handledOrders.set(orderKey, 1);
```

#### C2. offerHandleTimeout 建议从 60s 降到 15s

当前字典 `offerHandleTimeout=60000`（60s），麻花平台单独 120s。60s 超时太长——单次报价卡住时会长时间阻塞队列（`offerConcurrencyPerSeries=1` 时尤其严重）。

缓存上线后单次报价 <0.5s，15s 超时绰绰有余且能快速释放卡住的队列位。**建议缓存上线观察 1-2 天后，手动将字典改为 15000**（麻花 120s 保持不变，因其锁座候选多确有特殊需求）。SQL 脚本里已附调整语句（注释状态，需人工执行）。

#### C3. 新增字典字段（运行时可调，不停机）

| dict_type               | 说明                   | 默认值 |
| ----------------------- | ---------------------- | ------ |
| `handledOrdersCapacity` | handledOrders Map 容量 | 500    |
| `isCacheLogEnabled`     | 缓存命中日志开关       | 1      |

> `minOfferQueueEndTime` / `minOfferHandleEndTime` 为已有字典字段，单量大时可调小 `minOfferQueueEndTime` 让更多临界单入队。

### 支柱 D：完整可观测性（缓存日志受字典控制）

#### D1. offer_duration + queue_wait_ms 耗时度量

| 字段             | 含义               | 起点                                       | 终点                         |
| ---------------- | ------------------ | ------------------------------------------ | ---------------------------- |
| `offer_duration` | 报价处理耗时       | `orderHandle` 开跑（`orderHandleStartAt`） | singleOffer 结束、写记录前   |
| `queue_wait_ms`  | 入队到开跑等待耗时 | 入队（`order._offerEnqueueAt`）            | 开跑（`orderHandleStartAt`） |

诊断矩阵：

| offer_duration | queue_wait_ms | 诊断                     | 优化方向                         |
| -------------- | ------------- | ------------------------ | -------------------------------- |
| 高（2-4s）     | 低            | 报价本身慢，缓存未命中   | 检查缓存命中率、第三方响应       |
| 低（<1s）      | 高（>3s）     | 队列堆积，没轮到跑就过期 | 调大 `bigChainSeriesConcurrency` |
| 中             | 中            | 两者都有                 | 先缓存后调并发                   |

#### D2. cinema_cache_query_log 日志表 + 字典开关

记录每次缓存查询的 hit/miss，受字典 `isCacheLogEnabled` 控制（高峰期可关闭减少 DB 写入）。`series_code` 标识系列，`data_type` 标识数据类型（city_list/cinema_list/movie_schedule）。

## 九、后续可优化方向

本次方案上线后，根据 `offer_duration` / `queue_wait_ms` / 缓存命中率的实际数据，可按需推进以下方向：

### 9.1 缓存层深化

**① 主动预热 cron**

- 当前是被动缓存（首个请求 miss 后回源写入），高峰期首批订单仍会慢
- 可新增 node-cron 定时任务（每 15min），用首个有效 session 预热各系列活跃影院的场次缓存
- 参考现有 `SyncPriceWorkerManager`（worker_threads 模式），用独立 Worker 避免阻塞主进程
- 受字典 `isPrefetchCacheEnabled` 控制开关

**② 直连系列纳入缓存体系**

- SFC（group.leying.com）、UME 小程序（oc.yuekeyun.com）、金逸（ct.womovie.cn）目前前端直连第三方，后端不可控
- 可后端新增缓存代理路由（如 `/sfc-cache-ser/`、`/ume-cache-ser/`、`/jinyi-cache-ser/`），查询走后端缓存，写操作（锁座/下单/支付）保持直连
- 这是旧版方案的 Phase 3，可按需推进

**③ 卡券库存前端短期缓存**

- 会员卡列表、券库存当前实时查（方案明确规定不走缓存），避免数据不一致
- 但可考虑前端进程内 30s 短期缓存（同影院连续报价时复用），降低后端查询压力
- 需评估券库存超卖风险后决定

**⑪ 报价时缓存第三方 ID 供出票复用** 🆕

- 当前报价和出票各自独立调 `getBuyPrevCinemaInfo()` 解析影院/影片/场次，每个订单重复 3-4 次第三方 API 调用
- 报价阶段 `getEndOfferPrice()` 内部已解析出 `city_id`、`cinema_id`（storeId/cinemaLinkId）、`film_id`、`show_id`（showtimeId）等第三方 ID，但用后就丢弃了
- 优化思路：在 `offer_record` 表新增 `third_party_ids` JSON 列，报价完成时将已解析的第三方 ID 存入；出票时 `getOrderOfferRule()` 已查 `offer_record`，顺带取出这些 ID，`getBuyPrevCinemaInfo()` 检测到已有时跳过 API 调用直接使用

| 系列      | 报价时已解析的第三方 ID                                             |          出票时可跳过接口          |
| --------- | ------------------------------------------------------------------- | :--------------------------------: |
| wanda     | `city_id`, `cinema_id` (storeId), `film_id`, `show_id` (showtimeId) | 城市列表、影院列表、影片列表、场次 |
| fenghuang | `cinemaLinkId`, `filmId`, `scheduleId`                              |      影院列表、影片列表、场次      |
| chenxing  | `cinema_id`, `film_id`, `show_id`                                   |      影院列表、影片列表、场次      |
| lma       | `cinema_id`, `film_id`, `show_id`                                   |      影院列表、影片列表、场次      |
| h5ume     | `cinemaLinkId`, `filmId`, `scheduleId`                              |      影院列表、影片列表、场次      |

- **收益**：出票时跳过 3-4 次 API 调用（含 Redis 查询），每单节省约 0.2-0.3s
- **风险**：第三方 ID 在短时间内（场次 15min 内）不会变化，TIMEOUT 风险极低；座位/价格等实时数据仍需出票时实时查
- **实施**：需改动 `offer_record` 表 + `addOrderHandleRecord` 写入 + 各系列 `getBuyPrevCinemaInfo` 读取

### 9.2 并发控制调优

**④ 基于 queue_wait_ms 动态调大连锁并发上限**

- 上线后观察各系列 `queue_wait_ms` 分布，若某系列普遍 >3s，说明并发上限太低
- `bigChainSeriesConcurrency` 字典已支持按系列配置，可直接调大（如 wanda 从默认 2 调到 3-4）
- 注意：调大并发会增加第三方 API 并发压力，需观察第三方限流情况

**⑤ 拉单与调度解耦**

- 当前 `BaseOfferQueue.start()` 的拉单循环是阻塞的（`await this.fetchOrders(fetchDelay)`），单量大时拉单本身耗时导致新单入队延迟
- 可将拉单改为独立定时器（`setInterval`），与调度器解耦，拉单失败不阻塞下一轮
- `handleNewOrder` 入队后立即触发 `startProcessingQueue` 的逻辑已存在，解耦后响应更快

**⑥ findNextOrderToRun 调度策略优化**

- 当前按 `offer_end_time` 升序贪心调度，同系列满员时 continue 跳过
- 可考虑"紧急度加权"：距截止时间越近且系列空闲的订单优先级越高，避免紧急订单被非紧急的同系列订单间接阻塞

### 9.3 可观测性增强

**⑦ offer_duration 分阶段细化**

- 当前 `offer_duration` 是 singleOffer 整体耗时，无法区分"查询链"和"提交报价"各占多少
- 可在 `getEndOfferPrice`（查询阶段）和 `submitOffer`（提交阶段）分别打点，入库时拆成 `query_duration` + `submit_duration`
- 便于精准定位是查询慢还是第三方提交慢

**⑧ 缓存命中率报警**

- 当某系列命中率持续 <30% 时，可能 Redis 故障或 endpoint 匹配失效
- 可在 `cinema_cache_query_log` 上加定时统计，命中率过低时推送 WxPusher 告警

### 9.4 代码质量

**⑨ logCacheQuery 函数去重**

- 当前 `proxyFactory.js` 和 `proxyWandaFilmApi.js` 各有一份 `logCacheQuery`，逻辑几乎相同
- 可抽到 `api/cacheQueryLog.js` 作为公共方法，或挂到 `cacheManager` 实例上，避免维护两份
- 各系列 data_type 的正则差异可通过参数化解决

**⑩ CACHEABLE_ENDPOINTS 匹配机制改进**

- 当前用 `url.includes(endpoint)` 匹配，`film` 等短关键词可能误匹配
- 可改为正则匹配或按路由前缀 + endpoint 精确匹配，降低误缓存风险
- 优先级低，当前 15 个 endpoint 均为查询类接口，误匹配无实际影响

### 9.5 实施优先级建议

| 方向               | 优先级 | 触发条件                     | 预期收益                   |
| ------------------ | :----: | ---------------------------- | -------------------------- |
| ④ 动态调并发       |   高   | queue_wait_ms 普遍偏高       | 直接减少"报价已结束"       |
| ⑪ 报价缓存第三方ID |   高   | 出票阶段查询耗时长           | 跳过出票时 3-4 次 API 调用 |

| ⑤ 拉单解耦         |   中   | 拉单周期 >5s                 | 新单入队更快               |
| ⑦ 分阶段耗时       |   中   | 需精确定位慢查询环节         | 指导后续优化               |
| ② 直连系列缓存     |   低   | 直连系列报价慢               | 覆盖最后 3 个系列          |
