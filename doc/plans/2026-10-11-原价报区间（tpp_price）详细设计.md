# 原价（tpp_price）报区间 详细设计

> 日期：2026-10-11
> 需求：报价前按订单原价（`tpp_price`）过滤规则 —— **订单原价落在配置区间内才参与报价，不在区间内则剔除该规则**；未配置 = 不限制 = 照报。
> 关联：《2026-10-11-原价不报（tpp_price）详细设计.md》（本方案**取代**其「不报条件」部分）、《2026-09-30-猎人B钱包加价报价整改说明.md》（规则级新增字段的落库/回显/兜底先例）、《2026-06-04-报价失败原因分类.md》（`OFFER_FAIL_TYPE` 枚举）。
> 状态：设计已评审确认（2026-10-11，**方案 A**），待实施。

## 一、需求变更与已确认决策

### 1.1 变更点

上一版实现的是**「原价不报」**：`rule_record` 新增列 `noOfferTppRule`，支持 `>50 / >=50 / <30 / <=30 / 30-80 / !30-80`，分号分隔多条，命中任一即剔除规则，并配套「条件行 + 表达式输入框」双向互转的配置 UI。

现需求变更为**「原价报区间」**：只保留**一个区间**，订单原价在区间内才报、不在区间内则剔除该规则；去掉灵活表达式与 6 种操作符。

新旧对照：

| 维度 | 旧（原价不报） | 新（原价报区间） |
| ---- | -------------- | ---------------- |
| 列名 | `noOfferTppRule` | `offerTppRange` |
| 类型/长度 | `VARCHAR(255)` | `VARCHAR(64)` |
| 配置形态 | 分号多条 + 6 种操作符 + 表达式输入框 | **单个区间**（下限、上限两个数字输入） |
| 语义 | 命中条件 → 剔除 | **不在区间内 → 剔除**；未配置 → 照报 |
| 判定 | `> / >= / < / <= / between / notBetween` | `min ≤ 原价 ≤ max`（闭区间，含端点） |
| 失败原因 `err_msg` | `按原价筛选后，报价规则为空` | `按原价区间筛选后，报价规则为空` |

### 1.2 已确认决策（方案 A，2026-10-11）

| # | 决策点 | 结论 |
| - | ------ | ---- |
| 1 | 列怎么改 | **改名 + 改类型 + 改注释**（`CHANGE COLUMN`）。旧列 `noOfferTppRule` 已投产（DDL 于 2026-10-11 由用户在生产库执行）且**从未配置过数据**，改名安全、无需数据迁移 |
| 2 | 存储格式 | **单字符串 `下限-上限`**，闭区间含端点；端点可留空：下限空 = 0，上限空 = 正无穷；`NULL`/空串 = 未配置 |
| 3 | `tpp_price` 缺失 / 非数值 / ≤0 | **照报（放行）** —— 平台字段缺失时宁可照报，避免全量停报 |
| 4 | 配置非法（无法识别 / 下限 > 上限） | **照报（放行）** + `errorSave`；保存前由前端 `validateOfferTppRange` 阻断脏配置落库 |
| 5 | 由平台报价的规则 | **继续跳过该过滤**（与旧口径一致）：已同步猎人平台 + 固定价 + 字典开关 + 时段内的规则由平台报价、本地不参与算价，本地过滤对这类规则无效 |
| 6 | 失败原因 | 编号沿用 **15**；`err_msg` 与分类正则改为 `按原价区间筛选后，报价规则为空` |
| 7 | 灵活表达式 | **去掉**：不再支持分号多条与 6 种操作符，只有"一个区间" |
| 8 | 出票链路 | **不改**：出票按已选定的规则 id 取规则，不做二次过滤；规则变更不追溯已出票订单 |

### 2.2 `tpp_price` 在报价阶段的来源（沿用上一版核实结论）

各平台报价队列的 `fetchOrders` 均已写入 `tpp_price`，报价阶段该字段齐备，`offerRuleMatch` 可直接读 `order.tpp_price`：守兔 `unitInitPrice`、商展 `price_ori`、芒果/麻花/哈哈/票生 `maoyan_price`、蚂蚁 `unitprice`、洋葱 `unitPrice`、省 `showPrice`、影划算 `net_price`。

> 注意：字段名统一为 `tpp_price`，但**各平台语义是"该平台的原始价/市场价"**，不是同一个口径的"猫眼价"。按原价配置区间时需按平台分别评估（规则本身已按平台维度建，可在各自规则里分别配区间）。

### 2.3 过滤位置（沿用上一版结论）

所有影线系列的报价都经过 `BaseOfferPrice.getEndOfferPrice` → `getEndMatchOfferRule(order)` → `offerRuleMatch(order, logger)`（`src/utils/utils.js:1300`）。过滤层放在 `offerRuleMatch` **末尾（会员日过滤之后、`return` 之前）**，只影响"本来能匹配到规则"的订单，**不改变既有「按城市/影院/影厅/座位数筛选为空」的统计口径**，且一处改动覆盖全部 8 个影线系列（sfc/ume/h5ume/lma/wanda/chenxing/fenghuang/jinyi）。

## 三、数据模型

### 3.1 DDL（需先于客户端发版执行）

```sql
ALTER TABLE rule_record
  CHANGE COLUMN noOfferTppRule offerTppRange VARCHAR(64) NULL DEFAULT NULL
  COMMENT '原价报区间：下限-上限(闭区间，含端点)；端点可留空，下限空=0，上限空=正无穷。未配置=不限制';
```

- `CHANGE COLUMN` 同时完成「改名 + 改类型 + 改注释」；旧列已投产、**无数据**，等价于新增一列，无需数据迁移。
- 命名沿用表内驼峰风格（`bWalletMarkup` / `shadowLineName` / `offerType`）。
- `NULL` 表示"未配置"（区别于空串；空串在保存时统一转 `null`，见 §6.3）。
- 落盘为**新文件** `doc/sql/2026-10-11-offer-tpp-range.sql`（含校验与回滚语句）。不修改已执行的 `2026-10-11-no-offer-tpp-price.sql`（迁移文件已执行即冻结）。

### 3.2 兼容性

- 后端 `auto-ticket-service/api/ruleRecord.js` 为 `Object.keys(obj)` 动态拼字段 + `SELECT *`，**无需改后端代码**，改名后自动可见。
- 客户端先发版、DDL 后执行的窗口期：保存链路有缺列兜底（§6.3），报价侧读不到 `offerTppRange`（`undefined`）即等价于"未配置"（放行），不会造成停报。

## 四、存储格式与解析器

### 4.1 存储格式（单字符串）

| 存储值 | 语义 | 说明 |
| ------ | ---- | ---- |
| `NULL` / `""` / 全空白 | **未配置 → 不限制（照报）** | 存量规则零影响 |
| `50-80` | `50 ≤ 原价 ≤ 80` 才报 | 闭区间含端点 |
| `50-` | `原价 ≥ 50` 才报 | 上限空 = 正无穷 |
| `-80` | `原价 ≤ 80` 才报 | 下限空 = 0 |
| `-` | `原价 ≥ 0` 恒真 → 等价"不限制" | 解析兼容；UI 两端都空时存 `""` 而非 `-` |
| `80-30` / `abc` / `1-2-3` | **非法 → 照报（放行）** | 解析标记 `invalid`，运行期放行 + `errorSave`；保存前前端已阻断 |

- 允许小数与条目内空格（如 ` 50 - 80 `）。
- 只有一个区间，不再有分号分隔的多条条件。

### 4.2 解析器重写：`src/utils/tppPriceRule.js`（纯函数、无 store 依赖）

| 导出 | 签名 | 说明 |
| ---- | ---- | ---- |
| `parseOfferTppRange` | `(rangeStr) => { configured, min, max, invalid, reason }` | 未配置 → `{ configured:false }`；合法 → `{ configured:true, min, max }`（`min` 默认 0、`max` 默认 `Infinity`）；非法 → `{ configured:true, invalid:true, reason }` |
| `isTppPriceInOfferRange` | `(tppPrice, rangeStr) => boolean` | **true = 保留/照报**。原价缺失/非数值/≤0 → `true`；未配置/非法 → `true`；否则 `min ≤ 原价 ≤ max` |
| `formatOfferTppRange` | `(rangeStr) => string` | 人话回显：`原价50~80` / `原价≥50` / `原价≤80` / `不限`；未配置 → `""`；非法 → `配置无效:原文` |
| `validateOfferTppRange` | `(rangeStr) => { ok, msg }` | 保存前校验：未配置 → ok；非法格式或下限>上限 → `ok:false` 并给出原因与原文 |

解析正则与规则：

1. `rangeStr` 为 `null/undefined/全空白` → `{ configured:false }`；
2. `^\s*(-?\d+(?:\.\d+)?)?\s*-\s*(-?\d+(?:\.\d+)?)?\s*$`（两端均可缺省）→ 命中后：下限缺省取 `0`、上限缺省取 `Infinity`；
3. 命中且 `min ≤ max` → 合法；`min > max` → `invalid`（reason：`下限不能大于上限`）；
4. 未命中 → `invalid`（reason：`格式无法识别`）。

判定顺序（`isTppPriceInOfferRange`）：数值化 `tppPrice` → 非有限数或 `≤0` 直接 `true` → `parseOfferTppRange` → 未配置/非法直接 `true` → `min ≤ price ≤ max`。

### 4.3 为什么不再复用 `calculateMarkup` / 不再保留旧解析器

「灵活加价」的 `calculateMarkup`（`src/utils/utils.js:2286`）以"首段比较价 + 条件+金额"为单位，且其区间操作符 `<>` / `!<>` 实现有误（`<>` 恒真、`!<>` 语义与命名相反）。上一版出于"形态一致"选择了独立解析器；本轮需求已**收敛为单一区间**，直接用"两端点"表达最简，旧的多条/6 操作符解析器全部删除，**不保留兼容分支**（旧数据为空、无迁移负担）。

```js
// UI → 存储：两端都空 → ""（未配置）；否则拼 "下限-上限"（端点可空）
const syncOfferTppRangeStr = () => {
  const min = String(rangeMin.value ?? "").trim();
  const max = String(rangeMax.value ?? "").trim();
  if (!min && !max) {
    formData.offerTppRange = "";
    return;
  }
  formData.offerTppRange = `${min}-${max}`;
};

// 存储 → UI：未配置两端置空；非法串原样落到下限（保存会被校验拦截）
const fillOfferTppRangeFromStr = () => {
  const { configured, invalid, min, max } = parseOfferTppRange(
    formData.offerTppRange
  );
  if (!configured) {
    rangeMin.value = "";
    rangeMax.value = "";
  } else if (invalid) {
    rangeMin.value = String(formData.offerTppRange ?? "");
    rangeMax.value = "";
  } else {
    rangeMin.value = min === 0 ? "" : String(min);
    rangeMax.value = max === Infinity ? "" : String(max);
  }
};
```

- 存储字符串 `formData.offerTppRange` 仍是**唯一真源**；`rangeMin/rangeMax` 是它的可视化视图，两处双向同步（`@change`/`@input` 调 `syncOfferTppRangeStr`）。

## 七、边界与异常

| 场景 | 行为 | 理由 |
| ---- | ---- | ---- |
| `tpp_price` 为空 / `null` / 非数值 / ≤ 0 | **照报（放行）**；**不写日志** | 平台字段缺失时宁可照报，避免全量停报（决策 3）。`info` 日志只在"原价不在区间内、剔除该规则"时写；`errorSave` 只在配置非法/全部被剔除时写 |
| 未配置 `offerTppRange`（`NULL`/空串） | **照报（不限制）** | 存量规则零影响（决策 2） |
| 配置非法（`80-30` / `abc`） | 运行期**放行** + `errorSave`；保存期前端 `validateOfferTppRange` **阻断** | 不因配置错误停报（决策 4） |
| 原价在区间内 | 规则保留，正常报价 | — |
| 原价不在区间内 | 剔除该规则；若全部被剔除 → `errorSave("按原价区间筛选后，报价规则为空")` | 决策 6 |
| 规则是"平台报价规则" | 跳过过滤（规则保留，走平台报价既有分支） | 决策 5 |
| 平台报价时段外（如猎人 23:00-9:00） | 过滤**生效**（本地算价） | 判定与守卫含同样时段条件 |
| 测试单（`isTestOrder`） | 同样生效 | 口径一致，便于用测试单验证 |
| 出票链路 | **不改** | 决策 8 |

## 十、已知限制与待确认

1. **平台报价的规则不受约束**（业务已知悉）：已同步猎人平台 + 固定价 + 字典开关 + 时段内的规则由平台报价，本地过滤跳过 → 该区间对这类规则**不生效**。若需平台侧也生效，需平台侧支持，另行推进。
2. **`tpp_price` 的平台口径差异**：各平台映射来源不同（守兔 `unitInitPrice`、商展 `price_ori`、芒果/麻花/哈哈/票生 `maoyan_price`…），配置区间时需按平台分别评估（规则已按平台维度建，可在各自规则里配不同区间）。
3. **只有上/下界一端时另一端按"0 / 正无穷"处理**：无"开区间"表达（不支持"严格大于 50"），如需严格边界可用 `50.01-` 这种精度变通。
4. **不做"命中即整单不报"**：只剔除不满足区间的规则；如需"这类场次一律不碰"，应通过规则覆盖范围（影院/影片白名单）实现。
