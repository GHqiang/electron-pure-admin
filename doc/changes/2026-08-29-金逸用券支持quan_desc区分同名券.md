# 金逸系列用券支持按 quan_desc 区分同名不同类型券整改

- 日期：2026-08-29
- 先例参照：凤凰系列（`fenghuang/cardQuanManage.js`）同名券双重过滤实现

## 一、背景与问题

金逸系列用券出票时，目标券筛选**只按券名单一字段匹配**：接口券对象的 `show_name`（映射为 `couponName`）与券类型库的 `quan_flag`（券标识）经 `couponInfoSpecial` 归一化后全等比较。券描述 `quan_desc` 虽在出票时已从券类型库查出（`offerRule.quan_desc`），但从未参与选券比对。

当同一影院存在**券名相同但类型（quan_value/面额）不同**的多种券时：

1. **选券错用券码**：同名券的券码全部混入 `targetQuanList`，可能把其他类型的券码核销出去，实际面额/成本与报价规则（`quan_value`/`quan_cost`）不符；
2. **库存互相污染**：`syncUpdateQuanStock` 异步同步库存同样只按券名统计，同名券库存被重复计入每一个同名券类型，导致报价阶段（`getQuanTypeListByApp` → `applyQuanStockFilter`）库存判断虚高、误报价。

字段对应关系：服务端券类型 `quan_desc`（券描述，QuanDialog 中标注"仅同名券必填"）↔ 金逸接口券对象的 `show_desc` 字段。`show_desc` 原先随 `...item` 展开保留在券对象上，但代码从未映射、从未读取。

同类问题在凤凰系列已通过「券名 + 券描述」双重过滤解决，本次将同一模式对齐到金逸。

## 三、核心变更说明

### 1. 券列表映射补齐 couponDesc（cardQuanManage.js 两处）

```js
couponName: item.show_name,
couponDesc: item.show_desc,   // 新增
couponCode: item.coupon_code,
```

### 2. 选券双重过滤（useQuanOrCard，原 L168-171）

```js
let targetQuanList = quanList.filter(
  item =>
    couponInfoSpecial(item.couponName) ===
      couponInfoSpecial(quan_flag) &&
    (quan_desc
      ? couponInfoSpecial(item.couponDesc || "") ==
        couponInfoSpecial(quan_desc)
      : true)
);
```

### 3. 库存同步双重过滤（syncUpdateQuanStock，原 L877-882）

券名匹配与黑名单过滤之后追加同样的描述比对；`item.quan_desc` 来自 `getQuanTypeListByApp` 的 queryFields（原已包含 `quan_desc`），查询无需改动：

```js
(item.quan_desc
  ? couponInfoSpecial(item.quan_desc) ===
    couponInfoSpecial(itemA.couponDesc || "")
  : true)
```

### 4. 绑券透传（getNewQuan + buyTicket.js 调用处）

`getNewQuan` 签名解构增加 `quan_desc`，传给公共方法 `getQuanValueListByQuanFlag`（`src/mixins/usesMachineBaseFun.js` 已支持 `quan_desc` 透传服务端 queryQuanTypeList，用于按券描述精确圈定同名券类型的 quan_value 列表再绑券）；出票流程调用处同步传 `offerRule.quan_desc`。

### 5. 行为变化边界（明确"不改什么"）

- **向后兼容**：券类型未配置 `quan_desc` 时，过滤条件恒为 `true`，选券/库存/绑券行为与改动前完全一致；仅当配置了 `quan_desc` 才要求接口券 `show_desc` 归一化后全等匹配；
- 与凤凰先例的唯一偏离是比对时加 `|| ""` 防护——金逸接口 `show_desc` 字段覆盖率未经代码验证，防止个别券缺该字段时 `couponInfoSpecial(undefined)` 在用券主流程抛 TypeError；效果上：配置了 `quan_desc` 的券类型，无描述的接口券自然被过滤（符合"配置了描述就必须匹配"的语义）；
- 选券后续链路（已用记录过滤、黑名单、过期排序、利润计算）及"无券转用卡/转单"流转完全未动。

## 五、回归风险评估

| 风险 | 评估 | 缓解 |
|---|---|---|
| 金逸接口券对象实际无 `show_desc` 字段 | 低-中：若字段不存在，配置了 `quan_desc` 的券类型会因 `couponDesc` 全为 `""` 而选不出券，走「优惠券不够用 → 灵活用券转用卡 / 报错」既有兜底，不会错用券码 | 上线前先用单个配置了 quan_desc 的同名券影院灰度验证；L2 日志「获取未使用券返回-示例仅展示前5条」可确认接口原始字段；确无该字段则清空对应券类型 `quan_desc` 即回退旧行为 |
| 存量已配 quan_desc 的金逸券类型行为变化 | 低：此前选券从未使用 quan_desc，若历史配置的描述与接口 `show_desc` 文案不一致，改造后该券类型将选不出券（转用卡/报券不足），属暴露存量配置问题而非引入故障 | 上线后观察「面额券不足」日志中相关 quan_value；必要时订正券描述配置 |
| 库存统计口径变化 | 低：配置了 quan_desc 的券类型库存由"同名全部"收敛为"同名同描述"，库存数可能下降——更真实，报价判断随之保守 | 无需处理，属预期修正 |
| 未配 quan_desc 券类型回归 | 极低：过滤条件退化为 `true`，逻辑等价 | 券库存公共链路 25 个用例通过 |

## 六、上线步骤与观察指标

   - 「面额券不足」日志若集中出现在新配 `quan_desc` 的券类型，优先核对描述文案与 `show_desc` 是否归一化后一致；
   - 报价侧同名券库存数变化（收敛为真实同类库存）属预期。
