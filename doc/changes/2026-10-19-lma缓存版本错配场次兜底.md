# 卢米埃「缓存版本错配导致场次匹配失败」整改说明（修复订单 2026101812371520452 出票失败）

- 日期：2026-10-19
- 关联问题：订单 `2026101812371520452`（猎人 → 卢米埃，生化危机：爆发夜，2026-10-18 13:40，1号厅，2 张）出票失败，单据 `order_status=2`
- 排查报告：`reports/analyze-issue/2026-10-18-2026101812371520452-出票失败.md`（本地，不入库）
- 修复范围：**纯客户端、仅卢米埃**（未改后端接口契约；兜底 + 进程内版本短码记忆，稳态零额外请求）

## 一、问题现象

订单出票时报：

```
匹配影片放映场次失败   {"start_time":"13:40","showList":[20:05 IMAX厅, 22:00 IMAX厅]}
获取购票前影院信息异常 {"error":"\"获取影院/影片/场次信息失败\""}
降级-转单-进入 → 自动转单处于关闭状态（仅告警，不转单）
```

单据落库 `order_status=2`、`err_msg=获取购票前影院信息异常`、`err_info="获取影院/影片/场次信息失败"`，出票耗时 773ms。

**关键事实**：该场次在影院侧是正常在售的——卢米埃小程序「电影排期 → 今天10月18日」明确显示 13:40「1号厅-激光高亮-皮质座椅-影迷群有福利（2D/原版）」¥50.9 起、可选座购票。所以不是影院撤排、也不是售罄。

## 二、根因

### 1. 卢米埃的 short_code 是「影片版本」级，不是「影片」级

同一部片在卢米埃系统里按版本拆成不同 `short_code`：

| 影片 | 版本 | short_code |
| --- | --- | --- |
| 生化危机：爆发夜 | 2D/原版（1号厅、2号厅、3号厅…） | `067101570026` |
| 生化危机：爆发夜 | IMAX2D/原版（IMAX 厅） | `067701570026` |
| 复仇者联盟4（加码臻享版） | 2D/原版 | `051101440026` |
| 复仇者联盟4（加码臻享版） | IMAX2D/原版 | `051701440026` |

生产数据佐证（近 30 天全卢米埃）：生化危机「非 IMAX 厅」4326 单全部用 `067101570026`；「IMAX 厅」188 单用 `067701570026`。

补充两点实测（2026-10-19 复核）：

- **影片列表解析结果可能是「组合短码」**：`short_code` 存成 `"051101440026,051701440026"` 这种逗号形态，近 90 天卢米埃共 4967 条记录是这样的。
- **温州该影院的影片列表确实能解析出多版本**：温州「复仇者联盟4（加码臻享版）」非 IMAX 厅有 `cache_hit=0`（即完全走影片列表 + 影片名匹配，没走缓存）的记录，落库 `short_code` 就是组合短码 `051101440026,051701440026`。这证明该影院同名多版本在影片列表里可解析 —— 兜底方案能拿到含 2D 版本的短码，不需要依赖"缓存里先有 2D 版本"。

### 2. 第三方 ID 缓存以「影院 + 影片名」为唯一键，不含版本

- 客户端本地 LRU：`thirdPartyIdsCache.js:69-71`（`buildCacheKey`），key = `app_name|cinema_code|film_name`
- 后端 Redis：`auto-ticket-service/api/offerRecord.js:20-24`（`buildTpidCacheKey`），key = sha1(同三元组)
- 后端 MySQL：`offerRecord.js:373-400`，同三元组 `ORDER BY src, processing_time DESC LIMIT 1`（取**最新一条**）

三处都缺版本维度，于是「同影院同影片」的 IMAX 单与 2D 单会互相串用短码。

### 3. 温州该影片历史只沉淀了 IMAX 版

温州该影院该影片全部 112 条报价记录（2026-09-25 ~ 2026-10-17）**short_code 全是 `067701570026`**，`067101570026` 出现 0 次。第一单是 IMAX 场次，此后每单都命中这份缓存，形成自我维持的污染。

### 4. 命中缓存后直接盲用短码，且失败不回头

`lma/cinemaManage.js` 命中缓存时置 `skipPlayInfo=true`，跳过影片列表与版本鉴别，直接用缓存短码调 `sell_session`；随后：

- 场次匹配失败 → `errorSave("匹配影片放映场次失败")` 并 `return null`（改动前位于该文件的场次匹配分支，现为 `:394` 附近，前面已插入兜底）；
- 已有的「降级回退」只在**日期**匹配失败时触发（原 `:230`，现为 `:297` 附近），**日期命中、场次缺失**这条路径当时没有任何兜底。

所以最终链路是：

```
缓存命中 IMAX 版短码 0677 → sell_session(0677) 只返回 IMAX 场次
  → 13:40（属 0671，2D/原版）匹配不到 → 出票失败
```

### 5. 为什么连续 3 单都失败

10-17 17:40、10-18 15:40、10-18 13:40 三张 1号厅 单，明细日志里都是「命中 IMAX2D 缓存 → 查 IMAX 短码 → 只回 IMAX 场次」，同一根因，且缓存不会自我纠正。

## 四、核心变更说明

### 1. 触发点（`getMovieInfo` 内，原 `:297` 之前）

```js
// 缓存命中但场次匹配不到：卢米埃同一影片会按版本拆成不同 short_code …
if (!targetShow && (skipPlayInfo || cacheHit > 0)) {
  const versionMatch = await this.matchShowByFilmVersions({
    cinema_id, film_name, hall_name, start_day, start_time,
    excludeShortCode: short_code, film,
    variants: this.cachedVersions
  });
  if (versionMatch) {
    targetShow = versionMatch.targetShow;
    short_code = versionMatch.short_code;
    movieInfo = { ...movieInfo, ...versionMatch.movieInfo };
    // 记住该影厅版本的正确短码，后续同版本订单直接命中，不再兜底
    setFilmVersionMemo({ app_name, cinema_code, film_name, hall_name }, versionMatch.movieInfo);
  }
}

if (!targetShow) { /* 原有失败分支保持不变 */ }
```

（对应 `lma/cinemaManage.js:367-391`，失败分支在 `:393-398`。）

### 2. 新增 `matchShowByFilmVersions()`

两级匹配，**任何一级失败都继续下一级**（`lma/cinemaManage.js:424` 起）：

1. **第一级 · 后端候选版本**（`with_versions=1` 才有效）：直接用候选短码，按「与影厅版本一致优先」排序，省掉影片列表请求；
2. **第二级 · 影片列表**（候选救不回来时必定执行，兼容旧后端）：
   - 调用方已查过影片列表则复用，否则调 `getMoviePlayInfo`；
   - 先按**影片全名**筛同名条目（同一影片的各版本），取不到再按「去标点/大小写归一」名称兜底；
   - 用 `triedShortCodes` 排除已试过的短码（含缓存那条），避免重复请求；
3. 逐条候选查 `sell_session`，按 `日期 + start_time` 匹配；同一时间多场次按影厅名相似度择优；
4. 命中即返回 `short_code` + 影片属性，并记 `warnSave("缓存场次匹配失败，按影片版本兜底命中")`；
5. **只回填有值的属性**：候选可能缺 `feature`/`language_type`，此时用命中场次上的 `language_type` 回填，绝不用 `undefined` 覆盖调用方已有值（否则报价的电影格式过滤会拿到 `undefined` 而抛错）；
6. 全部失败 → 返回 null，**保持原有失败行为**（不改变告警与转单逻辑）。

命中后 `this.cinemaInfo` 会带上正确短码，后续写入 `third_party_ids` 即为该版本，下单一单若版本不同会再次走兜底，行为自洽。

### 3. 影片版本短码记忆（省请求、出票更快）

仅做兜底的话，**同影片同版本的每一单**都要先拿错短码查一次、再兜底查影片列表+正确场次，等于每单稳定多 2 次请求。为此增加一个进程内记忆（`Map`，TTL 6 小时、上限 500 条、FIFO 淘汰）：

- key：`app_name|cinema_code|film_name|影厅版本(IMAX/普通)`
- value：兜底解析出的正确 `short_code` + `feature` + `language_type`
- 命中缓存后先查记忆：有就直接用正确短码查场次，**不再白查错版本、不再重查影片列表**
- 只在「兜底成功」时写入（证据来自实际场次匹配），因此不是拍脑袋的推断
- 记忆失效自愈：若影院换了版本/短码，用记忆查不到场次会重新走兜底并覆盖记忆

（请求数对比见 §5，此处不重复。）

### 4. 后端返回候选版本（`with_versions=1`，向下兼容）

`auto-ticket-service/api/offerRecord.js` 的 `findCachedThirdPartyIds` 增加**可选**参数：

- 不传 `with_versions`：**完全走原逻辑**（Redis `tpid:v1` 30min → MySQL `LIMIT 1` → 只返回 `third_party_ids`），旧客户端字节级无感
- 传 `with_versions=1`：走独立 Redis 键 `tpid:v2`（30min / 空标记 60s）→ 未命中查 MySQL `LIMIT 10`，按 `short_code` 去重取最多 3 条，返回
  `{ third_party_ids, third_party_ids_list: [...] }`（`third_party_ids` 仍是最新一条，结构不变）

客户端只有卢米埃传该参数（`tryGetCachedThirdPartyIds` → 本地缓存键加 `|versions` 后缀，与单条结果互不污染），其它系列不传，行为不变。

| --- | --- | --- | --- | --- |
| 缓存版本正确 | 1 次 sell_session | 1 次 | 1 次 | **1 次** |

| 缓存版本错误·候选不够（见 §5.1，本单真实情况） | 直接失败 | 3 次 | 3 次 | **3 次**（错版本+候选+影片列表） |

### 5.1 生产阻塞项（自查发现并已修）

**问题**：后端候选来自历史报价记录。该影院该影片历史里**只有 IMAX 版**（生产实测：7 天内 `offer_record` 只有 `067701570026` 一个 short_code），所以
`third_party_ids_list` 只会返回当前这个错误版本；若客户端在「候选列表里没有可试版本」时直接返回 null，就会**跳过真正能救的影片列表兜底**，本次修复等于无效。

**修复**：兜底改为两级——先用后端候选（省一次影片列表请求），**候选救不回来时必定再查影片列表**（用 `triedShortCodes` 去重，不重复请求同一短码）。
已加用例「后端候选版本只有当前错误版本时，仍要回退影片列表兜底（生产真实场景）」，修复前该用例返回 null。

### 5.2 其它自查修复

| 项 | 问题 | 处理 |
| --- | --- | --- |
| 根因缓存污染 | 兜底异常原用 `errorSave`，会写 `_lastErrCache`，导致后续转单/失败原因被顶掉 | 改为 `warnSave`（只进 L2），并加用例锁定 |
| 影片属性被覆盖 | 候选（历史记录）可能缺 `language_type`，spread 会用 `undefined` 冲掉已有值，导致报价「电影格式过滤」`filmType.includes` 抛错 | 只回填有值属性；`language_type` 缺失时用命中场次上的版本回填 |
| 后端重复打 MySQL | 带版本查询若不走 Redis，进程重启/本地 LRU 失效时会反复扫表 | 新增独立键 `tpid:v2`（30min），与旧键互不影响 |

> 说明：本地 LRU 命中时不会产生 `cached-ids` HTTP；候选版本随一次查询一起带回，不额外增加请求。

### 6. 设计取舍

- **不用影厅名直接推版本**：生产数据里出现过 IMAX2D 版在 2号厅放映的情况（10-06 23:00 单用 `0677` 匹配到了 2号厅 场次），版本跟拷贝走、不跟影厅名走，用影厅名硬推会引入新的错配。因此仍以「试场次」为准；影厅名只用于候选排序与记忆分桶，不影响正确性。
- **触发条件含 `cacheHit > 0`**：老缓存记录可能只存了 `short_code`（无 `feature/language_type`），此时 `skipPlayInfo=false` 但仍是缓存串码，同样需要兜底。
- **记忆只在兜底成功后写入**：来源是真实场次匹配结果而非推断；过期/换片时查不到场次会再次兜底并覆盖，无副作用。
- **版本候选只给卢米埃**：后端能力通用，但只有卢米埃的场次查询按版本隔离；其它系列按需再开，避免无谓的查询放大。
- **带版本查询用独立 Redis 键**：`tpid:v2` 存候选列表，与 `tpid:v1` 的单条结构隔离；旧键保持原样，回滚时直接可用。

### 7. 兼容性矩阵（重点）

| 客户端 | 后端 | 行为 |
| --- | --- | --- |
| 旧（未升级） | 旧 | 原行为，不受影响 |
| 旧（未升级） | **新** | 不传 `with_versions` → 返回结构/Redis/SQL 全不变，**零影响** |
| **新** | 旧 | 后端不返回 `third_party_ids_list` → `versions` 为 null → 走影片列表兜底（已实现并有单测） |
| **新** | **新** | 优先用候选版本，省掉影片列表请求 |

因此**可以先发后端、再发客户端**，两个方向都安全。

## 六、回归风险评估

| 风险 | 评估 |
| --- | --- |
| 正常出票（缓存命中且版本正确） | 触发条件要求 `!targetShow`，版本正确时根本不进入兜底；已有用例锁定「不重复请求影片列表」 |
| 缓存未命中的普通订单 | `cacheHit=0` 时不进入兜底，行为与改动前完全一致 |
| 兜底引入额外请求 | 仅失败路径、最多「同名版本数」次 `sell_session`（通常 1~2 次）；影片列表已查过则复用，不重复请求 |
| 兜底误选其它版本 | 以「日期 + 开始时间」硬匹配，且排除已试短码；同时间多场次再按影厅名相似度择优，误选概率低 |
| 记忆命中错误短码 | 记忆只在兜底成功后写入；若影院换了版本，用记忆查不到场次会自动重新兜底并覆盖记忆，属自愈 |
| 记忆占用内存 | 上限 500 条、TTL 6 小时、FIFO 淘汰，每条仅存 3 个短字段，内存可忽略 |
| 记忆跨订单串版本 | key 含 `app|影院码|影片名|影厅版本(IMAX/普通)`，已有用例锁定「普通厅记忆不会被 IMAX 单误用」 |
| 失败语义变化 | 全版本都不命中时仍走原 `errorSave("匹配影片放映场次失败")` + 返回 null，告警/转单链路不变 |
| 报价链路 | `offerManage` 复用同一个 `getMovieInfo`，报价阶段同样受益；失败语义不变 |
| 后端接口兼容 | `with_versions` 不传时走原分支（含 Redis）：返回结构、SQL、key 均不变；已用「旧结构不含 `third_party_ids_list`」用例锁定 |
| 共享缓存模块改动 | `getCachedThirdPartyIdsWithCache` 第三参可选，其它 6 个系列调用方式不变；版本列表用独立本地键 `|versions`，与单条结果互不污染 |
| 带版本查询成本 | 独立 Redis 键 `tpid:v2`（30min），命中不打 MySQL；键与旧键隔离，回滚安全 |

## 七、发布与后续

1. **发布顺序**：先发后端（`with_versions` 默认不生效，旧客户端零影响）→ 再发客户端。客户端先发也可（旧后端不返回候选列表，自动走影片列表兜底）。
2. **其它影线同源风险**：ume / h5ume / sfc / fenghuang / chenxing / jinyi / wanda 也有同样的缓存复用逻辑（其中 6 个系列已自带「场次实时查+失败回退完整查询链」，sfc 缓存只存影院 id）。后端能力通用，若其它平台也出现「同片多版本」短码，只需在该系列传 `withVersions` 即可复用；建议按失败数据排查后再决定。
3. **本单处理**：修复发版后可直接「重新出票」（会拿到 `067101570026` 匹配 13:40）；未发版的客户端请仍走后台手动出票。
4. **监控**：`warnSave`「缓存场次匹配失败，按影片版本兜底命中」（仅 L2）、`infoSave`「命中影片版本短码记忆」。前者频次≈缓存缺版本造成的实际损失面，后者≈记忆生效次数；联调阶段可先看这两条日志判断是否已切到候选版本路径。

## 九、验证方法（看哪条日志 / 怎么算成功）

### 9.1 取证命令（只读，连接信息由脚本自动读取）

```bash

node scripts/prod-query.js order <订单号>

# ② L1 操作日志（errorSave 才入库）：看还有没有"匹配影片放映场次失败"
```

### 9.4 失败判据与对应处置

| 现象 | 含义 | 处置 |
| --- | --- | --- |
| L2 只有 `匹配影片放映场次失败`，没有 3/3' | 新逻辑没走到 | 确认客户端已升级到本次版本；确认走的是 lma `cinemaManage` 链路 |

### 9.5 后端是否已生效

- 接口入参：后端路由会打 `查询第三方ID缓存入参` 日志，参数里应出现 `with_versions: "1"`（只有新版卢米埃客户端会带）；
- 接口返回：带 `with_versions=1` 请求 `GET /svpi/offerRecord/cached-ids`，响应数据应含 `third_party_ids` + `third_party_ids_list`（≤3 条）；不带该参数时**响应结构与上线前完全一致**（可用同一接口对比验证向下兼容）；
- 若 `third_party_ids_list` 只有 1 条（该影院该影片历史上确实只有一个版本），属正常 —— 此时客户端会走「影片列表」这一级兜底完成换版本。

### 9.6 回滚判据

出现下列任一情况，回滚客户端（后端可保留，旧客户端走原逻辑）：

1. `按影片版本重匹配场次异常` 持续出现；
2. 出现 3 但 `matchedShortCode` 长期等于 `excludeShortCode`（等于没换版本）；
3. lma 出票耗时明显上升（`出票链路耗时统计` 的 `出票执行耗时ms` 分位数抬高），且集中在正常单。
