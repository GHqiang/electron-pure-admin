## 二、报价侧（offerManage.js）

### calcSteps 拼装段（getEndMatchOfferRule + getMinAmountOfferRule）

```
初始匹配命中N条
→ 电影格式过滤剩N条            （filmTypeFlag 内联过滤后；无独立 filterByFilmType 方法）
→ 会员日规则命中(X元)           （onlyMemberDayRuleList 命中即返回）
→ 券库存过滤剩N条               （fixedAmountRuleList 券类型库存+当日票数过滤后）
→ 会员价加价命中(X元)           （memberOfferAmount 计算完成）
→ 定价策略段                     （仅固定价 / 仅会员价 / 固定 vs 会员取低，对照 chenxing 模式）
```

- `getMinAmountOfferRule(ruleList, order, movieInfo, calcSteps = [])` 签名加 `calcSteps = []`（默认值兼容其它调用点）
- 返回前：`const endRuleCopy = JSON.parse(JSON.stringify(endRule)); endRuleCopy.calc_path = calcSteps.join("→"); endRuleCopy.hit_rule_name = endRule.ruleName || "";`（替换原 `endRule = JSON.parse(...); return endRule;`）
- `calc_path`/`hit_rule_name` 由 BaseOfferQueue serOrderInfo 收口（截断 500）入库，本文件只负责挂到 offerRule

### 与 jinyi 控制流的差异（结构化对应）

- sfc 的 `getMinAmountOfferRule` 存在 **3 个提前 return 最小固定报价规则** 的分支（`memberPriceRes` 获取失败 / `getRealAddMount` 失败 / 无加价规则），jinyi 无此结构。
  处理：在每个提前 return 前 push `仅固定价(X元)`（`if (mixFixedAmountRule)` 保护，空则跳过），保证“仅固定价”策略段覆盖所有纯固定价路径。
- 定价策略段放在 `if (!mixFixedAmountRule)` 之前：固定+会员并存 → `固定价X vs 会员价Y，取固定/会员`；无固定价 → `仅会员价Y`；三分支对齐 chenxing/jinyi 模式。
- 电影格式过滤为 `if (filmTypeFlag)` 条件内联（非独立方法），过滤块后统一 push，无 film_type 规则时条数不变（与 jinyi filterByFilmType no-op 语义一致）。
- sfc 的 `getEndMatchOfferRule` 无 jinyi 的 isTestOrder 测试规则兜底块，无需对应处理。

## 三、出票侧（buyTicket.js）

### 采集字段（oneClickBuyTicket 成功路径 return 前）

| 字段 | 来源 | 单位 |
|------|------|------|
| `paymentAmount` | `pay_money = Number(priceInfo.total_price \|\| priceInfo.price \|\| 0)`（buyTicket.js:537 既有变量） | **已是元**（与 quan_fee_total / real_member_price 元值直接比较、createOrder/buyTicket 实付、syncCardAfterPayment 同元运算），`?? null` 原样采集 |
| `cardBalance` | `cardList?.find(item => (isV3App ? item.member_id : item.id) == card_id)?.balance` | **已是元**（sfc getCardList 走 syncCardBalanceToSv `balanceDivisor: 1`；`balance * 100 >= quan_fee * 100` 与元值同口径），`?? null` 原样采集 |
| `coupons` | 见下方“结构差异” | 快照数组 |
| `usePath` | `buildTicketUsePath({offer_type, useQuan, cardNum, cardBalance, paymentAmount, currentParamsInx})` | 一句话路径 |

### 作用域处理

- `cardBalance` 原声明在 `if (card_id)` 块内（`let cardBalance = ...`），return 处不可访问 → **提升为 `let cardBalance = null;`**（if 块前），块内改赋值（照 jinyi 模式）；块内既有日志/`syncCardAfterPayment` 逻辑不受影响。
- `cardNum`/`pay_money` 均为函数级作用域变量，return 处可直接访问，无需提升。

### 与 jinyi 的结构差异（coupons/usePath 数据源）

- **sfc 的 `cardQuanManage.useQuanOrCard` 不返回 useQuan 数组**（jinyi/chenxing 返回 `{couponCode, couponName,...}[]`，sfc 仅返回 `quan_code`/`coupon_id`/`member_coupon_id` 拼接串 + `quanType`），且任务范围限定只改 offerManage.js + buyTicket.js。
  处理：在 oneClickBuyTicket 内从 `[quan_code, coupon_id, member_coupon_id]` 拼接串 `split(",")` 还原用券标识列表 `usedCouponList`，作为 coupons 快照与 usePath 的 useQuan 数据源（张数、尾号判断语义与 jinyi 一致）：
  - `couponCode` = 实际券号/券 id（offline_quan 为 coupon_num，线上券为 id）
  - `couponType` = `quanType`（offline_quan/online_quan/offline_member_quan/online_member_quan）
  - `couponName` = `""`（该作用域无券名数据，留空；券号已可溯源）
- `buildTicketUsePath` 方法体照抄 jinyi（换号N次 / 用券N张→卡尾号付券手续费 / 用卡尾号→支付前余额→实付），保持 sfc 文件风格。
