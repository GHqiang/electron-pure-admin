# 报价出票日志追踪与根因缓存整改说明

> 日期：2026-08-06
> 状态：**已全部实施**
> 说明：本文件由《2026-08-04-报价出票环节日志追踪规范设计》与《2026-08-04-日志根因缓存与辅助模块日志补充方案》合并而成，统一记录本次报价/出票日志整改的目标、规范、实现与验收。
>
> 目标：让**单个订单**的报价、出票流程在日志（`logList` / 上传）中形成一条**可读、可检索、可定位**的环节时间线，做到"一眼看出走了哪些环节、卡在哪一步、失败原因是什么"；并保证转单推送、出票/报价记录取到的失败原因不因降级动作而失真。

---

## 一、背景与现状

当前各影院系列 + 核心框架的日志存在三类问题，导致**单订单链路无法快速追踪**：

1. **环节标记不统一**：同一语义的日志在不同系列写法五花八门（如"获取购票前的影院信息返回"、"用卡用券返回"、"创建订单成功"），无统一前缀，无法一眼按环节梳理链路。
2. **关键环节缺失**：锁座成功、创建订单成功、支付结果、取票码提交平台成功等关键节点，部分系列（如 sfc、fenghuang）根本没有明确的成功/失败日志。
3. **级别用错**：关键失败（计算价格异常、创建订单失败、锁座失败）被写成不持久化的 `info`/`console`，日志丢失；大量无价值中间数据却用 `infoSave` 持久化，造成噪音。
4. **失败根因被覆盖**：`err_msg`/`err_info` 取"最近一次 `errorSave`"，降级路径的 `errorSave`（转单-开始等）会**覆盖根因**，导致转单推送、出票记录取的失败原因失真。
5. **辅助模块缺日志**：影院/座位/卡券等辅助模块在链路中用到的**方法内部**缺少日志，环节内细节（接口返回、失败原因）无法在订单时间线里看到。

### 1.1 现状量化诊断（来自《2026-08-04-出票日志整改分析报告》）

> 抽样脚本 `scripts/analyze-order-logs.js` 对 123 单、7353 条日志（69 组「系列 × 用卡/用券」组合，覆盖全部系列）的分析结论：

| 编号 | 问题 | 严重度 | 量化证据 |
|---|---|---|---|
| ① | 关键环节日志缺失（更新券库存、转单/换号） | 🔴 P0 | 更新券库存仅 **37%**、转单/换号仅 **16%** 订单有日志 |
| ② | 日志保留期仅 1~2 天 | 🔴 P0 | 超 1 天订单无日志可回溯（运维侧，不在代码库范围） |
| ③ | 敏感信息明文落库（session_id/token/卡密码） | 🔴 P0 | **已决策不做**：确认不脱敏（见第十章决策 2） |
| ④ | 日志爆炸（单订单最多 208 条） | 🟠 P1 | 支付轮询/锁座重试每次迭代落库 |
| ⑤ | 关键字段携带率低（券号 11%、取票码 8%、卡号 37%） | 🟠 P1 | 用券/取票码环节无法定位到具体券和码 |
| ⑥ | 噪音日志与无效日志（`[object Object]` 6 处） | 🟡 P2 | 稀释关键日志、浪费存储 |

> 本整改聚焦 ①④⑤⑥ 及失败根因失真问题；② 属 `auto-ticket-service` 运维侧（日志保留期 30 天），不在本代码库范围；③ 已按用户确认改为**不脱敏**。

## 二、设计原则

1. 以 `[报价]` / `[出票]` 前缀标记环节，`des` 全文可被 `order_number` 过滤后按 `opera_time` 排序成时间线。
2. **成功用 `infoSave`，失败/异常用 `errorSave`**；仅控制台调试用 `info`/`warn`，**不持久化**。
3. 每环节一个"进入"标记 + 一个"结果"标记（成功/失败/跳过），避免重复打印。
4. **大对象裁剪**：环节信息只带关键字段；完整返回/异常详情放 `errorSave` 的 `err_info`。
5. **不脱敏**：保留完整卡号、手机号、取票码等信息，便于二次排查（已与用户确认）。

## 三、日志标记规范

统一前缀格式：

```
[报价]环节名-业务描述
[出票]环节名-业务描述
```

示例：

```
[出票]锁定座位-成功 lockOrderId=xxx
[出票]用卡用券-失败 无可用优惠券(用券), err=...
[报价]规则匹配-进入
[报价]规则匹配-结果 命中规则 id=xxx offerType=1
```

> 说明：`order_number` 已由 `logger.init(order)` 注入上传，无需每条重复；环节内如需定位，可带 `order_number` 作为兜底。
>
> 双流程共用方法（影院/座位/卡券模块）无需显式加前缀：`Logger.log()` 内部 `_applyFlowPrefix()` 依据实例 `type`（1=报价 / 3=出票）自动拼接前缀（借助 `getFlowPrefix()`），已带 `[报价]`/`[出票]` 前缀的日志不重复拼接，避免双流程写死。独立 `new Logger({ logType })` 的场景（异步绑券=3、同步更新券库存=1）按其流程显式指定。

### 6.2 打点要求

对链路中用到的关键方法，统一补三类日志（`进入`、`结果`、`失败`）：

- 进入/参数：`this.logger.info(前缀 + 方法名-参数, 关键字段)`（**非持久化**，因调用方已有环节"进入"日志，模块内不重复入时间线）。
- 成功/结果：`this.logger.infoSave(前缀 + 方法名-结果, 关键字段)`（大对象裁剪到关键字段）。
- 失败/异常：`this.logger.errorSave(前缀 + 方法名-失败, { error, 关键上下文 })`。
- 不重复打印：调用方（buyTicket/offerManage）已有环节"进入/结果"终态日志的，模块内部只补**接口返回/失败细节**，不做重复环节标记。

> **为何 errorSave 的 meta 统一为 `{ error }` 而非 `formatErrInfo(error)`**
> - *格式化职责归 logger*：`Logger.getLastErrMsgAndInfo()` 取 `err_info` 时内部已执行 `formatErrInfo(meta?.error || meta)`。调用方传 `{ error }` 即可，由 logger 在读取时统一格式化；若调用方预先 `formatErrInfo(error)`（已是字符串），logger 会对字符串再 `JSON.stringify` 一次，造成双重转义、不干净。
> - *保留结构化信息*：`formatErrInfo(error)` 会把错误压缩成 `{message, stack, name}` 字符串，丢失 axios 错误中的 `response.data`、`config` 等字段；直接传 `{ error }` 保留原始对象，排查上下文更完整。
> - *格式一致*：统一为 `{ error }` 后，格式完全由 logger 一处控制，避免各模块写法不一导致日志格式不一致。
> - 副作用：原先把 `formatErrInfo` 仅用于错误格式化打点的文件，改后其 import 变为未使用，需一并清理（见 8.3 清理）。

### 6.4 轮询收敛

`orderManage.getPayResult` 支付结果轮询由"每次迭代 `infoSave` 落库"收敛为：

- **首次**（`inx === 1`）：参数 + 返回各落一条 `infoSave`（首次参数保留）；
- **成功**（取到取票码）：落一条 `infoSave`（末次结果）；
- **中间轮询**：仅控制台 `logger.info`（不落库）；
- **失败收敛**：首次失败 `errorSave`，后续失败仅控制台——外层已有兜底 errorSave（主流程"取票码不存在，转异步获取"、异步轮询"3分钟/7分钟仍失败"）。

效果：异步轮询路径（9+21 次）由最多 30 条落库收敛为约 4 条，单订单日志量显著下降。

## 七、根因缓存（`src/common/logger.js`）

### 7.1 问题

原 `getLastErrMsgAndInfo()` 返回 `_lastErrCache`（= 最近一次 errorSave）。降级路径（转单-开始、换号、释放座位异常、取消订单异常）都是 errorSave，会把它顶掉，根因丢失。

### 7.2 方案：根因 = 最近一次非降级 errorSave，环节成功时重置

> 修订说明：初版"首个 errorSave 记为根因"经 chenxing 实测发现两个失真场景：
> 1. **瞬态失败后恢复**：锁定座位首次失败（errorSave）→ 重试/辅助锁座成功 → 后续用卡用券失败，首个根因会错记为"锁定座位-异常"；
> 2. **换号多账号重试**：第 1 个手机号用卡用券失败（首个根因）→ 换号 → 第 2 个手机号创建订单失败，err_msg 仍记第 1 个号的原因。
>
> 修订为：**根因 = 最近一次"非降级" errorSave**（排除转单/换号/释放座位/取消订单/申请换座等补救动作），且**主链路环节成功终态时重置**。

```javascript
// 降级/补救型前缀：这些 errorSave 表示"怎么补救"，不作为根因
const REMEDY_PREFIXES = [
  "[出票]转单", "[出票]换号", "[出票]释放座位",
  "[出票]取消订单", "[出票]申请换座"
];
// 主链路环节成功终态后缀（如"锁定座位-成功"）：出现后作废之前缓存的根因
const SUCCESS_SUFFIX_RE = /-[^-]*成功$/; // 注意用 [^-]* 而非 [^-]+：成功紧贴 "-"（如"锁定座位-成功"）时 + 会吞掉"成"导致永不匹配

errorSave(message, meta) {
  this.log(Logger.levels.ERROR, message, true, meta);
  this._lastErrCache = { message, meta };
  // 补救型 errorSave 不覆盖根因；其余 errorSave（环节失败本身，如"创建订单-失败，走转单"）作为根因
  if (!REMEDY_PREFIXES.some(p => message?.startsWith(p))) {
    this._rootErrCache = { message, meta };
  }
}

infoSave(message, meta) {
  this.log(Logger.levels.INFO, message, true, meta);
  // 环节成功终态（锁定座位-成功等）作废旧错误；降级链路成功（转单-成功等）与"超时当成功处理"不重置
  if (!message?.includes("超时当成功") &&
      SUCCESS_SUFFIX_RE.test(message || "") &&
      !REMEDY_PREFIXES.some(p => message?.startsWith(p))) {
    this._rootErrCache = null;
  }
}
```

- `getLastErrMsgAndInfo()`：**优先返回根因** `_rootErrCache`，为空时回退 `_lastErrCache`，再回退 `logList` 里最近 error。
- `getLastErrMsg()`：同样优先根因。
- 根因缓存独立于 `logList`，不受 `logUpload` splice 清空影响，稳定可读。

### 7.3 语义说明

- 出票：非降级 errorSave 通常是"为什么失败"（如锁座失败、用卡用券失败、创建订单失败），后续降级 errorSave（转单-开始、换号-走换号等）是"怎么补救"——根因取最近一次非降级失败；
- 报价：errorSave 均为终止性失败（券库存为空、无可用卡、利润不足），无降级路径，根因即最近一次失败；
- 瞬态恢复：环节失败（errorSave）→ 重试/辅助锁座/换号成功后，成功终态（锁定座位-成功、创建订单-成功、取票码上传-成功等）重置根因缓存，后续失败从新错误算起；
- 分支前置：部分调用方在首个 errorSave 前会先 `warnSave`（如 `规则匹配-结果-为空`），`warnSave` 不写缓存，不影响根因。

### 7.4 调用点核对

| 调用点 | 现状 | 根因化影响 |
|--------|------|-----------|
| 各系列 `orderManage.transferOrder` 推送 failReason | 取最近 error（可能被"转单-开始"覆盖） | ✅ 修复 |
| `BaseTicketQueue.saveTicketRecord` 出票记录 err_msg/err_info | 同上 | ✅ 修复 |
| `BaseOfferPrice.buildErrorResponse` 报价记录 err_msg/err_info | 取最近 error（报价侧根因≈最近） | 基本不变 |
| `chenxing/h5ume/.../buyTicket` 中 `errInfo.includes("锁座失败/座位已销售")` 判断是否申请换座 | 取最近 | ✅ 根因更稳（锁座失败判断点前无其他非降级 errorSave，取值不变） |
| `chenxing/buyTicket` 无可用卡券时 `getLastErrMsg()` 拼错误串 | 取最近 | 根因更稳 |

> 结论：根因化后所有调用点语义都是"失败根因"，符合预期；不存在依赖"最近错误"的业务分支需保留 `_lastErrCache` 兜底。

1. **环节前缀**：采用 `[报价]环节名` / `[出票]环节名`（简洁，配合 `order_number` 过滤即可定位整条链路）。

### A.1 级别约定

### A.2 关键设计要点

- 抽样脚本：`node scripts/analyze-order-logs.js --days 1 --per-type 2 --output report.md`（对照 1.1 量化诊断指标）。
