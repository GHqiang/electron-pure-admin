# 报价规则影院 code 类型归一化（修复 2026-10-17 华联万柳订单命中已排除规则问题）

- 日期：2026-10-17
- 关联问题：订单 2026101712543566908 命中「华联全国」（rule 1755）固定报价 36，而该规则已配置排除影院「华联影城（万柳店）」
- 排查报告：`reports/analyze-issue/2026-10-17-2026101712543566908-固定报价规则排除影院失效.md`（本地，不入库）

## 一、根因

猎人平台接口返回的订单 `cinema_code` 是**数字**（如 `11063401`），而影院映射表（`cinema_code_match`）与报价规则里存的是**字符串**：

1. `getCinemaMatchInfo()` 用 `item.plat_cinema_code === plat_cinema_code` 严格比较 → 数字永远查不到映射；
2. `offerRuleMatch` 里「按 app_cinema_code 排除」的分支被整段跳过；
3. 退化到按影院名称匹配，而名称匹配内部同样要先按 code 查映射，取不到 `app_cinema_name` 时
   `cinemNameSpecial(undefined)` 抛 `TypeError`，被 `catch` 吞掉并返回 `undefined`；
4. 排除分支 `return !isExclude` 对 `undefined` 恒为 `true` → **规则被保留（fail-open）**。

生产对照：同一批排除规则下，字符串 code 的平台（蚂蚁/芒果/哈哈/省等）零命中被排除影院，猎人命中 26+12 次；真实函数复现中「数字 → 保留、字符串 → 排除」，唯一变量是类型。

## 三、核心变更说明

### 1. 新增 `src/utils/cinemaCode.js`

```js
export const normalizeCinemaCode = code =>
  code === null || code === undefined ? "" : String(code).trim();
export const splitCinemaCodes = codes => normalizeCinemaCode(codes).split(",").map(...).filter(Boolean);
```

统一「数字 / 字符串 / 空值 / 带空格」四种形态，避免各处各写一套比较。

### 2. `src/store/specialNameRule.js`

- `getCinemaMatchInfo(plat_cinema_code, app_name)`：code 两侧 `normalizeCinemaCode()` 后比较（`targetCinemaCode && ...` 保留空值守卫）。
- `getCinemaCodeFlag`、`getCinemaAppFlag` 首段 code 查找同样归一化。
- 该处是 `offerRuleMatch` 影院过滤、`cinemaMatchHandle` 名称匹配、`getTargetCinemaCommon`、万达直营判定等所有调用方的**唯一映射入口**，一处修复即可全覆盖。

### 3. `src/utils/utils.js`

- `offerRuleMatch`：
  - 入口 `const orderCinemaCode = normalizeCinemaCode(cinema_code)`，后续影院过滤统一使用；
  - 规则 code 清单改用 `splitCinemaCodes()`（去空格、去空项），替代原来的 `string.split(",").includes(...)`；
  - 映射查不到 `app_cinema_code`、而规则配了 `includeCinemaCodes`/`excludeCinemaCodes` 时：**按排除处理（fail-closed）** 并 `logger.errorSave("影院映射缺失，影院code规则无法判定，已按排除处理", {...})`——此前完全静默且 fail-open，是本次问题排查最耗时的点；
  - 名称兜底分支：`cinemaMatchHandle` 返回 `undefined`（映射缺失）时同样 fail-closed + `errorSave`。
- `cinemaMatchHandle`：取不到 `app_cinema_name` 时显式 `return undefined` 并 `console.error`，不再靠 `cinemNameSpecial(undefined)` 抛错后被 `catch` 吞掉。

### 4. 设计取舍

- **失败方向**：排除类规则在「无法判定」时改为排除该规则。理由：错报价（报出本不该报的价格、后续转单/亏损）比不出价更难发现、损失更直接；且该分支只有在「影院没有映射」时才会触发，而这种订单通常连 `app_name` 都解析不出来、进不了报价队列。
- **没有做**：入队处强制把 `order.cinema_code` 转 `String`。归一化已收敛到映射入口，改造订单对象类型反而扩大影响面（出票、换座、入库等多处依赖该对象）。
- **未改动**：`getRuleIdByPlat`（按 code 传给平台接口查询，无严格比较）、名称/影厅/影片等其它过滤层。

## 五、回归风险评估

| 风险 | 评估 |
| --- | --- |
| 影院 code 比较改动影响面 | `getCinemaMatchInfo` 等仅做类型归一化，字符串入参行为完全不变；只有「数字 code」从「查不到」变为「查得到」，即目标修复 |
