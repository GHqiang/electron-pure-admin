## 一、背景

8-14 部署新版（6.6.25）后，客户端 D3 观测日志（`network-error-20260814.log`）记录了 69 条"网络连接异常"。对日志的初步判断是"Chromium 6 连接槽限制导致排队超时"，但**日志本身无法直接证明**（服务器对超预算请求静默挂起，客户端看到的都是自身超时）。为确认 6 槽限制是否真实存在、是否就是故障机制，用项目自带 Electron（Chromium 真实网络栈）做了三组实测。

## 三、6 槽限制实测验证（test-6slot/，三组实验）

### 3.1 实验设计

- 测试服务器：Node 原生 http，统计**同时活跃 TCP 连接峰值** + 每请求到达时间偏移（[test-6slot/server.cjs](../../test-6slot/server.cjs)）
- 客户端：项目自带 Electron 30.0.4 渲染进程发 XHR（与生产 axios→XHR 同栈），对照用 Node 原生 http 客户端

### 3.2 实验 A：Electron 20 并发慢请求（每请求保持 3s）

```
并发 TCP 连接峰值 maxActiveSockets: 6    ← 铁证
并发请求峰值 maxActiveReqs: 6
/r0~r5   +0~2ms     到达（占满 6 条连接）
/r6~r11  +3038ms    到达（等首批 3s 完成，复用 socket#1~6）
/r12~r17 +6046ms    到达（等第二批）
/r18~r19 +9051ms    到达（等第三批）
```

20 个请求 = 4 批 × 3s ≈ 12s 串行完成，全程仅 6 条 TCP 连接反复复用。

### 3.3 实验 B：Node 原生客户端对照（同一服务器）

20 条连接全并发，全部 +1~3ms 同时到达，总耗时 3s。→ **排队是 Chromium 特有行为，与服务器/网络无关**。

### 3.4 实验 C：生产故障 1:1 复现（6 长预算占槽 + 14 短预算）

| | 客户端结果 | 服务器端看到 |
|---|---|---|
| 6 个长预算（8s，模拟 filmSchedules 20s） | 6/6 OK（+8041ms） | 全部到达，占满 6 槽 |
| 14 个短预算（1.5s，模拟 grab 5s / cached-ids 7s） | **14/14 超时**（+1508ms） | **0 个到达** |

### 3.5 实测结论

1. **Chromium 对同一 host 的 HTTP/1.1 连接上限 = 6，且无法放开**（硬限制）。
2. **XHR 超时计时从 send() 开始、包含排队时间**——队列深时短预算请求必挂，且**服务器从未收到**（与生产"服务器侧查不到 grab 但客户端超时"现象一致）。
3. **长预算请求占槽是短预算全灭的直接机制**：上游一慢，filmSchedules(20s)/real_time_seat(25s)/bid(25s) 占满 6 槽 → grab(5s)/cached-ids(7s) 排队超时 → 业务失败。
4. 生产日志 inFlight 高达 131 与 6 槽**不矛盾**：排队请求同样计入在途。

## 四、现状全面分析（问题清单，按优先级）

### P0-1 ~~抢票（grab）无客户端重试~~（修正：是设计，不加）
- 原判断：lieren 实例无 handleNetworkRetry 视为缺陷。
- **复查结论（8-14 二次走查）**：lieren 不加实例级重试是**有意的分层设计**：
  - grab（拉单）/bid（待出票列表）：`LierenAdapter.fetchOrderList` 失败 `return []`（不抛错），`BaseOrderFetcher.start()` 的 `while + mockDelay(5)` **5s tick 循环即重试机制**——加 HTTP 层重试会把单 tick 从 5s 拉长到 11s，反而降低抢单频率，且拥堵时重试照样排队（实验 C），无收益。
  - confirm（确认接单）：`LierenAdapter.confirmOrder` 特意 `throw error`（注释"确保上游 sendNewOrderMsg 的重试逻辑生效"），`BaseOrderFetcher.js:87` for 循环重试 3 次 + 失败微信推送。
  - offer/submit/unlock/transfer/applyForSeatChange：**写操作，幂等性未保证**，盲加 HTTP 重试可能重复报价/重复解锁/重复换座——不加重试是保守正确。
- **真正让抢票失败的机制**：P0-2 长占槽 + P1-1 请求量放大，拥堵期 tick 每轮都失败。修复根因后 tick 自动恢复，无需动 lieren。

### P0-2 服务器硬超时行为不统一：静默挂起 vs 返回 500
- proxyFactory（B2 改造，8-14）：硬超时 `ctx.respond=false` **静默挂起**，客户端只能等自身超时（grab 5s / wanda 25s / cardRecord 30s）——长预算请求占槽 20~30s（实验 C 证明这是短预算全灭的直接原因）。
- openApiFactory（B9）：超时 catch **返回 500**（openApiFactory.js:215）——与 proxyFactory 不一致；500 对 lieren（无重试）= 直接失败。
- 正确行为应是：**到预算即主动断开入站连接**（客户端立即收到网络错误 → 走重试路径 → 槽秒释放），两个工厂统一。

### 为什么不用主进程 Node 发起请求（规避 6 槽）？（8-14 评估，结论：不采用）
- 可行性：nodeIntegration 已开，主进程 Node http 无 6 槽限制（实验 B 实测 20 并发畅通）。
- **不采用的原因——瓶颈不在客户端 6 槽，而在服务器/上游**：
  1. 服务器 MySQL 连接池 `connectionLimit: 20`（实测 Threads_connected 24），并发请求上限受池约束；
  2. 上游代理 `HttpsProxyAgent maxSockets: 1`（proxyFactory.js:282，每代理 IP host 仅 1 socket）——客户端并发放大后，请求在**服务器侧**排队（HttpsProxyAgent 队列），队列只是从客户端搬到服务器；
  3. 服务器侧排队无客户端超时保护：客户端放弃后服务器仍占内存/连接/上游 socket，比客户端排队更危险；
  4. 6 槽实为"客户端限流保护"，放开它违背"减量"原则。
- 正确方向：缩短占槽时间（P0-2）+ 减少排队请求量（P1），而非打开更多连接。

### P1-1 失败路径 logUpload 放大请求（改为攒批上传）
- 每次网络失败：`saveFailLogToLocal`（IPC 本地盘，无害）+ `logUpload` → `POST /svpi/operaRecord/addList`（sv-api.js:254，30s 超时 + 超时重试 3 次 1s/2s/4s）。
- 8-14 爆发期 60+ 次失败 → 60+ 条 addList 追加请求（重试更多）——**inFlight 列表里 addList 占绝对多数即为证据**，失败越多请求越多。
- **保留云端可查 + 砍请求量**：addList 本就是批量接口 → 网络错误日志**内存攒批（30s 窗口或满 20 条）后一次上传**；上传失败不再重试（D3 本地文件已兜底）。云端查询路径不变，请求量降一个量级。

### P1-2 长轮询无退避
- filmSchedules 轮询在 failStreak 高达 6~10 时仍每 ~10s 继续发起（日志 t= 时间戳可见），持续占槽。
- networkMonitor 已有 failStreak 数据，可直接用于退避，但无人消费。

### P2-1 cached-ids 超时 5s→7s 无收益
- sv-api.js:89 `timeout: 7 * 1000`（11:26 日志尚为 5000ms）。7s 照样 22 条超时（13:47 起），只拖长排队占位。

### P2-2 观测缺陷
- inFlightUrls 只记录最近 15 条（看不到占槽者）；无"排队时长"指标（客户端发起到服务器到达的时差无法测）。

### P3-1 13:05:24 双条同秒 ERR_NETWORK
- 传输层瞬时失败（非超时非排队），独立小问题，与本次故障无关。

### P3-2 服务器侧实证（8-14 弹窗窗口 proxy_record，818 条）——占槽根因定案
用户执行 3 条 SQL 对表 13:40~13:53 窗口，结果：

**① err_type 分布（代理层故障合计 272/818 = 33%）**

| err_type | 条数 | 含义 |
|---|---|---|
| response_retry | 127 | 大量请求走代理重试路径（上游不稳定） |
| proxy_network_ETIMEDOUT | 96 | TCP 连接超时——代理 IP 连不上 |
| proxy_deadline_expired | 88 | 代理 IP 过期 |
| IP_UPDATE_ALL_RETRIES_FAILED / ATTEMPT_FAILED | 50 | 换 IP 失败 50 次 |
| deadline_expired / 无需更新走重试 / 提取ip质量不高 | 35 | 其它代理异常 |

**② 满 20s 预算的占槽长请求**：filmschedules.get / scheduleseats.get / cinemafilms.get 窗口内 **30+ 条 requestTime 恰为 20000ms**（满预算超时），另有大量 6~19s 慢请求——每个占服务器 20s、占客户端 1 槽 20s，6 槽被占满后短预算请求（grab 5s / cached-ids 7s）排队超时。

**③ 对照**：同窗口 authn.refresh（token 刷新）正常 300ms、慢时 5~19s——代理池整体质量差，非单接口问题。

**④ 总量对照**：服务器处理 818 条 vs 客户端 65 条失败——服务器忙在"代理重试风暴"，非业务并发。

**定案结论：占槽主因 = 代理 IP 池失效/响应慢（33% 代理故障 + 满预算长请求），业务并发仅放大器。** 与用户历史观察一致：以前弹窗伴随带宽打满（瓶颈在传输层，升带宽即好）；带宽充足后瓶颈暴露在上游代理池（青果短效 IP 质量波动、间歇失效）。

**隐藏设计问题**：fenghuang 客户端超时 20s = 服务器转发预算 20s（openApiFactory B9 非 grab 首次 20s），**零余量**——服务器 20s 满预算超时后客户端同时超时，上游 19s 才返回也来不及回传。

### P3-3 关键历史对比：为什么"升带宽"从有效变无效（8-13 部署副作用定案）
用户核心疑问：以前代理质量也差，升带宽就能解决弹窗；8-13/8-14 改动后升带宽无效。git 对比 8-13 部署（be8fae4）前后 proxyFactory：

| | 8-13 之前（5dc37b4） | 8-13 19:51 部署后（B2/B8） |
|---|---|---|
| 代理失效处理 | axios timeout 25s 单次超时 → 换 IP 重试（maxRetries=3，每次独立 25s） | **B2：20s 共享预算内反复换 IP 重试**（最多 5 次 × 1s 间隔，预算耗尽才失败） |
| 请求前检查 | 无——过期 IP 直接请求 | **B8：deadline 检查，过期则预算内循环换 IP（最多 5 次 × 1s）** |
| 硬超时 | 无（可挂 130s） | AbortController 剩余预算 |

**因果链**：
1. 8-13 前：弹窗主因 = 带宽打满（传输层拥塞）→ 升带宽 = 消除传输瓶颈 = 不弹；代理失效只是单次 25s 超时，偶发且被带宽瓶颈掩盖。
2. 8-13 后：带宽充足 → 传输层不是瓶颈 → 暴露 B2/B8 副作用——青果短效 IP 过期是常态，**每个请求都可能先花 5~10s 循环换 IP（B8），换到坏 IP 后请求失败，预算内再换再试（B2），烧满 20s**；服务器"换 IP 重试风暴"（818 条窗口内 response_retry 127 + 代理故障 272 + IP 更新失败 50）。
3. 客户端多实例并发 → 6 槽被烧 20s 的请求占满 → 短预算排队超时弹窗。**升带宽解决"客户端↔服务器"传输，解决不了"服务器↔代理池烧 20s 预算占槽"→ 所以无效。**
4. 8-14 客户端 6.6.25 又叠加 D3 logUpload 反馈循环 + 5xx/超时重试放大（×2~4）。

**结论：整改必须同时缩短服务器烧预算时间（20s→10s、换 IP 5→2 次、间隔 1s→300ms）+ destroy 入站连接 + 客户端砍反馈循环。**

## 五、整改方案（确认版 v1.4，2026-08-14 预算误杀风险复核后修订）

> 原则：6 槽无法放开 → 目标 = **缩短占槽时间 + 减少排队请求量 + 失败可自愈**。
> v1.4 修订：**撤销"预算 20s→10s"**（会误杀 connect 成功但上游响应 10~20s 的正常慢请求，重演 8-14 出票失败）；病根重新定位：**占槽 20s = 换 IP 重试 5 次 × (connect 3s + 间隔 1s) 恰好烧满预算**，而非预算本身。修正为：预算不动，换 IP 改快速失败（2 次、无间隔）。

### 方案 1（P0，服务器）：换 IP 快速失败 + destroy（B2/B8 参数修正，预算不动）
- 病根：代理失效时 `HttpsProxyAgent timeout: 3s`（connect 超时）→ 换 IP 重试 5 次 × (3s + 1s 间隔) = 20s 恰好烧满预算 → 占槽 20s → 6 槽满 → 短预算排队超时。
- 改动：
  1. **换 IP 上限 5 → 2 次**（proxyFactory.js 换 IP 循环 + B8 请求前 deadline 换 IP 循环）；
  2. **换 IP 间隔 1s → 0**（连续尝试，不再人为拖长）；
  3. **预算 TOTAL_BUDGET_MS 保持 20000**（connect 成功但上游 10~20s 慢响应能完整返回，不误杀出票/锁座等关键接口）；
  4. proxyFactory.js:480 与 openApiFactory.js catch：硬超时/预算耗尽 `ctx.res.destroy()`（客户端提前收到错误走重试，不等满自身超时）；
  5. openApiFactory 非 grab 转发预算 20s → 15s（客户端 20s 超时留 5s 回传余量——现状转发 20s + 回传必超客户端 20s，零余量必丢）；grab 保持 4s。
- 效果：代理失效时单请求占槽 **20s → 6~8s**（connect 3s + 换 IP 3s）；6 槽 8s 内周转 → cached-ids(7s) 排队后能活；grab(5s) 失效期仍可能超时但 tick 循环兜底；**正常慢请求不被误杀**（预算未动）。
- 风险：代理池整体差时快速失败 → 客户端重试（退避 1s/3s，sv/wanda/fenghuang maxRetries 2~3）+ lieren tick 循环兜底，请求量放大但占槽短、服务器资源占用低（AbortController 已释放 socket）。
- 验证：jest + 实验 C 复跑（6 长预算改为"快速失败"模式后 14 短预算存活）+ 生产观察弹窗下降、出票失败不反弹。

### 方案 2（P1，客户端）：网络错误日志攒批上传
- 改动：sv/lieren/wanda 等错误拦截器网络错误分支，日志进内存队列（30s 窗口 / 满 20 条触发一次 `logUpload`），上传失败不重试（D3 本地兜底）。
- 效果：云端查询路径不变，请求量降 30 倍，砍掉反馈循环。
- 验证：观察 inFlight 峰值回落、operaRecord 网络错误记录仍可查。

### 方案 3（P1，客户端）：长轮询按 failStreak 退避
- 改动：filmSchedules 轮询（fenghuang 系）failStreak ≥ 3 时暂停/降频（复用 networkMonitor）。
- 依据：服务器实证 30+ 条满预算 filmschedules 请求——连败时继续每 10s 发起只会持续占槽。
- 验证：生产观察轮询失败时不再持续占槽。

### 方案 4（P2，客户端）：cached-ids 超时维持 7s（撤销改回 5s）
- 修订：占槽缩短到 6~8s 后，7s 比 5s 更能活过排队——原"改回 5s"判断基于占槽 20s 时代，作废。

### 方案 5（P2，服务器）：代理 IP 健康管理加强
- 现状：已有 deadline 检查（B8）+ 失败换 IP，但窗口内仍有 96 条 ETIMEDOUT（失效 IP 被继续使用）与 50 次换 IP 失败。
- 改动方向：失败 IP 即时拉黑（同批次 IP 标记降级）；换 IP 失败时提高告警；代理池预检频率与字典配置化。
- 验证：观察 ETIMEDOUT / deadline_expired 占比下降。

### 上线顺序
方案 1（服务器）→ 方案 2+3（客户端，同包发布）→ 方案 4/5（观察后迭代）。

## 七、v1.5 修订：移除 500 重试（2026-08-14 用户实证反馈）

### 背景
6.6.25（5xx 重试 + 8-14 静默挂起服务器）部署后用户反馈**弹窗更频繁**。

### 机制
代理失效 → 服务器静默挂起 20~30s → 客户端 ECONNABORTED → 5xx/超时重试 2 次（1s/3s 退避）→ **每个业务请求变成 3 个请求、每个挂 20~30s** → 6 槽被"3 倍挂起请求"占满 → 短预算全部排队超时 → 弹窗风暴。5xx 重试的本意（8-14 出票失败 97 单）是修复"服务器返 500 → 客户端不重试"，但**修错了层**——正确修复是 v1.4 服务器 destroy（不再返 500），而非客户端接受 500 重试。

### 决策
| 状态码 | 结论 | 理由 |
|---|---|---|
| **500** | **移除重试** | v1.4 destroy 后代理失败不再返回 500，500 只剩真实服务器 bug，重试无意义且是弹窗放大主因 |
| 502/503/504 | 保留 | 服务不可用抖动时重试可恢复；sv-request"连续 10 次失败退出登录"依赖失败计数，移除会导致抖动误触发退出登录 |
| 408 | 保留 | 7-18 猎人 429/408 限流修复 |

### 改动
- `src/utils/http/retry-helper.js`：`(500|502|503|504)` → `(502|503|504)`
- `src/common/tests/retry-helper.test.js`：500 → false 断言（31/31 通过）
- 部署顺序：**先服务器 v1.4（destroy）→ 再发前端**（中间窗口期旧 6.6.25 的 5xx 分支对真实 500 重试无害）

## 八、8-15 生产事故记录：attachTracking TypeError（已修复，6.6.28 发布）

### 事故
- 8-15 发版（6.6.27）后，客户端大量 `Cannot read properties of undefined (reading 'url')`，8-15 16:00 单小时 1953 条，累计 1975 条（reading 'url' 1953 + cinemaPlanDto 22）。

### 根因（两层）
1. **attachTracking 追加拦截器收到业务数据**：4 平台原生成功拦截器 `return data?.data`（业务数据，非 axios response）；attachTracking 在文件末尾**追加注册**（后执行），裸访问 `response.config.url` → `response.config` 为 undefined → TypeError。
2. **为何 6.6.25 没炸**：6.6.25 打包时 4 平台尚未接入 attachTracking（8-14 晚接入，随 6.6.27 发布）。8-14 全天 0 条 → 8-15 08:05（6.6.27 上线）起出现，时间线吻合。
3. **附带发现**：chenxing `offerManage.js:249` / `buyTicket.js:207-210` 裸访问 `targetSeatRes.cinemaPlanDto`（targetSeatRes 为 undefined 时抛 reading 'cinemaPlanDto'，8-15 22 条）。

### 修复（6.6.28）
| 文件 | 修复 |
|---|---|
| `src/common/networkMonitor.js` attachTracking | 成功/失败分支均加 `response?.config?.url` / `error?.config?.url` 可选链防御（一处覆盖 4 平台） |
| `src/common/tests/networkMonitor.test.js`（新增） | 6 个用例：收到业务数据/undefined/业务 reject 值不抛错 + axios response 正常 resetFail——回归防护 |
| `chenxing/offerManage.js:249` / `buyTicket.js:207-210` | `targetSeatRes?.cinemaPlanDto` 等可选链防御 |
