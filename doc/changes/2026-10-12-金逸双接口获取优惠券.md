# 金逸系列双接口获取优惠券变更说明

- 日期：2026-10-12
- 需求来源：金逸系列取券需从两个接口获取——原 `vistax/voucher/list` + 新增 `user/voucher/list`（用户券包，含团购券），并适配新接口字段、把中转义中文解成明文

## 一、背景

金逸系列此前仅通过 `vistax/voucher/list` 获取优惠券，返回 `data` 为券数组，字段为
`show_name` / `show_desc` / `coupon_code` / `expire_time`。

现新增用户券包接口 `user/voucher/list`，返回结构完全不同：

| 维度 | 旧接口 `vistax/voucher/list` | 新接口 `user/voucher/list` |
|---|---|---|
| `data` 结构 | 券数组 | `{ unused, used, disabled }` |
| 券名 | `show_name` | `voucher_name`（`\uXXXX` 字面量，需解中文） |
| 券描述 | `show_desc` | `voucher_desc`（同上） |
| 券码 | `coupon_code` | `voucher_code`（另有 `voucher_code_mask` 掩码，不可用于核销） |
| 过期时间 | 日期字符串 | **秒级时间戳**（如 `1796054400`）+ `expire_time_string` |
| 张数 | — | `voucher_num`（样例为 1） |

`couponCode` 会直接作为 `quan_code` 传给 `priceCalculation` 参与核销（`buyTicket.js`），
因此新接口必须取**真实券码** `voucher_code`，不能用掩码。

## 三、核心变更说明

### 1. 结构自适应拍平（`quanListAdapter.js`）

`normalizeQuanList(data)` 自动判别结构：数组按旧接口映射；`data.unused` 按新接口映射并**只取
`unused`**（`used`/`disabled` 忽略）。两者产出同一份券对象：

```js
{
  ...原始字段,          // 保留 voucher_num 等原始字段便于日志排查
  couponName,          // show_name  | voucher_name（已解中文）
  couponDesc,          // show_desc  | voucher_desc（已解中文）
  couponCode,          // coupon_code | voucher_code（真实券码）
  endDateTime          // 统一毫秒时间戳
}
```

### 2. 中文解成明文（`decodeUnicodeStr`）

接口中文字段可能以 `\uXXXX` 字面量下发，按正则解成明文；**已是明文时原样返回（幂等）**，
非字符串入参原样返回不抛异常。覆盖 `voucher_name` / `voucher_desc`：

```
"\\u56e2\\u8d2d\\u5238"  →  "团购券"
```

### 3. 秒级时间戳修正（`parseQuanExpireTime`）

新接口 `expire_time` 为**秒级**时间戳，直接 `new Date(1796054400)` 会解成 1970 年，进而破坏
「优先使用快过期的券」排序与券期筛选。现统一转换：数值小于 1e11 视为秒级 ×1000，毫秒级原样保留，
日期字符串仍走 `new Date()`。

### 4. 双接口并行 + 合并去重（`getQuanListFromBothApis`）

- 两接口**并行**发起（`Promise.allSettled`），不串行叠加耗时；
- 合并语义：**按券码去重取并集，旧接口优先**（`mergeQuanList`），避免同一张券被两个接口重复计数
  导致券库存虚高、误报价；
- 合并时**跳过无券码（`couponCode` 为空）的条目**：此为口径收紧，旧实现不过滤。无券码本就无法
  作为 `quan_code` 提交核销，旧实现会把它计入券库存并在选券时产出空券码；现直接剔除。
- 新接口为补充来源，调用时传 `silentError: true`，失败不弹全局错误提示；登录失效仍会正常告警。

### 5. 单侧失败隔离（本次实现中修正的关键点）

`Promise.allSettled([a(), b()])` 的数组字面量会**先同步求值**：若某一侧同步抛错（例如
`appApi.getQuanListByUser` 缺失），异常会在 `allSettled` 之前抛出，被外层 `catch` 兜住并
`return []`，导致**另一侧本已取到的券被一并丢弃**。现已把两侧各包一层 thunk：

```js
Promise.resolve().then(() => this.appApi.getQuanList(oldParams)),
Promise.resolve().then(() => this.appApi.getQuanListByUser(...))
```

同步抛错即转为该侧的 rejected，另一侧结果不受影响。该场景已有对应用例（未包 thunk 时 2 例失败，
`Array []`；包 thunk 后通过）。

### 6. 日志口径

- 新增 `双接口取券来源统计`：`{ oldApiTotal, newApiTotal, mergedTotal }`，可直接判断团购券是否
  已从新接口取到；
- 新增 `获取用户券包优惠券列表异常(不影响原接口取券)`（`infoSave`）；
- 保留既有 `获取未使用券返回-示例仅展示前5条`（总数 + 前 5 条样例，避免全量券码撑爆日志）、
  `获取优惠券列表为空`、原接口失败沿用 `获取优惠券列表异常`（`errorSave`）；
- 新增外层兜底 `双接口获取优惠券列表异常`（`errorSave`）：仅当适配/合并阶段抛错才走到
  （`allSettled` 本身不 reject，故正常网络/接口失败不会触发），返回空券列表；
- 以上 `errorSave` 的 meta 一律传**原始错误对象**（`{ error, params }`），**不预先 `formatErrInfo`**。
  原因：`logger.getLastErrMsgAndInfo()` 会对 `meta.error` 统一再做一次 `formatErrInfo`
  （`logger.js:271`），若此处预格式化，字符串会被二次 JSON 转义，落库 `err_info` 出现转义引号。
  项目内既有 11 处 `{ error: formatErrInfo(...) }` 写法同受此影响，属存量问题，本次未一并改动。
- `getQuanList`（金逸模块内无调用方，属存量未用方法）不再打印整份原始响应 `获取优惠券列表返回`，
  改由来源统计替代；其余签名与返回结构不变。

### 7. 顺带发现（未修改，供决策）

`jinyi-request.js` 的 `retryWhitelist` 现有条目**全部**含 `channelCode`/`cinema_id` 占位符，而
`checkUrlCanRetry` 比对的是请求拦截器**替换占位符之后**的 `config.url`（已变成真实
channelCode/cinema_id），因此这些条目实际永不匹配，金逸查询类接口目前不会触发网络重试。

本次仅把新增接口的白名单项写成替换后仍存在的路径片段 `/user/voucher/list/`，使其真正生效；
**未改动其余存量条目**（调整后会让所有金逸接口开始重试，属独立的行为变更，需另行评估）。

另：项目内既有 11 处 `errorSave(..., { error: formatErrInfo(error) })` 与若干
`errorSave(msg, formatErrInfo(error))` 写法，同样会让 `err_info` 落库出现二次转义（同 §6 原因）。
本次仅保证新增代码不引入该问题，**未批量整改存量写法**，需另行评估后统一处理。

## 五、回归风险评估

| 风险 | 评估 | 缓解 |
|---|---|---|
| 新接口在部分影院/channelCode 不存在 | 中：新接口为补充来源，失败已隔离，仅少一批团购券 | 新接口失败只记 `infoSave` 不阻断；`双接口取券来源统计` 中 `newApiTotal` 可观测 |
| 券库存口径变化（并集去重后券数可能变化） | 低：去重避免同券重复计数，库存更真实；团购券纳入后库存可能上升 | 观察报价侧券库存与 `面额券不足` 日志；必要时以 `oldApiTotal`/`newApiTotal` 定位来源 |
| `voucher_num > 1` 未按张数展开 | 低-中：样例为 1，本次按「1 券码 = 1 券」计数（与旧接口口径一致）。若线上存在一码多张，券库存会被低估 | 上线后以 `双接口取券来源统计` 与券面核销结果比对；若出现 `>1` 需单独评估展开与 `quan_code` 去重规则 |
| 同券在两接口券码不一致（无法去重） | 低：去重依赖券码相同，若两接口编码规则不同则同一张券会计两次 | 观察券库存是否异常虚高；异常时可改为「券名+券描述+过期时间」辅助去重 |
| 无券码券被过滤（口径比旧实现更严） | 低：旧实现不过滤，此类条目会被计入券库存、甚至产出空券码去核销；现直接剔除，库存计数可能小幅下降 | 属预期修正（无券码本就无法作为 `quan_code` 提交）；若发现某券类型库存骤降，核对接口返回中 `coupon_code`/`voucher_code` 是否为空 |
| 新接口 `msg` 非 `successfully` 被拦截器判错 | 低：样例为 `successfully`；拦截器按该字段判成功 | 失败会落 `获取用户券包优惠券列表异常` 日志，便于及时调整判定 |
| 存量 `getQuanList` 调用方 | 极低：金逸模块内该方法无调用方（全仓 grep 确认仅定义处） | 仍保留原签名与返回结构 |
| 非金逸系列 | 无：改动仅落在 jinyi 目录 + jinyi-api/白名单，未触碰共享模块 | 全量测试回归 |

## 六、上线观察指标

1. 常规打包发布（`yarn build`）→ 客户端更新生效；
2. 关注 `双接口取券来源统计`：`newApiTotal` 是否稳定取到团购券（预期 >0）；
3. 关注 `获取用户券包优惠券列表异常(不影响原接口取券)` 频次：持续出现说明该影院/渠道不支持新接口，
   功能自动退化为原单接口行为，无需回滚；
4. 对比上线前后金逸出票成功率与 `面额券不足` 日志：团购券纳入后应持平或上升；
5. `voucher_num` 若在日志样例中出现 `>1`，按风险表单独评估。
