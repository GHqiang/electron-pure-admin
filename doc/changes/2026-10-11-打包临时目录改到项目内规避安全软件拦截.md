# 2026-10-11 打包临时目录改到项目内（规避安全软件拦截 esbuild 删除临时文件）

## 问题现象

`yarn build:staging` 在渲染层打包完 2754 个模块、进入 renderChunk 降级阶段时中断，报错：

```
error during build:
Error: [vite:esbuild-transpile] remove C:\Users\24675\AppData\Local\Temp\esbuild-<32字节随机值>: Access is denied.
```

`release/` 目录不会生成，版本号脚本已经把版本 +1（失败也照样 +1）。

## 根因

1. `build.target = "es2015"` 会让 vite 在 `renderChunk` 阶段对**每个 chunk** 调一次 esbuild 做降级（插件名 `vite:esbuild-transpile`）。
2. 当 chunk 源码 **>1MB** 时，esbuild 的 JS 层会先把源码写到 `os.tmpdir()` 下的 `esbuild-<随机值>`，由 esbuild 的 Go 服务进程读完后删除该临时文件（`node_modules/esbuild/lib/main.js` 的 `fsAsync.writeFile` → Go 侧 `os.Remove`）。删除失败即整个 transform 失败，vite 视为构建失败。
3. 本机安全软件（360 杀毒 7.0.0.1060，`ZhuDongFangYu` 主动防御服务运行中，加载 `360FsFlt.sys`/`360AvFlt.sys`/`360Box64.sys`）**按程序**拦截了 `esbuild.exe` 在“自身/工作目录之外”删除文件的操作，返回 ERROR_ACCESS_DENIED。esbuild 对该删除不做重试，因此每次都必挂。

对照实验（同一目录、同一时刻）：

| 临时目录 | 串行 8 次 | 并发 4 次 |
| --- | --- | --- |
| `%TEMP%` | 0 过 / 8 失败 | 4 失败 |
| `D:\probe-tmp` | 0 过 / 8 失败 | 4 失败 |
| `D:\Electron\build-tmp`（已在 360 信任区内） | 0 过 / 8 失败 | 4 失败 |
| **项目目录内** | **8 过 / 0 失败** | **0 失败** |

补充证据：同目录同时刻 PowerShell（`Remove-Item`）与 node.exe 都能正常删除，只有 `esbuild.exe` 被拒 → 是“按程序生效”的 HIPS 类规则，不是文件 ACL/权限损坏，也不是 DSH 会话沙箱（本机普通 cmd 里同样复现）。

## 修改文件清单

| 文件 | 变更 |
| --- | --- |
| `package.json` | `build`、`build:staging` 两个脚本开头追加：创建并使用项目内 `.build-tmp` 作为 TEMP/TMP（`node -e mkdirSync` + `set "TEMP=%CD%\.build-tmp"` + `set "TMP=%CD%\.build-tmp"`） |
| `.gitignore` | 追加 `.build-tmp/`（该文件本身已在 .gitignore 列表内，不入库） |

## 核心变更说明

- 让 vite/esbuild/yarn icon/electron-builder **整条打包链**的临时目录都落在 `D:\Electron\electron-pure-admin-fix\.build-tmp`，即 `esbuild.exe` 允许删除的范围内，从而绕开拦截。
- 脚本开头用 `node -e "require('fs').mkdirSync('.build-tmp',{recursive:true})"` 幂等建目录（cmd 的 `mkdir` 在目录已存在时会返回非 0，会打断 `&&` 链）。
- 不改 `dev`/`browser:dev`：开发态不会出现 >1MB 的 transform 输入，走不到这条路径。
- 未改 `browser:build`：如需同样处理，加同样前缀即可。
- `set` 语法在 POSIX shell 中是空操作（只设置位置参数），不会破坏其他平台上的脚本解析；Windows 上由 yarn 默认的 cmd 执行（已实测子进程拿到 `TEMP=D:\Electron\electron-pure-admin-fix\.build-tmp`）。

## 测试结果

1. `yarn build:staging` **exit code 0**，全流程（vite build → yarn icon → electron-builder NSIS）耗时 103.97s。
2. 产物：`release/6.6.62/electron-pure-admin_6.6.62.exe`（111.3MB）、`win-unpacked/electron-pure-admin.exe`（169.1MB）、`latest.yml`、`*.blockmap`。
3. `.build-tmp` 内 **esbuild 临时文件残留 0**（仅剩 yarn/tsx 自己的缓存目录，已清理）；`%TEMP%` 不再新增 esbuild 残留。
4. 修复前对照：同样命令连续 6+ 次全部在 `remove ...: Access is denied.` 处失败，每次留下 4 个同尺寸残留文件（1382945/1768766/2421974/2824889 字节）。

## 回归风险评估

- **影响面小**：只改打包脚本的临时目录与一条 ignore 规则，未动任何业务代码、依赖与构建产物结构；`dist`/`dist-electron`/`release` 输出路径不变。
- **开发态无影响**：`yarn dev` 脚本未改。
- **磁盘**：`.build-tmp` 会保留少量缓存（yarn/tsx），可随时整目录删除；已加入 .gitignore，不会污染仓库。
- **未根治**：根因是机器上的安全软件策略（360 主动防御）。若 360 后续再变更策略，或换机器/换同事机器打包，需要重新验证；彻底根治仍需在 360「主动防御/程序规则」里放行 `node_modules\@esbuild\win32-x64\esbuild.exe`（“信任区/查杀白名单”无效，已实测）。
- **版本号提示**：失败重试会把 `package.json` 与 `public/platform-config.json` 的版本号一路 +1（本次已到 6.6.62）；要出指定版本，先把两个文件改到目标版本 -1 再打包。
- 遗留：`%TEMP%` 下仍有前几次失败留下的 12 个 `esbuild-*` 残留（约 24MB），可手动 `del /q "%TEMP%\esbuild-*"` 清理。
