# 渲染进程白屏防护与崩溃自愈整改说明

> 日期：2026-08-07
> 状态：**已实施（B/C/D + 本地兜底日志）**
> 关联方案：《2026-08-07-渲染进程崩溃自愈与队列自动恢复方案.md》
> 关联问题：6.6.8 用户 1 天内连续 2 次白屏（8/6 23:40 前后、8/7 12:25 前后），白屏期间报价/出票队列完全停摆，需手动重启程序恢复。
>
> 目标：**从源头阻断渲染进程内存持续增长（OOM 白屏根因），并在崩溃发生后自动恢复（窗口自愈 + 队列自动拉起），同时保留排查证据（上传失败日志本地落盘）。**

---

## 一、背景与根因分析

### 1.1 白屏现象（用户反馈）

| 项 | 第一次 | 第二次 |
|----|--------|--------|
| 白屏区间 | 8/6 23:40:57 → 8/7 07:09:39 | 8/7 12:25:00 → 13:44:25 |
| 白屏前最后订单 | mahua/ume_h5/wanxiangh5 报价 | haha/ume_h5/wanxiangh5 报价 |
| 白屏期间 | 完全无订单（报价+出票队列全停） | 同左 |
| 恢复方式 | 用户手动重启程序 | 同左 |

### 1.2 根因方向（已排查结论）

- 白屏 = **渲染进程崩溃/无响应**。6.6.8 代码无死循环、无无限递归（已逐文件排查）；崩溃与具体订单无强因果。
- 最可能的机制：**渲染进程内存持续增长 → OOM**：
  1. 队列级 logger（`BaseTicketQueue.this.logger`）长期存活，每次订单 `infoSave` 3 条 + `logUpload`
  2. `logUpload` 上传失败时 **`logList` 不清空**（`utils.js` 原 `break` 保留），长时间运行累积
  3. 日志量大（6.6.8 全系列日志含大对象：手机号级库存明细、完整规则列表、座位布局等）→ 上传慢/超时概率高 → 失败滞留更多 → 内存增长更快
- **6.6.10 用户不白屏的反证**：6.6.10 的日志优化（`d008dd9d`）大幅裁剪了日志体积（`trimRuleForLog`、券列表精简、console 大对象删除），同样场景下内存增长速度降低 1~2 个数量级，达不到 OOM 阈值。这支持了"日志量→内存累积→OOM"的根因判断。
- **关键缺陷**：主进程无任何 `render-process-gone` / `unresponsive` 监听，渲染进程一崩，窗口永久白屏，只能手动重启。

## 二、本次整改内容

### 2.1 B：logList 上限保护（阻断内存无限增长）

**文件**：`src/common/logger.js`

`_addToLogList` 增加 logList 上限保护（**500 条**），超过上限丢弃最旧日志，保留最新日志便于排查：

```js
_addToLogList({ opera_time, des, level, info }) {
  this.logList.push({ opera_time, des, level, info });
  // 上限保护：logUpload 上传失败时 logList 不清空，长时间运行会导致渲染进程内存持续增长（OOM 白屏根因）
  const MAX_LOG_LIST = 500;
  if (this.logList.length > MAX_LOG_LIST) {
    this.logList.splice(0, this.logList.length - MAX_LOG_LIST);
  }
}
```

> 效果：即使日志上传长期失败，单个 logger 的 logList 内存占用有界（500 条），不再无限累积。

### 2.2 C：logUpload 上传失败时强制清空（不再保留滞留）

**文件**：`src/utils/utils.js`

`logUpload` 上传失败分支由"保留 logList（break）"改为"清空已处理批次"：

```js
} catch (error) {
  console.error("日志上送异常", error);
  hasError = true;
  lastError = error;
  // 本地兜底：上传失败的日志落盘（见 2.5）
  try {
    saveFailLogToLocal(batch, order);
  } catch (e) { /* 静默 */ }
  // 上传失败时强制清空已处理批次，避免 logList 无限累积（OOM 白屏根因）
  logList.splice(0, batchSize);
  break;
}
```

> 说明：失败日志不再保留重试（重试大概率同样失败），微信告警（msgType 9）兜底通知人工关注；日志内容已本地落盘（2.5）不丢失。

### 2.3 D1：主进程崩溃自愈（窗口自动恢复）

**文件**：`electron/main/index.ts`

新增 `setupCrashRecovery(win)`，在 `createWindow` 中启用：

| 能力 | 实现 |
|------|------|
| **崩溃自愈** | 监听 `render-process-gone`，自动带恢复标记重载页面（登录信息在 localStorage，不丢失） |
| **无响应自愈** | 监听 `unresponsive`，15 秒后强制 reload（统一走 `reloadWithRecovery("unresponsive")`，计入防循环计数，防"死循环→reload→再死循环"无限循环）；期间自行恢复（`responsive`）则取消 |
| **防循环** | 5 分钟窗口内崩溃 ≥2 次 → 停止自动恢复，弹窗提示人工介入；`render-process-gone` 先取消未决的无响应恢复定时器，避免"先无响应后崩溃"场景下 15 秒后对 reload 后的新页面误判连续崩溃 |
| **本地留证** | 崩溃事件（真实崩溃 / crash-test 模拟）均写入 `userData/logs/crashEvent-YYYYMMDD.log`，离线可查 |
| **取证传递** | 恢复时通过 URL query 传递 `crashRecovery=1&crashReason=xxx` 给渲染层 |

### 2.4 D2/D3：队列快照 + 自动恢复

**文件**：
- `src/views/queueManage/index.vue`（快照写入/清除）
- `src/main.ts`（恢复标记消费）
- `src/common/queueRestore.js`（新增，自动恢复公共函数）

| 环节 | 实现 |
|------|------|
| **快照写入** | `oneClickStart` 成功时，将已启动的报价平台列表 + 出票影院列表写入 `localStorage("__queueSnapshot")` |
| **快照清除** | `oneClickStop` 时清除快照，避免崩溃自愈误恢复已停止的队列 |
| **启动逻辑同源** | 队列启动抽为公共函数 `startQueues()`（`queueRestore.js`），**一键启动与崩溃自愈共用同一套逻辑**：启动前从持久化的平台规则表（`platQueueRule`）取 platToken 写回 `platTokens` store——reload 后 store 初始为空，haha/mangguo 等请求层直接读 store token，不写回则自愈后报价必失败 |
| **自动恢复** | 渲染层挂载后检测 `crashRecovery` 标记 → 3 秒后调用 `autoRestoreQueues()`：按快照调 `startQueues()` 重建报价/拉单/出票队列并 `start()`，无 token / 无登录信息的平台跳过 |
| **不重复上报** | 自动恢复不触发 `svApi.updateUser`，避免副作用 |

> 登录信息（`userInfo`/`loginInfoList`/平台 token）均在 localStorage，reload 后保留，**无需重新登录**；自动恢复后队列即续跑。

### 2.5 本地兜底日志（上传失败落盘，保留排查证据）

**文件**：
- `src/common/localFailLog.js`（新增，落盘逻辑）
- `electron/main/index.ts`（新增 `ipcMain.handle("save-fail-log")`）
- `src/utils/utils.js`（失败分支调用）

| 点 | 处理 |
|----|------|
| **文件路径** | `%APPDATA%\electron-pure-admin\logs\` 下按用途分文件（按天）：`logUploadFail-YYYYMMDD.log`（上传失败兜底）、`queueRestore-YYYYMMDD.log`（队列恢复摘要兜底）、`crashEvent-YYYYMMDD.log`（崩溃事件留证） |
| **内容格式** | 逐条 JSON 行：原日志 + `local_save_time` + 上传方信息（plat/app/order/type）；单条序列化失败（如 info 含循环引用/函数）降级为占位行，不影响其余日志落盘 |
| **大小控制** | 单文件超 20MB 自动截断（保留最新批次 + 截断提示） |
| **架构** | 渲染层经 preload 暴露的 `ipcRenderer.invoke("save-fail-log")` 调主进程写盘（渲染层不直接操作文件系统） |
| **失败静默** | 写盘失败只记 console.error，不影响 logUpload 主流程；异步 fire-and-forget 不阻塞 |

### 2.6 配套修复：preload 加载失败（测试自愈链路时发现并修复）

自愈验证时发现渲染层 `window.ipcRenderer` 始终为 `undefined`，主进程诊断日志报 `preload 加载失败: require() of ES Module ... not supported`，根因与修复：

| 问题 | 原因 | 修复 |
|------|------|------|
| preload 构建产物为 ESM 语法 | `package.json` 声明 `"type": "module"`，vite-plugin-electron 未显式指定 preload 输出格式时产出 ESM `.js` | 构建配置显式指定 `output.format: "es"` + `entryFileNames: "index.mjs"`（Electron 28+ 支持 ESM preload 脚本），主进程引用 `preload/index.mjs` |
| `contextBridge.exposeInMainWorld` 未生效 | `contextIsolation: false` 时 contextBridge 注入不可靠（electron#21437） | preload 直接挂载 `window.ipcRenderer`（共享上下文，必然生效），并补 `window.electron = { ipcRenderer }` 兼容旧用法 |

> 修复后 `electron/preload/index.ts` 的 `window.ipcRenderer` 直接可用，业务代码统一走 `window.ipcRenderer`；该问题在 6.6.8 之前的旧包中即存在（`window.ipcRenderer` 一直不可用），本次顺带修复，`save-fail-log` 等主进程通道得以在渲染层正常调用。

## 四、如何模拟崩溃自愈场景（测试方法）

项目主进程开启了 `nodeIntegration: true`（`electron/main/index.ts`），渲染进程可直接执行 Node API，因此可以在**开发模式或生产环境**（打包后的 exe）下用 Electron 官方崩溃模拟 API 逐项验证自愈能力：

### 前置条件

```bash
npm run dev   # 开发模式；生产环境则直接运行打包后的 exe（DevTools 打开方式见下）
```

> 生产环境打开 DevTools：菜单栏"开发者工具"（`electron/main/index.ts` 中 `appMenu` 默认保留该菜单项）→ Ctrl+Shift+I，或菜单 显示→开发者工具。然后执行下述 `crash-test` 命令即可在生产包上验证完整自愈链路。

### 测试 1：模拟渲染进程崩溃（render-process-gone → 自动恢复）

在渲染进程 **DevTools Console** 中执行：

```js
window.ipcRenderer.invoke("crash-test")
```

> 说明：本项目 `index.html` 覆盖了 `window.process = {}`（为兼容浏览器预览），`process.crash()` 不可用；故主进程在**开发与生产环境**均注册了 `crash-test` IPC（生产环境注册是刻意保留，便于现场验证自愈），内部调用 Electron 官方崩溃模拟 API `webContents.forcefullyCrashRenderer()`。

**预期**：
1. 窗口自动 reload（白屏自愈），登录态保留（localStorage 未丢）
2. 主进程控制台输出 `[崩溃自愈] 渲染进程崩溃，自动恢复中`，含崩溃原因（reason/exitCode/count）
3. 若崩溃前已一键启动队列 → 3 秒后队列自动拉起，页面自动跳转队列管理页；后端日志表出现 `des = "渲染进程崩溃自愈-队列自动恢复"` 记录（info 含 crashReason、恢复的队列列表）
4. `%APPDATA%\electron-pure-admin\logs\crashEvent-<日期>.log` 出现本次崩溃事件记录（crash-test 触发的模拟崩溃在崩溃前已写入一条"崩溃测试"记录，**同时验证了本地日志写入功能**）
5. 若本地有上传失败的日志 → 同目录 `logUploadFail-*.log` 出现落盘文件

> **排查提示**：若页面回到首页但队列未恢复——检查主进程控制台是否有"无队列快照"提示（崩溃前未一键启动）；若找不到 `crashEvent` 文件——确认 dev 主进程已重启（crash-test 写文件是本次整改新增，旧进程无此逻辑），文件路径为 `C:\Users\<用户名>\AppData\Roaming\electron-pure-admin\logs\`。

### 测试 2：模拟渲染进程无响应（unresponsive → 15 秒强制恢复）

在 DevTools Console 中执行（会卡死主线程，需在卡死前先在 Console 输入好并回车）：

```js
while(true){}   // 主线程死循环，触发 unresponsive
```

**预期**：
1. 窗口无响应 15 秒后自动强制 reload
2. 若 15 秒内自行恢复（如执行了其他操作中断循环），`responsive` 事件取消强制恢复，主进程输出 `渲染进程已自行恢复，取消强制 reload`

### 测试 3：模拟连续崩溃（防循环 → 停止自愈并弹窗）

在 DevTools Console 中连续执行 2 次：

```js
window.ipcRenderer.invoke("crash-test")
```

**预期**：
1. 第 1 次崩溃 → 自动恢复
2. 恢复后 5 分钟内再次崩溃 → 第 2 次**不再自动恢复**，弹出"程序连续崩溃"对话框（含崩溃原因），需人工介入

> 说明：防循环计数保存在主进程内存（`crashTimes`），主进程不重启则持续有效；5 分钟后窗口期过期，计数自动清零。

### 测试 4：队列自动恢复（需真实登录环境）

**前置条件（重要）**：恢复依赖快照——必须先"一键全部启动"成功（此时 `__queueSnapshot` 已写入 localStorage）。**若崩溃前未一键启动过，恢复会跳过**（控制台输出"无队列快照"）。

1. 正常登录 → 进入"队列管理"页 → 点击"一键全部启动"（此时 `__queueSnapshot` 已写入 localStorage）
2. DevTools 执行 `window.ipcRenderer.invoke("crash-test")`
3. 恢复后观察：页面因 hash 路由回到首页 → **自动跳转"队列管理"页**（`main.ts` 恢复成功后 `router.push("/set/queueManage")`），报价/拉单/出票队列自动 start（主进程/后端日志可见队列续跑、新订单被处理）
4. 验证快照清除：恢复完成后 localStorage 的 `__queueSnapshot` 已被删除（避免下次正常启动重复拉起）

### 测试 5：本地兜底日志落盘（可选，需后端日志接口不可用）

- 临时把 `logUpload` 目标接口地址改错（或断网），触发上传失败
- 预期：`%APPDATA%\electron-pure-admin\logs\logUploadFail-<日期>.log` 出现 JSON 行日志，含 `local_save_time` 与上传方信息
