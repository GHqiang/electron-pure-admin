## 二、核心变更说明

### 1. 换座成功后本地记录写回座位/取票码

`PlatCommon.submitTicketCode` 的 `onlyTicketCode` 分支在派发 `ticketCodeReady` 之前，先调用 `updateTicketRecord` 写入：

```js
{
  qrcode,
  order_status: 1,
  lockseat, // 有值时写，空值不写，避免清空原座位
  err_msg: "换座出票成功（未上传平台）"
}
```

这样同步出票、异步出票（含 h5ume 等原先异步成功不回写的平台）都能在页面收到事件前看到正确状态、取票码和新座位；页面 `searchData` 不再读到「出票中/失败 + 旧座位」。

`BaseTicketQueue.saveTicketRecord` 的 `isAgain` 成功分支也补写 `lockseat` 和 `err_info: ""`，覆盖普通重新出票/自动换座重新出票场景。

### 2. 取票码事件与列表刷新时序

- 事件只在记录写回之后派发；
- 页面收到取票码事件后不再立即清空 `codeWatchOrders` / 停止轮询，保留监听等待 `saveTicketRecord` 后的权威事件或轮询确认；
- 事件后立即 `searchData()`，并在 2 秒后再补刷一次，覆盖 `saveTicketRecord` 后写入的利润、用券等字段；
- 轮询从 8 分钟延长到约 11 分钟，覆盖 3 分钟 + 7 分钟异步取码。

### 3. 重复换座保留首次原座位

`resolveSeatChangeOrigin` 优先使用已记录的 `seatChangedFrom`：

```js
const origin = seatChangedFrom || lockseat || fallback || "";
seatChangedFrom: seatChangedFrom || origin
```

避免第二次换座把第一次目标座位当成原座位，导致后续「重新出票」还原错座位。

### 4. 队列未启动不再卡「出票中」

- 派发前通过 `window.__ticketQueueRegistry` 检查该院线出票队列 `isStart`；未启动直接提示，不写状态 5、不派发；
- `markTicketingStatus` 改为 await 并捕获异常，先成功写库再派发，避免后到的状态 5 覆盖队列最终写入的成功/失败状态；写库失败中止操作；
- 「重新出票」增加防重复点击标记，避免重复派发导致重复出票。

### 5. 多订单取票码监听

`codeWatchOrder` 单值改为 `codeWatchOrders`（Set）+ `codePollTimers`（Map）：

- 多个订单可同时等待取票码，互不覆盖；
- 同一订单同一个码只弹一次，关闭后不被轮询重新弹开；
- 弹窗已展示其他订单时，新码提示到出票详情查看，避免覆盖当前码；
- 取票码弹窗增加订单号展示。

## 四、回归风险评估

| 风险 | 评估 | 缓解 |
|---|---|---|
| 仅取票码模式增加一次 `updateTicketRecord` 网络请求 | 低：只在手动换座、拿到取票码后执行，且已 try/catch | 失败仅记日志，不阻断出票；事件/轮询仍可兜底 |
| 队列启动校验过严 | 中低：若队列实例未通过 `getTicketQueue` 创建，会被判定未启动 | 这是当前队列管理的唯一创建入口；未启动时本来也无法出票，提前提示优于卡状态 5 |
| 多订单取票码弹窗只展示一单 | 低：其他单提示去详情查看 | 同步/异步记录均已写回 qrcode，详情可查 |
| 11 分钟轮询增加请求量 | 低：10 秒一次、仅换座单，最多 66 次 | 拿到码/卸载/超时立即停止 |
| `change_seat_info` 写入正常出票记录 | 低：此前变量未使用，本应写入 | 仅申请换座分支有值；其它分支不写该字段 |
