# 待报价拉单分页改造说明

> 日期：2026-07-25
> 状态：**仅设计说明，未动代码**
> 关联背景：省平台为主反馈"少拉待报价单"（详见根因分析），本文档针对各平台拉单分页能力给出改造方案。
> 本期范围：
> - **翻页/增量改造**：猎人、芒果、守兔、省
> - **配置调整（免改代码）**：蚂蚁（拉单间隔调 1 秒）
> - **参数微调**：麻花、票圣（pageLimit 200→300）
> - **保持现状**：影划算、哈哈
> - **本期不涉及**：洋葱（缺接口文档）；商展**已停用**，不再考虑

## 1. 背景与目标

### 1.1 问题背景

各平台"获取待报价订单列表"的拉单实现长期存在分页处理不一致的问题：除守兔外，所有平台只拉取单页数据。当同一时刻平台侧待报价订单数超过单页容量时，超出部分永远拉取不到，导致这部分订单不进入报价队列、不报价。

拉单调用链统一为：

```
XxxOfferQueue.fetchOrders (定时轮询, BaseOfferQueue._startFetchLoop)
  → XxxAdapter.fetchOrderList
    → src/api/xxx-api.js queryStayOfferList
      → src/utils/http/xxx-request.js (axios 实例)
```

改造集中在 **Adapter 层**（`fetchOrderList`）。**例外**：①猎人——水位线状态由 Queue 层持有（见 §3.1）；②通用——拉单锁超时复位涉及 `BaseOfferQueue` 基类、拉单请求超时调整涉及 api 层（见 §5.1/§5.2）。蚂蚁为纯配置调整。

### 1.2 改造目标

| 目标 | 说明 |
| --- | --- |
| 不漏单 | 单页容量不足以覆盖平台侧待报价总量时，通过翻页/增量方式拉全 |
| 可容错 | 单页/某次请求失败时，保留已拉取到的数据降级返回，不再整轮作废 |
| 有上限 | 翻页设置最大页数保护，避免异常响应导致死循环或长时间占用拉单锁 |
| 可观测 | 翻页拉取过程记录页码/条数/总数日志，便于线上验证"是否拉全" |

## 3. 本期改造平台详细方案

### 3.1 猎人（Lieren）—— timestamp 增量拉单

#### 现状

`src/common/platform/adapters/LierenAdapter.js:25-33`：

```js
async fetchOrderList(params = {}) {
  try {
    const res = await this.api.queryStayOfferList(params);   // queue 传 {}，无任何筛选/分页参数
    return res?.data || [];
  } catch (error) { ... return []; }
}
```

api 定义（`src/api/lieren-api.js:11-13`）：`POST /lieren/openapi/order/grab`。

#### 接口能力（用户提供文档）

| 字段 | 必选 | 类型 | 说明 |
| --- | --- | --- | --- |
| `timestamp` | 否 | number | 秒级时间戳。**返回大于这个时间的待抢订单；不传返回未读取订单** |

接口本身**不支持传统分页**，平台通过 `timestamp` 提供增量拉取能力。当前完全依赖"未读取"标记：平台默认返回的未读订单数量有限，单次拉不全即漏单。

#### 改造方案

拉单时增加 `timestamp` 传参，以"上一次拉单时刻"为水位线增量拉取：

1. **水位线存储位置**：水位线状态维护在 **Queue 层**（`LierenOfferQueue`），不放 Adapter。当前 `LierenAdapter` 是无状态的（仅做参数转发），所有状态（queue、handledOrders 等）均由 Queue 基类持有。水位线作为 Queue 实例属性（`this.lastFetchTimestamp`），**不做 localStorage 持久化**。Queue 调用 `fetchOrderList({ timestamp })` 时显式传入，Adapter 保持无状态。
2. **首次拉单**（`lastFetchTimestamp=0`）：以**当前时间**作为水位线，传 `timestamp = now - 2`。不走平台"未读取订单"全量逻辑——全量也按当前时间查、且可能不全；平台侧存量旧单大多已过报价截止时间，拉到也无意义。
3. **后续拉单**：传 `timestamp = lastFetchTimestamp - 2`。
   - 减 2 秒作为重叠缓冲，防止同秒边界（订单创建时间 == 水位线）漏单；
   - 重叠带来的重复订单，由队列层 `BaseOfferQueue.handleNewOrder` 的 `handledOrders` 按 `平台_订单号` 去重兜底，无副作用。
4. **水位线更新时机**（关键：先暂存、成功后才提交）：
   - 每次发起请求**前**，用局部变量 `requestStartTs = Math.floor(Date.now()/1000)` 暂存"本轮请求起点"；
   - 请求**成功返回后**，才将 `lastFetchTimestamp` 提交为 `requestStartTs`；
   - **拉单失败时（catch / 超时 / 网络异常）：不提交**，`lastFetchTimestamp` 保持旧值，下一轮仍按旧水位线重拉，避免失败期间漏单。
   - 用"请求前时间"而非"请求后时间"作为暂存值：请求耗时期间创建的订单，创建时间 ≥ 请求前时间，下一轮能拉到；若用请求后时间，请求期间创建的单会落入盲区。
   - **不**使用返回订单里的某个时间字段作为水位线：字段名/时区/精度不可靠。
5. **stop→start 重启**：`BaseOfferQueue.start()` 调用 `resetFetchState()` 钩子，猎人重写为 `lastFetchTimestamp = 0`。重启后首轮重新以当前时间起步，**不用停机前的旧水位线**——停机后旧水位线远小于当前时间，中间订单大多查不到或已过报价截止，无意义。

#### 流程示意

```
启动首次: requestStartTs = now (暂存)
          baseTs = lastFetchTimestamp(=0) || requestStartTs  → baseTs = now
          queryStayOfferList({ timestamp: now - 2 })         → 成功 → lastFetchTimestamp = requestStartTs
                                                            → 失败 → lastFetchTimestamp 保持 0(下一轮仍走首次逻辑)
第2轮:    requestStartTs = now (暂存)
          queryStayOfferList({ timestamp: lastFetchTimestamp - 2 })  → 成功 → lastFetchTimestamp = requestStartTs
                                                                    → 失败 → lastFetchTimestamp 保持不变(下一轮按旧水位线重拉)
第3轮:    requestStartTs = now (暂存)
          queryStayOfferList({ timestamp: lastFetchTimestamp - 2 })  → ...
```

> 说明：不做"存量旧单兜底轮"。理由：①全量也按当前时间查、且可能不全；②平台侧存量旧单大多已过报价截止时间，拉到也无意义；③避免引入轮次计数、字典配置等不必要的复杂度（过度工程）。若线上确认存在"创建时间早但仍在待抢池且未过截止"的旧单需捞回，再评估是否补充兜底机制。

### 3.2 芒果（Mangguo）—— page_size 300 + 按 count 翻页

#### 现状

`src/common/platform/adapters/MangguoAdapter.js:25-40`：

```js
const res = await this.api.queryStayOfferList({
  order_type: "1",
  page: params.page || 1,
  page_size: 100,            // ← 单页 100，只拉第 1 页
  sort_field: "created_at",
  sort_order: "desc",
  ...params
});
return res?.data?.list || [];
```

api 定义（`src/api/mangguo-api.js:11-13`）：`GET /v2/api/637ca60f4dc12`。

#### 接口能力（用户提供文档）

- 响应 `res.data.count` 为待报价**总数**；
- 目前 1 页 100 条基本够用，基本不会超过 100——但存在超过的可能，需兜底。

#### 改造方案

1. **`page_size` 由 100 调整为 300**。
2. **按 count 翻页**：第 1 页返回后读取 `count = res?.data?.count`；同时满足以下两个条件则 `page+1` 继续拉取并合并：
   - 已拉取条数 `< count`（还没拉完）；
   - 当前页返回 `list.length === page_size`（当前页是满的，说明大概率还有下一页）。
3. **终止条件**（任一满足即停）：
   - 当前页 `list.length < page_size`（最后一页必然不满，自然终止）；
   - 已拉取条数 `>= count`；
   - 达到最大页数保护上限（建议 `MAX_PAGE = 5`，即单轮最多拉 1500 条，防 `count` 异常）。
4. **单页容错**：每页请求单独 try/catch；某页失败时记录日志（含页码），**保留已拉取到的数据降级返回**并中断翻页，不再整轮返回 `[]`。

#### 流程示意

```
page=1: 拉 300 条, count=650, list.length=300(满) 且 300<650 → 继续
page=2: 拉 300 条, 累计 600, list.length=300(满) 且 600<650 → 继续
page=3: 拉  50 条, list.length=50 < 300 → 终止, 共 650 条拉全
```

> 保持 `order_type:"1"`、`sort_field/sort_order` 等现有筛选与排序参数不变，翻页时逐页透传相同参数。

### 3.3 守兔（Shoutu）—— 翻页逻辑加固

#### 现状

`src/common/platform/adapters/ShoutuAdapter.js:25-55`（11 个平台中唯一已实现翻页的）：

```js
const allOrders = [];
let pageNo = 1;
let hasMore = true;
while (hasMore) {
  const res = await this.api.queryStayOfferList({ pageNo, pageSize: 50, ...params });
  const list = res?.data?.list || [];
  const totalPage = res?.data?.totalPage || 1;   // ← 取不到时退化为只拉 1 页
  allOrders.push(...list);
  if (pageNo >= totalPage) { hasMore = false; } else { pageNo++; }
}
return allOrders;
// 整个 while 在单个 try 中：任一页异常 → catch 返回 []，已拉数据全部作废
```

api 定义（`src/api/shoutu-api.js:7-11`）：`POST /yp-api/ticket/order/list-wait-quote-order`。

#### 接口能力（用户提供文档）

- 有分页参数；**`pageSize` 平台固定最多返回 50 条，传更大无效**；
- 响应含总条数与总页码数，示例：`total: 205, totalPage: 5`。

#### 现状问题

| # | 问题 | 影响 |
| --- | --- | --- |
| 1 | `res?.data?.totalPage || 1`：响应结构异常/字段路径变化导致取不到 `totalPage` 时，静默退化为只拉第 1 页（最多 50 条），**超出部分漏单且无任何感知** | 漏单 |
| 2 | 整个 `while` 在单个 `try` 内，任一页超时/报错 → `catch` 返回 `[]`，**前面已拉到的页全部作废**，本轮一单不剩 | 漏单放大 |
| 3 | 无最大页数保护，`totalPage` 为异常值时存在翻页失控风险 | 稳定性 |
| 4 | 终止条件只看 `totalPage`，未用 `total` 做双保险 | 健壮性 |

#### 改造方案（保留现有翻页框架，做加固）

1. **核实并兼容 `total`/`totalPage` 取值路径**：以 `res?.data?.totalPage`、`res?.data?.total` 为准；若线上实际存在嵌套（如 `res.data.page.totalPage`），需兼容。改造前先按 §6 验证方案打印一页原始响应确认结构。
2. **双保险终止条件**：`pageNo >= totalPage` **或** 已拉取条数 `>= total` 即终止。
3. **单页容错**：每页请求单独 try/catch；某页失败时记录日志（含页码），**保留已拉取的 `allOrders` 降级返回**并中断翻页。可选：单页失败重试 1 次再降级。
4. **最大页数保护**：`MAX_PAGE = 5`（50×5=250 条，覆盖日常量级），达到上限记录告警日志并返回已拉数据；超量部分由下一轮从 page=1 重拉 + `handledOrders` 去重兜底，不漏单。
5. **可观测日志**：每页记录 `pageNo / totalPage / 本页条数 / 累计条数 / total`，便于核对"应拉 vs 实拉"。

#### 耗时评估（与 5s 超时 + 30s 锁复位配合）

单页超时 5s（本期调整，见 §5.2），`MAX_PAGE=5` 上限：单轮最坏 5×5s=25s（<30s 不触发锁复位）。常态量级（≤2 页）单轮 ≤10s，不影响报价时效。

### 3.4 省（Sheng）—— 按 count + 满页 20 翻页（本次主反馈平台）

#### 现状

`src/common/platform/adapters/ShengAdapter.js:28-41`：

```js
const res = await this.api.queryStayOfferList({
  supplierCode: tokens.shengToken,
  status: "0",   // 0待报价订单
  page: 1,       // 1页20条  ← 写死只拉第 1 页
  ...params
});
return res?.data?.rows || [];
```

api 定义（`src/api/sheng-api.js`）：`POST /supplier/listGrabPrice`。

#### 接口能力（用户提供文档）

- **有分页参数，但每页固定返回 20 条**（传更大无效）；
- 响应 `res?.data?.count` 为 **`status:"0"` 过滤后的待报价总数**（已确认）。

#### 现状问题

同刻待报价 >20 条时，第 21 条起永远拉不到——这是"少拉待报价单"的**主因**（详见根因分析报告）。佐证：省出票侧 `fetchTicketOrderList` 以 `status:"2"`/`status:"5"` 分两次请求合并、同样只拉 `page:1`，证明接口按 `page` 分页、单页条数有限，前端习惯性只拉第 1 页。

#### 改造方案（与芒果同构，但页容量固定 20）

1. **保留现有入参**：`supplierCode`、`status:"0"` 每页透传，`page` 从 1 开始递增。
2. **按 count 翻页**（count 已确认为待报价总数，作为主判断依据、"满页 20"为辅）：第 1 页返回后读取 `count = res?.data?.count`；同时满足以下两个条件则 `page+1` 继续拉取并合并：
   - 已拉取条数 `< count`；
   - 当前页返回 `rows.length === 20`（满页，说明大概率还有下一页）。
3. **终止条件**（任一满足即停）：
   - 当前页 `rows.length < 20`（不满页=最后一页）；
   - 已拉取条数 `>= count`；
   - 达到最大页数保护上限（`MAX_PAGE = 5`，即单轮最多拉 100 条，覆盖日常量级）；超量部分由下一轮从 page=1 重拉 + `handledOrders` 去重兜底，不漏单。
4. **单页容错**：每页请求单独 try/catch；某页失败时记录日志（含页码），**保留已拉取数据降级返回**并中断翻页，不再整轮返回 `[]`。
5. **可观测日志**：每页记录 `page / 本页条数 / 累计条数 / count`。

#### 流程示意

```
page=1: 拉 20 条, count=45, rows.length=20(满) 且 20<45 → 继续
page=2: 拉 20 条, 累计 40, rows.length=20(满) 且 40<45 → 继续
page=3: 拉  5 条, rows.length=5 < 20 → 终止, 共 45 条拉全
```

#### 耗时评估

每页固定 20 条。单页超时 5s，`MAX_PAGE=5` 上限：单轮最坏 5×5s=25s（<30s 不触发锁复位）。**上线后需重点观察省平台"拉单→报价"时效**；若翻页耗时不可接受，备选方案是与平台方确认单页容量是否可上调（接口文档当前标注固定 20）。

### 3.5 蚂蚁（Mayi）—— 拉单间隔调 1s（配置调整，免改代码）

#### 现状

`src/common/platform/adapters/MayiAdapter.js:25-38`：

```js
const res = await this.api.queryStayOfferList(params);   // 不传任何分页参数
return res?.data || [];
```

api 定义（`src/api/mayi-api.js:11-13`）：`GET /newwww/open/api/order/pool/list`。

#### 接口能力（用户提供文档）

- **无分页参数，接口每次返回当前的总条数**（一次返回全部待报价单）。
- **平台限流（已确认）：1 分钟不能超过 60 次请求**。

即蚂蚁**不存在单页漏单问题**，无需翻页改造。拉单侧的优化点是**拉单频率**：更快拉到新单、缩短"订单出现→被拉到→报价"的链路耗时。

#### 改造方案（纯配置，无需改代码、免发版）

在**队列管理页**（`src/views/queueManage/index.vue`）将蚂蚁（`platName=mayi`）行的**「订单获取间隔」`getInterval` 改为 1** 并保存（当前生效值以队列管理页显示为准，代码兜底默认为 5 秒）。

机制说明（已核实代码链路）：

- `BaseOfferQueue.getFetchInterval()`（`src/common/core/BaseOfferQueue.js:117-132`）每轮调度前实时读取 `localStorage.platQueueRule`，按 `platName` 匹配取 `getInterval`，默认 5 秒；
- 队列管理页编辑保存 → `src/store/platOfferRuleTable.js` 写回 `localStorage.platQueueRule`；
- 拉单循环每轮 tick 结束后重新调用 `getFetchInterval()` 计算下一次定时——**配置修改即时生效，无需重启队列**。

#### 注意事项

| # | 事项 | 说明 |

## 5. 通用设计约束与注意事项

### 5.1 与拉单循环（isFetching 锁）的关系

- `BaseOfferQueue._startFetchLoop` 默认每 5s 一个 tick，`isFetching` 防重入：上一轮拉单未完成则跳过本轮。
- 翻页会拉长单轮拉单耗时，tick 被跳过属**正常防重入行为**，但必须设置最大页数上限，避免单轮长时间占锁、报价时效劣化。
- 兜底依赖：拉单请求统一 5s 超时（本地改动，见 §5.2）+ 翻页最大页数上限 + **拉单锁超时强制复位**（见下）。

#### 拉单锁超时强制复位（本期配套实现，非可选）

`isFetching` 仅在 `fetchOrders().finally()` 中释放，依赖 fetchOrders 链路所有 await 均均能 settle。翻页平台最坏锁持有 = 页数×5s（守兔 5×5s=25s、省 5×5s=25s、芒果 5×5s=25s），均 <30s 不触发锁复位；但接口卡死/异常 hang 住（await 永不 settle）时锁会永久持有，为此新增强制复位机制，锁持有超 30s 则强制释放，让下一轮 tick 可重新拉单。

**实现要点**（改动 `BaseOfferQueue.js`，约 15 行）：

1. 构造函数新增 `this._fetchStartedAt = 0`。
2. `_startFetchLoop` tick 开头检测：`if (this.isFetching && Date.now() - this._fetchStartedAt > FETCH_LOCK_TIMEOUT)` 则 `this.isFetching = false; this._fetchStartedAt = 0` + `console.warn` 告警日志。
3. tick 中置 `isFetching = true` 时同步记录 `this._fetchStartedAt = Date.now()`，并用闭包保存 `const myStartedAt = this._fetchStartedAt`。
4. `fetchOrders().finally(() => { if (this._fetchStartedAt === myStartedAt) this.isFetching = false; })`——**startedAt 比对**保证：被超时复位后旧 fetchOrders 完成时 `myStartedAt` 已不匹配（`_fetchStartedAt` 已被复位为 0 或被新一轮覆盖），不会误释放新一轮的锁。

**阈值 30s 依据**：常态翻页（5 页×5s=25s）不误触发；接口卡死/异常时 30s 内恢复。阈值可字典化配置（`fetchLockTimeout`，默认 30000ms），便于线上调参。

**极端并发兜底**：复位后旧 fetchOrders 仍在运行，其返回的订单由 `handleNewOrder` 的 `handledOrders` 去重，重复无副作用；adapter 层 try/catch 容错防并发异常。即极端情况下两轮 fetchOrders 并发，靠 adapter 容错 + handledOrders 去重兜底，不会污染报价流程。

### 5.2 与拉单请求超时的关系

- api 层本地已统一为拉单请求加超时（未发布）。**本期将超时由 10s 调整为 5s**：平台拉单接口 RT 普遍 <1s，5s 足够覆盖正常波动，又能把翻页最坏耗时砍半。3s 偏激进，偶发 RT 抖动会误杀正常请求导致漏单，故取 5s。
- **超时按单次请求计**，翻页平台的单轮最坏耗时 = 页数 × 5s（但受 §5.1 锁超时复位 30s 截断，锁最多持有 30s）。
- 改造后各平台单轮最坏耗时参考：
  - 芒果：5 页×5s=25s（仅 count>300 的极端场景；<30s 不触发锁复位）；
  - 守兔：最坏 5 页×5s=25s（<30s 不触发锁复位）；
  - 省：最坏 5 页×5s=25s（<30s 不触发锁复位）；
  - 猎人/蚂蚁/麻花/票圣：不翻页，单请求 ≤5s。

### 5.3 重复订单消化

- 猎人 timestamp 重叠缓冲（-2s）、翻页过程中的同单重复，统一由队列层 `BaseOfferQueue.handleNewOrder` 的 `handledOrders`（key=`平台_订单号`，默认容量 500 淘汰、字典可配）去重，不会对报价流程产生副作用。

### 5.4 容错统一原则

- 所有翻页实现遵循：**单页失败 ≠ 整轮失败**。每页独立 try/catch，失败时保留已拉数据降级返回并记录日志（含平台、页码、已拉/总数）。
- 保留现有的 adapter 层最外层 catch → `return []` 作为最后兜底。

### 5.5 可观测性

- 翻页平台每页输出拉取日志（页码/本页条数/累计/总数），上线后第一轮重点核对"平台后台待报价量 vs 本地实拉条数"。
