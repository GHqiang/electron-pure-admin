# 猎人接口 429 限流根因修复

> 日期：2026-07-18
> 问题：猎人相关接口（`openapi/order/record`、`openapi/rule/list`）频繁报 429，`rule_operation_log` 表出现大量 `{"code":0,"message":"操作失败！"}` 失败记录
> 关联文档：[2026-07-15-429限流错误优化方案.md](./2026-07-15-429限流错误优化方案.md)（针对 proxyFactory.js 复杂代理层，本次针对 openApiFactory.js 签名代理层及业务路径）

---

## 一、问题现象

| 接口 | 现象 | 数据库证据 |
|------|------|-----------|
| `openapi/order/record` | HTTP 429 Too Many Requests | 报价队列日志 |
| `openapi/rule/list` | HTTP 429 Too Many Requests | 浏览器控制台报错 |
| `openapi/rule/add` | HTTP 200 + `{"code":0,"message":"操作失败！"}` | rule_operation_log 表 685 条失败记录 |
| 代理层 | `ERR_UNEXPECTED_PROXY_AUTH` | 系统代理认证失败（独立问题） |

`rule_operation_log` 表统计（2026-07-10 ~ 2026-07-18）：
- 失败记录 685 条，100% 来自 `trigger_source=rule_edit_save`、`operation_type=sync_add_update`、`plat_name=lieren`
- 7天失败率 4.77% ~ 19.18% 波动
- 同一规则在 1-2 秒内被多次保存（如 rule_id=1019 在 1 秒内 3 次失败）

## 二、根因分析

### 2.1 `order/record` 的 429 — 缓存击穿

**位置**：`src/common/core/BaseOfferQueue.js` 的 `_checkPlatformAlreadyQuoted` 方法

该方法有 30 秒缓存，但**没有 Promise 锁**。多个系列并发报价时，缓存一旦过期，N 个 `orderHandle` 会同时发起 N 个相同的 `queryOfferRecord` 请求：

```
缓存过期瞬间：
  订单1 → 检查缓存 → 已过期 → 发起 queryOfferRecord
  订单2 → 检查缓存 → 已过期 → 发起 queryOfferRecord  (同时！)
  订单3 → 检查缓存 → 已过期 → 发起 queryOfferRecord  (同时！)
```

违反项目已有约束（`getDictList` 必须用 Promise 锁防并发 DB 查询）。

### 2.2 `rule/list` 的 429 — 批量同步密集请求

**位置**：`src/mixins/useLierenOfferRuleSyncFun.js` 的 `checkAndUpdateLierenRuleState` 方法

登录时自动触发的双向同步流程：
1. 调 1 次 `ruleList` 拉取猎人全部规则
2. 对**每条不一致规则**循环调用 `lierenOfferRuleSyncPlat`
3. `lierenOfferRuleSyncPlat` 内部又调 1 次 `ruleList` 查旧状态 + 1 次 `ruleAdd` 同步

最坏情况：20 条不一致规则 → `1 + 20×2 = 41` 次 `rule/list` 请求（串行但密集）。

### 2.3 `rule/add` 的"操作失败" — 重复提交 + 业务层限流

**位置**：`src/components/RuleDialog.vue` 保存按钮 + `src/views/offerRule/index.vue` 的 `saveRule`

保存按钮**无防抖**，用户连续点击或回车键触发会导致同一规则在 1-2 秒内被多次提交。猎人平台对 `ruleAdd` 接口采用业务层限流（返回 `{"code":0,"message":"操作失败！"}` 而非 HTTP 429）。

### 2.4 出票后 `rule/add` 频繁触发 — 已禁用规则被重复同步（根因之二，2026-07-19 复查发现）

**位置**：`src/common/autoTicket/commonQuanStock.js` 的 `checkLierenFixedRuleByQuanStock` 方法

第一阶段修复（2.1~2.3 + 重试策略）上线后，`rule_operation_log` 表当天仍有大量 `success=0` 失败记录。复查发现：出票流程触发链 `buyTicket → syncUpdateQuanStock → singleUpdateQuanStock → checkLierenFixedRuleByQuanStock → lierenOfferRuleSyncPlat → lierenApi.ruleAdd` 中存在比较逻辑 bug。

**问题代码**（修复前）：
```js
let targetSeatNum = maxQuanStock >= 4 ? 4 : maxQuanStock;
let targetStatus = targetSeatNum == 0 ? "2" : "1";
if (targetStatus == 2) {
  targetSeatNum = undefined;          // 禁用时座位数置为 undefined
}
if (rule.seatNum == targetSeatNum && rule.status == targetStatus) {
  continue;                            // ← rule.seatNum("2") != undefined → 永远 false
}
```

**触发链**：券库存归零 → `targetStatus="2"`，`targetSeatNum=undefined` → 规则已禁用 `rule.status="2"`、`rule.seatNum="2"` → `rule.seatNum("2") == undefined` 为 false → **永远触发 `ruleAdd`** → 同步成功后本地 DB 写入 `seatNum: undefined`（实际可能为 null 或保持原值，状态不会变）→ 下一张订单再次触发，形成死循环。

**数据库证据**（2026-07-19 复查）：
- 4 条规则（id=116/1704/1776/1777）当前 `status="2"`、`seatNum="2"`
- 当天 `old_status="0"→new_status="2"` 成功记录 **4019 次**（重复同步已禁用规则）
- 当天 `old_status=null, new_status=null` 失败记录 **517 次**（被猎人平台业务层限流）
- 失败率与请求量正相关：高峰 13.7%、低峰 3.6%

**用户约束**：每次出票后或券库存更新时都必须同步最新规则，因此不能加缓存或失败退避跳过同步。修复方向是**只在规则状态真正需要变化时才同步**，避免对已禁用规则的重复同步。

## 四、详细变更说明

### 4.1 P0-1：`_checkPlatformAlreadyQuoted` 加 Promise 锁

**文件**：`src/common/core/BaseOfferQueue.js`

在 `_platformQuotedCache` 中新增 `refreshPromise` 字段作为 Promise 锁。缓存过期时，只有首个请求发起 `queryOfferRecord`，其余并发请求 await 同一个 Promise：

```js
// constructor 初始化
this._platformQuotedCache = { data: [], fetchedAt: 0, refreshPromise: null };

// _checkPlatformAlreadyQuoted 方法
if (now - this._platformQuotedCache.fetchedAt > 30000 && !this._platformQuotedCache.refreshPromise) {
    this._platformQuotedCache.refreshPromise = (async () => {
        try {
            const res = await this.platformAdapter.api.queryOfferRecord({ page: 1, limit: 50 });
            this._platformQuotedCache.data = res?.data || [];
            this._platformQuotedCache.fetchedAt = Date.now();
            // 日志在 IIFE 内部记录，确保多个并发等待者共享一次刷新时只记录一条
            logger.infoSave("刷新平台已报价缓存", { count: this._platformQuotedCache.data.length });
        } finally {
            this._platformQuotedCache.refreshPromise = null;
        }
    })();
}
if (this._platformQuotedCache.refreshPromise) {
    await this._platformQuotedCache.refreshPromise;
}
```

**设计要点**：
- `finally` 块保证 `refreshPromise` 在成功/失败两路径都被清理
- 日志在 IIFE 内部记录，避免并发等待者重复记录
- 异常时 `refreshPromise` 被 reject，外层 catch 捕获后返回 null（放行报价）
- 与项目已有的 `h5ume-request.js`/`fenghuang-request.js` 的 Promise 锁模式一致

### 4.4 P1-2：后端代理层 429 退避重试

**文件**：`auto-ticket-service/middlewares/openApiFactory.js`

```js
const MAX_RETRY = 2;
const RETRY_TIMEOUT = 10000;  // 重试请求超时 10s（首次保持 30s）
let retryCount = 0;
let response;
while (true) {
    response = await axios({
        method,
        url: targetBaseUrl + originalPath,
        headers: forwardHeaders,
        data: requestBody,
        timeout: retryCount === 0 ? 30000 : RETRY_TIMEOUT,
        httpsAgent: getHttpsAgent(),
        validateStatus: (status) => status >= 200 && status < 500,
    });

    if (response.status !== 429) break;

    if (retryCount >= MAX_RETRY) {
        console.warn(`⚠ [${platformName}代理] 收到 429 限流，已达最大重试次数，放行 429 响应`);
        break;
    }
    const backoffMs = 500 * Math.pow(2, retryCount);  // 500ms, 1000ms
    console.warn(`⚠ [${platformName}代理] 收到 429 限流，${backoffMs}ms 后重试`);
    await new Promise(resolve => setTimeout(resolve, backoffMs));
    retryCount++;
}
```

**设计要点**：
- 429 由网关层即时返回（<100ms），实际 429 场景下总耗时 < 3s
- 重试请求 timeout 降为 10s，最坏总耗时 51.5s（首次30s + 0.5s + 10s + 1s + 10s）
- 签名复用安全：重试总退避 1.5s，远小于阿里云网关 5 分钟时间戳容差
- 适用于猎人和万达两个平台（共享同一上游网关）

### 4.6 P0-3：修正 `checkLierenFixedRuleByQuanStock` 禁用规则比较逻辑（2026-07-19 复查发现）

**文件**：`src/common/autoTicket/commonQuanStock.js`

**问题**：禁用规则时 `targetSeatNum = undefined`，与 `rule.seatNum`（如 `"2"`）比较永远不等，导致已禁用规则每次出票后都被重复同步。

**修复代码**：

```js
// 修复前
if (rule.seatNum == targetSeatNum && rule.status == targetStatus) {
  continue;
}

// 修复后
// 禁用规则的座位数无业务意义，禁用时只比较状态，不比较座位数；
// 否则会因 rule.seatNum("2") != undefined 永远触发 ruleAdd，导致已禁用规则被重复同步
const isSameState =
  rule.status == targetStatus &&
  (targetStatus == "2" || rule.seatNum == targetSeatNum);
if (isSameState) {
  continue;
}
```

**设计要点**：
- **不违背用户约束**：每次出票后或券库存更新时仍会进入同步检查流程，只是当目标也是禁用且规则已禁用时跳过 `ruleAdd` 调用
- **状态从启用→禁用**：`rule.status != "2"` → `isSameState = false` → 正常触发同步
- **座位数变化（启用→启用）**：`targetStatus = "1"` → 比较 `rule.seatNum == targetSeatNum` → 不一致触发同步
- **已禁用规则重复检查**：`rule.status == "2"` 且 `targetStatus == "2"` → `isSameState = true` → 跳过同步
- 启用规则的比较逻辑完全不变

**效果预期**：4 条已禁用规则（id=116/1704/1776/1777）每次出票后不再触发 `ruleAdd`，预计每日减少约 4000+ 次无效同步请求，从源头消除猎人平台业务层限流的触发条件。

### 4.7 P1-3：补充失败日志的状态字段（2026-07-19 复查发现）

**文件**：`src/mixins/useLierenOfferRuleSyncFun.js`

**问题**：`rule_operation_log` 表中失败记录的 `old_status`、`new_status`、`old_seat_num`、`new_seat_num` 四个字段全部为 null，排查时无法知道当时想同步成什么状态。

**根因**：`lierenOfferRuleSyncPlat` 的 catch 块记录失败日志时，根本没传这4个字段：
- `old_status`/`old_seat_num`：在 `ruleAdd` 失败时尚未查询（`ruleList` 查询在 `ruleAdd` 之后），必然为 null
- `new_status`/`new_seat_num`：`ruleInfo` 入参里有值，但代码没传，也变成 null

**修复**：catch 块里补充传入 `new_status` 和 `new_seat_num`，并从 `ruleInfo.platOfferList` 重新查找 `platRuleId` 来推断 `trigger_source` 和 `change_reason`（因为 `lierenOfferRule` 在 try 块内声明，catch 块访问不到）：

```js
} catch (error) {
  // old_status/old_seat_num 在 ruleAdd 失败时尚未查询，只能为 null
  // new_status/new_seat_num 来自入参 ruleInfo，补充传值便于排查当时想同步成什么状态
  const failedPlatRuleId = ruleInfo.platOfferList?.find(
    item => item.platName === "lieren"
  )?.platRuleId;
  svApi.addRuleOperationLog({
    // ...
    new_status: ruleInfo.status,
    new_seat_num: ruleInfo.seatNum != null ? String(ruleInfo.seatNum) : null,
    trigger_source: failedPlatRuleId ? "rule_edit_save" : "rule_add_save",
    change_reason: failedPlatRuleId ? "更新猎人平台规则" : "新增猎人平台规则",
    success: 0,
    // ...
  });
}
```

**注意点**：`old_status`/`old_seat_num` 保持 null 是合理的，因为 `ruleAdd` 在 `ruleList` 查询之前执行，失败时确实拿不到旧状态值。

**效果**：失败记录将带有 `new_status`/`new_seat_num`，排查时可明确知道"当时尝试把规则同步成什么状态失败"，便于判断是禁用操作失败还是启用操作失败。

### 4.8 P0-4：失败日志补充请求入参和平台响应到 ext_data（2026-07-19 复查发现）

**文件**：`src/mixins/useLierenOfferRuleSyncFun.js`

**问题**：`rule_operation_log` 表失败记录的 `error_msg` 字段只有 `{"code":0,"message":"操作失败！"}` 这 36 个字符，看不到请求入参 `params`，也看不到完整响应详情，无法排查"为什么操作失败"。

**根因（三重信息丢失）**：

1. **猎人响应拦截器丢上下文**（`src/utils/http/lieren-request.js` L80）：
   ```js
   return Promise.reject(data);   // data = {code:0, message:"操作失败！"}
   ```
   拦截器只把响应体 `data` 当成 error 抛出，完全丢弃了 axios 的 `response`（含 status/headers）和 `config`（含请求入参 `config.data`）。

2. **formatErrInfo 过滤字段**（`src/utils/utils.js` L1894-L1920）：
   - 对 Error 实例：只提取 `message/stack/name`，丢弃 `config`/`response`
   - 对非 Error 实例（猎人抛的 `{code:0, message:"操作失败！"}` 普通对象）：直接 `JSON.stringify`，输出就是 `{"code":0,"message":"操作失败！"}`

3. **catch 块未主动补充请求入参**：
   只调用 `formatErrInfo(error)` 写入 `error_msg`，没有把 try 块构造的 `params` 塞进 `ext_data` 字段（对比成功日志 L206-L209 是写了 `ext_data` 的）。

**修复方案（最小改动，仅改 catch 块）**：

```js
} catch (error) {
  const failedPlatRuleId = ruleInfo.platOfferList?.find(
    item => item.platName === "lieren"
  )?.platRuleId;
  // 主动补充请求入参快照到 ext_data（脱敏 AK/SK）
  let safeParams = null;
  if (params) {
    const { lieren_ak, lieren_sk, ...rest } = params;
    safeParams = rest;
  }
  // 平台响应分类记录：猎人业务错误 / AxiosError / 其他异常
  let platformResponse = null;
  if (error) {
    if (error.response) {
      platformResponse = { type: "axios_error", status, statusText, data };
    } else if (error.code != null && error.message != null && !error.stack) {
      platformResponse = { type: "lieren_biz_error", code, message };
    } else {
      platformResponse = { type: "unknown_error", name, message };
    }
  }
  svApi.addRuleOperationLog({
    // ...
    error_msg: formatErrInfo(error),
    ext_data: JSON.stringify({
      platRuleId: failedPlatRuleId,
      requestParams: safeParams,
      platformResponse
    })
  });
}
```

**设计要点**：

- **不动拦截器**：避免破坏性变更影响其他调用 lieren API 的地方（error 从普通对象变成 Error 实例会改变 `error.message` 的格式）
- **不动 formatErrInfo**：避免影响 `logUpload` 等所有用 formatErrInfo 的调用方
- **AK/SK 脱敏**：虽然请求拦截器会从 `config.data` 中删除 `lieren_ak/lieren_sk`，但 try 块构造的 `params` 原对象上 AK/SK 仍存在，写入 `ext_data` 前手动脱敏
- **平台响应分类**：
  - `lieren_biz_error`：HTTP 200 + `{code:0, message:"操作失败！"}`（拦截器 Promise.reject(data) 抛出的普通对象，无 stack）
  - `axios_error`：HTTP 4xx/5xx（如 429），AxiosError 带 response
  - `unknown_error`：其他异常（TypeError、网络异常等）
- **`error_msg` 保持不变**：继续存 `formatErrInfo(error)`，兼容已有查询和解析逻辑；扩展信息放 `ext_data`

**修复后的失败记录示例**：

```json
{
  "rule_id": 116,
  "operation_type": "sync_add_update",
  "new_status": "2",
  "new_seat_num": null,
  "trigger_source": "rule_edit_save",
  "success": 0,
  "error_msg": "{\"code\":0,\"message\":\"操作失败！\"}",
  "ext_data": "{\"platRuleId\":999,\"requestParams\":{\"rule_id\":999,\"name\":\"规则A\",\"cinema_group\":\"万达\",\"price\":35,\"sum_mode\":2,\"state\":0,\"seats\":\"\"},\"platformResponse\":{\"type\":\"lieren_biz_error\",\"code\":0,\"message\":\"操作失败！\"}}"
}
```

排查时可直接从 `ext_data.requestParams` 看到当时往猎人发了什么参数，从 `ext_data.platformResponse.type` 判断是哪种类型的失败。

**未实施（暂缓）的更彻底方案**：

修改 `lieren-request.js` 响应拦截器，把 `Promise.reject(data)` 改为构造带上下文的 Error（保留 `response.config` 和 `response`），让所有调用 lieren API 的地方都能拿到上下文。这是破坏性变更（error 从普通对象变成 Error 实例），需要评估对其他调用方的影响，暂不实施。
