# 出票队列 v3Mode 判定失效修复说明

> 日期：2026-08-21
> 状态：已实施（待提交）
> 用途：修复出票队列系列判定失效导致的日志分级错乱（成功订单日志误入 opera_record / L1，明细 L2 不采集）

---

## 一、问题现象

出票记录（如 lieren 平台 → 苏艺影城 sfc_applet）中，订单最终**出票成功**（order_status=1），但其日志出现在"异常日志"（opera_record / L1）查询结果里，且日志级别非 error（info 级快照）。预期：成功订单的普通 info 快照只进"明细"（L2），不进 L1。

## 二、根因分析

L1 收窄逻辑（`src/common/logger.js` `log()`）只在 `v3Mode=true` 时执行：

```js
if (isSaveIntent && this.v3Mode && level !== "error") { ... }
```

而**出票队列 logger 的 v3Mode 判定恒为 false**，收窄整体短路，全部 Save 日志（含 info 快照）照常入 L1，同时 `traceEnabled=false` 导致 L2 明细不采集。判定失败链路：

1. **订单无 `app_type_code` 字段**：出票队列 `BaseTicketQueue.handleNewOrder` 调 `logger.init(order)` 传平台原始订单（fetcher 派发），平台订单 JSON 无 `app_type_code`（系列标识在订单/DB 里叫 `app_type`）；`_applyV3FlagsSync` 的 `if (app_type_code)` 直接跳过，localStorage 字典缓存也不生效；
2. **异步反查依赖账号可用影线列表**：`_applyV3Flags` 无 app_type_code 时走 `GET_APP_TYPE_LIST()`（= `cinemaStore.getCanAppTypeList`，基于**当前登录账号**的 `canAppList`）反查——猎人跨影线派单等场景，登录账号可用影线不含该影院 → `find` 返回 undefined → `v3Mode=false`。

对照组：报价队列各 init 显式传 `app_type_code: GET_APP_INFO(app_name)?.app_type_code`（基于 `allAppList` 全量影线配置），判定正常。

## 三、修改内容

| 文件 | 修改 |
| --- | --- |
| `src/common/logger.js` | ① `_applyV3Flags` 异步反查改为 `GET_APP_INFO(app_name)?.app_type_code`（allAppList 全量影线配置，必然含本影线）**优先**，原 `getCanAppTypeList`（账号可用列表）降级为兜底；② L1 入站规则调整（2026-08-21 用户裁定，见下） |
| `src/common/core/BaseTicketQueue.js` | `handleNewOrder` 与"重复执行"分支：`logger.init` 后、写日志前 `await logger.v3Ready()`，消除异步判定完成前快照误入 L1 的竞态（与 `BaseOrderFetcher` 2026-08-20 二轮修复同款） |
| `src/components/HistoryTicketRecord.vue` | 「重新出票」（againTicket）配套：v3Mode 生效后订单入口快照（infoSave）不再入 L1，改为 L1 查不到时**兜底查 L2 明细**（`queryLogTrace`，取 processing_time 作 date）；快照缺失时 ElMessage 提示，不再静默抛错 |

### L1/L2 入站规则（2026-08-21 用户裁定，log() 收窄逻辑）

| 条件 | L1（opera_record/异常日志） | L2（明细 /svpi/log/trace） |
| --- | --- | --- |
| type 1/2/3 + 开 V3 系列 | **只收 errorSave（全量，不设条数上限）**；infoSave/warnSave 一律不入（原"降级-/辅助- 前缀白名单放行"移除） | infoSave/warnSave/errorSave 全量 |
| type 4/5/6 + 开 V3 系列 | 保持原逻辑：errorSave ≤5 条上限；info/warn 仅"降级-/辅助-"前缀入 | Save 全量 |
| 未开 V3 系列 | 保持旧逻辑（Save 全量入） | 不采集 |
| **非 Save 日志（info/warn/error）** | **任何系列一律不入**（`if (isSave)` 唯一入口判定，与 v3Mode 无关，现有实现已满足） | 一律不入（`isSaveIntent` 条件） |

修复后效果：出票队列 v3Mode 正确判定 → 「异常日志」（L1）仅剩 errorSave（type 1/2/3 全量）；info 级普通快照只落 L2 明细。

## 五、回归风险评估

- **低**：修改仅影响 v3Mode 判定路径、L1 入站规则与重新出票的日志来源兜底；判定失败时行为回退为旧逻辑（全量入 L1），不改变出票主流程
- **需生产观察**：① 修复后出票队列 info 快照将不再出现在「异常日志」（只落 L2），errorSave 全量入 L1（无 5 条上限）——L1 体积由 error 级日志自然控制，极端场景需关注 opera_record 增长；② 重新出票在快照超过 L2 保留期（7 天）后可能查不到（L1 也没有）——出票失败后重新出票通常发生在当天/数日内，可接受；③ 字典 `log_v3_enabled_series` 值须为 app_type_code 格式（如 `sfc_applet`）而非系列名（如 `sfc`），否则 `series.includes(appTypeCode)` 仍不命中——如需按系列名配置，判定需另行适配
