## 二、关键代码解析

### 2.1 券库存驱动的规则同步（`commonQuanStock.js` L208-340）

#### 业务规则

```js
// L246-251
let targetSeatNum = maxQuanStock >= 4 ? 4 : maxQuanStock;
let targetStatus = targetSeatNum == 0 ? "2" : "1"; // 券库存为0时规则状态改为关闭
if (targetStatus == 2) {
  targetSeatNum = undefined;
}
```

- 最大券库存 ≥ 4 → 座位数锁定为 4
- 最大券库存 1~3 → 座位数 = 库存数
- 最大券库存 = 0 → 状态禁用（`"2"`），座位数置 `undefined`

#### 比较逻辑（修复后）

```js
// L252-266
// 禁用规则的座位数无业务意义，禁用时只比较状态，不比较座位数；
// 否则会因 rule.seatNum("2") != undefined 永远触发 ruleAdd，导致已禁用规则被重复同步
const isSameState =
  rule.status == targetStatus &&
  (targetStatus == "2" || rule.seatNum == targetSeatNum);
if (isSameState) {
  // ...日志...
  continue;
}
```

通过短路避免禁用规则被无限重复同步。详见第四节"已修复问题 #1"。

#### 同步失败处理

```js
// L282-289
const syncRes = await lierenOfferRuleSyncPlat(lierenRule);
if (!syncRes) {
  logger.infoSave("猎人平台同步返回空，跳过本地更新", { ruleId: rule.id });
  continue;
}
```

同步失败时不写本地 DB，下次券库存变化时仍会触发，保证最终一致性。这是项目硬约束（"每次出票后或券库存更新时都必须同步最新规则"）。

### 2.2 单规则同步（`useLierenOfferRuleSyncFun.js` L59-280）

#### 新增规则回填 `platRuleId`

### 2.3 双向同步（`useLierenOfferRuleSyncFun.js#checkAndUpdateLierenRuleState` L425-700）

#### 期望状态计算

```js
// L497-504
const isNoOfferActive =
  localRule.allow_offer_time &&
  +new Date(localRule.allow_offer_time) > +new Date();
const expectedState = isNoOfferActive
  ? 0  // 当日不报生效中 → 禁用
  : localRule.status == "1" ? 1 : 0;  // 本地启用→启用，本地禁用/仅报价→禁用
```

#### 三类不一致处理

1. **状态/座位数不一致**（L512-604）
   - 调 `lierenOfferRuleSyncPlat(ruleForSync, platRule)` 完整同步
   - 失败时回退到 `lierenApi.ruleState(params)` 至少同步状态
   - 每条之间 `await sleep(200)` 避免 429

2. **平台有、本地无（孤儿规则）**（L614-665）
   - 自动禁用（`ruleState` 设 `state: 0`）
   - 批量禁用之间间隔 200ms

3. **本地有、平台无（localOnly）**（L667-678）
   - 仅记录警告，不自动修复（保守设计，避免误操作）

### 2.4 平台已报价缓存的 Promise 锁（`BaseOfferQueue.js` L1064-1107）

```js
// L1072-1096
if (now - this._platformQuotedCache.fetchedAt > 30000 &&
    !this._platformQuotedCache.refreshPromise) {
  this._platformQuotedCache.refreshPromise = (async () => {
    try {
      const res = await this.platformAdapter.api.queryOfferRecord({ page: 1, limit: 50 });
      this._platformQuotedCache.data = res?.data || [];
      this._platformQuotedCache.fetchedAt = Date.now();
      logger.infoSave("刷新平台已报价缓存", { count: this._platformQuotedCache.data.length });
    } finally {
      this._platformQuotedCache.refreshPromise = null;  // 成功/失败都清理
    }
  })();
}
if (this._platformQuotedCache.refreshPromise) {
  await this._platformQuotedCache.refreshPromise;  // 并发等待者共享同一刷新
}
```

通过 `refreshPromise` 锁保证缓存过期瞬间只有一个刷新请求，N 个并发 `orderHandle` 共享同一个 Promise。`finally` 块保证锁在成功/失败两路径都被清理。

### 2.5 后端 429 退避重试（`openApiFactory.js` L138-170）

```js
const MAX_RETRY = 2;
const RETRY_TIMEOUT = 10000; // 重试请求超时 10s（首次保持 30s 不影响正常业务）
let retryCount = 0;
while (true) {
  response = await axios({
    /* ... */
    timeout: retryCount === 0 ? 30000 : RETRY_TIMEOUT,
    validateStatus: (status) => status >= 200 && status < 500,  // 让 429 进入重试逻辑
  });
  if (response.status !== 429) break;
  if (retryCount >= MAX_RETRY) break;
  const backoffMs = 500 * Math.pow(2, retryCount);  // 500ms, 1000ms
  await new Promise(resolve => setTimeout(resolve, backoffMs));
  retryCount++;
}
```

退避序列：500ms → 1000ms（指数退避），最多重试 2 次。重试 timeout 缩短为 10s，避免最坏总耗时超过前端 25s 超时。

### 2.6 三层 429 防御体系

| 层级 | 位置 | 策略 |
|------|------|------|
| L1 后端代理层 | `openApiFactory.js` L138-170 | 收到 429 后指数退避重试 2 次（500ms, 1000ms） |
| L2 前端网络层 | `retry-helper.js` L84-117 | 仅对网络错误/超时重试 2 次（1s, 3s），**不对 429 重试**（已在 L1 处理） |
| L3 业务层间隔 | `useLierenOfferRuleSyncFun.js` L562, L644 | 批量同步时每条规则之间 sleep 200ms |

## 四、已修复问题清单

### #1 已禁用规则被重复同步（根因之二，2026-07-19 复查发现）

- **位置**：`commonQuanStock.js#checkLierenFixedRuleByQuanStock`
- **修复前**：`if (rule.seatNum == targetSeatNum && rule.status == targetStatus)` —— 禁用时 `targetSeatNum=undefined`，与 `rule.seatNum("2")` 比较永远不等，触发死循环式 `ruleAdd`
- **修复后**：`isSameState = rule.status == targetStatus && (targetStatus == "2" || rule.seatNum == targetSeatNum)` —— 禁用规则只比较状态
- **证据**：4 条已禁用规则（id=116/1704/1776/1777）每天触发 4019 次重复同步
- **关联**：[2026-07-18-猎人接口429限流根因修复.md](./2026-07-18-猎人接口429限流根因修复.md) 2.4 节

### #2 `order/record` 缓存击穿（2026-07-18 修复）

- **位置**：`BaseOfferQueue.js#_checkPlatformAlreadyQuoted`
- **修复**：增加 `refreshPromise` Promise 锁，并发请求共享同一刷新
- **效果**：N 个并发请求 → 仅 1 个请求

### #3 `rule/list` 批量同步密集请求（2026-07-18 修复）

- **位置**：`useLierenOfferRuleSyncFun.js#checkAndUpdateLierenRuleState`
- **修复**：`lierenOfferRuleSyncPlat` 增加 `cachedPlatRule` 参数，批量同步时复用调用方已查询的平台规则
- **效果**：最坏 `1+2N` 次 `ruleList` → `1+N` 次

### #4 `rule/add` 重复提交（2026-07-18 修复）

- **位置**：`RuleDialog.vue#saveRule`
- **修复**：增加 `saving` 防抖锁，覆盖所有解锁路径（正常保存、异常、取消、X 按钮、重新打开）
- **效果**：消除 1-2 秒内多次保存导致的业务层限流（`{"code":0,"message":"操作失败！"}`）

### #5 后端 429 退避重试（2026-07-18 修复）

- **位置**：`openApiFactory.js`
- **修复**：增加指数退避重试 2 次（500ms, 1000ms），重试 timeout 缩短为 10s

### #6 `checkAndUpdateLierenRuleState` 批量间隔（2026-07-18 修复）

- **位置**：`useLierenOfferRuleSyncFun.js` L562, L644
- **修复**：每条规则同步之间 `await sleep(200)`，避免密集请求触发 429

## 五、潜在问题与风险

### 5.1 回退调用缺少 try/catch（2026-07-20 已修复）

**位置**：`useLierenOfferRuleSyncFun.js` L548-569

**修复前**：回退的 `ruleState` 调用无 try/catch，失败会抛出异常被外层 `try/catch`（L429）捕获，**整个 `checkAndUpdateLierenRuleState` 会中止**，后续规则不会被检查。

**修复后**：为回退调用加 try/catch，失败时仅记录警告，让循环继续处理下一条规则：

```js
if (!syncRes) {
  const params = { rule_id: [platRule.rule_id], state: expectedState, ... };
  try {
    await lierenApi.ruleState(params);
  } catch (err) {
    console.warn(
      `回退 ruleState 失败: platRuleId=${platRule.rule_id}`,
      err?.message || err
    );
  }
}
```

### 5.2 `_checkPlatformAlreadyQuoted` 持续失败场景的锁退化（低风险）

**位置**：`BaseOfferQueue.js` L1072-1096

**风险**：若 `queryOfferRecord` 持续失败，`finally` 会清理 `refreshPromise` 但 `fetchedAt` 不更新，下一个并发请求会再次创建新的 IIFE，**失去 Promise 锁的意义**（但每次只有一个 IIFE 在执行，并发等待者仍会等待，影响有限）。

**实际影响**：正常情况下 `queryOfferRecord` 不会持续失败；外层 catch 会返回 null 放行报价，不阻塞业务。属于次要问题。

### 5.3 `checkLierenFixedRuleByQuanStock` 循环无间隔（可接受）

**位置**：`commonQuanStock.js` L245

**观察**：与 `checkAndUpdateLierenRuleState` 不同，此处的 `for` 循环没有 `await sleep(200)` 间隔。

**评估**：`usedRules` 通常只包含同一 `quan_value` 的规则，数量较少（通常 1-3 条），且循环内有多个 await（`checkQuanInRules`、`lierenOfferRuleSyncPlat`、`updateRuleRecord`、`addRuleOperationLog`），实际请求密度不高。属于可接受范围。

### 5.4 `localOnlyRules` 不自动修复（设计上的保守选择）

**位置**：`useLierenOfferRuleSyncFun.js` L667-678

**风险**：本地有 `platRuleId` 但猎人平台对应规则已被删除时，本地规则会一直保持不一致状态，需人工干预。

**评估**：这是设计上的保守选择（避免错误自动修复）。建议在 `offerRule/index.vue` 提供手动"重新同步"按钮，将本地 `platRuleId` 清空后重新 `ruleAdd`。

### 5.5 日志失败被静默吞掉（设计上的合理选择）

**位置**：多处使用 `.catch(() => {})` 吞掉 `addRuleOperationLog` 的失败

**评估**：这是合理的设计（日志失败不应影响业务流程），但意味着日志系统的失败会被完全忽略。若日志接口持续失败，可能导致问题难以排查。建议在 `sv-request.js` 层增加日志接口失败计数告警，便于运维感知。

### 5.6 `lieren-request.js` 拦截器丢失上下文（已有弥补方案）

**位置**：`lieren-request.js` L80 `return Promise.reject(data);`

**问题**：响应拦截器只把响应体 `data` 当成 error 抛出，丢弃了 axios 的 `response`（含 status/headers）和 `config`（含请求入参）。

**现状**：未修改拦截器（避免破坏性变更），通过 catch 块主动补充 `requestParams` 和 `platformResponse` 到 `ext_data` 字段弥补（见 2.2 节）。

### 6.2 设计稳健性

整体设计稳健，主要问题（死循环、429、重复同步）已通过多层防御解决：

1. **入口防抖**（`RuleDialog` saving 锁）
2. **比较逻辑修复**（`isSameState` 短路）
3. **批量同步优化**（`cachedPlatRule` 复用 + 200ms 间隔）
4. **后端 429 退避**（指数退避 2 次）
5. **Promise 锁**（防缓存击穿）
