# 麻花平台报价超时与失败记录修复

## 一、问题描述

麻花平台（mahua）部分订单出现以下异常：

1. **出票时获取不到报价记录**：`getOrderOfferRule()` 查询 `offer_record` 表返回 `null`，导致 `offerRule = null`，不允许出票，发送微信通知手动处理。

2. **报价记录存入失败表**：用 `putOrderId` 去 `offer_record_fail` 表能查到记录，但 `offer_record` 成功表中没有。

3. **同一订单被重复报价**：同一条订单在短时间内进入报价队列两次，均以超时告终。

## 二、问题分析

### 2.1 完整时间线还原

```
14:28:11  singleOffer 启动 → getEndOfferPrice()
           └── jinyi 报价流程：循环锁座候选（最多 10 个，每个锁座含重试可达 30s）

14:29:11  ⏰ Promise.race 60s 超时触发
           ├── resolve(undefined) → offerResult = undefined
           ├── addOrderHandleRecord(undefined) → order_status="2" → offer_record_fail
           └── ❌ singleOffer 仍在后台执行（Promise.race 不中止 loser）

14:37:05  订单被重新拉取，再次进入报价队列（handledOrders Map 可能已淘汰该条目）

14:38:06  第二次 60s 超时触发，Promise.race 返回 undefined
           └── ❌ 第二次的 singleOffer 仍在后台执行

14:38:13  第二次 singleOffer 超时后 7s 终于跑完
           ├── getEndOfferPrice 返回 { endPrice: 33, offerRule }
           ├── "准备提交报价" 日志不可见（logger 已被 upload 清空）
           └── ⚠️ submitOffer 可能已提交到麻花（造成"我们记录失败、平台已报价"）
```

### 2.2 根因链

```
① jinyi 锁座候选循环耗时长（最多 10 候选 × 每次含重试 ~30s）
    ↓
② 60s 超时触发，但 Promise.race 的 resolve() 不中止 singleOffer
    ↓
③ singleOffer 继续跑完 → submitOffer 可能已提交到麻花
    ↓
④ offerResult=undefined → order_status="2" → 记录进 offer_record_fail
    ↓
⑤ 出票时 queryOfferInfo 只查 offer_record，不查 offer_record_fail → 查不到
```

### 2.3 关联影响

- **`queryOfferInfo` 只查成功表**（`offer_record`），不查失败表（`offer_record_fail`），即使失败表中有可用的报价规则也无法被出票流程使用。
- **日志不可见**：`singleOffer` 和 `orderHandle` 共用 logger，超时后 logger 被 upload，`singleOffer` 后续日志进孤儿批次永不显示。

## 三、原因总结

| 编号 | 原因                                                                | 严重程度 |
| ---- | ------------------------------------------------------------------- | -------- |
| ①    | `Promise.race` 超时用 `resolve()` 而非 `reject()`，异常被静默       | 高       |
| ②    | `Promise.race` 不中止 loser，`singleOffer` 超时后仍会提交报价到平台 | 高       |
| ③    | `queryOfferInfo` 只查 `offer_record`，失败表中的报价规则无法复用    | 中       |
| ④    | 麻花报价默认超时 60s 对金逸系列（锁座候选多）偏短                   | 中       |

## 四、整改说明

### 4.1 修改文件清单

| 文件                                             | 修改内容                                             |
| ------------------------------------------------ | ---------------------------------------------------- |
| `src/common/core/BaseOfferQueue.js`              | 新增 `timeoutFlag` 中止机制 + 超时阈值支持平台级覆盖 |
| `src/common/platform/configs/platform-config.js` | 麻花平台 `offerHandleTimeout` 调整为 120s            |

### 4.2 timeoutFlag 中止机制（BaseOfferQueue.js）

超时后 `resolve()` 仍走原有路径 → `addOrderHandleRecord(undefined)` → 写入 `offer_record_fail`，无需额外改动。

核心修复是引入 `timeoutFlag`，阻止超时后 `singleOffer` 继续向平台提交：

```javascript
const timeoutFlag = { value: false };

// 超时时设为 true
setTimeout(() => {
  timeoutFlag.value = true;
  resolve();
}, timeout);

// singleOffer 在 getEndOfferPrice 返回后检查
if (timeoutFlag?.value) {
  return { offerRule: result?.offerRule, err_msg: "报价处理超时，已跳过提交" };
}

// singleOffer 在 submitOffer 前再次检查（最终防线）
if (timeoutFlag?.value) {
  return { offerRule, err_msg: "报价处理超时，已放弃提交" };
}
```

防止超时后 `singleOffer` 继续调用 `dynamicPrice` 和 `submitOffer`。

### 4.3 超时配置支持平台级覆盖（BaseOfferQueue.js）

超时取值优先级：**平台 features > 字典全局 > 默认 15s**

```javascript
const offerHandleTimeout =
    this.platformAdapter?.config?.features?.offerHandleTimeout ??
    dictStore.dictInfo.offerHandleTimeout ||
    15 * 1000;
```

### 4.4 麻花超时调整为 120s（platform-config.js）

```javascript
mahua: {
    features: {
        // ...
        offerHandleTimeout: 120 * 1000, // 金逸系列锁座候选多，需更长超时
    }
}
```

### 4.5 修复效果

| 场景                        | 改前                       | 改后                                                 |
| --------------------------- | -------------------------- | ---------------------------------------------------- |
| 超时后 singleOffer 是否中止 | ❌ 继续跑，可能提交到平台  | ✅ getEndOfferPrice 后检测超时，立即返回             |
| 失败记录错误信息            | `err_msg: ""`（无信息）    | `err_msg: "订单报价处理超时，超过120000ms 未完成"`   |
| 超时后是否重复报价          | 可能（handledOrders 淘汰） | 不变（同 session 不重复，跨 session 有失败记录可查） |
| 麻花报价超时阈值            | 60s（全局字典）            | 120s（平台级覆盖）                                   |

## 五、后续建议

1. **`queryOfferInfo` 增加 `offer_record_fail` 回退查询**：当成功表查不到时，查失败表，提高报价规则复用率。
2. **`handledOrders` 持久化**：当前为内存 Map，页面刷新后丢失，建议改为 `localStorage` 或后端校验，防止跨 session 重复报价。
3. **金逸锁座候选策略优化**：减少候选座数量或缩短单次锁座超时，从根源减少报价耗时。
