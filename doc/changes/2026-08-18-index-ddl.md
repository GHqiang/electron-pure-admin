# 2026-08-18 慢 SQL 优化第一批：索引 DDL

## 背景

`offer_record` / `ticket_record` 建表只有主键，全项目无业务索引，导致 6 类慢 SQL（详见 `2026-08-18-slow-sql-scenarios-and-plan.md`）：

- S1 出票日统计：全表扫 30.9 万行，3~6 秒 × 10 并发
- S2 中标价批量更新：锁等待 51~59 秒
- S3 is_deal 定时更新：JOIN 无索引
- S4 列表/单查：2~7 万行扫描
- S6 卡用量统计：出票关键路径全表扫

## DDL 清单（`scripts/ops/mysql-slow-optimize-indexes.sql`）

| 表 | 索引 | 覆盖场景 |
|---|---|---|
| offer_record / offer_record_fail | `idx_user_plat_orderno(user_id, plat_name, order_number)` | S2 批量更新、S4 单查 |
| offer_record | `idx_isdeal_user_plat(is_deal, user_id, plat_name, order_number)` | S4 is_deal 单查、S3 |
| offer_record / offer_record_fail | `idx_processing_time(processing_time)` | 列表排序、历史查询 |
| ticket_record | `idx_app_status_type_time(app_name, order_status, offer_type, processing_time)` | S1 日统计 |
| ticket_record | `idx_user_plat_orderno(user_id, plat_name, order_number)` | S4 列表、防重 |
| ticket_record | `idx_card_app(card_id, app_name, order_status, processing_time)` | S6 卡用量 |
| ticket_record | `uk_user_plat_orderno` 唯一索引 | 防重 INSERT（配合 `ON DUPLICATE KEY UPDATE`） |
| sync_offer_record | `idx_plat_rule_cinema(plat_name, rule, cinema_code, offer_rule_id)` | 最近中标记录查询 |
| opera_record / opera_record_partitioned | `idx_opera_time(opera_time)` | 操作记录排序 |

## 执行步骤（低峰期）

1. 宝塔面板对 autoticket 库做一次备份（已有每日备份任务，建议手动触发一次）
2. 执行查重 SQL（唯一索引前置检查，应返回 0 行）
3. 执行 DDL：`mysql -uroot -p autoticket < scripts/ops/mysql-slow-optimize-indexes.sql` 或面板 SQL 逐条执行
4. 验证 `SHOW INDEX`

## 预期收益

- S1：30.9 万行全表扫 → 索引命中 < 50ms
- S2：锁等待 51s → 秒级
- S3/S4：毫秒级
- S6：出票关键路径不再拖慢

## 风险与回滚

- 唯一索引前必须查重（脚本已含检查）；如有重复需先清理
- InnoDB 在线 DDL 短暂元数据锁，低峰执行
- 回滚：`ALTER TABLE ... DROP INDEX ...`
