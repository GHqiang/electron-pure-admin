1. 券库存更新场景是否有问题需要优化
2. 规则给猎人同步场景是否有问题需要优化

| 前提 | 说明 |
|------|------|

## 三、问题一：券库存更新场景

### 3.1 调用链梳理

**报价前路径**（所有 8 个平台）：
```
validateQuanStock
  → getQuanTypeListByApp (公共/自有)
    → 1 小时窗口判断（超时或库存变化才继续）
    → syncUpdateQuanStock
      → getQuanListByPhone (拉取每个号的券列表)
      → singleUpdateQuanStock (写 DB + 触发规则同步)
```

**出票后路径**（所有 8 个平台）：
```
buyTicket 成功
  → updateQuanStock (平台自有)
    → singleUpdateQuanStock (写 DB + 触发规则同步)
```

### 3.2 券库存更新场景的问题

#### 问题 A1：出票后路径无 1 小时窗口，每次出票都全量触发

**位置**：`commonQuanStock.js#L193-206` `singleUpdateQuanStock`

**问题**：出票后路径 `updateQuanStock` 没有任何节流，每次出票都调用 `singleUpdateQuanStock` → 写 DB + 触发规则同步检查。

**评估**：
- 这是**设计意图**：出票后库存必然变化，必须更新 DB 并同步规则状态
- 按"每次出票后或券库存更新时都必须同步最新规则"硬约束，**不能跳过**
- 真正可优化的是同步检查内部的 DB 查询（见问题二）

**结论**：**不需要优化**。出票后必须更新是业务要求。

#### 问题 A2：报价前路径触发规则同步

**位置**：`commonQuanStock.js#L193-206` `singleUpdateQuanStock`（报价前路径和出票后路径共用）

**问题**：报价前路径只是"读取最新库存用于规则过滤"，但也会触发 `checkLierenFixedRuleByQuanStock` → 可能调 `ruleAdd`。

**评估**：
- **有 1 小时窗口保护**：1 小时内 + 库存未变化时不触发 `singleUpdateQuanStock`
- 只有"库存已变化"或"超 1 小时"才触发，属于合理刷新
- 报价路径触发规则同步是否有业务必要性？**待用户确认**

**修复方案**（可选）：给 `singleUpdateQuanStock` 增加 `skipRuleSync` 参数，报价前路径传 `true`：

```js
export async function singleUpdateQuanStock(obj, skipRuleSync = false) {
  const { logger, app_name, quan_value, ...params } = obj;
  try {
    const res = await svApi.updateQuanType(params);
    logger.infoSave("单个更新券库存返回", { res, params });
    if (!skipRuleSync) {
      checkLierenFixedRuleByQuanStock(obj);
    }
  } catch (error) { /* ... */ }
}
```

**待确认点**：
- 报价路径触发规则同步是否有业务必要性？（报价时发现库存变化，是否需要立即同步规则状态？）
- 若有业务必要性，则**不优化此项**

**结论**：**待用户确认**。如有业务必要性则保留现状。

#### 问题 A3：1 小时窗口触发全量更新

**位置**：`commonQuanStock.js#L42-57`（公共方法）和各平台自有方法

**问题**：只要一个券类型超 1 小时未更新（或库存已变化），就拉取所有号的所有券，然后逐个触发 `singleUpdateQuanStock` → N 次规则同步检查。

**评估**：
- 全量更新是**设计意图**（避免反复拉取，一次性更新所有号的所有券）
- 副作用是触发 N 次 `checkLierenFixedRuleByQuanStock`，但内部 `isSameState` 短路（2026-07-19 已修复）已避免无效 `ruleAdd`
- 残留开销是 N 次 `checkQuanInRules` DB 查询（见问题 B1）

**结论**：**不需要优化**。属设计取舍，依赖问题 B1 间接降低开销。

### 3.3 券库存更新场景小结

| 问题 | 结论 |
|------|------|
| A1 出票后路径无节流 | 不优化（业务要求必须更新） |
| A2 报价前路径触发规则同步 | 待用户确认业务必要性 |
| A3 1 小时窗口全量更新 | 不优化（设计取舍） |

**券库存更新场景本身没有必须优化的问题**，真正可优化的是同步检查内部的 DB 查询（见问题二）。

## 四、问题二：规则给猎人同步场景

### 4.1 调用链梳理

```
checkLierenFixedRuleByQuanStock (券库存变化触发)
  → checkQuanInRules (查规则列表)
  → 遍历规则做 isSameState 比较
  → 不一致才调 lierenOfferRuleSyncPlat
    → ruleList (查平台旧规则，可选 cachedPlatRule 优化)
    → ruleAdd (调猎人平台)
```

### 4.2 规则给猎人同步场景的问题

#### 问题 B1：checkLierenFixedRuleByQuanStock 没有 maxQuanStock 变化检测 ★★★★（已实施）

**位置**：`commonQuanStock.js#L209-355` `checkLierenFixedRuleByQuanStock`

**问题**：不管新 `maxQuanStock` 与上次是否一致，都执行：
1. `checkQuanInRules`（DB 查询规则列表）
2. 遍历规则做 `isSameState` 比较
3. 不一致才调 `lierenOfferRuleSyncPlat`

虽然 `isSameState` 短路（2026-07-19 修复）已避免无效 `ruleAdd`，但前面的 `checkQuanInRules` DB 查询仍然每次执行。

**业务影响**：
- 高峰期同一券类型的 `maxQuanStock` 变化频率远低于出票频率
- 例如：某券类型库存为 4，连续出 10 张订单，只有第 1、5、9 张会改变 maxQuanStock（4→3→2→1→0），其余 7 次都是无效检查
- 90%+ 的 `checkQuanInRules` DB 查询是无效的

**修复方案**：模块级缓存上次的 `maxQuanStock`，相同则直接 return；同步失败时回滚缓存：

```js
const _lastMaxStockMap = new Map();  // key: `${app_name}|${quan_value}`

async function checkLierenFixedRuleByQuanStock(obj) {
  let { logger, id, app_name, quan_value, quanStockList } = obj;
  try {
    quanStockList = JSON.parse(quanStockList);
    let maxQuanStock = 0;
    if (quanStockList.length > 0) {
      maxQuanStock = quanStockList.reduce((pre, cur) => {
        return pre.quan_stock > cur.quan_stock ? pre : cur;
      })?.quan_stock || 0;
    }
    
    const cacheKey = `${app_name}|${quan_value}`;
    const lastMax = _lastMaxStockMap.get(cacheKey);
    if (lastMax === maxQuanStock) {
      logger.infoSave("maxQuanStock 未变化，跳过规则同步", {
        app_name, quan_value, maxQuanStock
      });
      return;
    }
    _lastMaxStockMap.set(cacheKey, maxQuanStock);
    
    // ...后续同步逻辑...
  } catch (error) {
    // 同步失败时回滚缓存，让下次还能触发
    const cacheKey = `${obj.app_name}|${obj.quan_value}`;
    _lastMaxStockMap.delete(cacheKey);
    // ...原日志...
  }
}
```

**缓存 key 设计**：
- 用 `${app_name}|${quan_value}`：`maxQuanStock` 是该 `app_name` 下该 `quan_value` 的库存，与角色无关
- 每个用户有独立的 `app_name`，跨用户不会共享同一 `app_name`，无跨用户污染风险
- 模块级 `Map`，每个 Electron 进程独立，无跨进程污染

**待确认点**：
- 缓存 key 用 `${app_name}|${quan_value}` 是否足够？
- 同步失败时回滚缓存的逻辑是否正确？
- 缓存是否需要 TTL？（长期不变化的库存一直跳过，业务上没问题）

**预期收益**：maxQuanStock 不变时跳过整个同步流程（含 DB 查询），预计减少 90%+ 的 `checkQuanInRules` DB 查询。

**风险**：低。同步失败时回滚缓存，下次仍会触发。

#### 问题 B2：循环内日志非批量写入 ★★

**位置**：
- `commonQuanStock.js#L310-339` 循环内 `addRuleOperationLog`
- `useLierenOfferRuleSyncFun.js#L571-600` 循环内 `addRuleOperationLog`

**问题**：循环内每条规则都 `await addRuleOperationLog`，N 条规则 N 次请求。已有 `batchAddRuleOperationLog` API。

**修复方案**：循环内收集日志，循环结束后用 `batchAddRuleOperationLog` 一次性写入。

**待确认点**：
- `batchAddRuleOperationLog` 接口的入参格式与 `addRuleOperationLog` 是否完全一致？
- 批量写入失败时如何处理？

**预期收益**：N 次 sv-api 请求 → 1 次。

**风险**：低。日志失败本就不影响业务。

#### 问题 B3：跨用户并发同步同一规则（前端无法解决）★★

**背景**：
- 同角色 2 个用户并发出票 → 共享同一 AK/SK → 共用同一限流桶
- 同一规则（同角色公用）可能被并发同步 2 次
- 但 4 个用户独立 Electron 进程，模块级 `Map` 跨用户不共享，**前端 in-flight lock 无法解决**

**评估**：
- 同进程内：同 `app_name` 串行，本就不会并发
- 跨进程：Map 不共享，锁无效
- 残留场景：仅"同进程内不同触发路径并发"（如出票后路径 + 手动修复路径同时触发），属低频场景

**结论**：
- **前端不实施 in-flight lock**（收益有限）
- 跨用户并发同步同一规则的兜底方案：
  - 短期：依赖 `isSameState` 短路（同进程有效）+ 429 退避重试（跨进程兜底）+ 猎人 `ruleAdd` 幂等性
  - 长期：考虑后端 sv-api 层加分布式锁（超出本次范围）

**待确认点**：
- 跨用户并发同步同一规则依赖猎人 `ruleAdd` 幂等性 + 429 退避重试兜底，是否可接受？

#### 问题 B4：券库存触发路径未传 cachedPlatRule，每次同步多调一次 ruleList ★★★★★（已实施）

**位置**：
- `commonQuanStock.js#L282` 调用 `lierenOfferRuleSyncPlat(lierenRule)` 未传第二个参数 `cachedPlatRule`
- `useLierenOfferRuleSyncFun.js#L162-185` 内部 `ruleAdd` 后会调 `ruleList` 查旧状态记日志

**问题**：
```js
// commonQuanStock.js#L282
const syncRes = await lierenOfferRuleSyncPlat(lierenRule);  // ← 没传 cachedPlatRule
```

```js
// useLierenOfferRuleSyncFun.js#L162-185
const res = await lierenApi.ruleAdd(params);  // ① 调猎人 ruleAdd
if (lierenOfferRule.platRuleId) {
  if (cachedPlatRule) {
    oldStatus = cachedPlatRule.state;       // 用调用方传入的缓存
    oldSeatNum = cachedPlatRule.seats;
  } else {
    const listRes = await lierenApi.ruleList({...});  // ② 没缓存就再调 ruleList
    oldStatus = listRes?.data?.[0]?.state;
    oldSeatNum = listRes?.data?.[0]?.seats;
  }
}
```

**业务影响**：
- **每次券库存触发的同步，都会产生 2 次猎人平台接口调用**：`ruleAdd` + `ruleList`
- `ruleList` 是查"旧状态"用于记日志，但券库存场景下我们**已经从本地 DB 查到了 `rule.status` 和 `rule.seatNum`**（旧状态），完全不需要再查猎人平台
- 这是 429 限流的**直接来源之一**：每次有效同步 = 2 次猎人接口调用，其中 1 次是多余的

**修复方案**：在 `commonQuanStock.js#L282` 调用时，用本地规则数据构造 `cachedPlatRule` 传入：

```js
// commonQuanStock.js#L282 修改为：
// 用本地规则数据构造平台旧规则快照，避免 lierenOfferRuleSyncPlat 内部再调 ruleList
// 状态映射：本地 status "1"→1(启用), 其他→0(禁用)
const cachedPlatRule = {
  state: rule.status == "1" ? 1 : 0,
  seats: formatSeats(rule.seatNum)  // 注意：需引入 formatSeats 或内联实现
};
const syncRes = await lierenOfferRuleSyncPlat(lierenRule, cachedPlatRule);
```

**关键点**：
- `cachedPlatRule.state`：本地 `rule.status` 映射到猎人 `state`（"1"→1, 其他→0）
- `cachedPlatRule.seats`：本地 `rule.seatNum` 映射到猎人 `seats`（`formatSeats` 生成 "1,2,3,4" 格式）
- 这两个值就是"同步前的旧状态"，与猎人平台 `ruleList` 返回的 `state`/`seats` 语义一致

**待确认点**（已核查确认）：

1. **本地 `rule.status`/`rule.seatNum` 是否能准确反映"同步前的猎人平台状态"？**
   - ✅ 已确认（用户确认）：正常情况下本地 `rule.status`/`rule.seatNum` 能准确反映"同步前的猎人平台状态"
   - 前提：`commonQuanStock.js#L283-289` 同步失败时跳过本地更新，本地 DB 始终是"上次成功同步的状态"

2. **`formatSeats` 函数如何共享？**
   - ✅ 已核查：`formatSeats` 是 [useLierenOfferRuleSyncFun.js#L31-38](file:///d:/Electron/electron-pure-admin-fix/src/mixins/useLierenOfferRuleSyncFun.js#L31-38) 的模块级私有函数，未导出
   - **方案**：从 `useLierenOfferRuleSyncFun.js` 导出 `formatSeats`，在 `commonQuanStock.js` 内 import 使用
   - 代码改动：
     ```js
     // useLierenOfferRuleSyncFun.js 末尾 return 前新增导出（或在模块顶部 export）
     // 但因为 formatSeats 是模块级 const，不在 useLierenOfferRuleSyncFun() 函数内，需单独 export
     export const formatSeats = seatNum => { /* ... */ };
     
     // commonQuanStock.js 顶部 import
     import { formatSeats } from "@/mixins/useLierenOfferRuleSyncFun";
     ```
   - 注意：`useLierenOfferRuleSyncFun.js` 当前是 `export default function useLierenOfferRuleSyncFun()`，需新增具名导出 `export const formatSeats`

3. **`cachedPlatRule` 的 `state`/`seats` 字段名与猎人 `ruleList` 返回值是否完全一致？**
   - ✅ 已核查：完全一致
   - 猎人 `ruleList` 返回值结构（通过 [useLierenOfferRuleSyncFun.js#L178-181](file:///d:/Electron/electron-pure-admin-fix/src/mixins/useLierenOfferRuleSyncFun.js#L178-181) 和 [L509-510](file:///d:/Electron/electron-pure-admin-fix/src/mixins/useLierenOfferRuleSyncFun.js#L509-510) 确认）：
     - `state`：数字类型，`1`=启用，`0`=禁用
     - `seats`：字符串类型，如 `"1,2,3,4"` 或 `""`
   - `cachedPlatRule` 设计：
     - `state: rule.status == "1" ? 1 : 0` → 数字 1/0 ✅
     - `seats: formatSeats(rule.seatNum)` → 字符串 `"1,2,3,4"` 或 `""` ✅
   - **既有模式佐证**：[useLierenOfferRuleSyncFun.js#L507-510](file:///d:/Electron/electron-pure-admin-fix/src/mixins/useLierenOfferRuleSyncFun.js#L507-510) 已经用 `formatSeats(localRule.seatNum)` 构造 `expectedSeats` 与 `platRule.seats` 比较，证明此映射是**既有且正确**的模式

**结论**：B4 修复方案的所有待确认点均已通过，可安全实施。

**预期收益**：**每次券库存触发的同步从 2 次猎人接口调用 → 1 次**，直接减少 50% 猎人接口请求。

**风险**：低。本地 DB 状态准确反映上次同步状态，仅用于日志记录的 `old_status`/`old_seat_num` 字段，不影响业务逻辑。

#### 问题 B5：只需改状态时也用 ruleAdd 而非 ruleState ★★★（新发现）

**位置**：`commonQuanStock.js#L282` 统一用 `lierenOfferRuleSyncPlat`（即 `ruleAdd`）

**问题**：
- 当 `targetStatus == "2"`（库存归零禁用）时，`targetSeatNum = undefined`
- 此时只需改状态，不需要改座位数
- 但代码仍用 `ruleAdd`（全量参数同步），而不是 `ruleState`（仅改状态）
- `ruleAdd` 参数多（cinema_code、city、film、hall 等十几个），更容易触发限流
- `ruleState` 参数少（rule_id、state、ak/sk），轻量得多

**业务影响**：
- 库存归零场景（`maxQuanStock == 0`）是高频场景（每个券类型最终都会归零）
- 每次归零都用 `ruleAdd` 全量同步，参数多、易触发限流
- 改用 `ruleState` 可大幅减少请求体积和限流风险

**修复方案**：在 `commonQuanStock.js` 内根据 `targetStatus` 分流：

```js
let syncRes;
if (targetStatus == "2") {
  // 仅禁用：用轻量的 ruleState，避免 ruleAdd 全量参数触发限流
  // 需要在 useLierenOfferRuleSyncFun.js 导出 lierenOfferRuleEditStatusPlat
  syncRes = await lierenOfferRuleEditStatusPlat(lierenRule);
} else {
  // 改座位数：用 ruleAdd 全量同步
  const cachedPlatRule = {
    state: rule.status == "1" ? 1 : 0,
    seats: formatSeats(rule.seatNum)
  };
  syncRes = await lierenOfferRuleSyncPlat(lierenRule, cachedPlatRule);
}
```

**待确认点**：
- `lierenOfferRuleEditStatusPlat` 的返回值格式与 `lierenOfferRuleSyncPlat` 是否一致？（前者无返回值，后者返回 `{ platOfferList }`）
- 若不一致，需要统一返回值格式或调整调用方处理逻辑
- 库存归零禁用后，是否需要更新本地 DB 的 `seatNum`？（当前 `targetSeatNum = undefined`，`seatNum` 会被设为 undefined）

**预期收益**：库存归零场景的同步请求体积大幅减小，降低限流风险。

**风险**：中。需要确认 `lierenOfferRuleEditStatusPlat` 返回值格式，以及本地 DB 更新逻辑的兼容性。
