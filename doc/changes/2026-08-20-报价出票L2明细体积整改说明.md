## 一、问题背景

生产实测：L2 明细（后端 `logs/trace/{userId}/{date}/shard-{n}.log`）**单用户单日落盘约 4G，4 用户单日 16G**，远超主设计文档 V4.6 按"1G/用户/天"做的容量预算（128 分片 ≈ 8MB/分片、7 天保留 + gzip 归档后约 38G 总预算）。

## 二、根因分析

日志链路逐环排查，两道体积防线全部失效：

### 根因 1：后端 8KB 单条截断是"假截断"（最后防线失效）

`auto-ticket-service/api/traceFile.js` writeTrace 原实现：

```js
if (line.length > MAX_LINE_BYTES) {      // 8KB
  obj.des = obj.des.slice(0, keep) + "…[截断]";  // ← 只截 des（几十字文案）
  line = JSON.stringify(obj);            // ← info（大头）原样，行长度基本不变
}
```

`des` 是描述文案，`info` 才是真正的大头（完整订单/响应/卡列表/座位列表，单条 10~100KB+）。截 des 不截 info → 8KB 上限形同虚设，大对象行**原样超长落盘**。

### 根因 2：前端源头瘦身方案（08-18 方案）未落地

《2026-08-18-报价出票日志写入体积整改方案》设计的四道防线全部缺失：

| 方案设计 | 实际代码 | 状态 |
|---|---|---|
| `logTrim.js`（summarizeForLog/trimOrderForLog/trimResForLog…） | 文件不存在，全 src 无引用 | ❌ 未实施 |
| "入列即瘦身"（infoSave 前统一 summarize） | `logger.js _pushTrace` 原样 push meta | ❌ 未实施 |
| `sanitizeLogInfoForUpload` 增强（数组≤10/字符串≤500/深度40→10） | 仅深度40 + Error.stack 12000，无数组/字符串截断 | ❌ 未实施 |
| Top 清单大对象打点改摘要（12 处高危位置） | 全量对象仍直传（`{res, order}`、`{cardList}`…） | ❌ 未实施 |

### 根因 3：trace 采集范围放大

`logger.js:154` traceEnabled 后**所有** `info()/warn()`（非 Save 版本）也进 traceBuffer → 每单 trace 条数 150~200+，远超 L1 的 110~140 条。条数叠加单条体积失控 → 4G/用户/天。

## 四、修复方案（本次实施）

### 1. 前端 sanitize 增强（源头减量，L1+L2 全链路生效）

`src/utils/utils.js` `sanitizeLogInfoForUpload`（08-18 方案 §3.2 原文落地）：

- 数组 ≤10 项（超出追加 `…共N项` 计数标记）
- 字符串 ≤500 字符（超出追加 `…`）
- 嵌套深度 40 → 10

效果：卡列表/座位/规则等大列表 100KB → 1~3KB，上传前即瘦身，不落内存不落盘。

### 2. 后端 writeTrace 整体行硬截断（最后防线修复）

`auto-ticket-service/api/traceFile.js` 新增 `trimLineToBudget(obj, budget)`：

1. 序列化后未超限 → 直接返回
2. `des` 超 500 字符先裁 des
3. `info` 递归裁剪（数组 ≤10 项 / 字符串 ≤300 字符 / 深度 6）
4. 仍超限 → 丢弃 info 主体，只留定位字段（des/level/opera_time/upload_*）+ `info_dropped: true`

保证**每一行落盘 ≤8KB 且 JSON 合法可 parse**（查询接口不会因坏行静默丢数据）。

### 3. 基类 3 处完整订单/响应改摘要（全系列受益）

新建 `src/common/autoTicket/common/logTrim.js`（08-18 方案 §3.1 字段集）：

- `trimOrderForLog`：订单只留 12 个业务定位字段（order_number/plat_name/app_name/cinema_name/hall_name/film_name/show_time/ticket_num/tpp_price/supplier_end_price/lockseat/offer_end_time）
- `trimResForLog`：响应只留 7 个结果判定字段（success/msg/order_status/quote_id/qrcode/profit/card_id）
- `summarizeForLog`：通用兜底裁剪（深度5/数组≤10/字符串≤200）

打点改造（基类，一改全系列生效）：

| 位置 | 原 | 改 |
|---|---|---|
| BaseOfferQueue.js:536 | `{newOrder: item, oldOrder}` | `{newOrder: trimOrderForLog(item), hasOldOrder: !!oldOrder}` |

## 七、已知边界与风险

1. **本次不动系列内 20+ 处列表打点**（ume 登录信息/卡券组合、8 系列 movieInfo/cardList 等）：sanitize 增强已在源头兜住列表类大对象（数组≤10），达到同样减量效果，无需逐点改。如后续要根治（连前 10 项摘要字段都精简），按 08-18 方案附录 B 逐项推广。
2. **des 超长截断**：des 一般几十字符，500 字符截断实际几乎不触发，纯防御。
3. **info 整体丢弃（极端超限）**：仅当 info 裁剪后仍超 8KB（如超大嵌套结构）才触发，保留 des/level/时间/订单号定位字段，不影响排查主干；查询接口 brief 模式不受影响。
4. **sanitize 对 L1（opera_record 入库）同样生效**：入库日志 info 也被数组/字符串截断——L1 只存异常（error≤5 条），meta 多为 `{error}` 小对象，截断阈值远大于正常错误栈，无实际影响；反而防止异常大对象入 DB。
5. **trace 条数未降**：本次只降单条体积，条数（每单 150~200 条）保持现状——如需再降条数，走 08-18 方案"轮询收敛 + 去重"方向，另立任务。

## 九、第二轮整改（2026-08-20，用户追加两点要求）

### 9.1 要求一：非 Save 日志不写后端本地、不入表

`logger.info()/warn()/error()`（不带 Save 后缀）为调试/console 级日志，原实现 `traceEnabled` 时**无条件**进 traceBuffer 写 L2 文件（每条日志都落盘，是条数放大量之一）。用户要求：非 Save 日志**既不写后端本地（L2 文件）也不入表（L1 opera_record）**。

**改动**（`src/common/logger.js` `log()` 方法）：

```js
// 改前：所有级别无条件进 traceBuffer（含非 Save）
if (this.traceEnabled) { this._pushTrace({...}); }
// 改后：仅 Save 级进 L2；非 Save 仅 console（不入表也不写 L2）
if (this.traceEnabled && isSave) { this._pushTrace({...}); }
```

- 非 Save 不入表：原本即满足（`isSave=false` 时 `_addToLogList` 不执行）
- 非 Save 不写 L2：本次新增拦截
- 效果：traceBuffer 只保留业务 Save 日志（每单 110~140 条），条数下降约 30%，且不再落调试噪音

## 十、第三轮深入核查（2026-08-20，用户要求"日志变小但不变少、字段都有显示"）

对"非 Save 全部拦截"做全量回归核查（138 处非 Save 调用 + 25 处 error 级逐一审计），发现并修复 **1 个回归 + 12 处失败现场丢失**：

### 10.1 回归修复：L1 收窄误伤 L2 明细（logger.js，必须修）

**问题**：`log()` 中 v3Mode 的 L1 收窄逻辑（info/warn 非"降级-/辅助-"前缀、errorSave 超 5 条）会把 `isSave` 置 false——上一轮"非 Save 拦截"复用了同一个 `isSave` 判定 L2，导致**被 L1 收窄的 Save 级日志连 L2 也不进**（原设计注释明确"不入 opera_record，**仍进 traceBuffer/L2**"、"超上限后**仅 L2**"）。这是对 v3Mode 系列的严重误伤：正常 infoSave 明细全部丢失。

**修复**（`src/common/logger.js`）：拆分两个变量——
- `isSaveIntent`（调用方 Save 意图：infoSave/warnSave/errorSave=true）→ 判定 **L2 明细采集**
- `isSave`（L1 收窄后的入库标记）→ 只判定 **L1 opera_record 入库**

| 场景 | L1 入库 | L2 明细 |
|---|---|---|
| v3Mode infoSave 普通前缀 | ✗（收窄） | ✓（**修复前 ✗**） |
| v3Mode 降级-/辅助- 前缀 infoSave | ✓ | ✓ |
| v3Mode errorSave 超 5 条 | ✗（兜底） | ✓（**修复前 ✗**） |
| 非 Save error/info/warn | ✗ | ✗（用户要求） |
| 非 v3Mode（系列未开白名单） | ✓ | ✗（traceEnabled=false，通道未开，原设计） |

## 十二、第五轮生产就绪核查（2026-08-20，上生产前）

### 12.1 发现并修复：trace 上传超 body 限制风险（必须修）

**问题**：恢复订单快照全量后，单条 sanitize 后约 1.7KB——
- **修复前**：`traceUpload` 一次全传 traceBuffer（最多 500 条）≈ **0.8MB+**，逼近后端 `koa-bodyparser` 默认 `jsonLimit: 1MB`，订单复杂时必超 → **413 整批丢失**（trace 失败静默，明细直接丢）
- **修复**（双保险）：
  1. 前端 `traceUpload` 分批循环上传（`TRACE_BATCH_SIZE = 100` 条/批，与 logUpload 同模式；任一批失败即中止，保持"失败不重试不告警"既有语义，已成功批次不重复发送）
  2. 后端 `app.js` bodyparser `jsonLimit: '1mb' → '2mb'`（全局兜底；10mb 过大——前端 100 条/批最坏仅 0.6MB、真实 0.04MB，2mb 留 3 倍余量且不放大全局请求体上限防恶意大 body）

实测：100 条/批 ≈ **0.16MB**（最坏 0.6MB），远低于 2MB 上限 ✓；后端 `MAX_LINES_PER_BATCH=500` ≥ 前端 100 ✓
