## 二、核心变更

### 1. 一期：上游异常时不再「前一日」补查（仅幸福蓝海，请求 -50%）

- 原逻辑：`getTargetShow` 当日场次匹配失败 → 递归用 `getPreviousDay` 再查一次，失败后再记「匹配影片放映场次失败」。
- 现逻辑：`getMoviePlayTime` 捕获异常时打标 `_lastPlayTimeError`；**幸福蓝海**在 `getTargetShow` 中见到标记直接返回（记一条 warn），不再发第二次请求。
- 非幸福蓝海系列：判定条件不成立，递归补查逻辑原样保留。
- 依据：11-08 的 807 条「匹配场次失败」里 794 条的 `showDate` 是前一日 —— 这部分请求全是无效的。

### 2. 一期：Toast 节流 + 后台静默（仅幸福蓝海）

- `chenxing-request.js` 新增 `showErrorThrottled`：**同一文案 30 秒内只弹一次**；`notifyError` 只对 `xingfulanhai` 走节流，其它系列仍 `ElMessage.error` 立即弹。
- 新增 `config.silent`：仅幸福蓝海的 `getMoviePlayInfo / getUpcomingFilm / getMoviePlayTime` 传 `{ silent: true }`，失败只进日志不弹窗。
- 登录失效告警（`ElMessage.warning` + 微信推送）保持原样，不受节流影响。

### 3. 二期：限流熔断（仅幸福蓝海 + 仅只读查询）

- `isRateLimitedPayload` **只认文案**（`人太多|请耐心等待|系统繁忙|访问过于频繁|请求过于频繁|活动太火爆`）；不把 `code=500 + timestamp` 判为限流，避免吃掉登录告警/误伤真实业务错误。
- 熔断器按 `app_name` 计数，但只在 `isResilienceApp(app_name)` 为真时启用：
  - **2 分钟窗口内累计 5 次限流 → 冷却 60 秒**（不再要求严格连续，避免限流中夹一次成功就永远开不起来）；
  - 冷却结束只放一个半开探针，任何非限流完成都会关闭熔断；冷却期内的在途成功不会提前关闭。
- **快速失败只拦只读查询**（3.0C 路径均含 `/cticket/`：场次、影片、影院、座位布局）；
  - 锁座 / 下单 / 支付 / 释放 / 取消（`/trade/…`）**永不快速失败**，避免座位残留、支付中断；
  - C 版路径差异（如 `cbase/cityAndCinemaList` 不含 `cticket`）不在本次范围——本次只作用于幸福蓝海（3.0C）。
- 其它辰星系列不计数、不拦截、不节流（单测覆盖）；非幸福蓝海的 429 仍按原有「请求错误」处理。
- HTTP 429 在幸福蓝海同样计入熔断。

### 4. 二期：场次短缓存 + 同请求合并（仅幸福蓝海）

- 新增 `showTimeCache.js`：key = `app_name|cinemaCode|cinemaId|filmId|showDate`，TTL 90 秒，LRU 上限 200，惰性过期。
- **只缓存非空结果**，空数组/异常不缓存，避免把一次限流失败固化住；并发相同 key 只发一次上游请求。
- **仅幸福蓝海启用**：其它系列 `forceFresh` 直接透传，缓存逻辑完全不参与（行为与改动前一致）。
- **出票链路强制实时**：`flag !== 1` 时 `forceFresh=true`，跳过缓存与合并，避免用旧排期锁座。

### 5. 已移除：失败单冷却（评审 P0）

- 初版曾在 `BaseOfferQueue` 加「失败单冷却」。核实后确认该逻辑**实际不可达**：
  1. 各平台拉单已按 `handledOrders` 过滤（如 `MayiOfferQueue.js:102-104`）；
  2. `handledOrders` 只在容量淘汰时删除（`BaseOfferQueue.js:727`）；
  3. 冷却判定位于 `handledOrders.has` 之后。
- 按「最小改动、不扩大范围」原则，**整段删除**，`BaseOfferQueue.js` 已还原为改动前状态；限流期真正起作用的是熔断 + 缓存。

## 五、灰度与观察

1. 先灰度 1 台客户端，观察 15:00-18:00 高峰：
   - 同一文案 Toast ≤ 1 条/30 秒；
   - `获取电影放映场次异常` 条数应≈失败次数（不再 ×2）；
   - 幸福蓝海报价量恢复到上周日 80% 以上。
2. 若出现「报价成功但场次不对」，把 `showTimeCache` TTL 降到 30 秒即可（改一个常量，或让报价也 forceFresh）。

## 六、已知限制（未纳入本次）

1. 阈值/冷却/TTL 为常量（2 分钟窗口 / 5 次 / 60 秒 / 90 秒），调参需要发版。
2. 熔断键为 `app_name`：同一客户端若同时使用多个幸福蓝海登录号，一个号被限流会让其它号的只读查询一起快速失败（60 秒内）；写接口不受影响。
3. 单测目录被 `.gitignore` 忽略（仓库现状），新增用例不会进 CI。
4. 场次缓存 key 未含登录账号/tenant（当前按标准价使用，未做双账号实测）。
5. 「场次返回空（code 200）」形态仍走前一日补查（本次只处理上游异常形态）。
6. silent 覆盖幸福蓝海的**出票查询链**：人工测试出票失败时操作员看不到弹窗，但失败仍写入 `ticket_record` 与日志，可在记录页/日志中查。
7. 幸福蓝海还有子品牌 `yonglesuzhou`（幸福蓝海和乐影院），本次**不在作用范围**（近 7 天无报错日志）；如后续出现同样限流，在 `rateLimitGuard.js` 的 `RESILIENCE_APP_NAMES` 加一项即可。
