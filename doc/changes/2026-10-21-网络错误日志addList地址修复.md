# 网络错误日志 addList 上传地址修复

日期：2026-10-21
排查报告：`reports/analyze-issue/2026-10-21-operaRecord-addList-404.md`（本地，不入库）

## 修改文件清单

| 文件 | 说明 |
|------|------|
| `src/common/networkErrorBatcher.js` | `ADD_LIST_URL` 改为与 `sv-request` 同一套改写规则；移除硬编码主机 IP |
| `src/common/tests/networkErrorBatcherUrl.test.js` | 新增：生产/开发两分支的 URL 断言（3 例） |

## 核心变更说明

1. **根因**：`networkErrorBatcher` 用裸 axios 直连 `http://<host>:3000/svpi/operaRecord/addList`，但 `/svpi` 是客户端约定——只有 `sv-request` 拦截器（`src/utils/http/sv-request.js:108-118`）和 vite dev 代理会去掉它；裸 axios 不走拦截器，后端也没有 `/svpi` 前缀路由（`routes/opera_record.js:5` 为 `router.prefix("/operaRecord")`）。结果该请求 100% 404，而按设计失败静默丢弃 → 生产端「网络错误类日志」从未落库。
2. **修复**：抽出 `ADD_LIST_PATH = "/svpi/operaRecord/addList"`，生产分支改为
   `getServerBaseUrl(ADD_LIST_PATH) + ADD_LIST_PATH.slice(5)`，与 `sv-request` 完全一致（同一 hash 分片到 3000/3001/3002）；dev 分支保持相对路径走 vite 代理。
3. **顺带收益**：去掉硬编码 IP，换机/多环境不再改代码；同时消除同类历史坑（`src/utils/utils.js:2197` 注释记录过 `/svpi/log/trace` 的相同错误）。
4. 保持原设计不变：裸 axios 直传、失败静默、不重试（避免网络故障期反馈循环）。

## 测试结果

- `npx jest src/common/tests/networkErrorBatcherUrl.test.js --runInBand` → **3 passed**
  - 生产 URL 不含 `/svpi/`、以 `/operaRecord/addList` 结尾
  - 生产 URL 命中 3000/3001/3002 分片端口
  - 开发分支保持 `/svpi/operaRecord/addList`
- `npx jest src/common/tests/networkMonitor.test.js --runInBand` → **6 passed**（相关模块回归）
- 生产侧路由验证（服务器本机 curl）：
  - `POST /operaRecord/addList` → 3000/3001/3002 均 200（无 token 返回 401 业务码，属正常鉴权响应）
  - `POST /svpi/operaRecord/addList` → 3000/3001/3002 均 404（复现原问题，证明修复目标正确）
- 生产日志证据：窗口 18:40–20:56 内 `/svpi/operaRecord/addList` 404 **20 次**、200 **0 次**；正常路径 `/operaRecord/addList` 200 **4,627 次**；`opera_record` 日写入 2.2–2.7 万条，健康。

## 生效条件

客户端（Electron）代码，**需随前端发版生效**；后端无需改动。

## 回归风险评估

- 低。仅改 URL 拼接，上传体、超时、静默失败、队列上限等行为不变。
- 分片 hash 基于完整 `/svpi/...` 路径计算，与 `sv-request` 对同一逻辑接口的分片结果一致，keep-alive 复用不受影响。
- dev 环境路径不变，本地开发调试行为不变。
- 若 `getServerBaseUrl` 的三台分片端口有异常，仅影响这部分日志上传（静默失败），不影响主链路。
