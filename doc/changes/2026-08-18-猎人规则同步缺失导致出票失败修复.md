# 猎人规则同步缺失导致补写报价记录失败、出票失败修复说明

> 日期：2026-08-18
> 状态：**已实施并测试通过**
> 说明：本文件记录 8-18 线上事故"猎人平台规则报价中标后，机器未找到匹配规则 → 补写报价记录失败 → 出票失败"的根因分析与修复。
>
> 目标：规则已在 SV（rule_record）中存在且映射正确时，机器出票必须能匹配到该规则；机器自身的同步/更新行为不得让内存规则快照过期。

---

## 一、事故现象

订单 `2026081803491170652`（lieren / suzhousuyi / 苏艺影城）日志：

```
平台已报价-命中 {"order_number":"...","rule_id":2729464}
机器未找到匹配的报价规则，先允许出票，后面有报价记录校验
  {"platRuleId":2729464,"app_name":"suzhousuyi","appOfferRuleListCount":215,
   "useRuleListCount":2,"matchDiag":"未找到platRuleId=2729464的规则",
   "diagList":[{"id":1816,"shadowLineName":"suzhousuyi","status":"1","offerType":"1","lierenPlatRuleId":2439903}]}
订单报价记录信息 {"offerRule":null}
获取该订单报价记录失败，微信通知手动出票
单个订单自动出票结束，状态-失败
```

即：平台用规则 2729464 主动报价中标 → 机器出票前需用 `rule_id` 匹配本地规则补写报价记录 → 匹配失败 → 无报价记录 → 出票失败。

## 二、根因分析（结合 rule_operation_log / rule_record 表数据）

### 2.1 数据证据

| 时间 | 事件 | 证据（表） |
|---|---|---|
| 08-17 17:11:54 | 新增规则 1932（苏艺券），随后同步平台并回填 `platRuleId=2729464` | rule_operation_log 46431/46432（`rule_add_save`，ext_data `{"platRuleId":2729464}`） |
| 08-17 17:12/17:14 | 两次编辑（改名苏艺特殊），同步均带 2729464 | 46433~46436 |
| 08-17 22:15:31 | 用户禁用规则（DB status=2，平台 state=0） | 46449（`sync_status` manual_toggle）；rule_record.update_time=22:15:30 |
| 08-18 00:43:02 | **券库存变化（syldtd 券 maxQuanStock=9）触发批量同步**：规则 1932 重新启用（status 2→1）并同步平台（state 0→1） | 46475（`quan_stock_change`）、46474（`sync_add_update`） |
| 08-18 03:50 | 平台用规则 2729464 对事故订单主动报价并中标 | opera 日志"平台已报价-命中" |
| 08-18 03:51 | 机器匹配失败 | opera 日志"机器未找到匹配的报价规则" |
| 当前 | rule_record 1932 的 platOfferList 含 `{"platName":"lieren","isSyncPlat":"1","platRuleId":2729464}`，is_sync_plat=1 | rule_record 表 |

### 2.2 结论

1. **本地 DB 数据一直是正确的**：rule_record 1932（苏艺特殊/suzhousuyi/固定报价）自创建起就持有 1932↔2729464 映射，平台规则 id 全程未变（操作日志 ext_data 一致）。
2. **真正问题是机器内存规则 store（`offerRuleList`）过期**：
   - store 只在**登录**（`login/index.vue#setLocalRuleList`）与**打开规则页**（`offerRule/index.vue#setLocalRuleList`）时刷新；
   - 机器是长跑进程，本次出票时 store 中 suzhousuyi 的规则是 1932 创建/重新启用之前的旧快照（仅 1816/2439903 等），**根本没有 1932/2729464**；
   - 03:51 `lierenRuleCheck` 用陈旧 store 匹配 → 未找到 → 补写报价记录失败 → 出票失败。
3. **券库存同步不刷新 store（用户指出的关键点，已确认）**：
   - 00:43 的 46474/46475 是 `commonQuanStock.js#batchCheckLierenFixedRule`（券库存驱动）把规则 1932 在 **DB 与平台** 重新启用；
   - 该流程只 `updateRuleRecord` 落库 + 同步平台，**从不刷新内存 store**（`commonQuanStock.js` 未引入 offerRule store）——机器自己改完数据，自己匹配仍用旧快照。

## 三、修复方案

三层防御（按根因闭环），其中出票重试与券库存刷新均按"轻量优先、异步兜底"设计，避免影响出票速度：

| # | 位置 | 修复 | 目的 |
|---|------|------|------|
| 1 | `src/common/core/BaseTicketQueue.js#lierenRuleCheck` | 本地规则**匹配失败时两步恢复**：① 先按 `app_name` 轻量查询该影线规则（`queryRuleList({shadowLineName, rule})`），**同步等待**匹配结果，命中则补写报价记录；② **异步**（fire-and-forget，不阻塞出票）刷新全量规则 store，保证后续订单直接命中；仍失败才告警（failReason/日志带"已按影线查询重试"标记，诊断明细改用查询到的最新规则） | 出票兜底：store 过期时用轻量查询快速恢复本单出票，全量刷新不拖慢出票 |
| 2 | `src/common/autoTicket/commonQuanStock.js#batchCheckLierenFixedRule` | 规则状态/座位数**更新落库并同步平台后，异步刷新本地规则 store**（仅 `pendingLogs.length > 0` 规则实际变更时触发，不阻塞券库存同步流程） | 主动同步：机器自己的券库存同步改完 DB 后内存异步生效，出票匹配无需等失败兜底 |
| 3 | `src/mixins/useLierenOfferRuleSyncFun.js#lierenOfferRuleSyncPlat` | 平台返回的 `rule_id` 与本地不一致时（新增获得 / 编辑后平台侧新建了规则）**统一落库更新本地 platRuleId**（原实现只在"无 platRuleId 的新增"时回填） | 预防另一类不同步：平台规则 id 漂移时本地不再永远持有旧 id |

配套：查询/刷新逻辑收敛到共享模块 `src/common/ruleStoreRefresh.js`（`refreshLocalOfferRuleList(logger)` 全量刷新 store，**并发去重**——多个调用方同时触发共享同一次刷新，防打爆 SV；`queryAppOfferRuleList(app_name, logger)` 按影线轻量查询，**单条 platOfferList 容错解析**——损坏规则跳过不影响其余），`BaseTicketQueue` 委托调用，避免解析逻辑第 4 处复制。

新增用例覆盖的关键行为：

1. store 过期（无 2729464）→ 按影线轻量查询（`{shadowLineName, rule}`）重试匹配成功 → `addOfferRecord`（offer_rule_id=2999、plat_rule_id=2729464、order_status=1、offer_from=1），同时异步触发全量刷新（`{rule}`）；
2. 按影线查询后仍无匹配 → 微信告警、不补写记录（原安全行为保留）；
3. store 已含规则 → 不触发查询/刷新，直接补写；
4. 已有机器报价记录 → 跳过匹配与刷新；
5. 编辑同步平台返回新 rule_id → `updateRuleRecord` 落库新 id，返回值携带新 id 供调用方防旧 id 覆盖。

## 六、回归风险评估

| 风险点 | 评估 |
|---|---|
| `lierenRuleCheck` 按影线查询（仅匹配失败时） | 轻量查询（单影线规则，通常个位数~几十条），响应远快于全量；失败场景低频；命中后本单立即出票，全量刷新异步进行不占出票时间；SV 请求实例有 30s 超时 + 网络层重试，且该路径原本已有同步等待的 `queryOfferInfo`，无新增挂死风险类别 |
| 异步全量刷新与出票并发 | 刷新只写 store（`setRuleList`），与出票流程无共享可变状态；`refreshLocalOfferRuleList` 带 Promise 锁并发去重（复用 `BaseOfferQueue._platformQuotedCache` 模式），并发触发共享同一次刷新、完成后自动释放，防瞬时 N 个全量查询打爆 SV |
| `commonQuanStock` 同步后异步刷新 store（仅规则实际变更时） | 每次出票后的券库存同步大多被 B1 缓存短路（maxQuanStock 未变化），刷新仅在 `pendingLogs.length > 0` 时触发；异步执行不阻塞券库存同步流程；刷新调用的 queryRuleList 在触发点同步计数，测试断言无竞态 |
| store 被刷新可能影响报价流程（`utils.js#offerRuleMatch`） | 刷新后数据与 SV 一致，优于过期快照；解析/过滤逻辑与登录时 `setLocalRuleList` 完全一致 |
| `lierenOfferRuleSyncPlat` 落库新 platRuleId | 仅当平台返回的 rule_id 与本地不同才写库（正常编辑返回相同 id 时零影响）；写库失败走原 catch 记录失败日志，不阻断，调用方行为与改动前一致 |
| 共享模块 `ruleStoreRefresh.js` | 纯函数式查询/刷新，无副作用；模块内部 `useDataTableStore()`/`platTokens()` 在函数体内调用，无模块级 pinia 依赖；按影线查询对 platOfferList 损坏规则单条跳过，不影响其余规则匹配 |

## 七、遗留建议（本次未实施）

1. **登录/规则页之外增加周期性 store 刷新**（如队列空闲定时器）：可进一步减少所有规则相关流程的过期窗口；当前"失败兜底 + 同步后刷新"已覆盖已知事故路径，周期性刷新属增强项。
2. `checkAndUpdateLierenRuleState` 对"平台有、本地无"的启用中孤儿规则会**自动禁用**：若平台规则由人工在平台侧创建且属于有效业务（如本次 2729464 若在 SV 无记录），该行为会在下次登录同步时将其禁用，需人工在本地补建规则；建议保留现状（防误删设计）并在告警中提示人工处理。
