# 省平台接单后延迟发货及字典开关说明

- 日期：2026-09-30
- 涉及代码：`src/common/autoTicket/buyTicket/platManage.js`（省平台出票链路唯一收口）
- 涉及配置：字典表新增一项 `shengDeliverDelayEnable`

## 1. 背景

省平台推送消息：

> 调接单 `startDeliver` 接口，请延迟一下再调发货接口 `deliver`，订单分配给你，请延迟 10 秒后再发货，分配完成 10 秒内完成将返回无法发货，请做好对应机制。

即：接单成功后 10 秒内调发货接口会失败（`success=false`）。客户端需保证「接单 → 发货」间隔不小于 10 秒。

## 2. 实现方案

省平台出票链路在同一 `PlatCommon` 实例内串行执行，顺序为 **确认接单 → 提交取票码（发货）**，因此实现收敛在 `platManage.js` 的两处：

1. **接单成功记时间戳**：`startDeliver()` 中，仅当 `plat_name === "sheng"` 且接单接口返回成功时，记录 `this.order.shengConfirmAt = Date.now()`，作为「接单成功时刻」的唯一基准。
2. **发货前补足间隔**：`submitTicketCode()` 调发货接口前调用 `_waitShengDeliverGap()`，按 `SHENG_DELIVER_MIN_GAP`（`10 * 1000` 毫秒）计算缺口：
   - 已满 10 秒 → 不等待（链路自身耗时通常已超过 10 秒，正常流程无额外等待）；
   - 不足 10 秒 → `Math.ceil` 向上取整为秒后调用 `mockDelay(秒)` 补足（`mockDelay` 入参单位为秒）。
3. **字典开关控制**：`_isShengDeliverDelayEnabled()` 读取字典项 `shengDeliverDelayEnable`，**关闭时 `_waitShengDeliverGap()` 直接返回、不等待**（等同改造前的线上行为）。

```js
// 省平台接单后延迟发货是否开启（字典项 shengDeliverDelayEnable，1-开启）
_isShengDeliverDelayEnabled() {
  return dictStore.dictInfo.shengDeliverDelayEnable == 1;
}

async _waitShengDeliverGap(logger) {
  if (!this._isShengDeliverDelayEnabled()) return; // 开关关闭：不等待
  const confirmAt = this.order?.shengConfirmAt;
  if (!confirmAt) return; // 未记接单时刻（重新出票 isAgain 未走接单）：不等待
  const waitMs = SHENG_DELIVER_MIN_GAP - (Date.now() - confirmAt);
  if (waitMs <= 0) return;
  const waitSec = Math.ceil(waitMs / 1000); // mockDelay 单位为秒，向上取整
  logger.infoSave("省平台接单后延迟发货等待", { waitSec, confirmAt });
  await mockDelay(waitSec);
}
```

`startDeliver()` 中的时间戳记录**不随开关关闭而停记**：这样运行中开启开关也能立即对「已接单但尚未发货」的订单生效。

## 3. 字典项配置（运维）

| 项 | 值 |
| --- | --- |
| `dict_type` | `shengDeliverDelayEnable` |
| `dict_value` | `1` = 开启等待；其它值 / 未配置 = 关闭 |
| `status` | `1` = 生效（字典表信息只取 `status === 1` 的项） |
| 备注 | 省平台接单后延迟发货开关（固定 10 秒） |

- 维护位置：字典管理页，新增/修改上述一项即可，无需改代码、无需发版。
- **生效时机**：字典数据由客户端缓存在 `localStorage`（`dictTableList`，见 `src/store/dictTable.js`），修改字典后需客户端重新拉取字典（刷新页面 / 重启客户端）才对出票链路的开关判定生效；与项目既有所有字典开关一致。
- 关闭即回退：开关关闭时行为与改造前完全一致（单次提交、不等待）。

## 4. 行为矩阵

| 场景 | 开关开启 | 开关关闭 |
| --- | --- | --- |
| 省平台正常出票（接单→发货间隔 < 10 秒） | 等待补足至 10 秒后发货 | 不等待，立即发货 |
| 省平台正常出票（间隔 ≥ 10 秒，如取票码上传耗时较长） | 不额外等待 | 不额外等待 |
| 省平台重新出票 `isAgain`（未走接单流程） | 不额外等待（无 `shengConfirmAt`） | 不额外等待 |
| 非省平台（其它 `plat_name`） | 不受影响 | 不受影响 |
| 接单失败 | 不记时间戳，后续走原失败分支 | 同左 |

## 7. 已知边界与取舍

1. **等待时长写死 10 秒**：字典开关只控制「是否等待」，秒数不参数化；平台若调整该时长需改代码发版（已确认接受）。
2. **开关在发货前判定**：一次出票流程内不重复读取；若在等待过程中改字典，本次流程不变更。
3. **无特殊失败处理**：本节只保证「间隔 ≥ 10 秒」。若因网络/时钟等原因发货仍返回失败，走 `submitTicketCode` 通用失败分支（记日志、按各影院系列既有逻辑告警/人工上传取票码），不自动重试。
4. **接单时间戳不随开关停记**：`shengConfirmAt` 始终记录，便于开关动态开启后立即生效，无副作用（仅内存字段）。
