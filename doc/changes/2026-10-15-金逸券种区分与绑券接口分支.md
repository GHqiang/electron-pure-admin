# 金逸系列券种（电子券／实体券）区分与绑券接口分支 整改说明

- 日期：2026-10-15
- 需求来源：金逸小程序系列的券类型需区分「电子券／实体券」，绑券时按券种分别调用不同接口
- 状态：**已实施**（2026-10-15，代码已按本文档落地；DDL 需运维在客户端发布前执行）
- 评审修订：2026-10-15 已按代码核对结果修订，详见第十节

> **交叉引用约定**：文中 `§3.1`、`§3.4`、`§5.1` 这类带小数点的引用，
> 以及第十节里的 `§5 3.3` 这种带空格的写法，**均指第五节的对应子条目**
> （例：`§3.4` = 第五节 3.4「返回契约与状态置 3 的后果」）；
> `§六`、`§九` 等中文数字引用则指对应的大节。

> **适用范围已确认（2026-10-15）**：券种字段与绑券分支**均只做金逸小程序系列**
> （`app_type_code = jinyi_applet`）。辰星系列不在本次范围内。
>
> **安全码策略已确认（2026-10-15）**：实体券需要安全码时，**跳过绑定 + 发消息提醒 + 状态仍置 3
> （绑券异常）**。该取舍的已知后果见 §3.4。

## 一、背景

金逸系列绑券目前只有一条链路，统一走旧接口 `vistax/voucher/bind`（券种=电子券）：

- 接口定义：`src/api/jinyi-api.js` 的 `bandQuan`
- 调用方：`src/common/autoTicket/buyTicket/jinyi/cardQuanManage.js` 的 `bandQuan`
  （入参 `voucher_code` + `voucher_password` **固定为空字符串** + `session_id` + `cinema_id`）

线上新出现**实体券**（如团购券 `TGQ4…` 券码），web 端实测其绑券链路为**两步**：

| 步骤 | 接口 | 入参 | 返回 |
|---|---|---|---|
| ① 预检 | `POST /ticket/{channelCode}/cinema/{cinema_id}/user/voucher/security_need/` | `voucher_code` | `data.security_verify`（true/false） |
| ② 绑定 | `POST /ticket/{channelCode}/cinema/{cinema_id}/user/voucher/add/` | `voucher_code`、`voucher_password`、`voucher_type: "VOUCHER"` | 券明细：`voucher_code` / `voucher_name` / `expire_time` / `voucher_num` / `voucher_desc` |

① 的语义是「这张券绑定是否需要安全码（防伪码）」；`security_verify: false` 时 ② 的
`voucher_password` 传空即可。绑定成功后券进入用户券包，即上次改造已接入的
`user/voucher/list/`（`unused`）取券来源。

> 注：上表「入参」是**浏览器 web 端实测观察到的接口契约字段**；
> 我们客户端调用时**还必须额外带上 `cinema_id` / `session_id`**（请求拦截器依赖它们改写 URL
> 与写 `token` 头），详见 §3.3 的告警说明。请不要直接照上表实现。

由此产生的问题：**券种无法区分**，实体券若继续走电子券接口必然绑定失败，且失败原因不可分辨。
因此需要在券类型配置上增加券种，并让绑券按券种分支。

## 二、改造目标

1. 券类型维护增加「券种」字段（**仅金逸小程序系列**）。
2. 绑券时按券种分别走「旧接口（电子券）」与「预检 + 新接口（实体券）」。
3. **电子券行为零变化**；实体券需要安全码时可控跳过，并留下可定位的失败日志。
4. 实体券需要安全码时**发消息提醒**（新增 `msgType`），状态仍按既有逻辑置 3（绑券异常）。

## 五、详细设计

### 1. 数据层（DDL）

```sql
ALTER TABLE quan_type
  ADD COLUMN quan_kind TINYINT NOT NULL DEFAULT 1
  COMMENT '券种：1=电子券 2=实体券';
```

- **存量行默认 1（电子券）** → 所有既有配置维持原绑券行为，上线后零变化；
- `quan_kind` 为 **`NOT NULL DEFAULT 1`** 的非空列（原文误写为「可空扩展列」，已修正）；
  MySQL `ADD COLUMN` **不可重复执行**，若脚本在部分环境已执行需先判断（执行前用
  `SHOW COLUMNS FROM quan_type LIKE 'quan_kind'` 判断，或由运维按既有 ops 脚本习惯处理）；
- DDL 脚本按 `auto-ticket-service/scripts/ops/` 既有风格（顶部注释写关联说明、执行方式）。
  该目录已存在，现有脚本命名形如 `v3-log-columns-2026-08-18.sql` / `v3-log-dict-2026-08-19.sql`，
  故本文档拟定的 `quan-kind-2026-10-15.sql` 命名与之一致。
- ⚠️ **上线顺序硬性要求：DDL 必须先于客户端发布**（评审补充，见第十节 R7）。
  原因：缺**列**与缺**值**表现不同 —— 若客户端先上而列不存在，`queryFields` 里的 `quan_kind`
  会被**原样拼进 SQL**（`auto-ticket-service/api/quanType.js:109-113`，`fields` 直接字符串插值），
  触发 `Unknown column` 报错，而非「返回 undefined 值」。
  之所以最终仍表现为「兜底电子券」，只是因为 `findRecordData` 走 `failRes`
  （`quanType.js:142-145`）且共享 mixin 是**空 catch**（`src/mixins/usesMachineBaseFun.js:372`）。
  即：**降级是「碰巧」成立的，不能依赖**。同理，若第九节决定在列表页展示券种，
  上线顺序更不能颠倒。

### 2. 券类型维护 UI（`QuanDialog.vue`）

- 在「是否基础券」之后新增表单项「券种」，`el-radio-group` 两项：`1 = 电子券` / `2 = 实体券`
  （参照 `src/components/QuanDialog.vue:182-187` 的 `is_base_quan` 写法，字段类型用**数字**）；
- **显隐规则**：反查当前所选影线 `app_name` 所属系列
  （`APP_TYPE_LIST` 中 `item.app_name_list.includes(app_name)` 的 `app_type_code`），
  等于 `jinyi_applet` 才渲染该表单项（`quanType.vue` 的 `saveQuan` 已有同一反查写法可参照，
  见 `src/views/permission/quanManage/quanType.vue:635-640`；`APP_TYPE_LIST` 已在
  `QuanDialog.vue:210,217` 引入）；
- 切换影线（`shadowLineChange`）时按新系列重算显隐，并确保表单值被重置，避免串值；
- 表单默认值 `quan_kind: 1`（电子券），加在 `formData` 默认值块内（`QuanDialog.vue:255-279`）。

> ⚠️ **必须补 `open()` 的字段回填，否则会造成券种静默丢失**（评审新增，见第十节 R2）。
>
> `QuanDialog.open()` 是**逐字段显式拷贝**（`QuanDialog.vue:353-372`，形如
> `formData.is_base_quan = formInfo.is_base_quan`），**不拷贝的字段不会被赋值**。
> 而保存时 `saveQuan` 把**整个 `formData`** 交给 `updateQuanType`
> （`quanType.vue:630-643`），后端 `auto-ticket-service/api/quanType.js:174-206` 按
> `Object.keys` 全量拼 `SET`。
>
> 因此若 `open()` 里不补这一行：
> `编辑一条实体券（quan_kind=2）的任意字段 → formData.quan_kind 停留在默认 1 → 提交覆盖为 1
> → 该券类型从此误走电子券链路`。**「复制新增」路径（`quanType.vue:586`
> `open({ ...row, id: "" })`）同样中招。**
>
> 必须在 `open()` 的字段回填块内增加：
> `formData.quan_kind = formInfo.quan_kind ?? 1;`
>
> 补充：列表查询 `searchData`（`quanType.vue:383-387`）**未传 `queryFields`**，后端
> `quanType.js:108,113` 走 `SELECT *`，故记录**本身是带 `quan_kind` 的**；
> 「记录中无该字段取默认值」只适用于字段确实缺失（如列尚未上线）的情形，不能作为不回填的理由。
- 提交侧：**非金逸小程序系列不携带 `quan_kind`**，交由 DB 默认值处理。

### 3. 绑券分支（`jinyi/cardQuanManage.js`）

**3.1 券种来源（入参传入，卡券管理内不做本地判定）**

> **本节已被 2026-10-15 二轮指令取代**（原方案为「卡券管理内按 `quan_flag` 查询判定」，见第十节 R11）。
> 现方案：券种由调用方经 `getNewQuan` 入参传入，`cardQuanManage` 不再查询券类型。

- 新入参：`getNewQuan({ ..., quan_kind })`，`bandQuan` 同步接收 `quan_kind` 并按它分支；
- 调用方 `jinyi/buyTicket.js:467-478` 传 `quan_kind: offerRule?.quan_kind`；
- **`offerRule.quan_kind` 的来源与可得性**：`offerRule` 来自后端 `queryOfferInfo`
  （`auto-ticket-service/api/offerRecord.js:719-766`），该接口每次实时
  `SELECT * FROM quan_type` 取券类型记录。本次已将该处的「白名单合并」改为
  **通用合并**：显式覆盖字段保持原样，另把 `quan_type` 中凡报价记录未含同名列的字段
  一律原样带出（`quan_kind` 由此带出）；
  因此**后续 `quan_type` 再新增列无需再改后端代码**，客户端即可拿到。
- 判定口径：**仅 `quan_kind == 2` 走实体券分支，其余（含 `undefined` / 空 / 其他值）
  一律按电子券兜底**（宽松 `==`，兼容后端返回字符串），行为与改造前完全一致；
- 券种粒度由「同一 `quan_flag` 批量判定」（原 Q3 决策）改为
  「**调用方选中、实际用于出票的那条券类型记录**」——同名券混配时不再做整批兜底，
  也就不再需要 `quan_flag` 粒度的混配 `warn`；
- **不修改**共享 mixin `getQuanValueListByQuanFlag`：`getNewQuan` 中
  「按券标识取 `quan_value` 列表」的调用保持不变。

**3.2 电子券分支**

完全沿用现有 `bandQuan`（`vistax/voucher/bind`）：**入参、返回、成功日志均不变**；
唯一差异是「绑定新券异常」`errorSave` 的 meta 由 `formatErrInfo(error)` 规范化为 `{ error }`（见 §4 与 R5，实现已选 (a)）。

**3.3 实体券分支**

| 序号 | 动作 | 失败处理 |
|---|---|---|
| 1 | 调 `getQuanSecurityNeed({ voucher_code, cinema_id, session_id })` | 请求异常 → 记 `errorSave`「实体券预检失败，跳过绑定」并**跳过该券**，**不调 `add`** |
| 2 | 判 `res?.data?.security_verify` | `true` → 记 `errorSave`「实体券需要安全码，跳过绑定」+ **发消息提醒（整轮仅一条）**，并**跳过该券**，**不调 `add`** |
| 3 | 调 `bindQuanVoucher({ voucher_code, voucher_password: "", voucher_type: "VOUCHER", cinema_id, session_id })` | 异常 → 记 `errorSave`，与既有「绑券异常」口径一致 |

> ⚠️ **`cinema_id` / `session_id` 必须出现在 POST body 里**（评审修正，见第十节 R1）。
> 这两个字段不是接口契约字段，而是**客户端请求拦截器的输入**：
> `src/utils/http/jinyi-request.js:93-98` 从 `config.data`（POST）中读取它们，用于
> `:118-119` 写 `token` 头、`:121-129` 替换 URL 里的 `cinema_id` 占位符，随后**从 body 中删除**。
> 若照「只传接口契约字段」实现（body 仅 `voucher_code`），URL 会变成
> `.../cinema//user/voucher/security_need/`（占位符被替换为空串）且**不带 token**，请求必然失败。
> 现有 `bandQuan`（`jinyi/cardQuanManage.js:739-744`）正是这样传的，直接对齐即可。
> 原文「入参仅保留接口契约要求的字段，不额外传 `appFlag` 等自定义参数」的表述会误导实现，已由本注取代
> （`appFlag` 在本链路确实无用，但 `cinema_id`/`session_id` 必需）。

- `security_need` / `add` 的请求复用既有 jinyi axios 实例，URL 与 token 的改写方式与现有 `bandQuan` 一致；
- 两者均为 **POST**，`Content-Type` 由拦截器统一设为 `application/x-www-form-urlencoded`，与现有绑券接口一致。

**3.4 返回契约（不变）与「状态置 3」的已知后果**

`bandQuan` 仍返回「成功 `{ coupon_num }` / 失败 `undefined`」，`getNewQuan` 的循环、
`bandQuanList` 组装与 `svApi.addUseQuanRecord`（`quan_status: 3` + `remark: "绑券异常"`）
逻辑一律不动 —— 因此**实体券被跳过（需安全码 / 预检失败）与电子券绑定失败，都会把券码置为 3**。

> ⚠️ **该后果已确认接受（2026-10-15 决策）**，但必须知情（评审补充，见第十节 R4）：
>
> 1. `addUseQuanRecord` 不是写流水，而是**直接改 `quan_record` 表的状态列**：
>    `auto-ticket-service/api/quanRecord.js:257-262`
>    `UPDATE quan_record SET quan_status = ? ... WHERE quan_status = '1' AND rule = ? AND app_name = ? AND coupon_num = ?`。
> 2. 取券查询按同表的同一列过滤：`api/quanRecord.js:41,62`
>    （`FROM quan_record ... AND quan_record.quan_status = ?`；`getNewQuan` 传 `"1"`，
>    见 `jinyi/cardQuanManage.js:678`）。**读写同表、同列、同定位键**，故置 3 后该券码立刻脱离可用池。
> 3. 状态 3 是**粘性**的：重新导入同一批券码**不会复位** —— 导入前会过滤掉库中已处于
>    `["1","2","3"]` 的券（`src/views/permission/quanManage/quanList.vue:580-585`）；
>    导出异常券只会 `3 → 5`（`api/quanRecord.js:220-228`）。
>    **唯一恢复路径**：管理员在券管理页按 id 手工改状态
>    （`quanList.vue:661-674` → `api/quanRecord.js:313-315`）。
>
> 因此这是**用「券码永久变为不可用」换「不静默失败」**的取舍。既然是刻意接受，配套要求：
> - 提醒消息需足以定位：**影院（`app_name`）+ 券标识（`quan_flag`）**，
>   并明确提示「如需重新启用，请在券管理页把对应券码状态从 3 复位为 1」；
> - `getNewQuan` 一轮会遍历 `quanNum` 张券（默认约 10 张），若该批券普遍需要安全码，
>   **一轮即可置 3 十张**；提醒消息**整轮只发一条**（`securityRemind.sent` 门控），
>   不逐张发、不记录张数与券码明细（2026-10-15 二轮指令，见 R12）。

### 4. 日志口径

沿用项目约定「成功结果用 `infoSave`、失败异常用 `errorSave`」，且 `errorSave` 的 meta
**直接传原始 error / 上下文对象**，由 logger 统一格式化（**禁止**再套 `formatErrInfo()`，
避免重复转义）。

| 场景 | 级别 | 内容 |
|---|---|---|
| 实体券预检失败 | `errorSave` | 「实体券预检失败，跳过绑定」+ `{ error, voucher_code }` |
| 实体券需安全码 | `errorSave` + **消息提醒** | 「实体券需要安全码，跳过绑定」+ `{ voucher_code }`；提醒**整轮仅一条**（R12） |
| 实体券绑定请求/结果 | `infoSave` | 与现有「绑定券参数 / 绑定券返回」保持同风格 |
| 绑定新券异常 | `errorSave` | meta 规范化为 `{ error }`（原 `formatErrInfo(error)` 已改，见 R5） |

> **已删除的日志**（R11/R12 后不再存在）：原「券种判定结果」`infoSave`、
> 原「同名券券种配置不一致，按实体券处理」`warn`（均随本地判定方法删除）。

**消息提醒实现（评审补充）**：复用 `src/utils/utils.js:632` 的 `sendWxPusherMessage`，
它是**客户端直连** `https://wxpusher.zjiecode.com/api/manager/message/send`
（`utils.js:657-662`，token 取自 `dictStore.dictInfo.wxpusherToken`），
**新增一个 `msgType` 分支即可，无需改后端**。

- 新增 `msgType = 15`（= 已占用最大值 `14` + 1；`utils.js:637` 注释已登记，
  并补全原注释漏登的 `7/8/10`）；
- 文案只含 **影院 / 券标识 / 人工复位提示**（R12：不记券码明细与张数）；
- `sendWxPusherMessage` 为 async，绑券主流程不应因它失败而中断（按既有调用方习惯不 await）。

> 券码属于敏感信息，日志中按项目既有脱敏习惯处理（沿用 `bandQuan` 现有打点方式，不额外放大明文）。
> 提醒消息亦**不再携带券码明细**（R12 后仅影院 + 券标识 + 复位提示），人工据影院与券标识即可定位到券类型。

> 与该文件其余新增日志口径一致（见 `jinyi/cardQuanManage.js:811`）；§3.2 相应措辞已同步。
> 原 (b)「保持原样」未采用。

### 5. 接口白名单与重试

`user/voucher/security_need/`、`user/voucher/add/` **不加入** `jinyi-request.js` 的
`retryWhitelist`。理由：前者是校验、后者是写操作，重试可能造成重复绑定。

> ⚠️ **理由需修正（评审发现，见第十节 R6）**：结论正确，但「不加入白名单 ⇒ 不会重试」这个推理
> 在当前代码下**并非因为白名单机制生效**——现有 `retryWhitelist` 的条目**全部**含
> `channelCode` / `cinema_id` 占位符，而比对发生在请求拦截器**替换占位符之后**的 URL 上
> （`src/utils/http/retry-helper.js:59-63` 比对 `config.url`，
> 而 `jinyi-request.js:125-129` 已把占位符换成真实值），因此这些条目**实际永不匹配**，
> 金逸接口当前本就不会触发网络重试（同一发现在 2026-10-12 变更文档 §三.7 已记录）。
> 故本次的正确表述是：**两个新接口天然不会重试**（与金逸其余接口现状一致），无需额外处理；
> 若后续要修复白名单失效问题，属于独立变更，需重新评估两个新接口是否适合重试。

### 7. 回滚方案

- **DB**：`quan_kind` 列保留不回滚（`DEFAULT 1` 对既有逻辑零影响），无需删列；
- **前端**：隐藏「券种」表单项即可，**但隐藏 UI 不会修改库里已有的值**
  （评审修正，见第十节 R7）。若已把部分券类型配成 `quan_kind = 2`，
  回滚时必须附一条数据修正，否则这些券类型在客户端回滚后会全部走电子券链路而绑定失败：
  `UPDATE quan_type SET quan_kind = 1 WHERE quan_kind = 2;`
- **客户端**：`quan_kind` 缺失即兜底电子券；但**缺列 ≠ 缺值** ——
  列未上线时 `queryFields` 会让 SQL 报错，仅因 `findRecordData` 走 `failRes`
  与共享 mixin 空 catch 才表现为兜底（详见 §5.1），**不可作为「先发客户端」的依据**；
- 因电子券链路完全未改动，回滚客户端只需恢复 `bandQuan` 的分支判断；
- 回滚顺序建议与上线相反：先回滚客户端 → 再按需回滚前端 → 数据修正（如需）→ 保留列。

## 七、验证方式

1. **先执行 DDL**（顺序要求见 §5.1），券类型列表查询可见 `quan_kind`，存量行均为 1；

   「绑定券参数 → 实体券预检返回（`security_verify`）→ 实体券绑定返回」的完整序列；
4. 新增一条电子券券类型并绑定实测：日志与改造前完全一致（仅走旧接口）；

7. **券种端到端（对应 R11/R13）**：金逸影线配一条 `quan_kind = 2` 的券类型后，

   **均先于或同批于客户端上线**，再验证第 3/5 条；

   无回归。
