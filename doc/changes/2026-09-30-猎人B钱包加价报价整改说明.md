# 猎人 B 钱包加价报价整改说明

> 日期：2026-09-30
> 状态：**已实施（2026-09-30）**
> 背景：猎人平台订单列表新增 `pay_type` 字段区分 A/B 钱包（`pay_type`：number，**0-A钱包，1-B钱包**，取自待报价列表 `order/grab` 返回）。A 钱包沿用现有报价规则不变；B 钱包需要在报价规则里新增「B钱包加价」字段，B 钱包订单报价 = 现有规则计算报价 + B钱包加价。该字段**仅对未同步猎人平台的规则生效**。
> 本文档为方案说明 + 改动清单；方案已确认并按本文档实施，**实施结果、两处加固偏差与测试数据见第 10 节**。

---

## 1. 需求与场景界定

| 项 | 内容 |
| --- | --- |
| 生效平台 | **仅猎人（`lieren`）**。其他平台订单不会带猎人的 `pay_type`，一律按现有逻辑报价 |
| 钱包标识 | 订单 `pay_type`（number）：`0`-A钱包，`1`-B钱包；来源为待报价列表（`/lieren/openapi/order/grab`）返回，报价阶段即可取到（已确认） |
| 新增配置项 | 报价规则新增/编辑弹框新增字段「B钱包加价」（规则级字段，落库 `rule_record` 新列） |
| 报价公式 | B 钱包订单最终报价 = 现有规则计算报价（A 钱包报价）+ B钱包加价 |
| 生效条件 | ①猎人订单 ②`pay_type == 1` ③匹配到的规则**未同步猎人平台**（`platOfferList` 中 `platName=lieren` 的 `isSyncPlat != 1`） ④B钱包加价非空且 ≠ 0 |
| 不生效 | A 钱包订单（`pay_type=0`）；`pay_type` 缺失/异常；规则已同步猎人平台（平台侧报价，本地不参与）；非猎人平台订单 |
| 不在本次范围 | 出票环节差异、其他平台钱包概念、A/B 钱包报价统计报表、已同步平台规则的 B 钱包价格（见第 8 节待确认项 7） |

关键结论：

- **所有影线系列（SFC/辰星/凤凰/UME/H5UME/LMA/万达/金逸）的报价都汇集到 `BaseOfferPrice.getEndOfferPrice` 这一个模板方法**（`sfc` 只额外包了一层系统异常检查后 `super.getEndOfferPrice`），因此 B 钱包加价只需在基类加一处，不用改 8 个系列。
- `getOfferBasePrice(offerRule)`（`BaseOfferPrice.js:145`）= `offerAmount || memberOfferAmount`，即「规则基础报价」；`calculateFinalPrice` 的入参 `price` 就是它。
- 匹配到的规则对象就是 `rule_record` 的行（`ruleStoreRefresh.js` / `offerRule` store 直接存 DB 行），**DB 新增列会自动出现在 `offerRule` 上**，报价侧无需额外查询。

### 2.3 为什么「仅未同步猎人平台的规则生效」

- 规则同步平台时，同步参数是**显式构造**的固定字段集合（`src/mixins/useLierenOfferRuleSyncFun.js:138-161`：`rule_id/name/cinema_group/price/sum_mode/seats/state...`），新增字段不会进入平台请求 → **对平台侧规则零影响**。
- 已同步平台的固定价规则，报价时走 `BaseOfferPrice.getEndOfferPrice` 的提前返回分支（「该规则由平台进行报价」），**本地根本不参与算价**，因此该字段在已同步规则上天然无法生效——这与需求完全一致。

### 2.4 现有价格约束（影响 B 加价的实际结果）

| 机制 | 位置 | 行为 |
| --- | --- | --- |
| 利润加价 | `offerHelper.js:65 applyProfitAddition` | 加法项（`price + profitAddPrice`），仅对 `offerType != 1` 生效 |
| 动态调价 | `offerHelper.js:30 applyDynamicPricing` | 加法项；开关为本地 `adjustPrice` 配置（本仓库无写入处，恒为空 = 不调价） |
| 夜间顶价 | `offerHelper.js:93 applyNightMaxPrice` | 开关 `isOpenisNightMaxPrice`，01:00-06:00 直接把价格顶到 `supplier_max_price` |
| 超限处理 | `offerHelper.js:130 handleOverrunCheck`（辰星/金逸/LMA/凤凰另有同名系列内实现，语义一致：`chenxing/offerManage.js:412`） | 报价 > `supplier_max_price`：开关 `isOverrunOffer` **关闭 → 直接不报价**（返回 null，写失败报价记录）；**开启 → 顶到平台限价**（向下取整） |
| 成本利润校验 | 各系列 `calculateCostProfit` | 报价 ≤ 真实成本 → 不报价；并算出 `maxCostPrice` 用于券类型过滤 |

## 3. 方案选型：B 加价叠加位置

备选 3 个位置（均已核对代码路径）：

| 方案 | 位置 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** | **规则基础价**：`BaseOfferPrice.getEndOfferPrice` 里把 `price: this.getOfferBasePrice(offerRule)` 换成 `基础价 + B加价`，再传给 `calculateFinalPrice` | 加价参与后续全部既有机制（利润加价/夜间顶价/**超限检查**/成本利润校验），不会绕过平台限价；`maxCostPrice` 也按含加价的价格计算，券过滤更准确；正常情况最终价 = 原报价 + B加价（下游均为加法项，已逐项确认） | ①夜间顶价（01:00-06:00）会把价格顶到限价，此时 B 加价被「吃掉」（B=A=限价）；②加价后超限时按现有 `isOverrunOffer` 策略处理，可能不报价或顶到限价（见第 5 节） |
| B | 最终提交价：`BaseOfferQueue.singleOffer` 里对 `dynamicPrice` 之后的价格再加 | 字面严格等于「现价 + 加价」，100% 精确 | **绕过 `handleOverrunCheck`**：B 价可能超过平台限价被平台拒（甚至写出「报价成功」假记录）；`maxCostPrice`/利润拆分按未含加价的低价计算，与实际不符；需要为新绕过路径补一套超限处理 |
| C | 规则基础价 + 仅在动态调价开启时另做处理 | — | 增加分支复杂度，收益低 |

**结论：采用方案 A。** 你的判断（动态调价未开启 → 叠加在规则基础价上）与代码事实一致：

- 8 个影线系列的 `calculateFinalPrice` **都以入参 `price` 作为链路起点**（已逐个核对：sfc:200 / ume:198 / h5ume:251 / lma:192 / wanda:231 / 辰星:153 / 凤凰:153 / 金逸:215），因此改基类入参即可覆盖全部系列，无需改系列代码；
- 各系列的 `formatFinalPrice` 均为 `return price` 空实现（辰星:404 / 金逸:313 / LMA:296 / 凤凰:374），**不会对加价做二次取整**，B-A 差值即配置加价；
- 平台侧历史动态调价 `dynamicPrice` 由 `isAdjustPrice` 控制（`src/utils/utils.js:2990`），未开启时直接返回 `offer_end_amount`；
- 系列内 `applyDynamicPricing` 的开关 `adjustPrice` 在本仓库没有任何写入处，恒为空 → 不调价；
- 因此**当前口径下**方案 A 的结果 = 「现有报价 + B加价」，同时保留了限价/成本校验的安全网；将来若开启动态调价，加价会作为基准价一起参与，不会与动态调价打架。

**(b) 新增取加价金额方法（放在 `getOfferBasePrice` 旁）**

```js
  /**
   * 获取 B 钱包加价金额
   * 生效条件（需同时满足）：
   * 1. 订单来源平台为猎人
   * 2. 订单 pay_type == 1（B钱包；0-A钱包不加价，缺失/异常按 A 钱包处理）
   * 3. 匹配到的规则未同步猎人平台（已同步规则由平台侧报价，本地不参与算价）
   * @param {Object} order - 订单信息
   * @param {Object} offerRule - 报价规则
   * @returns {number} 加价金额（不生效返回 0）
   */
  getBWalletMarkup(order, offerRule) {
    try {
      if (this.plat_name !== "lieren") return 0;
      if (Number(order?.pay_type) !== 1) return 0;
      const isSyncToPlat =
        offerRule?.platOfferList?.find(item => item.platName === "lieren")
          ?.isSyncPlat == 1;
      if (isSyncToPlat) return 0;
      const markup = Number(offerRule?.bWalletMarkup || 0);
      return Number.isFinite(markup) ? markup : 0;
    } catch (error) {
      return 0;
    }
  }
```

**(c) `getEndOfferPrice` 第 4 步改为（:94 附近）**

```js
      // 4. 计算最终报价（B钱包订单：在规则基础价上叠加 B钱包加价，下游利润加价/超限检查照常生效）
      const bWalletMarkup = this.getBWalletMarkup(order, offerRule);
      let offerBasePrice = this.getOfferBasePrice(offerRule);
      if (bWalletMarkup) {
        offerBasePrice = addDecimal(offerBasePrice, bWalletMarkup);
        // V3 L0：B钱包加价段并入计算路径，报价记录可回溯

      const endPrice = await this.calculateFinalPrice({
        cost_price,

        rewards: order.rewards,
        offerType: offerRule.offerType,
        offerList,
        offerRule
      });
```

## 5. 生效边界（truth table）

| # | 订单 `pay_type` | 规则 `isSyncPlat` | 规则 `bWalletMarkup` | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 0（A钱包） | 任意 | 任意 | 不加价，与现状完全一致 |
| 2 | 1（B钱包） | 2/空（未同步） | 2（举例） | 报价 = 规则基础价 + 2 后走完整链路（利润加价/夜间顶价/超限检查/成本校验） |
| 3 | 1（B钱包） | 1（已同步） | 2 | 不加价（该单走平台报价，本地不参与） |
| 4 | 1（B钱包） | 2/空 | 空 / 0 | 不加价 |
| 5 | 缺失 / 非 0 非 1 | 任意 | 任意 | 按 A 钱包处理，不加价 |
| 6 | 非猎人平台订单 | 任意 | 任意 | 不加价（`plat_name` 守卫） |
| 7 | 1（B钱包）+ 01:00-06:00 且夜间顶价开启 | 2/空 | 2 | 价格被顶到 `supplier_max_price`，B 加价不体现（B=A=限价） |
| 8 | 1（B钱包）+ A 价 ≤ 限价 < A 价+B加价 | 2/空 | 2 | `isOverrunOffer` 关闭 → 不报价（失败记录：最终报价超平台限价）；开启 → 报价 = 平台限价向下取整 |

### 12.12 更新 `bWalletMarkup` 字段注释（SQL 脚本）

> 用途：当 `rule_record.bWalletMarkup` 列已存在、但注释仍是旧文案（「仅未同步猎人平台的规则生效」）时，用本脚本更新为新注释。
> 落盘为 `doc/sql/2026-10-10-bwallet-markup-column-comment.sql`。

**新注释文案**：`B钱包加价：未同步规则本地叠加；已同步规则随规则同步到平台（折扣模式为折扣值、其余为固定值）`

```sql
-- 更新 rule_record.bWalletMarkup 列注释
ALTER TABLE rule_record
  MODIFY COLUMN bWalletMarkup DECIMAL(10,2) NULL DEFAULT NULL
  COMMENT 'B钱包加价：未同步规则本地叠加；已同步规则随规则同步到平台（折扣模式为折扣值、其余为固定值）';

SELECT COLUMN_NAME, COLUMN_TYPE, COLUMN_COMMENT
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'rule_record'
  AND COLUMN_NAME = 'bWalletMarkup';
```

> 若该列**尚未创建**：直接用上面的 `COMMENT` 建列即可，不必先建后改（见 §12.3-c）。
