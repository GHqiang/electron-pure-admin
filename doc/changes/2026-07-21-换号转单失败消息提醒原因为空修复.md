# 换号转单后失败消息提醒失败原因为空修复

## 基本信息

| 项 | 内容 |
|---|---|
| 整改日期 | 2026-07-21 |
| 影响范围 | 全部 8 个出票平台的 `transferOrder` 失败消息提醒路径 |
| 优先级 | P0 |
| 触发场景 | 换号降级转单失败时，微信推送（消息提醒）的"原因"显示为空，但出票记录（ticket_record）中的失败原因正确 |
| 关联订单 | 2026072020381828997（凤凰平台，失败原因 "无可用优惠券-无可用卡"） |

## 一、问题现象

订单 `2026072020381828997` 在换号降级到无可用券/卡后触发了 `transferOrder`。出票记录表中保存了正确的失败原因 `"无可用优惠券-无可用卡"`，但下发的微信推送消息中"原因"字段为空（实际拼出的是 `"——"`）。

关键日志：
```
2026072020381828997  2026-07-20 20:40:11  用卡用券返回     {"profit":0,"useQuans":[]}                    3  info
2026072020381828997  2026-07-20 20:40:11  无可用优惠券-无可用卡  {"supplier_end_price":35,"ticket_num":1}  3  error
2026072020381828997  2026-07-20 20:40:11  开始准备转单     {"cinemaLinkId":"13382","lockOrderId":"3275013382349970994","session_id":"fd0bf422961c4dde8efd5763c32c0567"}  3  info
```

## 二、根因分析

### 2.1 两条失败原因获取路径不一致

**消息提醒路径**（修复前）—— 直接读 `this.logger.logList`，**无 `_lastErrCache` 缓存保护**：

```javascript
// fenghuang/orderManage.js 修复前 (transferOrder)
const errInfoObj = this.logger.logList
  .filter(item => item.level === "error")
  .reverse()?.[0];
let errMsg = errInfoObj?.des || "";
let errInfo = formatErrInfo(errInfoObj?.info?.error) || "";
// ...
sendWxPusherMessage({
  orderInfo: this.order,
  transferTip: des,
  failReason: `${errMsg}——${errInfo}`   // logList 被清空时得到 "——"
});
```

**出票记录路径** —— 走封装方法 `getLastErrMsgAndInfo()`，**优先读 `_lastErrCache`**：

```javascript
// BaseTicketQueue.js saveTicketRecord
let { err_msg: errMsg, err_info: errInfo } =
  logger.getLastErrMsgAndInfo() || {};
```

`Logger.getLastErrMsgAndInfo()`（`src/common/logger.js` 第 98-118 行）的设计：

```javascript
getLastErrMsgAndInfo() {
  try {
    // 优先使用缓存（防止 logUpload splice 清空 logList 后丢失）
    if (this._lastErrCache) {
      const { message, meta } = this._lastErrCache;
      return {
        err_msg: message,
        err_info: formatErrInfo(meta?.error || meta) || ""
      };
    }
    const errInfoObj = this.logList
      .filter(item => item.level === "error")
      .reverse()?.[0];
    // ...
  }
}
```

`_lastErrCache` 由 `errorSave()` 写入，且 `logUpload()` 不会清空它。开发团队在 `BaseTicketQueue.js` 第 486 行已有明确注释："fallback: 从出票结果中取错误信息（某些场景logger可能已被logUpload清空）"——已知此类竞态存在，但只为 `saveTicketRecord` 加了保护，未给 `transferOrder` 加。

### 2.2 `logList` 被异步清空的机制

1. **错误写入**：`buyTicket.js` 第 351 行 `errorSave("无可用优惠券-无可用卡", {...})` 同时写入 `logList` 和 `_lastErrCache`
2. **异步 logUpload 触发点**：`cardQuanManage.js` 第 668-672 行 `getNewQuan` 的 `finally` 块在 `asyncFlag` 为真时调用 `logger.logUpload()`
3. **fire-and-forget 异步**：`buyTicket.js` 第 411-420 行 `this.cardQuanManage.getNewQuan({ asyncFlag: 1 })` 没有 `await`，与主流程并发执行
4. **清空动作**：`utils.js` 第 1764 行 `logList.splice(0, batchSize)` 上传成功后直接清空

当异步清空发生在 `errorSave` 之后、`transferOrder` 读 `logList` 之前时（换号降级场景下易撞上，因为此前几次尝试可能已触发过 `getNewQuan` 异步），`transferOrder` 拿到空 `logList` → `failReason` 拼成 `"——"` → 消息提醒"原因"显示为空；而出票记录走 `_lastErrCache`，不受影响。

### 2.3 复现时序

```
T0  本次（最后一次换号）尝试 useQuanOrCard
T1  useQuanOrCard 返回 { profit:0, useQuans:[] }   ← 日志："用卡用券返回 {"profit":0,"useQuans":[]}"
T2  buyTicket.js L351 errorSave("无可用优惠券-无可用卡")
       ├─ logList.push({ des:"无可用优惠券-无可用卡", level:"error", ... })
       └─ _lastErrCache = { message:"无可用优惠券-无可用卡", meta:{...} }
T3  transferOrChangePhone 判定已是最后一次换号
       → 调 transferOrder
         （此时此前未完成的异步 getNewQuan 的 finally 块刚好执行 logger.logUpload()
          → utils.js L1764 splice 清空 logList → logList.length === 0）
T4  transferOrder L54-58（修复前）：
       errInfoObj = logList.filter(...).reverse()?.[0]   → undefined
       errMsg = "" ; errInfo = ""
T5  sendWxPusherMessage({ failReason: "——" })           ← 消息提醒"原因"看起来为空

——————————————————————————————————————————————————

U0  saveTicketRecord 被调用（出票流程末尾）
U1  logger.getLastErrMsgAndInfo()
       → 命中 _lastErrCache（T2 时设置，未被 logUpload 清空）
       → 返回 { err_msg:"无可用优惠券-无可用卡", err_info:"..." }
U2  svApi.addTicketRecord({ err_msg:"无可用优惠券-无可用卡", ... })
       → 出票记录的失败原因正确
U3  finally { await logger.logUpload(); }               → 此时才清 logList
```

### 2.4 与项目记忆中 `getBuyPrevCinemaInfo` 隐患的关系

项目记忆中记录的"`getBuyPrevCinemaInfo` 覆写 `buyTicketInfo` 丢失 `plat_name`"隐患确实存在，但**与本次 bug 无因果关系**——失败原因的传递链路完全不经过 `buyTicketInfo`，而是经由 `logger.logList` / `logger._lastErrCache`。

## 三、修复方案

### 3.1 修复原则

最小化修改：将所有平台的 `transferOrder` 中直读 `logList` 的代码统一替换为调用已有的 `Logger.getLastErrMsgAndInfo()` 封装方法，与 `saveTicketRecord` 路径保持一致。封装方法内部已经实现了"优先读 `_lastErrCache`，回退到 `logList`"的容错逻辑，复用它即可获得同样的竞态保护，无需新增 fallback 或并发控制。

### 3.3 修改前后对比

**修改前**（所有平台相同模式）：

```javascript
// 3、平台转单
// 获取转单原因
const errInfoObj = this.logger.logList
  .filter(item => item.level === "error")
  .reverse()?.[0];
let errMsg = errInfoObj?.des || "";
let errInfo = formatErrInfo(errInfoObj?.info?.error) || "";
```

**修改后**：

```javascript
// 3、平台转单
// 获取转单原因（优先读 _lastErrCache，防止 logList 被 logUpload 异步清空导致失败原因为空）
let { err_msg: errMsg = "", err_info: errInfo = "" } =
  this.logger.getLastErrMsgAndInfo() || {};
```

变量名 `errMsg` / `errInfo` 保持不变，后续 `sendWxPusherMessage({ failReason: \`${errMsg}——${errInfo}\` })` 与 `this.platManage.orderTransferByPlat(errMsg, errInfo)` 的调用无需改动。

## 四、修复验证

- 全量搜索 `this.logger.logList.filter` 在 `orderManage.js` 中的引用 → 0 处匹配，确认全部消除
- 全量搜索 `getLastErrMsgAndInfo()` 在 `orderManage.js` 中的引用 → 8 处匹配，覆盖全部平台
- 修复前后行为对比：
  - 正常路径（`logList` 未被清空）：行为完全一致，因为 `getLastErrMsgAndInfo()` 在 `_lastErrCache` 为空时回退到 `logList` 取值
  - 竞态路径（`logList` 被异步清空）：修复前 `errMsg/errInfo` 均为空串，修复后从 `_lastErrCache` 取到正确的失败原因

## 五、工程教训

1. **同一份数据的多个消费点必须走同一个封装方法**：开发团队已知 `logList` 存在异步清空问题，并在 `Logger.getLastErrMsgAndInfo()` 中实现了容错，但 `transferOrder` 绕过了封装方法直读 `logList`，导致同一问题在另一条路径上再次出现。后续凡涉及失败原因 / 错误信息读取，必须统一走 `getLastErrMsgAndInfo()` 或 `getLastErrMsg()`。
2. **修复时需横向排查同类模式**：本次发现 1 个平台问题后立即排查了全部 8 个平台，确认均存在相同代码模式，一次性修复。后续涉及 `logger` 读取的修复应同样做横向扫描，避免逐平台打补丁。
3. **fire-and-forget 异步与主流程共享可变状态需谨慎**：`getNewQuan({ asyncFlag: 1 })` 与主流程共用同一个 `logger` 实例，其 `finally` 块中的 `logUpload()` 会清空主流程还在用的 `logList`。本次修复通过让消费端走缓存规避了竞态，但 fire-and-forget 异步对共享状态的副作用仍是潜在风险，后续如出现相关问题应考虑：(a) 异步任务使用独立的 logger 子实例；或 (b) `logUpload` 改为拷贝后清空，避免影响正在读 `logList` 的调用方。
