## 二、核心变更说明

### 1. DDL（上线前提，必须先执行）
- offer_record / offer_record_fail：`calc_path VARCHAR(500)`、`hit_rule_name VARCHAR(100)`
- ticket_record：`payment_amount DECIMAL(10,2)`、`card_balance DECIMAL(10,2)`、`coupons TEXT`、`use_path VARCHAR(500)`
- **必须【先执行 DDL 再部署前端】**：addOfferRecord/addTicketRecord 为动态 INSERT（obj 键即列名），表无列会报 Unknown column

### 2. 采集链路（公共收口）
```
报价：chenxing offerManage 拼装 calc_path（过滤过程→会员价构成→策略选择）
      → BaseOfferPrice 追加"最终报价X"
      → BaseOfferQueue serOrderInfo 收口 calc_path/hit_rule_name → offer_record
出票：chenxing buyTicket 采集 coupons/cardBalance/paymentAmount/usePath
      → 挂 ticketRes return
      → BaseTicketQueue saveTicketRecord 收口 → ticket_record
```

### 3. 防呆设计
- 所有新字段收口处 `?? ""` 兜底，**防止动态 INSERT 出现 undefined 绑定参数**（mysql 驱动会报错）
- coupons 兼容数组（chenxing 传数组→自动 JSON.stringify）与字符串（其他系列未传→""）
- 提前 return 路径（转单/换号/测试模式）不采集，saveTicketRecord 解构默认值兜底，不影响原逻辑

### 4. calc_path 示例（chenxing 报价）
```
初始匹配命中5条→电影格式过滤剩3条→券库存过滤剩2条→会员价:真实45×折扣0.95%=成本42.75取整42.5+加价3=45.5→策略对比:会员45.5<固定46，选会员价→最终报价45.5
```

### 5. use_path 示例（chenxing 出票）
```
用券2张→卡尾号1234付券手续费3.96     （用券场景）
换号1次→用卡尾号5678→支付前余额200.5→实付36.6   （换号+用卡场景）
```

## 十五、2026-08-19 真实数据量驱动：分片存储重构（V4.6）

> 用户提供真实数据量：**1G/用户/天**（全站 10G/天、日订单几十万级），推翻此前估算（60~100MB/天）。

### 方案演进与裁定

| 方案 | 评估 | 裁定 |
|------|------|------|
| 按用户单日单文件（V4.5） | 1G/文件，逐行 parse 查询极慢（10s+） | ❌ 放弃 |
| 一订单一文件 | 几十万订单/天 → 几百万文件/15 天，inode/遍历/清理全崩 | ❌ 不可行（用户判断正确） |
| **订单号稳定哈希分片**（128 片） | 单文件 ~8MB/天（最坏 ~16MB，hash 实测最大/平均 ≤2.0）；订单查询 **O(1) 定位**；文件数 128×用户×天数可控；清理按 {userId}/{date} 目录级 | ✅ **采用** |

### 实现（auto-ticket-service/api/traceFile.js 重构 + cron 同步）

- 目录：`logs/trace/{userId}/{date}/shard-{hash(order_number)%128}.log`（djb2 稳定哈希，同订单恒同分片；无 userId 落 common/）
- 查询：订单号 → hash → 定位单文件（.log 或自动解压 .log.gz）；无订单号按用户遍历当日分片
- **容量控制组合**：保留 7 天（字典 trace_retain_days）+ 明文 3 天后 gzip 归档（字典 trace_active_days，~5:1）+ 全站超 trace_max_size_mb（2048MB）**降级仅写 error 行**（5 分钟检查缓存）+ 单条 8KB 截断
- 清理：删超期 {userId}/{date} 目录（一天=一个目录）+ 归档超明文期分片（先写 .gz 再删原文件，防中途崩溃丢数据）
- 预算：7 天保留（3 明文 + 4 归档）≈ 38G，紧贴服务器 45G 剩余——字典可调降保留/提高压缩比

### 验证（全链路脚本实测）

写入 2 用户 3 单 → 订单定位查询各命中（同订单同分片）→ brief 字段正确 → 管理员遍历聚合 → 过期目录删除。全部通过；测试数据已清理。

**注意**：容量模型按"1G/用户/天"是上限估算，实际以 §7.3 上线后 24h 实测为准（8KB 截断占比、gzip 压缩比列为必测项），字典随时可调。

- **复测事实**：用户列出 5 条残留日志（全部 infoSave，且全部来自**已 init 的订单级 logger**）：
  - `BaseOfferQueue:538 "新的待报价订单"`（订单级 logger，537 行 init(item) 后紧邻打点）
  - `BaseOfferQueue:576/582 "订单入队-调度诊断"`、`:814 "订单报价链路开始"`、`:888 "进入 singleOffer"`（同一订单级 logger 传递链路，832 行显式传入）
  - `chenxing/cardQuanManage:839 "不需要更新券库存"`（logType:3，809 行已 init(this.order)）
- **根因 ① 异步竞态**：`_applyV3Flags` 是 async（动态 import dictTable/constant + 查库）——`init()` 不 await，流程早期日志（如"新的待报价订单"紧跟 init）打点时 v3Mode 仍 false → infoSave 全量入库
- **根因 ② 反查失败**：`GET_APP_TYPE_LIST = () => cinemaStore.getCanAppTypeList`（**当前登录账号"可用影线"列表**）——若该影线不在列表（跨账号/多影线场景），`find` 反查 `appTypeCode=undefined` → `v3Mode=false` 恒成立（5 条中 4 条晚于 import 完成，只能由本根因解释）
- **修复（src/common/logger.js）**：
  1. **订单自带 `app_type_code` 直传优先**：`init({ plat_name, order_number, app_name, app_type_code })`——订单对象自带该字段（如 `chenxing_applet`，日志可见），最可靠；缺失时回退 getCanAppTypeList 反查
  2. **同步预判定 `_applyV3FlagsSync`**：init 内同步读 localStorage `dictTableList` 缓存（status=1 过滤 → `log_v3_enabled_series` 值）按 app_type_code 立即判定 → **消除异步竞态**（init 返回即 v3Mode 生效）
  3. **异步无条件判定（2026-08-20 简化）**：有 app_type_code 时同步（localStorage 缓存）与异步（dictTable store 同源缓存）的 series 相同 → 结果必然一致，无需"同步成功则不覆盖"标记（曾引入 `_v3SyncApplied`，复查确认多余已删除）；无 app_type_code 时异步反查补判；catch 静默不覆盖
  4. `commonQuanStock.js:84-88` 补 `app_type_code` 传递（order 解构可得）
- **调用点说明**：传整个订单对象的 init（BaseOfferQueue:537/758、chenxing 系列 orderManage/cardQuanManage/offerManage 等 `init(order/this.order)`）自动携带；无 order 对象的参数解构点（orderManage 轮询、updateCardDayUse 辅助日志、http 请求级）保持异步反查兜底
- **回归测试**：新增 `src/common/tests/v3ModeSync.test.js`（6 用例：白名单命中同步生效/未命中/无 app_type_code 同步不判/无缓存/脏数据/v3Mode 下 infoSave 不入 L1 仍进 traceBuffer）

- **复测跟进（2026-08-20）**：表格能回显后，info 列展示 `[object Object]`——明细 info 是**对象**（traceBuffer 原样入参），el-table 默认字符串化。修复：info 列加 `:formatter="formatTraceInfo"`（对象 JSON.stringify 紧凑序列化；字符串/空值原样返回；序列化失败 String 兜底）
