# 金逸系列实体券算价传参（voucher_code_type）修复

- 日期：2026-10-17
- 问题现象：实体券参与算价时价格计算不正确
- 根因：算价接口的 `voucher_code_type` 被**硬编码为电子券类型**，未按券种区分

## 一、背景与根因

金逸算价接口 `POST /ticket/{channelCode}/cinema/{cinema_id}/order/change/?version=tp_version`
用 `voucher_code` + `voucher_code_type` 描述「本次核销哪张券、哪种券」。
改造前 `jinyi/orderManage.js` 在有用券时**无条件**写入：

```js
params.voucher_code = quan_code;
params.voucher_code_type = "VISTAX_VOUCHER"; // 只有电子券类型
```

券种信息其实**已经存在**：`quan_type.quan_kind`（1=电子券，2=实体券，2026-10-15 方案已落地），
并经 `useQuanOrCard` → `offerRule` 带到出票流程（`buyTicket.js` 的 `getNewQuan` 已在用
`offerRule.quan_kind`）。算价处漏用了它，导致实体券按电子券类型算价。

## 二、修改文件清单

| 文件 | 变更 |
|---|---|
| `src/common/autoTicket/buyTicket/jinyi/cardQuanManage.js` | `useQuanOrCard` 查券类型信息后，把 `quan_kind` 回填到 `offerRule`（与既有 `quan_flag`/`quan_desc` 等同一处） |
| `src/common/autoTicket/buyTicket/jinyi/buyTicket.js` | 算价入参增加 `quan_kind: offerRule?.quan_kind` |
| `src/common/autoTicket/buyTicket/jinyi/orderManage.js` | `priceCalculation` 接收 `quan_kind`，按 `quan_kind == 2 ? "VOUCHER" : "VISTAX_VOUCHER"` 取值 |
| `src/common/tests/jinyiPriceVoucherCodeType.test.js` | **新增** 5 例：算价接口实际入参断言 |

无接口契约变更（仅字段取值变化）、无 DB 变更、无后端改动、**未改动 `quanListAdapter.js`**、
未触碰共享模块。

## 三、核心变更说明

### 1. 券种来源：直接取 `offerRule.quan_kind`

不做任何"推断"，券种就是券类型配置字段 `quan_kind`，由 `offerRule` 带出：

- `offerRule` 来自后端 `queryOfferInfo`，其通用合并会把 `quan_type` 的非同名列一并下发
  （`auto-ticket-service/api/offerRecord.js:757-765`），`quan_kind` 由此可得；
- **更关键的一步**：`useQuanOrCard` 本就会按**最终选中的券类型**查一次券类型信息
  （`getQuanInfo(offerRule.quan_value, appFlag)`，`SELECT *`），因此顺手回填
  `offerRule.quan_kind` 即可保证券种与**实际用于出票的那条券类型记录**一致。

```js
// cardQuanManage.js（与 quan_flag/quan_desc 等同一处）
offerRule.is_store = quanInfo?.is_store;
offerRule.black_quans = quanInfo?.black_quans;
offerRule.quan_kind = quanInfo?.quan_kind; // 新增
```

这样处理的必要性：`useQuanOrCard` 在上方会把 `offerRule.quan_value` 改写为
**另一个券类型**的场景真实存在 —— 灵活用券（`auto_quan_value`）、多 `quan_value` 按库存收敛、
以及"强制取第一个"容错。这些情况下报价记录里的 `quan_kind` 可能已不是最终用券的券类型，
故必须用 `getQuanInfo` 的结果覆盖一次。

### 2. 透传与取值

```js
// buyTicket.js 第 5 步算价
quan_code,
quan_kind: offerRule?.quan_kind,

// orderManage.js priceCalculation
params.voucher_code_type = quan_kind == 2 ? "VOUCHER" : "VISTAX_VOUCHER";
```

判定口径与绑券分支（`cardQuanManage.js` 的 `quan_kind == 2`）**完全一致**：
仅 `2` 走实体券，其余（`1`、`undefined`、空、其他值）一律按电子券兜底，宽松比较兼容字符串 `"2"`。

### 3. 为什么不需要"混用"处理

`voucher_code_type` 是单值字段，而 `voucher_code` 可能逗号拼接多张券。
由于券种是**券类型级**属性，而一次出票只用**一个券类型**的券
（`useQuanOrCard` 按单个 `quan_flag`/`quan_desc` 过滤，且 `offerRule.quan_value` 已收敛为单值），
所以券种天然唯一，不存在混用歧义 —— 这也是取 `offerRule.quan_kind` 相对
"逐张券推断券种"的优势。

### 4. 明确"不改什么"

- 算价其余参数（`discount_id` / `discount_type` / `card_id` / `pay_type` / `rewards` 等）一律未动；
- 支付/创建订单接口（`order/payment`）本身不接收券参，无需传递 `voucher_code_type`；
- 三个算价调用点中只有 `buyTicket.js` 第 5 步传券码；`buyTicket.js` 锁座价格明细与
  `offerManage.js` 报价取价不传券，`voucher_code_type` 仍为空串，行为不变；
- 选券、券库存、黑名单、利润计算链路未改动；
- 绑券分支（`getNewQuan`/`bandQuan` 的 `quan_kind` 用法）未改动。

## 五、回归风险评估

| 风险 | 评估 | 缓解 |
|---|---|---|
| `offerRule.quan_kind` 取不到（旧后端未做通用合并） | 低：算价路径不受影响 —— `useQuanOrCard` 的 `getQuanInfo` 走 `SELECT *`，只要 `quan_kind` 列存在即能回填 | 若该列未上线，则券种恒为 `undefined` → 兜底电子券（行为与改造前一致，不报错）；上线顺序按 2026-10-15 方案要求 |
| `getQuanInfo` 返回空导致券种被覆盖为 undefined | 极低：用券场景下 `quanInfo` 为空时，同处的 `quan_flag`/`quan_desc` 已先失效、选券会提前报错，走不到算价 | 与既有 7 个字段的回填方式保持一致，不额外加兜底以免偏离风格 |
| 实体券算价仍不正确（还缺其他字段） | 低-中：本次只按需求调整 `voucher_code_type`；若实体券算价还需其他字段（如 `voucher_password`）配合，需再补 | 上线后看「计算价格参数 / 返回」日志与 `paymentAmount`；异常会走既有「计算价格异常 → 转单」兜底 |
| 电子券链路回归 | 极低：`quan_kind` 为 `1`/缺失时取值与改造前逐字一致 | 58 例回归通过 |
