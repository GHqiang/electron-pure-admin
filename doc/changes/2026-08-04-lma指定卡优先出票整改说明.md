# LMA 系列指定卡优先出票整改说明

> 日期：2026-08-04
> 状态：**已实施**
> 背景：LMA 系列出票时希望控制优先使用指定几个会员卡的号出票（卡号通过字典表配置）。整改分两层生效：登录信息按"是否绑定指定卡"特殊排序（决定换号尝试顺序）+ 用卡环节优先尝试指定卡（决定换卡尝试顺序）。

---

## 1. 需求与场景界定

| 项 | 内容 |
| --- | --- |
| 生效系列 | 仅 LMA（`lma`） |
| 生效场景（优先） | **纯用卡出票**：`offerRule.offer_type != "1"`（直接用卡余额支付），指定卡账号与换卡候选绝对优先 |
| 生效场景（反向规避，2026-08-27 补充） | **用券补钱出票**：券单且需用卡付差价。语义相反——换卡候选中指定卡沉底、活跃卡恰为指定卡时让位，仅在其它卡都付不起时最后兜底；登录账号排序不参与反向调整，维持券库存排序主导（见第 8 节） |
| 指定卡来源 | 字典表新增 `dict_type = lmaPriorityCardNos`，`dict_value` 逗号分隔多个卡号 |
| 排序语义 | **绝对优先**：指定卡绑定的账号在登录信息排序中排最前（先于 `first=1` 标记与当前用户手机号）；选卡时指定卡排在其他换卡候选之前（活跃卡天然最优先，不改变） |
| 卡有效性判定 | 仅按卡号匹配（查询时过滤 `status=1`）。日/月限额、指定影院等动态条件不参与排序判定，超出限额时靠现有换号/换卡机制自动回退 |

## 2. 现状分析

### 2.1 登录信息排序（改造前）

`lma/buyTicket.js` 的 `getCinemaLoginInfo()`（L81-120）按如下优先级排序：

1. `first === "1"`（登录信息维护页"优先"标记）
2. 当前登录用户手机号（`tokens.userInfo.phone`）

调用链（`BaseBuyTicket.singleTicket`）：

```
singleTicket()
  → getCinemaLoginInfo()   // 排序登录信息（此时 offerRule 尚未获取，不知道是否纯卡）
  → getOrderOfferRule()    // 获取报价规则（拿到 offer_type）
  → oneClickBuyTicket()    // 出票主流程（offerRule 可用）
```

`oneClickBuyTicket` 内 `currentParamsInx === 0`（首次出票）分支已有**券单按券库存排序**的先例（L226-247），本次纯卡排序与其并列。

### 2.2 选卡流程（改造前）

`lma/cardQuanManage.js` `useCardHandle()`（L63-154）：

1. `getCardList()` 拉 LMA 实时卡列表（活跃卡 `unshift` 至首位）
2. `getUsableCardList()` 从 SV 库查 `card_record`（`status=1`），按**登录账号手机号**过滤 → 日/月限额过滤 → 指定影院过滤（该方法的排序仅用于存在性判定，**不影响**换卡尝试顺序）
3. `cardList` 按 LMA API 返回顺序过滤保留可用卡
4. `useCard()`：活跃卡余额足够直接使用；否则遍历 `otherCardList`（LMA API 顺序）逐张 `changeCardHandle` 换卡，取余额足够的第一张

**关键结论**：换卡尝试顺序 = LMA API 返回顺序（活跃卡 + `sleep` 数组顺序），不受 `getUsableCardList` 排序影响。因此"优先用指定卡"必须在 `useCard()` 遍历 `otherCardList` 前重排，或在 `useCardHandle` 传入前重排。

### 2.3 卡与登录账号的关联

- 卡：`card_record` 表，字段 `card_num`（LMA 中 `card_id` 与 `card_num` 同值）、`mobile`、`status`
- 登录账号：`login_record` 表，字段 `mobile`、`session_id`（LMA 即 `lmaToken`）、`member_pwd`
- 关联键：**`mobile` 手机号**（`getUsableCardList` L322-333 用登录账号手机号过滤卡）

因此"优先用指定卡的号出" = 把指定卡绑定的 `mobile` 对应的登录账号排最前 → 换号机制（`currentParamsInx++`）会优先尝试这些账号 → 这些账号只能使用自己绑定手机号的卡（含指定卡）。

## 3. 整改内容

### 3.1 字典表配置项

| 字段 | 值 |
| --- | --- |
| `dict_type` | `lmaPriorityCardNos` |
| `dict_label` | LMA优先出票卡号 |
| `dict_value` | 逗号分隔卡号，如 `200001,200002,200003` |
| `status` | `1` |

字典管理页（`src/views/dictManage/index.vue`）通用 CRUD 已支持，无需代码改动，运维添加记录即可。配置的 `rule`/`user_id` 按现有权限机制控制。

### 3.2 `lma/cardQuanManage.js`

**新增 `getPriorityCardNos()`**：读字典表配置，返回卡号数组（trim + 去空），供两处复用：

```js
// 读取字典表配置的优先出票卡号列表（无配置返回空数组）
getPriorityCardNos() {
  const dictStore = dictTable();
  return (dictStore.dictInfo.lmaPriorityCardNos || "")
    .split(",")
    .map(item => item.trim())
    .filter(Boolean);
}
```

**新增 `getPriorityCardMobileList()`**：查询 SV 卡列表，返回指定卡号绑定的手机号集合（去重），供登录信息排序使用：

```js
// 获取指定卡号绑定的手机号集合（登录信息排序用；查卡异常返回空数组，不影响出票）
async getPriorityCardMobileList() {
  const { appFlag } = this;
  const priorityCardNos = this.getPriorityCardNos();
  if (!priorityCardNos.length) return [];
  try {
    const res = await svApi.queryCardList({
      app_name: appFlag,
      rule: tokens.userInfo.rule,
      status: "1",
      isNeedTotalNum: 0,
      queryFields: "card_num,mobile"
    });
    const list = res.data?.cardList || [];
    return [
      ...new Set(
        list
          .filter(item => priorityCardNos.includes(item.card_num))
          .map(item => item.mobile)
      )
    ];
  } catch (error) {
    this.logger.errorSave("获取指定卡号绑定手机号异常", { error });
    return [];
  }
}
```

**`useCardHandle()` 选卡排序**：纯卡场景（`offer_type != "1"`）下，`otherCardList` 按"指定卡在前"稳定重排后再传入 `useCard`：

```js
// 纯用卡场景优先尝试指定卡：指定卡排到换卡尝试列表最前（组内保持原顺序）
if (offer_type != "1") {
  const priorityCardNos = this.getPriorityCardNos();
  if (priorityCardNos.length) {
    otherCardList = [...otherCardList].sort((a, b) => {
      const aHit = priorityCardNos.includes(a.card_number);
      const bHit = priorityCardNos.includes(b.card_number);
      if (aHit && !bHit) return -1;
      if (!aHit && bHit) return 1;
      return 0;
    });
  }
}
```

**`useCardHandle()` 券单补钱分支（2026-08-27 补充）**：配置了字典项时，用卡环节按场景分流——纯卡前置如上；券单补钱（函数内即 `offer_type == "1"`）则反向沉底，且活跃卡恰为指定卡时让出首选、并入候选末尾兜底：

```js
// 用卡环节按指定卡调整换卡尝试顺序（配置了字典项才生效）：
// 纯用卡场景指定卡排最前；券单（用券补钱）场景相反——指定卡沉底，仅在其它卡都付不起时最后兜底
const priorityCardNos = this.getPriorityCardNos();
if (priorityCardNos.length) {
  if (offer_type != "1") {
    // …纯用卡前置重排（同上）
  } else {
    // 券单补钱：指定卡排到换卡尝试列表末尾（组内保持原顺序）
    otherCardList = [...otherCardList].sort((a, b) => {
      const aHit = priorityCardNos.includes(a.card_number);
      const bHit = priorityCardNos.includes(b.card_number);
      if (aHit && !bHit) return 1;
      if (!aHit && bHit) return -1;
      return 0;
    });
    // 活跃卡恰为指定卡时不直接消耗：移出首选、并入候选末尾，仅作最后兜底
    if (activeCard && priorityCardNos.includes(activeCard.card_number)) {
      const demotedActiveCard = activeCard;
      otherCardList.push(demotedActiveCard);
      activeCard = null;
      this.logger.infoSave(
        "券单补钱场景活跃卡为指定卡，改为最后兜底尝试",
        { demotedActiveCard }
      );
    }
    this.logger.infoSave("券单补钱场景按指定卡号沉底排序换卡列表", {...});
  }
}
```

注意：LMA 的 `useCardHandle` 仅由 `lma/buyTicket.js` 在 `offer_type != "1" || (offer_type == "1" && quan_fee)` 时调用，因此函数内 `offer_type == "1"` 即为"用券补钱"，无需重复判断 `quan_fee`。

### 3.3 `lma/buyTicket.js`

`oneClickBuyTicket` 的 `currentParamsInx === 0` 分支，券库存排序（`offer_type == 1`）旁新增纯卡排序：

```js
// 纯用卡出票：指定卡号绑定的登录账号绝对优先（先于 first 标记与当前用户手机号）
if (offerRule.offer_type != "1") {
  const priorityMobiles = await this.cardQuanManage.getPriorityCardMobileList();
  if (priorityMobiles.length) {
    this.currentParamsList = this.currentParamsList.sort((a, b) => {
      const aHit = priorityMobiles.includes(a.mobile);
      const bHit = priorityMobiles.includes(b.mobile);
      if (aHit && !bHit) return -1;
      if (!aHit && bHit) return 1;
      return 0; // 组内保持 getCinemaLoginInfo 已排好的顺序（现代 V8 稳定排序）
    });
    this.logger.infoSave("登录信息按指定卡号优先排序后", {
      currentParamsList: this.currentParamsList,
      priorityMobiles
    });
  }
}
```

## 4. 整改后数据流

```
singleTicket
 → getCinemaLoginInfo()            // 原排序：first → 当前用户手机号（不变）
 → getOrderOfferRule()             // 拿到 offer_type
 → oneClickBuyTicket()
    └ currentParamsInx === 0
       ├ offer_type == "1"         → 现有券库存排序（不变）
       └ offer_type != "1"（纯卡） → 指定卡账号绝对优先排序
          → useCardHandle()
             ├ 活跃卡余额足够      → 直接使用（含指定卡时天然优先）
             └ 其他卡换卡          → 指定卡优先尝试 → 余额足够的第一张
          → 用卡失败 → currentParamsInx++ 换号回退到下一账号

   offer_type == "1" && quan_fee（券单补钱，账号排序维持券库存序不变）
     → useCardHandle()
        ├ 活跃卡为普通卡且余额足够 → 直接使用（不变）
        ├ 活跃卡恰为指定卡         → 让位：并入候选末尾
        └ 其他卡换卡               → 指定卡沉底尝试：普通卡先试，
                                     全部付不起才轮到指定卡兜底
     → 用卡失败 → 现有换号/转单机制回退（不变）
```

## 5. 边界与降级

| 场景 | 行为 |
| --- | --- |
| 未配置字典项 / 配置为空 | 跳过排序，行为与现状完全一致 |
| 查卡接口异常 | `getPriorityCardMobileList` 返回 `[]`（记日志），不影响出票 |
| 指定卡已超日/月限额、被指定影院过滤、休眠 | 账号仍排最前，用卡失败后现有换号/换卡机制自动回退，不阻断流程 |
| 配置的卡号不存在 / 无绑定账号 | 自然匹配不到 mobile，排序无效果 |
| 指定卡绑定多个账号 | 全部排最前，无碍 |
| 用券补钱场景（券单走用卡付差价） | 指定卡反向规避：换卡候选沉底、活跃卡让位末位兜底（2026-08-27 补充，见第 8 节）；登录账号排序仍由券库存排序主导 |
| 排序稳定性 | 组内保持原相对顺序（现代 Electron V8 稳定排序，项目现状依赖） |

## 8. 补充说明（2026-08-27）：用券补钱场景反向规避指定卡

### 8.1 需求缘由与语义界定

前版功能只覆盖"纯用卡优先"，券单场景属于中性不生效。业务要求相反：**用券补钱的订单应优先不用这些指定卡**——把指定卡留给纯用卡单。语义定为「沉底兜底」而非「彻底排除」：

- 其它卡能支付补差价时，绝不消耗指定卡；
- 所有非指定卡都付不起时，仍允许动用指定卡完成出票（宁出票、不强失败转单）。

若业务后续要求"宁可转单也不耗指定卡"，属「彻底排除」语义（需从候选中剔除指定卡，且活跃卡命中时主动放弃本次用卡），当前未采用。

### 8.2 实现要点

- 改造点仅 `lma/cardQuanManage.js` 的 `useCardHandle()`（代码见 3.2 节补充片段）：按 `offer_type` 分流；券单补钱时 `otherCardList` 指定卡沉底（稳定排序，组内保持原相对顺序），日志 `券单补钱场景按指定卡号沉底排序换卡列表`。
- **活跃卡让位是闭环关键**：`useCard()` 对余额足够的活跃卡会不经候选列表直接使用；若当前账号活跃卡恰为指定卡，将绕过沉底排序导致规避落空。故券单补钱时检测到活跃卡为指定卡，即将其移出首选并 push 到候选末尾——转为普通兜底候选，走既有 `changeCardHandle` 换卡链路（余额以换卡返回为准），日志 `券单补钱场景活跃卡为指定卡，改为最后兜底尝试`。
- **登录账号层不做反向排序**：券单场景账号顺序由券库存排序主导；若把指定卡绑定账号也沉底，会把持券的指定账号排到无券账号之后，引发报券失败的空转换号。"不用这些卡"在选卡层已闭环——即便最终轮到指定卡账号，其指定卡也已处于末位兜底。
- **余额判定归一化（配套修复，见 8.4）**：LMA 的 `money_str` 带 `￥` 前缀（如 `￥123.45`），`useCard()` 原有的 `money_str < Number(...)` 直接比较得 `NaN` 恒为 false，导致"余额不足继续换卡"判定失真、指定卡兜底永不触发。已在 `useCard()` 两处判定前用 `toNum()` 归一化（`parseFloat(String(v).replace(/[^\d.]/g, "")) || 0`，与 `syncCardBalanceToSv` 及出票后卡余额采集既有提取方式一致）。
- 其余系列（chenxing/fenghuang/jinyi/wanda/sfc/ume/h5ume）同名方法互不相干，不受影响。

### 8.3 验证清单（测试订单 + 日志）

1. 纯用卡回归：换卡尝试顺序仍为指定卡在前（日志 `纯用卡场景按指定卡号优先排序换卡列表` 不变）。
2. 券单补钱·普通账号：行为与历史一致。
3. 券单补钱·当前账号活跃卡为指定卡：日志出现 `券单补钱场景活跃卡为指定卡，改为最后兜底尝试`，随后先试其它卡。
4. 券单补钱·全部普通卡余额不足：日志确认普通卡逐张报 `换卡后卡余额不足,准备继续换卡`，最后才尝试指定卡并可成功扣款完成出票。
5. 未配置 `lmaPriorityCardNos` 字典项：两场景均与改造前完全一致。
6. 券单补钱·活跃卡为普通卡且余额不足（`money_str` 为 `￥xx.xx` 格式）：日志出现 `当前活跃卡余额不足,准备换卡`（而非误判足够直接使用），走换卡链路。

### 8.4 配套修复（2026-08-27）：`money_str` 余额判定归一化

**问题**：LMA 会员卡接口返回的 `money_str` 为 `￥123.45` 格式（`getCardList`/`changeCard` 均如此；出票侧 `price_str`、`card_balance` 同格式，见 buyTicket.js L659/L860 的 `replace("￥","")` 处理）。`useCard()` 原有的 `money_str < Number(member_total_price)` 直接比较：`Number("￥123.45")` 为 `NaN`，`NaN < x` 恒为 `false`，导致：

- 活跃卡余额判定恒"足够" → 余额不足的活跃卡被直接使用，出票阶段才失败；
- 换卡循环余额判定恒"成功" → 第一张卡即 break，"指定卡沉底兜底"**永远不会被触发**（仅账号内无普通卡、或普通卡全部报 error 时才会轮到指定卡）。

**修复**：`useCard()` 内新增 `toNum()`：`parseFloat(String(value).replace(/[^\d.]/g, "")) || 0`，两处判定改为 `toNum(money_str) < Number(member_total_price)`。对纯数字字符串幂等（`"123.45"` → `123.45`），空/异常返回 `0`（视为余额不足，安全方向）。与 `syncCardBalanceToSv`（cardQuanManage.js L360-361）及出票后卡余额采集（buyTicket.js L859-860）既有提取方式一致。

**影响**：
