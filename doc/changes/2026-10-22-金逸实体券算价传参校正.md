## 一、问题

2026-10-17 版按 `quan_kind == 2 → "VOUCHER"` 传 `voucher_code_type`，且沿用了电子券的
`discount_type = ""`。抓包确认实体券的真实取值与此不同，导致实体券算价传参仍不正确。

**生产实证**（订单 `12610221407050215`，洋葱 / `subojinsong` / 团购券 `subotuantiquan`）：
算价接口返回 `ret: 0 / successfully`，但返回体 `voucher_use: {}`、`voucher_discounts: []`，
`ticket_payment_total_price` 仍为 88（全价）—— **两张实体券完全未被抵扣**，
随后命中「用完券发现支付金额大于券手续费\*票数，走转单」，`order_status = 2`。

抓包（order_id `261022141010004691`）里实体券算价的完整参数：

| 字段 | 实体券实测值 | 本次校正前（生产实际） |
|---|---|---|
| `order_id` | `261022141010004691` | 同（lockOrderId） |
| `discount_id` | `0` | `0` |
| **`discount_type`** | **`TP_VOUCHER`** | `""` ❌ |
| **`card_id`** | **空**（纯券抵扣，未用卡） | `370977`（带了会员卡） ❌ |
| **`pay_type`** | **`WECHAT`** | `MEMBER` ❌ |
| `rewards` | `[]` | `[]` |
| `use_rewards` | `Y` | `Y` |
| `use_limit_cards` | `N` | `N` |
| `limit_cards` | `[]` | `[]` |
| `voucher_code` | `TGQ4000304206550,TGQ4000304211022`（2 张，逗号拼接） | 同格式 |
| **`voucher_code_type`** | **`VGC_T`** | `"VOUCHER"` ❌ |

该次算价返回 `ticket_total_price: 117.8`、`ticket_payment_total_price: 0`、
`voucher_use.use_num: 2`、`use_codes` 为上述两张券码 —— 即两张实体券全额抵扣。

## 三、核心变更

```js
if (quan_code) {
  params.voucher_code = quan_code;
  if (quan_kind == 2) {
    // 实体券：与 web 端实测一致；纯券抵扣，不带会员卡
    params.discount_type = "TP_VOUCHER";
    params.voucher_code_type = "VGC_T";
    params.card_id = "";
    params.pay_type = "WECHAT";
  } else {
    // 电子券：维持改造前取值
    params.discount_type = "";
    params.voucher_code_type = "VISTAX_VOUCHER";
  }
}
```

| 场景 | `discount_type` | `voucher_code_type` | `card_id` | `pay_type` |
|---|---|---|---|---|
| 实体券（`quan_kind == 2`） | `TP_VOUCHER` | `VGC_T` | **空** | `WECHAT` |
| 电子券（`1` / 缺失 / 其他） | `""`（改造前） | `VISTAX_VOUCHER`（改造前） | 原样传入 | `MEMBER`（改造前） |
| 不用券 | `MARKETING`（默认） | `""` | 原样传入 | `MEMBER` |

- **券种 1（电子券）完全不动**：四个字段取值与改造前逐字一致；
- 券种仍来自 `offerRule.quan_kind`（`useQuanOrCard` 已按最终券类型回填），**没有**改成按券码来源推断；
- 判定用宽松比较，兼容后端下发字符串 `"2"`；
- 只有「本次用券且券种为 2」才清空 `card_id`；不用券时 `card_id` 原样保留（锁座价格明细等场景不受影响）。

## 五、回归风险评估

| 风险 | 评估 | 缓解 |
|---|---|---|
| **实体券且券类型配置了 `quan_fee > 0`** | 需注意：本次对券种 2 一律不传 `card_id` 且 `pay_type = WECHAT`，券手续费将不再走会员卡。而 `buyTicket.js` 在算价后仍会因 `quan_fee > 0` 挑卡做余额同步（`buyTicket.js:547-550`），两侧口径可能不一致 | 抓包场景 `quan_fee = 0`，本次按需求对齐。若确实存在 `quan_fee > 0` 的实体券类型，需再确认手续费支付方式（是否改为「`quan_fee > 0` 时保留 `card_id` 与 `MEMBER`」） |
| 电子券链路回归 | 极低：电子券四个字段取值与改造前逐字一致，且有对应用例 | 59 例回归通过 |
| 实体券仍缺其他字段 | 低：抓包已覆盖算价全部入参；返回体 `voucher_use` 是否非空是最直接的成功判据 | 上线后看「计算价格参数 / 返回」日志 |
| 券种取不到 | 低：`offerRule.quan_kind` 由 `getQuanInfo`（`SELECT *`）回填；取不到时兜底电子券，行为与改造前一致 | 见 2026-10-17 文档 §五 |

## 六、上线观察指标

1. 打包发布（`yarn build`）后生效；
2. 实体券订单：`计算价格参数` 日志应为 `discount_type: "TP_VOUCHER"`、`voucher_code_type: "VGC_T"`、
   `card_id: ""`、`pay_type: "WECHAT"`；
   `计算价格返回` 应出现 `voucher_use` 非空（`use_num` = 票数）、`ticket_payment_total_price` 为 0 或等于券手续费；

   出票成功率持平；
4. 若实体券仍 `voucher_use: {}`，取日志与本文第一节参数逐字段比对。
