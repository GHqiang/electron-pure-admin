# 2026-08-19 各平台待出票订单日志补齐 oldOrder

## 背景

排查各平台「XX新的待出票订单」日志时发现：

- 票圣日志中 `oldOrder` 为字符串 `"undefined"`（`{"newOrder":{...},"oldOrder":"undefined"}`），缺少真实旧订单信息；
- 猎人、哈哈、省三个平台的日志完全没有 `oldOrder` 字段。

## 根因

1. **票圣/麻花**：数据转换时 `order_number` 先占位为出票单号 `id`，调 `orderDetail` 后又替换为报价单号 `res.putOrderId || id`；而日志中 `oldOrder: rawStayList.find(order => order.id === item.order_number)` 仍用报价单号去匹配原始列表的 `id` → 匹配失败返回 `undefined`，经 `sanitizeLogInfoForUpload`（`String(v)`）序列化成字符串 `"undefined"`。
2. **猎人/哈哈/省**：日志组装时从未携带 `oldOrder` 字段。

## 修改文件清单

| 文件 | 变更 |
| --- | --- |
| `src/common/platform/fetchers/PiaoShengOrderFetcher.js` | oldOrder 匹配键由 `item.order_number` 改为 `item.plat_order_sn`（保留的原始出票单号），保证必然命中原始待出票列表条目 |
| `src/common/platform/fetchers/MahuaOrderFetcher.js` | 同上（与票圣结构完全一致，一并修复） |
| `src/common/platform/fetchers/LierenOrderFetcher.js` | 日志 info 增加 `oldOrder: stayList.find(order => order.order_number === item.order_number)` |
| `src/common/platform/fetchers/HahaOrderFetcher.js` | 日志 info 增加 `oldOrder: rawStayList.find(order => order.orderNumber === item.order_number)`（原始字段 `orderNumber`） |
| `src/common/platform/fetchers/ShengOrderFetcher.js` | 日志 info 增加 `oldOrder: rawStayList.find(order => order.code === item.order_number)`（原始字段 `code`） |

## 核心变更说明

各平台「XX新的待出票订单」日志（`logUpload` type=2 拉单链路）现在统一携带：

- `newOrder`：转换处理后的新订单（原有）；
- `oldOrder`：原始待出票列表中的对应条目，便于对照转换前后字段；
- 猎人/省额外保留 `isAgain`（换座成功重新出票标识，原有）。

其余平台（芒果/蚂蚁/商展/守兔/洋葱/影划算）经核查 `oldOrder` 匹配键与转换后 `order_number` 来源一致（`order_number`/`tradeno`/`order_sn`/`orderId`/record_id 链路），无需修改。

## 测试结果

- 修改的 5 个文件 `node --check` 语法校验全部通过；
- 全量 Jest：15 套件通过；4 套件失败均为既有环境问题（`service-health-detection` 业务断言失败；`QueueFactory/PlatformFactory/BasePlatformAdapter` 因 `src/utils/auth.js` 不存在导致的模块解析失败），与本次修改无关（本次未改动被测模块）。

## 回归风险评估

低。改动仅限 fetcher 日志 `info` 组装：

- 票圣/麻花：匹配键指向只读字段 `plat_order_sn`（转换后从未变更），不影响业务逻辑；
- 猎人/哈哈/省：新增字段为纯日志用途，`find` 无副作用；
- 未触及报价队列（`BaseOfferQueue` 的「新的待报价订单」日志本就含 `oldOrder`）、出票逻辑与上传链路。
