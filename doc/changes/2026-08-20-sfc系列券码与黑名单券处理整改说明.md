# sfc 系列券码与黑名单券处理整改说明

> 日期：2026-08-20
> 状态：已实施（版本 6.6.37 提交）
> 关联：doc/plans/2026-08-18-报价出票日志整改-最终详细设计文档.md（V3 L0 字段采集）
> 用途：供独立评审/其他模型检查的完整整改说明

---

## 一、问题背景

### 问题 1：创建订单时黑名单券处理失效（线上券场景）

生产日志样例（订单使用线上券 `coupon_id:"977577,989692"`）：

```
创建订单参数        {"params":{...,"coupon_id":"977577,989692","card_id":"92917",...}}
创建订单异常        {"error":"{\"status\":0,\"errcode\":\"-1\",\"msg\":\"请联系影院将使用该券的原订单后台退款后，可重新使用此券\",...}"}
创建订单时发现券不可用，进行更新黑名单处理  {"quan_flag":"2026电子兑换码（泉城）","coupon":"undefined"}
```

黑名单处理日志里 `coupon` 为 `undefined` → 券不可用时**黑名单从不更新** → 坏券反复参与出票、反复走转单。

### 问题 2：出票记录表券码显示不准确（线上券/线下会员券）

`ticker_record.quan_code` 与 V3 新增 `coupons` 快照字段里，线上券/线下会员券场景存的是**券 ID**（如 `977577,989692`），不是真实券码（`coupon_num`，如 `50730142F2CD7322CBE7B2AB6F7735BD`）。

### 问题 3：出票成功后券库存不扣减（线上券/线下会员券）

`updateQuanStock` 触发条件只判 `quan_code`（仅线下券有值）→ 线上券/线下会员券出票成功后库存偏大，可能引起报价规则座位数偏大。

## 二、根因分析

sfc 用券有三种类型，出票链路各字段形态：

| 券类型 | quanType 判定 | 下单传参 | 值内容 | 真实券码 |
|--------|--------------|---------|--------|---------|
| 线下券 | `offline_quan` | `coupon`(quan_code) | 券码串 | ✅ quan_code 即券码 |
| 线上券 | `online_quan` / `online_member_quan` | `coupon_id` | **券 ID 串** | ❌ 未带到下游 |
| 线下会员券 | `offline_member_quan` | `member_coupon_id` | **券 ID 串** | ❌ 未带到下游 |

关键事实：

1. 黑名单机制按**券码 coupon_num** 过滤：前端 `black_quans?.includes(item.coupon_num)`（cardQuanManage.js），服务端 `black_quans` 分号串 split 后 `NOT IN` 精确匹配（auto-ticket-service/api/quanRecord.js:67）。
2. `useQuanOrCard` 返回的 `quan_code` 仅线下券场景有值；`coupon_id`/`member_coupon_id` 是券 ID，**无法参与黑名单比对**（ID 与券码是两个体系）。
3. 因此黑名单处理、出票记录券码、券库存扣减三处凡依赖 `quan_code` 的逻辑，对线上券/线下会员券全部失效。

## 三、修复方案（核心思路：从用券源头带出统一券码串）

`useQuan()` 内部持有 `useQuans`（实际用券数组，元素含 `coupon_num`），是唯一同时覆盖三种券类型的真实券码来源。改造链路：

```
cardQuanManage.useQuanOrCard
  └─ 返回值新增 coupon_nums = useQuans.map(item => item.coupon_num).join(",")
       （三种券类型统一的逗号分隔券码串）
buyTicket.js
  ├─ 解构 coupon_nums
  ├─ createOrder 传参带 coupon_nums（超时重试经 {...data} 自动透传）
  └─ 出票结果 quan_code(qc)/coupons 快照/测试模式均优先 coupon_nums
orderManage.createOrder catch 分支
  └─ blackCoupon = coupon_nums || coupon → updateQuanBlackInfo
```

### 逐文件改动

#### 1. `src/common/autoTicket/buyTicket/sfc/cardQuanManage.js`

`useQuanOrCard` 返回值新增字段：

```js
// 本次实际使用券的券码串（逗号分隔，三种券类型统一）。
// 黑名单按券码 coupon_num 过滤：线上券(coupon_id)/线下会员券(member_coupon_id)
// 场景 quan_code 为空且券 ID 无法参与黑名单比对，需单独带出券码
// 供创建订单失败时更新黑名单（2026-08-20）
```

## 四、数据链路验证（逐环确认）

| 环节 | 验证结论 |
|------|---------|
| `useQuans` 的券码 = 实际下单券 | `useQuans = targetQuanList.filter((item, index) => index < ticket_num)`，取前 N 张全程无替换；利润为负路径返回空数组不会走到创建订单 |
| 绑券不改券码 | `bandQuan` 成功时原样返回入参 `coupon_num`——异步绑券补券场景券码也不变 |
| 三种券类型条目均有 coupon_num | quanList 来自 `getQuanList(status:4)`，本地过滤逻辑本身依赖 `i.coupon_num`，三种类型统一有此字段 |
| 格式兼容 | coupon_nums 逗号 join ↔ `updateQuanBlackInfo` 入口 `coupon.split(",")` ✓；写库分号 join ↔ 服务端 `replace(/[；;]/g,'-').split('-')` NOT IN 精确匹配 ✓ |
| 无券路径安全 | 用卡场景 `coupon_nums` 为 undefined → `blackCoupon` falsy → `updateQuanBlackInfo` 入口 `!coupon` 直接 return，不写脏数据 |
| 超时重试透传 | createOrder 递归 `{...data}` 展开自动带 coupon_nums |
| 黑名单生效闭环 | 写入 black_quans → 下次 `continuousGetQuan`/`_getQuanListForPay` 过滤 `!black_quans.includes(coupon_num)` → 坏券不再入选；服务端取券 NOT IN 精确兜底 |

## 五、已知边界与风险（评审重点，请重点检查）

1. **一单多券全进黑名单**：服务端报错无法定位具体哪张坏券，本次用券的**全部券码**都会进黑名单（宁枉勿纵 + 微信推送人工复核）。这是既有设计（`updateQuanBlackInfo` 推送文案明确要求人工检查移除），非本次引入。
2. **前端黑名单过滤是子串匹配**：`black_quans?.includes(coupon_num)` 中 black_quans 是 DB 原始分号串，实际为 `String.includes` 子串匹配，存在理论误杀（好券码是黑名单券码的子串时）。**注意**：该写法是 8 系列统一存量模式（chenxing/wanda/jinyi/fenghuang/h5ume/ume/lma 同款），服务端取券为精确 NOT IN 不受影响，仅前端已绑券列表本地过滤受影响；sfc 券码为 32 位随机串，实际误杀概率趋近于零。本次不动，建议后续 8 系列统一改 `split(";")` 数组比对。
3. **`coupon_id` 兜底仍非券码**：`coupon_nums` 理论恒有值（走到该分支说明 useQuans 非空），`coupon_id || member_coupon_id` 兜底只是防御性保留，正常不会命中；若命中则出票记录仍显示券 ID（与修复前行为一致，不劣化）。
4. **券库存扣减行为变化**：线上券/线下会员券出票成功后开始扣库存（原来从不扣）。扣减口径与其他系列一致（`quan_stock: quanStock - ticket_num`），库存将从偏大逐步回归真实值；如历史库存已偏大较多，回归需要多单消化。
5. **黑名单 quan_flag 匹配**：`updateQuanBlackInfo` 按传入 `quan_flag` 过滤 `targetQuanList`，值为 offerRule.quan_flag（报价规则券标识），与出票用券标识同源，正常一致。
