## 二、核心变更说明

### 1. Redis 缓存扩展（最大收益点）

- **原状**：仅缓存 4 个接口（h5/凤凰的影院+影片列表），统一 60min TTL；辰星/卢米埃/万达完全无缓存；**场次接口完全没缓存**
- **现状**：扩展到 15 个接口，覆盖 5 个系列的 城市/影院/影片/场次 列表；分级 TTL（城市24h/影院4h/影片30min/场次15min）
- **SimpleProxy 增加缓存能力**：辰星、卢米埃原本用 SimpleProxy 纯透传无缓存，现开启 `cacheEnabled`
- **万达直连代理接入缓存**：万达走的是独立的 `proxyWandaFilmApi.js`（带 WASM 签名，非 SimpleProxy/ComplexProxy），原本完全无缓存。现已接入缓存命中检查 + 分级 TTL 写入 + 字典控制日志。万达的 userToken/userIdentifier 在请求头里、不在 URL 中，所以缓存 key 不含用户信息，城市/影院/影片/场次等全局数据可跨用户共享缓存
- **前端零改动**：前端请求走后端代理，缓存命中在后端透明完成

### 2. offer_duration + queue_wait_ms 耗时度量

- `offer_duration`：报价处理耗时（从 `orderHandle` 开跑到 singleOffer 结束），衡量第三方查询链路快慢，缓存优化直接反映在此指标
- `queue_wait_ms`：入队到开跑的等待耗时（`orderHandleStartAt - order._offerEnqueueAt`），衡量队列堆积程度。用于区分"报价已结束"的成因：
  - `offer_duration` 高 + `queue_wait_ms` 低 → 报价本身慢（缓存未命中）→ 优化缓存
  - `offer_duration` 低 + `queue_wait_ms` 高 → 队列堆积（并发瓶颈）→ 调大连锁并发上限
  - 两者都高 → 同时优化
- 两个指标在代码里都已有现成的计时变量（`orderHandleStartAt`、`order._offerEnqueueAt`），仅入库即可，零额外运行时开销
- 后端 `addRecordData` 是动态拼接 SQL（`Object.keys(obj)`），自动带上新字段，无需改后端代码

### 3. 缓存命中日志（受字典控制）

- 新建 `api/cacheQueryLog.js`，写入 `cinema_cache_query_log` 表
- `proxyFactory.js` 的 `logCacheQuery()` 先读字典 `isCacheLogEnabled`，为 false 则跳过（高峰期可关闭减少 DB 写入）
- 复杂代理和简单代理的缓存命中/未命中分支都接入

### 4. handledOrders 容量提升

- 原硬编码 100，单量大时不够，旧订单被淘汰后重复入队浪费调度
- 改为字典 `handledOrdersCapacity`（默认 500），可运行时调整

### 5. 万达影院列表+影片列表并行

- 万达的影片列表按 `city_id` 查询，与影院列表（也按 `city_id`）**无依赖**
- 用 `Promise.all` 并行执行，节省 1 次网络往返（约 0.5-1s）
- **注意**：fenghuang/h5ume/chenxing/lma 的影片列表依赖 `cinemaLinkId`（从影院列表匹配），有真实数据依赖，**不能并行**，保持串行。缓存命中后串行 3 次查询 <0.3s，已足够。

## 三、方案与原计划的差异说明

原计划提到"5 个系列 cinemaManage 串行→并行"，但深入阅读代码后发现：

- fenghuang/h5ume/chenxing/lma 的查询链是**严格数据依赖**（影院列表→cinemaId→影片列表→filmId→场次），无法并行
- 仅万达的影片列表按 city_id 查（与影院列表无依赖），可并行
- **缓存命中后串行查询总耗时已降至 0.1-0.3s**，并行化的边际收益有限，强行改造反而引入回归风险

## 五、回归风险评估

| 风险点                              | 评估                                          | 缓解措施                                 |
| ----------------------------------- | --------------------------------------------- | ---------------------------------------- |
| 场次缓存 15min TTL 导致数据不新鲜   | 低。场次变化频率 30min 级，15min TTL 足够新鲜 | 前端 `isNoCache:true` 参数可强制跳过缓存 |
| SimpleProxy 开启缓存影响辰星/卢米埃 | 低。仅缓存影院/影片/场次列表，写操作不缓存    | `canCacheRequest` 只匹配白名单 endpoint  |
| handledOrders 容量 500 增加内存     | 极低。500 个订单号字符串约几十 KB             | 字典可配，可调回 100                     |
| offer_duration 字段写入失败         | 无影响。动态 SQL 自动带上，失败不影响主流程   | 后端 `addRecordData` 已有 try/catch      |
| 缓存日志写入影响性能                | 低。异步写入 + 字典开关                       | 高峰期 `isCacheLogEnabled=0` 关闭        |
