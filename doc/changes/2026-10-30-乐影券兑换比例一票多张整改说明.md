# 乐影（SFC）券兑换比例「N 张券 : 1 张票」整改说明

- 日期：2026-10-30
- 状态：**方案稿（尚未改代码）**，供评审
- 关联设计：`docs/superpowers/specs/2026-10-30-乐影同种券一票多张-design.md`
- 依据：Charles 抓包 `无标题2.har`（场次 668235，2 张票用 4 张券，实付 0.00 元）

---

## 一、背景与问题

乐影（SFC 系列）部分影院特殊厅晚场存在「用同一种券的 2 张抵 1 张票」的捡漏出票场景，要求机器报价与出票都按该比例执行。

**现状是全链路写死「一票一券」**：

| 环节 | 现状 | 2:1 时会怎样 |
|---|---|---|
| 报价·券库存门槛 | `quan_stock >= ticket_num` | 库存 3 张也认为够 2 票 → 报出价但出不了票 |
| 报价·券成本 | 单张 `quan_cost` | 成本只算一半 → 利润虚高 → 亏本接单 |
| 报价·规则座位数 | `min(maxQuanStock, 4)` | 库存消耗快一倍，座位数不跟着降 → 持续超发 |
| 出票·选券 | 取前 `ticket_num` 张 | 只取一半券 → 实付不为 0，被价格校验拦掉 |
| 出票·异步绑券 | 按 `ticket_num` 补货、扣库存 | 库存只扣一半 → 虚高，越出越不准 |

### 抓包确认的四个事实

1. 多券是接口原生能力：`price/calculate` 的 `quan_code`、`order/ng-create` 的 `coupon` 都是**逗号分隔券码串**，本次一次传了 4 个；
2. 抓包为 **2 票 4 券（每票 2 张）**，`total_price=0.00`，`ng-create` 成功 → 平台接受「券数 = 票数 × 2」；
3. 挂券后**票价基座会变**：无券 `ticket_price=202`，挂券后 240（券可兑价 120/张）→ **券只覆盖一部分反而更贵**（只用 1 张时实付 211 > 204）；
4. `handle_fee` 不稳定（2 券 1.00、4 券 0.00），金额一律以 `price/calculate` 返回为准。

### 本次确认的口径

1. **规则级配置**：兑换比例是报价规则上的字段；
2. **仅乐影系列 + 内部角色**可配置；
3. **券库存口径不变**（仍是"张数"），不做 `stock ÷ N` 换算，只改报价门槛、座位数收缩、出票选券/绑券这几处消费；
4. **该规则不同步猎人平台**（`isSyncPlat = 2`），全程机器本地报价 + 机器出票，不存在平台口径分裂；
5. 出票侧读规则**当前值**（联表），不落快照。

## 二、方案总览

一句话：**给规则加一个「每票券张数」字段，然后把所有"按票数当券数用"的地方改成 `needQuanNum = ticket_num × N`。**

```
rule_record.quanExchangeRatio = 2
        │
        ├─ 报价（本地）: 库存门槛 ×2、券成本 ×2、座位数 = floor(库存/2)
        └─ 出票（机器）: 选 2×票数 张券 → 券码串 → price/calculate → ng-create → 核销扣 2×票数
```

比例为空 / 1 时，所有换算等于 ×1，**与现状完全等价**。

## 四、核心变更说明

### 4.1 规则字段与可见性

`RuleDialog.vue` 新增（位置在用券类型之后）：

```vue
<el-form-item v-if="showQuanExchangeRatio" label="券兑换比例">
  <el-input v-model="formData.quanExchangeRatio" type="number" clearable
    placeholder="每张票消耗券张数，2 表示 2 张券兑 1 张票；留空即一票一券" />
  <span style="color: red; margin-left: 15px">
    提示：报价成本 = 券库「券成本」× 该比例，请确认券成本填的是单张成本
  </span>
</el-form-item>
```

```js
const showQuanExchangeRatio = computed(
  () =>
    GET_APP_INFO(formData.shadowLineName)?.app_type_code === "sfc_applet" &&
    IN_RULE_LIST.includes(Number(rule))
);
```

`IN_RULE_LIST = [2]`（内部角色），**不含管理员（1）**——若管理员也要配，需要显式把 1 并入判断。

### 4.2 保存时的两个保护（必须做）

```js
// ① 空值转 null，避免 TINYINT 收到空串
ruleInfo.quanExchangeRatio =
  ruleInfo.quanExchangeRatio === "" || ruleInfo.quanExchangeRatio == null
    ? null
    : Number(ruleInfo.quanExchangeRatio);

// ② 非内部角色不提交该字段
// 外部角色看不到这个表单项，若照常提交空值，会把内部角色已配的比例覆盖成 NULL
if (!IN_RULE_LIST.includes(Number(rule))) {
  delete ruleInfo.quanExchangeRatio;
}
```

同时把该列纳入已有的缺列兜底 `NEW_RULE_COLUMNS`，保证"客户端先发版、DDL 后执行"的窗口期内规则仍能正常保存（保存会剔除该字段并提示运维执行 DDL）。

### 4.3 报价：库存门槛与成本

```js
// 改前（sfc/offerManage.getMinAmountOfferRule）
return appQuanTypeList.some(
  itemA => item.quanValue?.split(",")?.includes(itemA.quan_value) &&
           itemA?.quan_stock >= order.ticket_num
);

// 改后
const ratio = getQuanPerTicket(item);   // 该规则的 quanExchangeRatio
return appQuanTypeList.some(
  itemA => item.quanValue?.split(",")?.includes(itemA.quan_value) &&
           itemA?.quan_stock >= order.ticket_num * ratio
);
```

券成本覆写（`sfc/offerManage.js` 新增方法，N=1 时走 `super`）：

```js
async getCostPrice(offerRule) {
  const ratio = getQuanPerTicket(offerRule);
  if (ratio <= 1) return super.getCostPrice(offerRule);   // 现状逻辑
  const quanInfo = await this.cardQuanManage.getQuanInfo(offerRule.quanValue, this.appFlag);
  const list = Array.isArray(quanInfo) ? quanInfo : quanInfo ? [quanInfo] : [];
  // 保留 quanInfoList，但成本预乘 N：基类的 maxCostPrice 过滤才会按"每票真实成本"判断
  this.quanInfoList = list.map(i => ({ ...i, quan_cost: Number(i.quan_cost || 0) * ratio }));
  return Math.min(...this.quanInfoList.map(i => Number(i.quan_cost || 0)));
}
```

> 不能把 `quanInfoList` 清空：基类 [BaseOfferPrice](src/common/core/BaseOfferPrice.js) 用它按 `maxCostPrice` 裁剪券类型，清空会让多券类型规则选到高成本券。

### 4.4 报价：座位数随券库存收缩

```js
// 改前
let targetSeatNum = maxQuanStock >= 4 ? 4 : maxQuanStock;
let targetStatus = targetSeatNum == 0 ? "2" : "1";

// 改后
const effStock = Math.floor(maxQuanStock / ratio);        // 张数 → 可支撑票数
let targetSeatNum = effStock >= 4 ? 4 : effStock;
let targetStatus = targetSeatNum == 0 ? "2" : "1";
```

**同时必须放宽作用域**：现逻辑只匹配「固定报价 + 已同步猎人（`isSyncPlat === 1`）」的规则，本次规则不同步平台，只改公式等于不生效。改为匹配条件追加 `|| ratio > 1`，对这类规则**只更新本地 `rule_record` 的 `seatNum/status`，跳过 `lierenOfferRuleSyncPlat`**，日志 `trigger_source` 用 `quan_stock_update_local` 区分。

效果：库存 10 张 → 座位数 4（上限）；3 张 → 1；1 张 → 0 → 规则自动禁用。

### 4.5 出票：选券口径

```js
const ratio = getQuanPerTicket(offerRule);   // 1 | 2 ...
const needQuanNum = ticket_num * ratio;      // 本次订单要消耗的券张数
```

- 券不足判断、补券差额、赠券分组、垫卡余额、取券上限全部改用 `needQuanNum`；
- 券码串 `quan_code / coupon_nums` 仍是 `useQuans.map(...).join()`，**不新增字段**，`ng-create` 的 `coupon` 原样透传。

### 4.6 出票：异步绑券三处（重点，易漏）

```js
// ① 触发阈值
if (targetQuanList?.length - needQuanNum < 10 && is_store == "1") { ... }

// ② 补券数量
quanNum: Math.max(10 - (targetQuanList.length - needQuanNum), 1)

// ③ 绑券后库存修正（getNewQuan 内）
this.updateQuanStock({
  quan_stock: quanStock - needQuanNum + bandQuanList.length,   // 原为 - ticket_num
  ...
});
```

> ③ 漏改的后果：出 1 单 2 票 4 券，库存只扣 2 张 → **库存虚高一倍** → 后续持续超发，最后集体转单。已列为风险 R9 并配单测。

### 4.7 出票：利润不能被二次放大

```js
// 改前：useQuans.length 在 2:1 下等于 2×票数 → 利润被放大一倍
profit = (supplier_end_price - quan_cost - shouxufei) * useQuans.length;

// 改后
profit = (supplier_end_price - quan_cost * ratio - shouxufei) * ticket_num;
```

奖励金额计算仍用 `ticket_num`（单位是票），不变。

### 4.8 出票：价格强校验（安全闸）

沿用现有 `validateCouponPrice`，仅把票数实参换成 `needQuanNum`：**实付 > 手续费合计即判失败并转单**。

依据抓包第 3 条：券没覆盖满时实付反而比无券更贵，这条校验是"比例配错 / 券不够 / 平台只认一张券"的最后一道防线——宁可转单，不亏钱出票。

## 五、兼容、灰度与回退

| 项 | 说明 |
|---|---|
| 默认关闭 | `quanExchangeRatio` 为 NULL/1 时所有换算 = ×1，与现状等价 |
| 灰度 | 只给目标影院那一条规则填 2，其余规则不填 |
| 回退 | 把该规则比例清空保存即可，无需发版 |
| 上线顺序 | ① 执行 DDL → ② 发后端 → ③ 发客户端 → ④ 配置规则 |
| 客户端先行 | 有缺列兜底，保存不报错、仅提示"未包含券兑换比例" |
| 生效时机 | 规则页保存后 `searchData()` 刷新本地规则 store，报价立即用新比例；出票侧联表读同一规则，同源 |

## 七、回归风险评估

| # | 风险 | 评估 | 缓解 |
|---|---|---|---|
| R1 | 平台是否允许「券数 > 票数」 | 中低：抓包 2 票 4 券已证明 2:1 可用，**1 票 2 券未验证** | 上线前用 1 张票 + 2 张券手工下单，确认 `total_price=0` 且 `ng-create` 成功 |

5. **首单验证**：先用 1 张票 2 张券下一单测试单（不购买），确认 `quan_code` 券码数、`total_price=0`；
6. **观察 48 小时**：
   - 「使用优惠券计算价格后最终利润为负」是否异常升高（说明券成本口径或比例配错）；
   - 「目标券数量不足」是否集中在目标影院（说明库存门槛或座位数收缩未生效）；
   - 「用完券发现支付金额大于券手续费*票数」是否出现（说明平台只认部分券）；
   - 出票后券库存扣减是否为 `ticket_num × 2`。
