## 一、背景与问题

乐影（SFC 系列）部分影院特殊厅晚场存在「用同一种券的 2 张抵 1 张票」的捡漏出票场景，要求机器报价与出票都按该比例执行。

**现状是全链路写死「一票一券」**：

| 环节 | 现状 | 2:1 时会怎样 |
|---|---|---|
| 报价·券库存门槛 | `quan_stock >= ticket_num` | 库存 3 张也认为够 2 票 → 报出价但出不了票 |
| 报价·券成本 | 单张 `quan_cost` | 成本只算一半 → 利润虚高 → 亏本接单 |
| 报价·规则座位数 | `min(maxQuanStock, 4)` | 库存消耗快一倍，座位数不跟着降 → 持续超发 |
| 出票·选券 | 取前 `ticket_num` 张 | 只取一半券 → 实付不为 0，被价格校验拦掉 |
| 出票·异步绑券 | 按 `ticket_num` 补货、扣库存 | 库存只扣一半 → 虚高，越出越不准 |

### 抓包确认的四个事实

1. 多券是接口原生能力：`price/calculate` 的 `quan_code`、`order/ng-create` 的 `coupon` 都是**逗号分隔券码串**，本次一次传了 4 个；
2. 抓包为 **2 票 4 券（每票 2 张）**，`total_price=0.00`，`ng-create` 成功 → 平台接受「券数 = 票数 × 2」；
3. 挂券后**票价基座会变**：无券 `ticket_price=202`，挂券后 240（券可兑价 120/张）→ **券只覆盖一部分反而更贵**（只用 1 张时实付 211 > 204）；
4. `handle_fee` 不稳定（2 券 1.00、4 券 0.00），金额一律以 `price/calculate` 返回为准。

### 本次确认的口径

1. **规则级配置**：兑换比例是报价规则上的字段；
2. **仅乐影系列 + 内部角色 + 固定报价规则**（`offerType === "1"`）三者同时满足才可配置；
3. **券库存口径不变**（仍是"张数"），不做 `stock ÷ N` 换算，只改报价门槛、座位数收缩、出票选券/绑券；
4. **该规则不同步猎人平台**（`isSyncPlat = 2`），全程机器本地报价 + 机器出票，不存在平台口径分裂；
5. 出票侧读规则**当前值**（联表），不落快照。

## 二、方案总览

一句话：**给固定报价规则加一个「每票券张数」字段，把所有"按票数当券数用"的地方改成 `needQuanNum = ticket_num × N`。**

```
rule_record.quanExchangeRatio = 2   （仅 offerType=1）
        │
        ├─ 报价（本地）: 库存门槛 ×2、券成本 ×2、座位数 = floor(库存/2)
        └─ 出票（机器）: 选 2×票数 张券 → 券码串 → price/calculate → ng-create → 核销扣 2×票数
```

比例为空 / 1 时，所有换算等于 ×1，**与现状完全等价**。

## 四、核心变更说明

### 4.0 比例取值：取不到就是 1（老规则兼容的硬约定）

老规则（DDL 前创建）、旧缓存、旧后端、脏数据都必须按 `1` 处理，且**只在一处兜底**：

```js
// src/common/autoTicket/quanPerTicket.js（实际实现）
export function getQuanPerTicket(rule, logger) {
  const raw = rule?.quanExchangeRatio ?? rule?.quan_exchange_ratio;
  if (raw === null || raw === undefined) return 1;          // 老规则/字段缺失
  if (typeof raw === "string" && raw.trim() === "") return 1; // 空串/空白
  const num = Number(raw);
  if (Number.isInteger(num) && num >= 1) return num;        // 正整数（含 "2"）
  logger?.warn?.(`券兑换比例非法，按1处理：ruleId=${rule?.id}，值=${raw}`);
  return 1;
}
```

| 入参 | 结果 | 说明 |
|---|---|---|
| `2` / `"2"` | `2` | 正整数（含数字字符串） |
| `null` | `1` | **老规则（DDL 前创建，列默认为 NULL）** |
| `undefined` | `1` | **字段不存在**：旧 store 缓存、后端未返回该列、DDL 未执行 |
| `""` / `" "` | `1` | 表单清空后尚未落库的空值 |
| `0` / `-1` | `1` | 非法值 |
| `2.5` / `"2.5"` | `1` | **非整数一律回退 1**，不猜意图（避免成本算错） |
| `NaN` / `"abc"` / `{}` / `true` | `1` | 脏数据 |

配套要求：

1. 报价与出票 **18 个消费点全部调用 `getQuanPerTicket`**，禁止各自 `Number(rule.quanExchangeRatio) || 1`（会出现 `""`、`"2.5"`、`-1` 等多种漏判）；
2. `ratio === 1` 时各消费点走原有分支 → **老规则行为零变化**；
3. 非法值打一次 warn（带 ruleId/原值）便于发现脏配置；归一为 1 属正常路径，不刷日志；
4. 表单侧仍强制正整数校验，DB 兜底只是防御性措施。

### 4.2 保存时的保护（已实施）

判定统一收敛到 `validateQuanRatioInput()`，规则弹窗与列表页共用同一套口径：

```js
export function validateQuanRatioInput({ ratio, quanValueCount, isLierenSynced }) {
  if (ratio === "" || ratio === null || ratio === undefined) {
    return { ok: true, value: null };              // 留空 = 不配置
  }
  const num = Number(ratio);
  if (!Number.isInteger(num) || num < 1 || num > QUAN_RATIO_MAX) {
    return { ok: false, reason: "range" };          // 1-20，超出提示修正（不清空输入）
  }
  if (isLierenSynced) return { ok: false, reason: "lieren_synced" };
  if (Number(quanValueCount) > 1) return { ok: false, reason: "multi_quan_type" };
  return { ok: true, value: num };
}
```

**规则弹窗（保存时拦截）**：

- 已同步猎人平台 → 告警「该规则已同步猎人平台，不支持券兑换比例，已自动清空」并清空字段、阻断本次保存；
- 选择多个券类型 → 告警「该规则选择了多个券类型，不支持券兑换比例，已自动清空」并清空字段、阻断本次保存；
- 非 1-20 整数 → 告警但不自动清空（保留输入便于修正）。

**列表页落库（最后一道闸）**：

```js
// 乐影内部角色：非固定报价 / 多券类型 / 已同步猎人 / 非法值 → 一律写 null（清除历史残留）
// 外部角色 / 非乐影：delete 字段，避免把别人配的值抹掉
if (!isLeYingInternal) {
  delete ruleInfo.quanExchangeRatio;
} else {
  const ratioCheck = ruleInfo.offerType === "1"
    ? validateQuanRatioInput({ ratio, quanValueCount, isLierenSynced })
    : { ok: true, value: null };
  ruleInfo.quanExchangeRatio = ratioCheck.ok ? ratioCheck.value : null;

```

> 早期方案写的是"非固定报价就 `delete`"，这会导致 DB 旧值残留：固定报价切会员加价后，出票走灵活用券仍按 N 倍取券。现改为**乐影内部角色一律显式写值或 `null`**；只有外部角色/非乐影才 `delete`（避免误抹他人配置）。

同时把该列纳入缺列兜底 `NEW_RULE_COLUMNS`，保证"客户端先发版、DDL 后执行"窗口期内规则仍能保存（剔除该字段并提示运维执行 DDL）。

### 4.3 报价：券成本（含 `offerType` 守卫）

```js
async getCostPrice(offerRule) {
  const ratio = getQuanPerTicket(offerRule);
  // 关键：只有固定报价才走券成本；否则必须交还基类（会员价走 memberCostPrice）
  if (offerRule.offerType !== "1" || ratio <= 1) {
    return super.getCostPrice(offerRule);
  }
  const quanInfo = await this.cardQuanManage.getQuanInfo(offerRule.quanValue, this.appFlag);
  const list = (Array.isArray(quanInfo) ? quanInfo : quanInfo ? [quanInfo] : [])
    .filter(Boolean);
  if (!list.length) return null;   // 与基类"取不到成本即不报"语义一致，避免 Math.min() 得 Infinity

  // 保留 quanInfoList 但成本预乘 N：基类 maxCostPrice 过滤才会按"每票真实成本"判断
  this.quanInfoList = list.map(i => ({ ...i, quan_cost: Number(i.quan_cost || 0) * ratio }));
  return Math.min(...this.quanInfoList.map(i => Number(i.quan_cost || 0)));
}
```

> 两个坑都在评审里被点出：① 漏 `offerType` 守卫会让会员加价规则去查券成本，算价直接错；② 空列表 `Math.min()` 返回 `Infinity`，会让基类把"无券类型"当成有成本。

```js
// 改后
const effStock = Math.floor(maxQuanStock / ratio);   // 张数 → 可支撑票数
let targetSeatNum = effStock >= 4 ? 4 : effStock;
let targetStatus = targetSeatNum == 0 ? "2" : "1";
```

**同时必须放宽作用域**：现逻辑只匹配「固定报价 + 已同步猎人（`isSyncPlat === 1`）」的规则（`item.offerType == 1 && platOfferList 含 lieren isSyncPlat==1`）。本次规则不同步平台，只改公式等于不生效。匹配条件追加 `|| ratio > 1`，对这类规则**只更新本地 `rule_record` 的 `seatNum/status`，跳过 `lierenOfferRuleSyncPlat`**，日志 `trigger_source` 用 `quan_stock_update_local` 区分。

效果：库存 10 张 → 座位数 4（上限）；3 张 → 1；1 张 → 0 → 规则自动禁用。

### 4.6 出票：选券口径

```js
const ratio = getQuanPerTicket(offerRule);   // 1 | 2 ...
const needQuanNum = ticket_num * ratio;      // 本次订单要消耗的券张数
```

券不足判断、补券差额、赠券分组、垫卡余额、取券上限全部改用 `needQuanNum`；券码串 `quan_code / coupon_nums` 仍是 `useQuans.map(...).join()`，**不新增字段**，`ng-create` 的 `coupon` 原样透传。

### 4.7 出票：异步绑券三处（重点，易漏）

```js
// ① 触发阈值
if (targetQuanList?.length - needQuanNum < 10 && is_store == "1") { ... }

// ② 补券数量（补到"出票后仍余 10 张"）
quanNum: Math.max(10 - (targetQuanList.length - needQuanNum), 1)

// ③ 绑券后库存修正（getNewQuan 内）
this.updateQuanStock({
  quan_stock: quanStock - needQuanNum + bandQuanList.length,   // 原为 - ticket_num
  ...
});
```

> ③ 漏改的后果：出 1 单 2 票 4 券，库存只扣 2 张 → **库存虚高一倍** → 后续持续超发。已列风险 R9 并配单测。

### 4.8 出票：利润与价格强校验

**利润不能被二次放大**：

```js
// 改前：useQuans.length 在 2:1 下等于 2×票数 → 利润被放大一倍
profit = (supplier_end_price - quan_cost - shouxufei) * useQuans.length;

// 改后
profit = (supplier_end_price - quan_cost * ratio - shouxufei) * ticket_num;
```

**价格强校验（R3 的安全闸）—— 现状是空转，必须一并修**：

```js
// 现状：useQuanOrCard 返回体没有 useQuan 字段 → 传 [] →
// BaseBuyTicket.validateCouponPrice 里 `!useQuan?.length` 直接 return ok，从未生效
const couponCheck = this.validateCouponPrice({
  offerRule, ticket_num, paymentAmount: pay_money,
  useQuan: useRes?.useQuan || []
});
```

修复方案（**按比例规则限定范围，避免存量券单行为突变**）：

```js
const usedCouponList = String(coupon_nums || quan_code || "")
  .split(",").filter(Boolean);            // 真实核销券码，来自 useRes.coupon_nums

const couponCheck = this.validateCouponPrice({
  offerRule,
  ticket_num: needQuanNum == ticket_num ? ticket_num : needQuanNum,
  paymentAmount: pay_money,
  // 仅配了比例的规则启用该校验；其余保持现状（该校验对存量券单从未生效，
  // 全量启用会让"券只抵部分、余款另付"的存量场景新出现转单，需单独评估）
  useQuan: ratio > 1 ? usedCouponList : useRes?.useQuan || []
});
```

> 若后续确认存量场景也能承受，可把该修复放开到所有 SFC 券单（另一件独立的事，不在本次范围）。

## 八、上线步骤与观察指标

1. **DDL**：`ALTER TABLE rule_record ADD COLUMN quanExchangeRatio ...`，同步表结构文档；
2. **发后端**（仅 `queryOfferInfo` 一处 JOIN）；
3. **发客户端**；
4. **配置**：乐影目标影院那条**固定报价**规则填「券兑换比例 = 2」，其余留空；
5. **确认**：该规则 `isSyncPlat = 2`（不同步猎人），否则平台报价时段会由平台按 1:1 报，本地比例不生效；
6. **首单验证**：1 张票 2 张券下一单测试单（不购买），确认 `quan_code` 券码数、`total_price=0`；
7. **观察 48 小时**：
   - 「使用优惠券计算价格后最终利润为负」是否异常升高（券成本口径或比例配错）；
   - 「目标券数量不足」是否集中在目标影院（库存门槛或座位数收缩未生效）；
   - 「用完券发现支付金额大于券手续费*票数」是否出现（平台只认部分券 / 比例过大）；
   - 出票后券库存扣减是否为 `ticket_num × 2`。

## 九、待确认事项

1. **1 票 2 券**的平台可行性（抓包只证明了 2 票 4 券的 2:1 比例）；
2. **单订单券数上限**（如 5 票 10 券是否仍可）；
3. 券库「券成本」是否统一按**单张**维护（配了比例的影院尤其要确认）；
