# 券库存批量更新改造说明

> 日期：2026-07-30
> 状态：**已实施**
> 关联背景：线上反馈部分影院券类型数量过多（10+），报价前/出票后路径每次都要逐条调 `singleUpdateQuanStock` 落库 + 触发规则同步检查，单次刷新占用连接池 N 次，与报价/出票请求竞争 6 连接池导致拉单/报价被阻塞。
> 关联文档：[2026-07-20-券库存触发规则同步优化整改方案.md](./2026-07-20-券库存触发规则同步优化整改方案.md)、[2026-07-18-猎人接口429限流根因修复.md](./2026-07-18-猎人接口429限流根因修复.md)

---

## 1. 背景与目标

### 1.1 问题背景

既有券库存更新链路（`commonQuanStock.js`）：

```
syncUpdateQuanStock           (公共入口：报价前 + 出票后共用)
  → for (号 in 关联登录列表)
      → getQuanListByPhone    (拉取该号全部优惠券)
      → for (券类型 in quanTypeList)
          → 计算库存/比较 → 累积到 updateTypeList
  → for (item in updateTypeList)
      → singleUpdateQuanStock (逐条落库 1 次 HTTP)
        → checkLierenFixedRuleByQuanStock
            → checkQuanInRules        (逐条 DB 查询规则)
            → for (rule in usedRules)
                → lierenOfferRuleSyncPlat
                → svApi.updateRuleRecord
                → svApi.addRuleOperationLog   (逐条日志写入)
```

**主要问题**：

| 问题 | 影响 |
| --- | --- |
| 逐条 `singleUpdateQuanStock` 落库 | N 条券类型 = N 次 HTTP 请求，占用后端连接池 |
| 逐条 `checkQuanInRules` | N 次 DB 查询（即使 B1 缓存命中跳过同步，未命中时仍是 N 次） |
| 逐条 `addRuleOperationLog` | N 次日志写入 HTTP |
| 部分成功无原子性 | 中途异常时前几条已落库，后续未执行，状态不一致 |
| 7 个平台 `cardQuanManage.js` 各自循环调用 | 改造点分散，同一影院多券类型时连接池占用成倍放大 |

### 1.2 改造目标

| 目标 | 说明 |
| --- | --- |
| 接口调用减次数 | N 条券类型从 N 次落库 → 1 次批量请求 |
| 事务原子性 | 后端事务保证全部成功或全部回滚，避免部分成功 |
| 规则同步合并 | 同 `app_name` 下多券类型合并查 1 次规则，按 `rule.id` 去重后逐条同步平台 |
| 日志批量写入 | 操作日志收集后一次性 `batchAddRuleOperationLog` |
| 覆盖双路径 | 报价前路径 + 出票后路径全部切换批量接口 |
| 日志直观清晰 | 批量开始/返回/异常均带 `app_name`、`count`、`quanValues`、`costMs` 等关键字段 |

## 2. 改造方案

### 2.1 后端：事务 + 批量 UPDATE

**新增 `withTransaction`**（`auto-ticket-service/controllers/mysqlConfig.js`）：
- 从连接池获取连接 → `beginTransaction` → 执行业务 SQL → `commit` / 异常 `rollback` → `release`
- 业务侧通过 `query(sql, values)` 在事务内执行多条 UPDATE，任一异常整批回滚

**新增 `batchUpdateRecordData`**（`auto-ticket-service/api/quanType.js`）：
- 入参 `{ list: [{ id, quanStockList, update_time, end_use_time? }], rule }`
- 在事务内对每条记录动态构造 `UPDATE quan_type SET ... WHERE id = ? AND rule = ?`
- 返回 `{ affectedRows: 累计影响行数 }`

**新增路由**（`auto-ticket-service/routes/quan_type.js`）：
- `POST /svpi/quanType/batchUpdate`，从 `ctx.state.rule` 注入租户隔离字段

### 2.2 前端 API 层

**新增 `batchUpdateQuanType`**（`src/api/sv-api.js`）：
```js
const batchUpdateQuanType = params => axios.post("/svpi/quanType/batchUpdate", params);
```

### 2.3 前端核心逻辑：`commonQuanStock.js`

#### 2.3.1 `syncUpdateQuanStock`（公共入口）

改造点：保留原有"按号拉取券列表 → 计算库存"逻辑，把循环内逐条落库改为**收集 `updateTypeList` 后一次性批量调用**。

> **日志归属（配套）**：`syncUpdateQuanStock` 不再接收外部 `logger` 入参，内部创建独立 `Logger({ logType: 1 })` 并 `init` 绑定订单号。券库存更新全流程日志（分类明细、汇总、批量落库、规则同步）收集后**统一一次上传**，与报价/出票流程日志隔离，互不影响上传时机（背景与修复详见 2.6）。

```js
// quanStockList 统一序列化为 JSON 字符串（后端直接落库 + 批量规则同步内部 parse）
let updateTypeList = quanTypeListParams.map(item => ({
  id: item.id,
  quan_value: item.quan_value,
  quan_flag: item.quan_flag, // 仅日志展示用（落库时被 dbList 剥离）
  quanStockList: JSON.stringify(item.quanStockList),
  update_time: getCurrentTime()
}));
// 批量更新券库存 + 统一触发一次规则同步（替代循环内逐条 singleUpdateQuanStock）
await batchUpdateQuanStockWithSync({
  list: updateTypeList,
  app_name,
  logger
});
```

#### 2.3.2 `batchUpdateQuanStockWithSync`（新增，导出）

职责：批量落库 + 统一触发一次规则同步 + 异常隔离。

```js
export async function batchUpdateQuanStockWithSync({ list, app_name, logger }) {
  if (!list?.length) return;
  const batchStartAt = Date.now();
  logger.infoSave("批量更新券库存开始", {
    app_name, count: list.length, quanValues: list.map(i => i.quan_value)
  });
  try {
    // 1. 批量落库（后端事务原子性，任一 SQL 异常整批回滚）
    //    仅传 DB 字段，剥离 quan_value/app_name 等业务字段（避免后端动态 SET 构造报错）
    const dbList = list.map(({ id, quanStockList, update_time, end_use_time }) => {
      const item = { id, quanStockList, update_time };
      if (end_use_time != null) item.end_use_time = end_use_time;
      return item;
    });
    const res = await svApi.batchUpdateQuanType({ list: dbList });
    logger.infoSave("批量更新券库存返回", {
      affectedRows: res?.data?.affectedRows,
      count: list.length,
      costMs: Date.now() - batchStartAt
    });
    // 2. 统一触发一次猎人规则同步（用完整 list，含 quan_value 供缓存 key 与规则匹配）
    await batchCheckLierenFixedRule({ list, app_name, logger });
  } catch (error) {
    logger.infoSave("批量更新券库存异常", {
      error: formatErrInfo(error), app_name, count: list.length
    });
  } finally {
    logger.logUpload();
  }
}
```

#### 2.3.3 `batchCheckLierenFixedRule`（新增，内部函数）

相对单条版 `checkLierenFixedRuleByQuanStock` 的优化：

| 单条版（已删除） | 批量版 |
| --- | --- |
| 每条 `checkQuanInRules` 查 1 次 DB | 合并查 1 次 `queryRulesByApp(app_name)` |
| 每条独立 B1 缓存判断 | B1 缓存逐条判断，未跳过的项合并查询 |
| 每条 `addRuleOperationLog` | 收集到 `pendingLogs` 后一次性 `batchAddRuleOperationLog` |
| 同一规则可能被多次同步 | 按 `rule.id` 去重后逐条同步平台（平台接口无法批量） |

执行流程：

1. **逐条 B1 缓存判断**：`cacheKey = ${app_name}|${quan_value}`，命中（未过期且 `maxQuanStock` 相同）则跳过；未命中则更新缓存并加入 `needSyncItems`。
2. **合并查询规则**：`queryRulesByApp(app_name)` 一次性拿全部规则，过滤出 `offerType==1` + 关联 `lieren` 同步 + `quanValue` 命中 `needSyncItems` 的规则。
3. **按 `rule.id` 去重逐条同步**：
   - 计算 `targetSeatNum` / `targetStatus`（禁用规则只比较状态，沿用 2026-07-19 修复）
   - `isSameState` 短路，跳过无需更新的规则
   - `lierenOfferRuleSyncPlat(lierenRule, cachedPlatRule)` 同步平台（`cachedPlatRule` 用本地规则数据构造，避免内部再调 `ruleList`，沿用 B4 优化）
   - 同步成功 → `svApi.updateRuleRecord` + 收集日志到 `pendingLogs`
   - 同步失败 → 不更新本地 DB + 回滚该 `quan_value` 的 B1 缓存（下次重试）
4. **批量写入日志**：`svApi.batchAddRuleOperationLog({ logs: pendingLogs })`
5. **异常回滚**：同步过程异常时回滚所有未跳过项的 B1 缓存，不延迟、不退避

> B1 缓存命中条件、TTL（1 小时）、失败回滚策略均与单条版完全一致，不破坏既有"必须同步最新规则"约束。

### 2.4 7 个平台 `cardQuanManage.js` 适配

统一改造模式：**循环内收集 `updateTypeList` → 循环外一次批量调用**。出票后路径的 `updateQuanStock` 同时增加**空手机号防御**（详见 2.7）；各平台 sync 路径的分类日志统一为 `手机号—券类型—数量` 极简格式（data 含 `quan_value` + 券号列表），落库汇总统一走 `formatQuanTypeSummaryForLog`（详见 2.5）。

> **SFC 平台（公共 helper 路径）**：`updateQuanStockCommon`（`buyTicket/common/cardQuanHelper.js`，SFC 出票后路径共用）同步纳入改造——收集 `updateList` 后切 `batchUpdateQuanStockWithSync` 批量落库 + 统一规则同步（原为循环内逐条 `svApi.updateQuanType` 仅落库），并增加空 phone 防御（无匹配券类型时记日志跳过）。注：SFC 原实现**不触发**猎人规则同步，纳入后开始与 7 平台一致（无关联猎人规则时走"无关联规则"分支，无副作用）。SFC 报价前路径 `getQuanTypeListByAppCommon` 为只读查询，不涉及本次改造。

涉及文件：
- `src/common/autoTicket/buyTicket/wanda/cardQuanManage.js`
- `src/common/autoTicket/buyTicket/jinyi/cardQuanManage.js`
- `src/common/autoTicket/buyTicket/chenxing/cardQuanManage.js`
- `src/common/autoTicket/buyTicket/fenghuang/cardQuanManage.js`
- `src/common/autoTicket/buyTicket/ume/cardQuanManage.js`
- `src/common/autoTicket/buyTicket/h5ume/cardQuanManage.js`

改造示例（以 wanda 为例）：

```js
// 改造前：循环内逐条落库
for (const item of updateList) {
  await singleUpdateQuanStock({ ...item, app_name, logger });

// 改造后：收集后批量调用
const updateTypeList = updateList.map(item => ({
  id: item.id,
  quan_value: item.quan_value,
```

覆盖路径：
- **报价前路径**：`getQuanTypeListByApp` → `syncUpdateQuanStock`（公共入口，所有平台共用）
- **出票后路径**：各平台 `cardQuanManage.js` 内的券库存更新逻辑

### 2.5 日志可读性优化（配套）

批量日志统一为"一眼可读"格式（5 处统一：公共路径 + wanda/jinyi/chenxing/fenghuang）：

| 日志 | 格式 | 说明 |
| --- | --- | --- |
| 逐号分类明细 | `手机号—券类型—数量` | data 仅含 `quan_value` + `matchedQuanList`（券号列表），一行看清各号各券类型库存来源 |
| 落库汇总 | `最终要更新的券类型列表汇总` | `formatQuanTypeSummaryForLog` 精简：每类型 `{id, quan_value, quan_flag, maxQuanStock, stockByPhone}`（有货手机号 phone→stock 映射，全 0 类型为空对象），不再重复全量明细 |
| 批量入口/出口 | `批量更新券库存开始/返回` | `{app_name, count, quanValues}` / `{affectedRows, count, costMs}` |
| 最大券库存 | `最大券库存-{quan_value}-{maxQuanStock}` / `-未变化跳过` | 原"最大券库存"+"跳过"两条合并为一条，去重复字段，每类型一行 |
| 规则同步 | `批量规则同步：命中关联规则/无关联/整体跳过` | `{app_name, ruleCount, ruleIds}` 等精炼字段 |

同时删除冗余日志：`批量更新券库存落库入参`（dbFields 全相同 + 截断 sample 无排查价值，连带删除 `truncateStr` 工具）、`连续获取券最终返回`（ume/h5ume/lma，与分类日志重复）、不可读的 `console.log` 原始对象打印（`targetQuanList`/`quanStockList`/`quanTypeListParams`/`updateTypeList` 等）。

### 2.6 日志上传机制修复（配套）

**问题**：批量改造后日志"缺失/分散"：

1. `Logger.logUpload` 将同一 `logList` 数组引用传给 `utils.logUpload`（上传成功后 splice 清空）。多个调用点 fire-and-forget（不 await）并发时，两个 while 循环同时 slice/splice 同一数组 → **日志重复上传或部分丢失**（批量流程内层 finally 与外层 finally 紧邻两次调用、报价流程结束与后台异步任务并发均触发）
2. `syncUpdateQuanStock` 复用报价流程 logger：报价流程 `buildSuccessResponse` 触发上传（快照），后台券库存日志被"截断"成多次上传，DB 端看似不全

**修复**：

1. **`Logger.logUpload` 同实例串行化**（`src/common/logger.js`）：同一 logger 的多次上传通过 promise 链排队执行，前一次上传 splice 清空后，后续排队执行时 `logList` 为空自然跳过 → 不重复、不丢失；`.catch` 兜底，单次上传异常不阻断后续
2. **`syncUpdateQuanStock` 内部独立 Logger**（`logType: 1`，`init` 绑定订单号）：券库存全流程日志收集后**统一一次上传**，与报价/出票流程日志隔离，互不影响上传时机
3. **`isPrint` 判断修复**：`isPrint || true` → `isPrint ?? true`（原实现显式传 `false` 不生效）

### 2.7 空手机号库存条目治理（配套）

**背景**：出票后路径 `updateQuanStock` 的 `phone` 来自登录列表，影院无可用登录账号（`currentParamsList` 为空）或卡支付路径时 `phone` 为空字符串，会向 `quanStockList` 写入 `{"phone":"",...}` 条目并落库；报价前 sync 路径构建 `quanStockList` 时原样复制 DB 条目，且更新匹配 `findIndex(itemB => itemB.phone === mobile)` 永远匹配不到空号 → **该条目永不更新、永久保留**（线上已发现 `phone:""` 脏数据）。

**修复**（三层防护）：

1. **写入端防御（根因）**：7 平台 `updateQuanStock` 开头 `if (!phone)` 跳过并记日志（`跳过空手机号券库存更新`），杜绝新脏数据
2. **数据清理**：公共 `syncUpdateQuanStock` + wanda/jinyi/chenxing/fenghuang 自有 sync 路径构建 `quanStockList` 时 `.filter(itemA => itemA.phone)`，下次报价前刷新写回**自动清除**历史脏条目，无需手工清库
3. **容错**：`batchCheckLierenFixedRule` 解析后过滤空 phone 条目，任何漏网的空号 `quan_stock` 都不影响 `maxQuanStock` 计算（避免误同步规则座位数/状态）

### 2.8 死代码清理

`commonQuanStock.js` 中以下函数已被批量版完全替代，删除：
- `singleUpdateQuanStock`
- `checkLierenFixedRuleByQuanStock`
- `checkQuanInRules`

> 注：`src/views/permission/quanManage/quanType.vue` 内也有同名 `checkQuanInRules`，那是页面级"刷新规则"按钮的独立本地函数，与本次改造无关，未触碰。

## 4. 收益评估

以单影院 10 条券类型、其中 2 条触发规则同步为例：

| 指标 | 改造前 | 改造后 | 降幅 |
| --- | --- | --- | --- |
| 后端落库 HTTP 次数 | 10 | 1 | -90% |
| 规则列表 DB 查询次数 | 2（B1 未命中时） | 1（合并查 `app_name`） | -50% |
| 规则操作日志 HTTP 次数 | 2 | 1（批量） | -50% |
| 事务原子性 | 无（部分成功） | 有（全成功/全回滚） | — |

## 6. 风险与回滚

| 风险 | 评估 | 缓解 |
| --- | --- | --- |
| 后端事务执行时间过长 | 单批通常 < 10 条 UPDATE，毫秒级 | 已加 `costMs` 日志观测，异常可及时发现 |
| 批量接口失败导致整批未落库 | 低（接口稳定） | 异常日志带完整 `list` 上下文，下次刷新会重试 |
| 规则同步失败影响本地 DB 一致性 | 已有保护 | 同步失败不更新本地 DB + 回滚 B1 缓存，下次重试（沿用既有策略） |
| 回滚方案 | — | 还原 `commonQuanStock.js` 的 `singleUpdateQuanStock` + 各平台 `cardQuanManage.js` 的循环调用即可（git 回滚单次提交） |
