## 一、背景与目标

当前 `sys_dict` 字典表仅支持后端只读查询（`GET /svpi/dictRecord`），所有字典数据的新增/修改/删除都需 DBA 直接操作数据库。本次改造目标：

1. 在前端新增「字典管理」页面，支持字典数据的增、删、改、查（CRUD）。
2. 页面**仅针对内部角色显示**（采用整页动态路由注入，非内部角色完全不可见）。
3. CRUD 完成后自动刷新前端字典缓存（`dictTable` store + localStorage），保证报价、出票、第三方 ID 缓存等依赖模块即时生效。

## 二、现状调研

### 2.1 数据库表结构（sys_dict）

来源：`auto-ticket-service/doc/表ddl.md` 第 534-551 行

```sql
-- 现有表结构
CREATE TABLE `sys_dict` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `dict_type` varchar(50) NOT NULL COMMENT '字典类型(如:user_status)',
  `dict_label` varchar(200) NOT NULL COMMENT '字典标签(显示文本,如:正常)',
  `dict_value` varchar(200) NOT NULL COMMENT '字典值(如:1)',
  `dict_desc` varchar(500) DEFAULT NULL COMMENT '字典描述',
  `status` tinyint(1) DEFAULT '1' COMMENT '状态:0停用 1启用',
  `create_time` datetime DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `rule` int DEFAULT NULL COMMENT '指定角色，不指定就全角色可用',
  `user_id` varchar(100) DEFAULT NULL COMMENT '指定用户，不指定就全用户',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_type_value` (`dict_type`,`dict_value`),
  KEY `idx_type` (`dict_type`),
  KEY `idx_type_status` (`dict_type`,`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='数据字典表';
```

**本次改造需执行的 DDL（新增 is_readonly 字段，扩展 status 语义）：**

```sql
-- 1. 新增 is_readonly 字段（是否只读：0否 1是，只读项不可编辑/删除/切换状态）
ALTER TABLE `sys_dict`
  ADD COLUMN `is_readonly` tinyint(1) DEFAULT 0 COMMENT '是否只读：0否 1是。只读项不可编辑/删除/切换状态，由表数据直接控制' AFTER `status`;

-- 2. 现有 39 条核心系统配置全部标记为只读，防止误删误改
UPDATE `sys_dict` SET `is_readonly` = 1 WHERE `is_readonly` = 0;

-- 3. status 字段语义扩展（DDL 注释可选更新，tinyint(1) 可存 0/1/3）
--    0=停用  1=启用  3=已删除（逻辑删除标记，查询时过滤）
ALTER TABLE `sys_dict`
  MODIFY COLUMN `status` tinyint(1) DEFAULT '1' COMMENT '状态:0停用 1启用 3已删除(逻辑删除)';
```

**关键字段说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | bigint | 自增主键 | 修改/删除时使用 |
| dict_type | varchar(50) | 是 | 字典类型标识，与 dict_value 组成唯一键 |
| dict_label | varchar(200) | 是 | 显示文本 |
| dict_value | varchar(200) | 是 | 字典值（可为数字、JSON、逗号分隔列表等多种格式） |
| dict_desc | varchar(500) | 否 | 描述说明 |
| status | tinyint | 默认 1 | **0=停用，1=启用，3=已删除（逻辑删除）**（⚠️ 不是 1/2，见下方注意事项） |
| is_readonly | tinyint | 默认 0 | **是否只读：0否 1是。只读项不可编辑/删除/切换状态，直接由表数据控制**（本次新增） |
| rule | int | 否 | 指定角色（1管理员/2内部/3外部），null=全角色可用 |
| user_id | varchar(100) | 否 | 指定用户，null=全用户可用 |
| create_time | datetime | 自动 | 创建时间 |
| update_time | datetime | 自动 | 更新时间（ON UPDATE 自动维护） |

**唯一约束：** `uk_type_value(dict_type, dict_value)` —— 新增/修改时若违反唯一键，后端会抛出 `sqlMessage`，前端需在提交前做校验并友好提示。

> ⚠️ **注意**：唯一键 `uk_type_value` 未含 status，逻辑删除（status=3）后若想新增同 `dict_type+dict_value` 的记录会冲突。因此删除后不可新增相同键值的记录（如需恢复，把 status 改回 0/1 即可）。

### 2.2 现有数据概况

已连接生产库 `autoticket@47.113.191.173:3306` 查询，当前共 **39 条**记录，关键观察：

## 三、改造方案

### 3.1 总体设计

| 层 | 改动 |
|----|------|
| 数据库 | **新增 `is_readonly` 字段**（控制只读）；`status` 语义扩展为 `0停用/1启用/3已删除`；现有 39 条数据标记为只读 |
| 后端 API | 新增 5 个接口（分页查询/新增/修改/逻辑删除/批量逻辑删除），参照 `quanType` 实现；删除改为 `UPDATE status=3` |
| 后端路由 | `routes/dict_record.js` 新增 5 个路由，引入 `injectUserInfo` 中间件 |
| 前端 API | `sv-api.js` 新增 5 个方法 |
| 前端 Store | `dictTable.js` **不变**（沿用 `setDictTableList` 刷新缓存） |
| 前端页面 | 新增 `src/views/dictManage/index.vue` + `src/components/DictDialog.vue`；只读项禁用编辑/删除/状态切换按钮 |
| 前端路由 | `src/router/modules/settings.ts` 注册静态路由 + `src/router/utils.ts` 动态注入菜单 |

### 3.2 权限控制策略（整页动态注入）

采用用户确认的「整页动态注入」方案，参照 `CinemaRecord` 页面：

1. **静态路由注册**（`settings.ts`）：注册路由组件，但 `meta.showLink: false`（不在菜单显示）。
2. **动态菜单注入**（`router/utils.ts`）：仅当 `IN_RULE_LIST.includes(rule)` 时，将「字典管理」菜单项 push 到异步路由 children。
3. **效果**：非内部角色（rule=1 管理员、rule=3 外部用户）完全看不到菜单，且无法通过路由直接访问（路由本身仍可访问，但无入口）。

> ⚠️ **待确认问题 1**：当前 `IN_RULE_LIST = [2]` 仅含内部用户，管理员（rule=1）也看不到此页面。若希望管理员也能管理字典，需调整为 `IN_RULE_LIST = [1, 2]` 或单独判断。**见第六章待确认问题。**

### 3.3 status 取值与逻辑删除（重要）

⚠️ `sys_dict` 表的 `status` 字段本次扩展为三种取值：**`0=停用，1=启用，3=已删除`**（逻辑删除标记）。

- 前端 `dictTable.js` 的 `dictInfo` getter 用 `item.status === 1` 过滤启用项 —— `0/3` 均被排除，无需改动 getter。
- 前端 `el-switch` 必须用 `:active-value="1" :inactive-value="0"`，**不能**沿用 `offerRule` 页面的 `active-value="1" inactive-value="2"`。
- **删除 = 逻辑删除**：`UPDATE sys_dict SET status = 3 WHERE id = ?`，不执行物理 `DELETE`。
- **所有查询必须过滤 `status != 3`**（管理分页查询、业务消费的 findAllRecord 都要过滤已删除项）。
- 已删除（status=3）的记录：唯一键 `uk_type_value` 仍占用，不可新增相同 `dict_type+dict_value` 的记录；如需恢复，将 status 改回 0/1 即可。

### 3.4 is_readonly 只读控制（重要）

新增 `is_readonly` 字段（`0否 1是`），**直接由 DB 表数据控制**，不在前端表单中暴露：

- `is_readonly = 1` 的记录：前端禁用「编辑」「删除」按钮，禁用状态切换 `el-switch`，禁用批量删除勾选框。
- `is_readonly = 0` 的记录：正常 CRUD。
- **新增/编辑表单不展示 `is_readonly` 字段**（由用户直接在 DB 表中控制）。
- **新增字典时 `is_readonly` 默认 0（可编辑）**，是否标记为只读由用户自行在 DB 表中维护。
- 后端 `addRecordData` 不再接收前端传入的 `is_readonly`，统一走 DB 列默认值 0；`updateRecordData` 显式排除 `is_readonly` 字段，防止绕过。

## 四、接口设计

### 4.1 后端新增接口

路由前缀：`/svpi/dictRecord`（沿用现有 prefix），全部需要 `auth` + `injectUserInfo` 中间件。

| 方法 | 路径 | 说明 | 入参 |
|------|------|------|------|
| GET | `/` | 现有，保留（需加 `status != 3` 过滤） | 无（按当前用户 rule/user_id 过滤，业务消费用） |
| GET | `/query` | **新增**：分页查询（管理用，返回全部，过滤 `status != 3`） | dict_type, status, page_num, page_size |
| POST | `/add` | **新增**：新增字典 | dict_type, dict_label, dict_value, dict_desc, status, rule, user_id（is_readonly 不传，走 DB 默认 0） |
| POST | `/update` | **新增**：修改字典（只读项后端拒绝修改） | id + 上述任意可修改字段 |
| GET | `/delete` | **新增**：单条逻辑删除（status 置 3，不物理删除） | id |
| POST | `/batchdelete` | **新增**：批量逻辑删除（status 置 3） | { delIds: [id...] } |

```js

// 失败
```

### 4.2 后端 API 层实现要点（api/dictRecord.js）

参照 `api/quanType.js` 新增以下方法（并改造现有 `findAllRecord`）：

0. **`findAllRecord(params)`** — 现有方法改造
   - SQL: `SELECT * FROM sys_dict WHERE status != 3`（**新增 `status != 3` 过滤**，排除已逻辑删除项）
   - 保留现有 JS 层 rule/user_id 过滤逻辑

1. **`findRecordData(params)`** — 分页查询（管理用）
   - SQL: `SELECT * FROM sys_dict WHERE status != 3 [AND dict_type LIKE ?] [AND status = ?] ORDER BY update_time DESC, id DESC LIMIT ? OFFSET ?`
   - **不按 rule/user_id 过滤**（管理页面需看到全部未删除数据）
   - 同时查询 `COUNT(*)` 返回 `totalNum`
   - `update_time` 用 `utils.formatTimeOfTime` 格式化
   - `dict_type` 用 `LIKE '%keyword%'` 模糊匹配
   - `status` 查询参数若传 3（已删除），管理页面默认不传，故 WHERE 已用 `status != 3` 兜底

2. **`addRecordData(params)`** — 新增
   - SQL: `INSERT INTO sys_dict SET dict_type=?, dict_label=?, dict_value=?, dict_desc=?, status=?, rule=?, user_id=?`（**不写入 is_readonly**，走 DB 列默认 0）
   - 参数化查询，违反唯一键 `uk_type_value` 时捕获 `error.sqlMessage`（如 `Duplicate entry`）返回友好提示
   - `is_readonly` 由 DB 列默认值 0 控制，不接收前端入参

3. **`updateRecordData(params)`** — 修改
   - **前置校验**：先 `SELECT is_readonly FROM sys_dict WHERE id = ?`，若 `is_readonly = 1` 直接返回 `failRes(null, '只读项不可修改')`
   - SQL: `UPDATE sys_dict SET ... WHERE id = ?`（**不带 rule 条件**，字典是全局配置）
   - 同样处理唯一键冲突
   - `is_readonly` 字段本身不可通过 update 修改（只读项不可改为非只读，反之亦然，避免绕过），由后端显式排除该字段

4. **`delRecordData({ id })`** — 单条逻辑删除
   - **前置校验**：先 `SELECT is_readonly FROM sys_dict WHERE id = ?`，若 `is_readonly = 1` 直接返回 `failRes(null, '只读项不可删除')`
   - SQL: `UPDATE sys_dict SET status = 3 WHERE id = ?`（**逻辑删除，非物理 DELETE**）

5. **`batchdDelRecordData({ delIds })`** — 批量逻辑删除
   - **前置校验**：先 `SELECT id FROM sys_dict WHERE id IN (?) AND is_readonly = 1`，若存在只读项则返回 `failRes(null, '包含只读项，不可批量删除')` 并列出只读 id
   - SQL: `UPDATE sys_dict SET status = 3 WHERE id IN (?, ?, ...)`
   - 校验 `delIds` 为非空数组

## 七、风险与注意事项

1. **status 取值 0/1/3**（非 1/2）：`el-switch` 必须用 `active-value=1 inactive-value=0`，否则会破坏 `dictInfo` getter 的 `status === 1` 过滤逻辑，导致启用项被误隐藏或停用项被误启用。`3=已删除` 仅由后端逻辑删除写入，前端不直接展示。

2. **逻辑删除与唯一键冲突**：删除是 `UPDATE status=3`（非物理 DELETE），唯一键 `uk_type_value` 仍占用。因此**已删除的 dict_type+dict_value 不可重新新增**。如需恢复，将 status 改回 0/1（需 DBA 操作或单独的恢复接口）。前端新增时若命中已删除记录的唯一键，后端返回友好提示「该字典已存在（可能为已删除状态），请使用其他键值或恢复原记录」。

3. **唯一键约束 `uk_type_value`**：新增/修改时若 `dict_type + dict_value` 重复，后端 MySQL 会抛 `Duplicate entry` 错误。前端应在提交前查询当前列表做客户端预校验，后端捕获 `error.sqlMessage` 返回友好提示。

4. **CRUD 后必须刷新字典缓存**：`dictTable` store 被 `utils.js`、`offerRule`、`thirdPartyIdsCache` 等多个核心模块依赖。每次 add/update/delete/batchDelete/statusChange 成功后，必须调用 `svApi.queryDictList()` + `dictStore.setDictTableList()` 刷新，否则其他模块使用过期数据。

5. **删除风险**：字典数据影响系统行为（如删除 `offerHandleTimeout` 会导致报价超时回退到代码硬编码默认值）。逻辑删除后相关功能立即回退默认值。删除前必须 `ElMessageBox.confirm` 二次确认，提示文案为「删除后该字典将不再生效（状态置为已删除），确认删除？」。

6. **is_readonly 只读控制需前后端双重校验**：前端禁用按钮只是体验优化，**后端 update/delete/batchdelete 必须做 is_readonly 校验**，防止绕过前端直接调接口。update 时显式排除 is_readonly 字段，防止通过 update 把只读项改为非只读。

7. **`dict_type` 编辑限制**：编辑时禁用 `dict_type` 输入框（因为唯一键包含 dict_type，修改等同于删除+新增）。如需修改 dict_type，引导用户删除后新增。

8. **动态路由注入的 showLink**：需确认 pure-admin 框架中 `showLink: false` 的静态路由 + 动态 push 菜单项能否正确在侧边栏显示。若不行，备选方案是静态路由不设 `showLink: false`，改用 `meta.roles` 或在 `permission` store 层过滤。

9. **`findAllRecord` 的 JS 层过滤**：现有 `findAllRecord` 改造后需在 SQL 层加 `status != 3` 过滤，保留 JS 层 rule/user_id 过滤。新 `findRecordData`（管理用）也需 `status != 3`，但**不按** rule/user_id 过滤，需返回全部未删除数据供管理。两个接口职责分离。

10. **后端测试**：`auto-ticket-service/__tests__/api/` 下有 `quanType.test.js` 等测试用例，本次应参照新增 `dictRecord.test.js` 覆盖 CRUD 场景（含唯一键冲突、批量删除空数组、只读项拒绝修改/删除、逻辑删除 status=3 等边界）。
