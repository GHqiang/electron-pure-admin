# 猎人规则删除不同步及同步链路隐患修复说明

> 日期：2026-08-23
> 状态：已实施并测试通过
> 说明：本文件记录 8-23 事故"规则删除后平台残留孤儿规则 → 平台继续报价 → 本地匹配失败 → 出票失败"的根因修复，以及按用户要求对同步链路的全面隐患排查与修复。

---

## 一、事故根因（复述）

**8-22 ~19:00** 用户删除规则 1860（华联万柳/hualian）后，本地删除成功但**平台规则 2560557 未删除**：

1. `deleteRow`（`offerRule/index.vue`）的**两条路径漏调 `delRuleSyncToPlat`**：
   - 有关联券 + 点"仅删除规则"（cancel 分支）：只 `svApi.deleteRule`，无平台删除；
   - 无关联券直接删除：只 `svApi.deleteRule`，无平台删除。
2. 唯一有同步的"删除规则和券"分支，`delRuleSyncToPlat` 的 catch **吞掉异常**（仅 console.warn），且顺序是"先本地后平台"——平台删除失败时本地已删，用户无感知。
3. **8-23 08:05:48** 平台用残留的启用中孤儿规则 2560557 对"华联影城(万柳店)"订单报价中标（40元）→ 本地 `lierenRuleCheck` 匹配失败（本地已无该规则，`规则明细=[]`）→ 出票失败。
4. **8-23 08:48** 登录同步（47025）发现孤儿规则 → 禁用；手动修复（47026）→ 删除。清理机制本身正常，但发生在失败之后 43 分钟。

## 四、回归风险评估

| 风险点 | 评估 |
|---|---|
| 删除顺序改为"先平台后本地" | 平台删除失败时本地不删、规则保留，用户可重试或走登录同步兜底；与 `saveRule` 既有"先同步后落库"模式一致。未同步平台的规则（isSyncPlat!=1 或非固定价）在 `delRuleSyncToPlat` 内被过滤，直接跳过平台删除，行为不变 |
| `lierenOfferRuleEditStatusPlat` 失败改为 throw | 调用方仅 `editRuleStatusSyncToPlat`（页面），已同步改为捕获提示；login_sync 双向检查（`checkAndUpdateLierenRuleState`）不经过此函数，不受影响 |
| `saveRuleSyncToPlat` 同步失败 throw | 编辑场景阻断落库（符合注释原意）；新增场景本地已落库，用 try/catch 包裹避免中断流程，规则保留待下次同步/人工处理 |
| `lierenOfferRuleDelPlat` 新增可选参数 | 默认 `[]`，旧调用方（测试等）兼容；`firstRule` 空对象时 `rule_id: null` 与原行为一致 |
| 后端删除 SQL 加 update_time | 仅更新时间戳，不影响软删除逻辑（status=4）与查询过滤（`NOT status = '4'`） |
| 删除失败提示收敛为单次 | 双弹窗消除后行为不变：用户仍能明确看到"删除猎人平台规则失败"，本地删除被阻断 |

## 六、出票侧反查禁用（第二道防线，已实施）

> 承接原遗留建议第 1 条：`BaseTicketQueue#lierenRuleCheck` 匹配失败时反查平台规则，确认孤儿且启用则立即禁用，把孤儿危害窗口从"小时/天级"压到**分钟级**——出票时顶多失败一次，不会一直无限循环失败。

### 6.1 实现位置

`src/common/core/BaseTicketQueue.js#lierenRuleCheck` 匹配失败分支（`!targetRule` 时），在告警前新增：

1. 从 `dictStore.dictInfo.lierenMainAccountAkSk` 取 AK/SK（优先当前 rule，回退第一个可用，与 `_getLierenAkSk` 同逻辑；`JSON.parse` 非法时按未配置处理，不阻塞出票）；
2. `lierenApi.ruleList({ rule_id: [platRuleId], ... })` 反查平台；
3. 仅当平台规则**存在 && state=1（启用）&& sum_mode=2（固定价）** 时 `lierenApi.ruleState({ rule_id, state: 0 })` 立即禁用，并记录 `platOrphanDisabled`；
4. 告警 `failReason` 附上"已自动禁用平台孤儿规则(id=…, name=…)"，便于人工确认；
5. 反查/禁用**任何异常都不阻塞出票与告警**（catch 仅记录日志，下一单会再次触发）。

### 6.2 关键边界（防误伤）

- **仅固定价（sum_mode=2）孤儿才禁用**：`getRuleIdByPlat` 创建的会员价规则（sum_mode=4，如 `_10202492`）本地无关联是**正常业务**（link 表关联而非 rule_record），禁用会误伤机器会员价报价——明确排除。
- **仅"未找到 platRuleId"时反查**：`targetRule` 存在但 offerType 非固定报价时本地有规则，不触发反查。
- **平台已禁用（state=0）或平台无此规则**：不重复禁用，仅告警。

### 6.4 回归风险评估

| 风险点 | 评估 |
|---|---|
| 出票热路径新增平台反查 | 仅在匹配失败（低频）且本地确认无规则时触发一次 ruleList + 至多一次 ruleState；成功匹配/机器报价/已禁用场景零额外请求；反查异常被 catch 包裹，不影响出票主流程与告警 |
| 误禁会员价规则 | 已用 `sum_mode == 2` 严格限定，sum_mode=4 的机器会员价规则不会进入禁用分支 |
| 与登录同步孤儿清理的交互 | 登录 `checkAndUpdateLierenRuleState` 发现孤儿先禁用（47025 路径）→ 出票反查时 state 已为 0 不再重复禁用；两条路径策略一致（固定价孤儿 → 禁用），无冲突 |
| 平台侧禁用后本地仍无规则 | 本单仍按原逻辑失败并告警（无法补写报价记录），但平台不再用它报价，后续订单不再命中该孤儿——即"顶多一次失败"目标达成 |
