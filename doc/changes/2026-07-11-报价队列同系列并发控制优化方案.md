# 报价队列同系列并发控制优化方案

> 日期：2026-07-11
> 状态：方案设计

---

## 一、背景与问题

### 1.1 现状

当前报价队列对同系列订单采用**统一并发上限**控制：

| 控制维度       | 机制                                                                                     | 当前值     |
| -------------- | ---------------------------------------------------------------------------------------- | ---------- |
| 系列分组键     | `dictStore.dictInfo.offerConcurrencySeriesKey` 指定字段名，默认按 `app_name`（影院标识） | `app_name` |
| 每系列并发上限 | `dictStore.dictInfo.offerConcurrencyPerSeries` 全局统一值                                | `2`        |
| 调度选单       | `findNextOrderToRun()` 遍历队列，跳过当前系列运行数 ≥ limit 的订单                       | —          |
| 日志诊断       | `_getSeriesBlockReasons()` / `_buildSeriesDelaySummary()`                                | —          |

**关键代码位置**：`src/common/core/BaseOfferQueue.js`

当前两个字典字段的职责：

| 字典字段                    | 职责                   | 当前值     | 问题                |
| --------------------------- | ---------------------- | ---------- | ------------------- |
| `offerConcurrencySeriesKey` | 决定按**哪个字段**分组 | `app_name` | ✅ 分组没问题       |
| `offerConcurrencyPerSeries` | 决定每组**多少并发**   | `2`        | ❌ 所有组一样的上限 |

```javascript
// getSeriesKey：根据 offerConcurrencySeriesKey 决定分组字段（当前值为 app_name）
getSeriesKey(order) {
    const seriesKey = dictStore.dictInfo.offerConcurrencySeriesKey; // "app_name"
    if (seriesKey) return order[seriesKey] || "default";
    return order?.app_name ?? "default";
}
// 返回举例："wanda"、"sfc"、"ume"、"guangmeiwenhua" ...

// getOfferConcurrencyPerSeries：所有系列共用同一个上限值
async getOfferConcurrencyPerSeries() {
    return dictStore.dictInfo.offerConcurrencyPerSeries || 2;  // 返回 2
}

// findNextOrderToRun：核心问题 —— 不管 sk 是什么，limit 都是同一个值
findNextOrderToRun() {
    const limit = this._offerConcurrencyPerSeries ?? 2;  // 所有系列都是 2
    for (let i = 0; i < this.queue.length; i++) {
        const sk = this.getSeriesKey(order);  // 能正确区分 wanda / sfc / ume ...
        if ((this.runningCountBySeries.get(sk) || 0) >= limit) continue;
        // ↑ 关键：不管 sk 是 wanda 还是小影院，都用同一个 limit=2 判断
    }
}
```

**一句话总结**：`offerConcurrencySeriesKey` 只管了"按什么字段分桶"，但每个桶的容量（`offerConcurrencyPerSeries`）对万达和小影院一视同仁都是 2。

### 1.2 核心痛点

**订单一多就出现大量"订单已结束"报价异常**，根本原因在于 **小影院和大连锁共用 2 的并发上限**，大连锁订单严重积压排队：

```
假设猎人平台瞬时涌入 100 个订单：
├── 万达系列: 30 单  ──→ 同一时刻只能跑 2 单，剩余 28 单排队
├── SFC 系列:  25 单  ──→ 同一时刻只能跑 2 单，剩余 23 单排队
├── UME 系列:  20 单  ──→ 同一时刻只能跑 2 单，剩余 18 单排队
├── 卢米埃系列:15 单  ──→ 同一时刻只能跑 2 单，剩余 13 单排队
└── 其他小影城:10 单  ──→ 同一时刻只能跑 2 单（资源浪费）

总计：2 × N_series 并发，但大连锁积压远超小影城
```

**问题链条**：

```mermaid
graph TD
    A[大量订单涌入] --> B[每系列限2并发]
    B --> C[大连锁排队严重]
    C --> D[单个报价耗时 10-15s]
    D --> E[排队时间 >> 竞价窗口]
    E --> F[offer_end_time 到期]
    F --> G[平台返回"订单已结束"]
```

### 1.3 各影院系列体量对比

| 系列             | 订单量级 | 2并发下排队风险 |
| ---------------- | -------- | --------------- |
| 万达 (wanda)     | 大       | 🔴 高风险       |
| SFC/乐影 (sfc)   | 大       | 🔴 高风险       |
| UME (ume)        | 大       | 🔴 高风险       |
| 凤凰 (fenghuang) | 中       | 🟡 中风险       |
| 金逸 (jinyi)     | 中       | 🟡 中风险       |
| 辰星 (chenxing)  | 中       | 🟡 中风险       |
| 卢米埃 (lma)     | 中       | 🟡 中风险       |
| 其他独立影院     | 小       | 🟢 低风险       |

## 二、并发安全性分析（哪些系列适合提高并发）

提高并发上限之前，需先分析各影院系列报价流程是否存在**有状态写操作**（锁座、扣余额等），否则并发报价可能导致：

- 🔴 **锁座冲突**：两个并发订单同时锁同一场次的"最贵座位"，后锁者覆盖前锁者
- 🟡 **会员价取错**：并发锁座时获取的 `order_id` 对应了不同座位，导致价格串号
- 🟢 **只读 API 并发**：多个订单同时查询同一场次座位布局，返回相同数据，无副作用

### 2.1 关键问题：`getSeatLayout` 实际发送的 API 请求是否带登录态

同一个登录态短时间内并发多次调影院接口，可能被影城判定为"异常高频"触发风控。因此不能只看 `offerManage` 里传了什么参数，**必须看 `seatManage.getSeatLayout` 的实际实现**，确认最终发送到影城 API 的请求中是否包含 session/token。

**逐系列实测分析**：

| 系列 | offerManage 传参 | seatManage 实际处理 | **请求含用户token?** |
|------|-----------------|-------------------|:---:|
| **SFC** | `session_id: ""` | `...(session_id && { session_id })` → 空串 falsy → **丢弃** | ❌ |
| **辰星 v3** | `featureAppNo`（影院编码） | 直接透传 → 非用户 token | ❌ |
| **辰星 v2** | `sessionId: movieInfo.sessionId` | 直接透传 → 用户 session | ⚠️ |
| **卢米埃** | `lmaToken: ""` | `...(lmaToken && { lmaToken })` → 空串 falsy → **丢弃**（`session_id: show_id` 是场次ID不是token） | ❌ |
| **UME** | `session_id: ""` | `...(session_id && { session_id })` → 空串 falsy → **丢弃** | ❌ |
| **万达** | `{ dId, json: true }` | 直接透传 → 只有场次ID | ❌ |
| **H5UME** | 未传 session_id | `...(session_id && { umeToken: session_id })` → undefined falsy → **丢弃** | ❌ |
| **凤凰** | `fenghuangToken` | 直接透传 → **带 token** | ✅ |
| **金逸** | `session_id` | 直接透传 → **带 session_id** | ✅ |

**SFC/UME 的关键代码**（seatManage.js）：
```javascript
// SFC seatManage.js
let { session_id } = data || {};
let params = {
    city_id, cinema_id, show_id,
    ...(session_id && { session_id }),  // ← "" 是 falsy，不会加入 params
    width: "240"
};

// UME seatManage.js
let { session_id } = data || {};
let params = {
    params: { cinemaCode, cinemaLinkId, scheduleId, scheduleKey, ... },
    ...(session_id && { session_id })  // ← "" 是 falsy，不会加入
};
```

**卢米埃的关键代码**（seatManage.js）：
```javascript
let { cinema_id, show_id, lmaToken } = data || {};
let params = {
    cinema_id,
    session_id: show_id,           // ← show_id 是场次ID，不是用户token
    ...(lmaToken && { lmaToken }) // ← "" 是 falsy，lmaToken 不会加入
};
```

**结论**：6 个系列（SFC/辰星v3/卢米埃/UME/万达/H5UME）实际发送的 API 请求**不含用户登录态**，如同"游客查场次"。只有凤凰和金逸真正带了 token。

### 2.2 各系列 `getMemberPrice` 操作全景

**所有 8 个系列**在 `getMinAmountOfferRule` 中都会调用 `getMemberPrice` 来获取真实会员价。各系列操作汇总：

| 系列 | getSeatLayout | 传登录态 | queryCardList | 额外 API | **锁座** | 并发风险来源 |
|------|:---:|:---:|:---:|------|:---:|------|
| SFC | ✅ | ❌ | ✅ | — | ❌ | IP 限流 |
| 辰星 v3 | ✅ | ❌ | ✅ | `fetchAvailableCards` | ❌ | IP 限流 |
| 辰星 v2 | ✅ | ⚠️ sessionId | ✅ | `fetchAvailableCards` | ❌ | 账号风控 + IP |
| 卢米埃 | ✅ | ❌ | ✅ | — | ❌ | IP 限流 |
| UME | ✅ | ❌ | ✅ | — | ❌ | IP 限流 |
| 万达 | ✅ | ❌ | ✅ | `getUsableCardList` | ❌ | IP 限流 |
| H5UME | ✅ | ❌ | ✅ | `getOptimalCardQuanCompose`(传session轮换) | ❌ | 查券 API 传 token |
| 凤凰 | ✅ | ✅ fenghuangToken | ✅ | `getSeatPrice`(查价) | ❌ | 账号风控 + IP |
| 金逸 | ✅ | ✅ session_id | ✅ | `lockSeatForOfferPrice` + `priceCalculation` | ✅ | 账号风控 + 锁座冲突 |

### 2.3 为什么不传登录态的系列是并发安全的

以 SFC 为例（卢米埃/UME/万达/H5UME 同理）：

```javascript
// sfc/offerManage.js — getMemberPrice 核心流程
async getMemberPrice({ order, movieData, minAddAmountRule }) {
    let movieInfo = await this.cinemaManage.getMovieInfo(order);     // API查场次

    const seatInfo = await this.seatManage.getSeatLayout({
        city_id, cinema_id, show_id,
        session_id: ""   // ← 空字符串！不鉴权，如同游客访问
    });

    // 取分区最高价（纯内存计算）
    maxSeatPrice = area_price.sort(...)[0].price;

    const cardRes = await svApi.queryCardList({...});    // DB只读

    return { real_member_price, discount, member_price }; // 纯计算
}
```

**并发 5 单时的实际效果**：
```
订单1 → getSeatLayout (无session) ─┐
订单2 → getSeatLayout (无session) ─┤  5个"游客"同时查同一场次
订单3 → getSeatLayout (无session) ─┤  影城只看到 5 个来自同一IP的查询
订单4 → getSeatLayout (无session) ─┤  不会关联到"某个账号频繁操作"
订单5 → getSeatLayout (无session) ─┘
```
- 返回的 `area_price` 是场次静态数据，5 次相同 → **会员价不会取乱**
- 影城按 IP 限流（通常阈值远高于 5） → **不易触发**

### 2.4 凤凰和金逸为什么有风险

**凤凰**传了 `fenghuangToken = useLoginList[0]?.session_id`：
```
订单1 → getSeatLayout(fenghuangToken="abc") ─┐
订单2 → getSeatLayout(fenghuangToken="abc") ─┤  影城看到"同一账号 4 次查座位布局"
订单3 → getSeatLayout(fenghuangToken="abc") ─┤  可能触发风控：临时封号/验证码
订单4 → getSeatLayout(fenghuangToken="abc") ─┘
```
- 如果 `useLoginList` 有多个不同手机号 → 可用不同 token 分散 → 风险降低
- 如果只有一个手机号 → 4 个并发都用同一个 token → **高风险**
- **建议上限 4**（比不传 token 的系列低一档）

**金逸**同理且更严重——传了 session_id 且还有锁座操作，**建议保持 1-2**。

### 2.5 最终配置建议

| 系列 | seatManage 实际发 token? | 锁座 | 风险 | 配置到字典 | 上限 |
|------|:---:|:---:|:---:|:---:|:---:|
| wanda | ❌ 无 | ❌ | 🟢 IP限流 | ✅ | **5** |
| sfc | ❌ 空串被丢弃 | ❌ | 🟢 IP限流 | ✅ | **5** |
| ume | ❌ 空串被丢弃 | ❌ | 🟢 IP限流 | ✅ | **5** |
| chenxing | ❌ v3传影院编码 | ❌ | 🟢 IP限流 | ✅ | **5** |
| lma | ❌ 空串被丢弃 | ❌ | 🟢 IP限流 | ✅ | **5** |
| fenghuang | ✅ 透传 token | ❌ | 🟡 账号风控 | ✅ 谨慎 | **4** |
| jinyi | ✅ 透传 session_id | ✅ | 🔴 风控+锁座 | ❌ 不配置 | **1-2** |

> **注**：以上为单平台单系列上限。多平台×同系列 = 实际并发（如猎人+芒果都有万达订单 → 2×5=10）。

## 三、方案设计

### 3.1 总体思路

增加字典表字段 `bigChainSeriesConcurrency`，以 JSON 格式配置各大型连锁系列的专属并发上限，未配置的系列仍使用全局默认值 `offerConcurrencyPerSeries`。

```
调度选单时：
  if (系列在 bigChainSeriesConcurrency 中有配置)
      → 使用该系列的专属并发上限
  else
      → 使用 offerConcurrencyPerSeries 全局默认值（兜底 2）
```

### 3.2 字典表新增字段

| 字段         | 值                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------ |
| `dict_type`  | `bigChainSeriesConcurrency`                                                                |
| `dict_value` | JSON 对象，key 为系列标识（与 `offerConcurrencySeriesKey` 对齐），value 为该系列的并发上限 |
| `status`     | `1`（启用）                                                                                |

**示例值**（当前分组键为 `app_name`，JSON key 必须用具体影院标识；**不包含金逸**——金逸报价阶段需锁座，不宜提高并发）：

```json
{
  "wanda": 5,
  "sfc": 5,
  "ume": 5,
  "chenxing": 5,
  "lma": 5,
  "fenghuang": 4,
  "jinyi": null
}
```

> **注意**：
>
> - JSON 的 key 必须与 `offerConcurrencySeriesKey` 指定的字段返回值一致。当前 `offerConcurrencySeriesKey = "app_name"`，所以 key 是影院标识如 `"wanda"`、`"sfc"`。
> - **金逸 (jinyi) 不配置专属上限**——其报价阶段会真实锁座（`lockSeatForOfferPrice`），提高并发会导致锁座冲突。金逸走 `offerConcurrencyPerSeries` 全局兜底值（建议保持 1-2）。
> - 如果将来把 `offerConcurrencySeriesKey` 改为 `app_type_code`，则 JSON key 需同步改为 `"wanda_applet"`、`"sfc_applet"` 等。

### 3.3 代码改造明细

#### 改造点 1：`BaseOfferQueue` 新增 `_getSeriesConcurrencyLimit(sk)` 方法

**文件**：`src/common/core/BaseOfferQueue.js`

**现状**（line 103-108）：

```javascript
_getSeriesConcurrencyLimit() {
    return (
      this._offerConcurrencyPerSeries ??
      dictStore.dictInfo.offerConcurrencyPerSeries ??
      2
    );
}
```

**改造后**：

```javascript
/**
 * 获取指定系列的并发上限
 * 优先使用 bigChainSeriesConcurrency 字典字段中的专属配置，
 * 未配置时回退到全局 offerConcurrencyPerSeries
 * @param {string} sk - 系列标识（与 offerConcurrencySeriesKey 分组结果一致，如 "wanda"、"sfc"）
 * @returns {number}
 */
_getSeriesConcurrencyLimit(sk) {
    const baseLimit =
      this._offerConcurrencyPerSeries ??
      dictStore.dictInfo.offerConcurrencyPerSeries ??
      2;

    // 解析大连锁专属并发配置
    const bigChainConfig = dictStore.dictInfo.bigChainSeriesConcurrency;
    if (bigChainConfig) {
      try {
        const configMap = typeof bigChainConfig === "string"
          ? JSON.parse(bigChainConfig)
          : bigChainConfig;
        if (sk && configMap[sk] && typeof configMap[sk] === "number") {
          return configMap[sk];
        }
      } catch (e) {
        console.warn("解析 bigChainSeriesConcurrency 失败，使用全局默认值", e);
      }
    }

    return baseLimit;
}
```

**查找逻辑对照表**（假设 `offerConcurrencyPerSeries=2`，`bigChainSeriesConcurrency={"wanda":5,"sfc":5,"ume":5,"chenxing":5,"lma":5,"fenghuang":4}`）：

| 订单 `app_name`  | 在 JSON 中？    | 返回值 | 来源                             | 报价阶段安全性 |
| ---------------- | --------------- | ------ | -------------------------------- | :------------: |
| `wanda`          | ✅ 有，value=5  | **5**  | `bigChainSeriesConcurrency`      |   🟢 纯计算    |
| `sfc`            | ✅ 有，value=5  | **5**  | `bigChainSeriesConcurrency`      |   🟢 纯计算    |
| `ume`            | ✅ 有，value=5  | **5**  | `bigChainSeriesConcurrency`      |   🟢 纯计算    |
| `chenxing`       | ✅ 有，value=5  | **5**  | `bigChainSeriesConcurrency`      |   🟢 纯计算    |
| `lma`            | ✅ 有，value=5  | **5**  | `bigChainSeriesConcurrency`      |   🟢 纯计算    |
| `fenghuang`      | ✅ 有，value=4  | **4**  | `bigChainSeriesConcurrency`      |   🟡 查价API   |
| `jinyi`          | ❌ 故意不配     | **2**  | `offerConcurrencyPerSeries` 兜底 |  🔴 锁座取价   |
| `guangmeiwenhua` | ❌ 不在 JSON 中 | **2**  | `offerConcurrencyPerSeries` 兜底 |   🟢 纯计算    |

**保留无参重载用于向后兼容**：

```javascript
/**
 * 全局默认并发上限（向后兼容，不带 sk 参数时使用）
 * @returns {number}
 */
_getSeriesConcurrencyLimit() {
    return (
      this._offerConcurrencyPerSeries ??
      dictStore.dictInfo.offerConcurrencyPerSeries ??
      2
    );
}
```

#### 改造点 2：`findNextOrderToRun()` — 从"全局统一上限"改为"按系列查独立上限"

**文件**：`src/common/core/BaseOfferQueue.js` line 322-336

**现状（关键只有一行要改）**：

```javascript
findNextOrderToRun() {
    const minOfferHandleEndTime = dictStore.dictInfo.minOfferHandleEndTime;
    const limit = this._offerConcurrencyPerSeries ?? 2;   // ← 所有系列都是同一个 limit
    const now = Date.now();
    // ...
    for (let i = 0; i < this.queue.length; i++) {
      const order = this.queue[i];
      if (!skipCheck && order.offer_end_time - now <= minOfferHandleEndTime) {
        continue;
      }
      const sk = this.getSeriesKey(order);  // 返回 "wanda"、"sfc" 等
      if ((this.runningCountBySeries.get(sk) || 0) >= limit) continue;
      // ↑ 不管 sk 是 wanda 还是小影院，都用同一个 limit 判断
      return { order, index: i };
    }
    return null;
}
```

**问题举例**（假设 `offerConcurrencyPerSeries = 2`）：

```
队列中有：wanda 订单×30, sfc 订单×25, guangmeiwenhua 订单×5

遍历到 wanda 订单 → sk="wanda" → runningCountBySeries.get("wanda")=2 → 2 >= 2 → 跳过
遍历到 sfc 订单   → sk="sfc"   → runningCountBySeries.get("sfc")=2   → 2 >= 2 → 跳过
遍历到 小影院订单  → sk="guangmeiwenhua" → runningCountBySeries.get(...)=0 → 0 < 2 → 执行

结果：wanda 和 sfc 最多只能同时跑 2 单，大量积压
```

**改造后（只改一行：`limit` → `this._getSeriesConcurrencyLimit(sk)`）**：

```javascript
findNextOrderToRun() {
    const minOfferHandleEndTime = dictStore.dictInfo.minOfferHandleEndTime;
    const now = Date.now();
    const skipCheck =
      this.platformAdapter?.config?.features?.skipOfferEndTimeCheck === true;
    for (let i = 0; i < this.queue.length; i++) {
      const order = this.queue[i];
      if (!skipCheck && order.offer_end_time - now <= minOfferHandleEndTime) {
        continue;
      }
      const sk = this.getSeriesKey(order);
      // ✅ 唯一改动：查该系列专属上限，而非全局统一值
      const seriesLimit = this._getSeriesConcurrencyLimit(sk);
      if ((this.runningCountBySeries.get(sk) || 0) >= seriesLimit) continue;
      return { order, index: i };
    }
    return null;
}
```

**改造后效果举例**（`bigChainSeriesConcurrency = {"wanda":5, "sfc":5, "ume":5}`，其余走兜底 2，金逸保持兜底 2）：

```
遍历到 wanda 订单 → sk="wanda" → _getSeriesConcurrencyLimit("wanda")=5 → running=2 → 2<5 → 可执行 ✅
遍历到 sfc 订单   → sk="sfc"   → _getSeriesConcurrencyLimit("sfc")=5   → running=2 → 2<5 → 可执行 ✅
遍历到 jinyi 订单  → sk="jinyi" → _getSeriesConcurrencyLimit("jinyi")=2 → running=2 → 2≥2 → 排队等待（金逸锁座风险，不提高）
遍历到 小影院订单  → sk="guangmeiwenhua" → _getSeriesConcurrencyLimit(...)=2 → running=0 → 0<2 → 可执行 ✅

结果：wanda 最多 5 单、sfc 最多 5 单、金逸保持 2 单、小影院 2 单，互不干扰
```

#### 改造点 3：`_getSeriesBlockReasons()` 日志适配系列专属上限

**改造后**：

```javascript
_getSeriesBlockReasons(order) {
    const sk = this.getSeriesKey(order);
    // ✅ 按系列获取专属上限
    const limit = Number(this._getSeriesConcurrencyLimit(sk)) || 2;
    const running = this.runningCountBySeries.get(sk) || 0;
    const reasons = [];
    const now = Date.now();

    if (!this._isOrderDeadlineRunnable(order, now)) {
      const remain = order.offer_end_time - now;
      reasons.push(
        `【本单不可调度】距报价截止过近(剩余${remain}ms，需大于${dictStore.dictInfo.minOfferHandleEndTime}ms)`
      );
      return reasons;
    }

    if (running >= limit) {
      const isBigChain = this._isBigChainSeries(sk);
      reasons.push(
        `【同系列阻塞】${sk}${isBigChain ? "(大连锁)" : ""} 已有 ${running} 单正在报价，达到并发上限 ${limit}，本单需等同系列报完`
      );
    }
    // ... 后续同系列排队逻辑不变
}
```

#### 改造点 4：新增辅助方法 `_isBigChainSeries(sk)`

```javascript
/**
 * 判断指定系列是否为大连锁系列（在 bigChainSeriesConcurrency 中有专属配置）
 * @param {string} sk - 系列标识
 * @returns {boolean}
 */
_isBigChainSeries(sk) {
  try {
    const bigChainConfig = dictStore.dictInfo.bigChainSeriesConcurrency;
    if (!bigChainConfig) return false;
    const configMap = typeof bigChainConfig === "string"
      ? JSON.parse(bigChainConfig)
      : bigChainConfig;
    return sk && typeof configMap[sk] === "number";
  } catch {
    return false;
  }
}
```

## 五、风险评估

| 风险                           | 等级      | 缓解措施                                                              |
| ------------------------------ | --------- | --------------------------------------------------------------------- |
| 并发过高导致平台 API 限流      | 🟡 中     | 大连锁上限建议从 4-5 起步，观察平台是否有 429/限流错误再调整          |
| 金逸锁座取价冲突（不再提高）   | 🟢 已规避 | 金逸不配专属上限，保持 `offerConcurrencyPerSeries` 兜底值（建议 1-2） |
| 凤凰/H5UME 查询 API 压力增大   | 🟡 中     | 上限控制在 3-4，观察 API 响应时间是否恶化                             |
| 并发过高导致本地浏览器资源紧张 | 🟢 低     | 报价操作主要是网络 IO，CPU 占用不高；如遇性能问题可适度降低上限       |
| JSON 配置格式错误导致解析失败  | 🟢 低     | 有 try-catch + warn 日志 + 回退兜底                                   |
| 多机器同时运行导致实际并发翻倍 | 🟡 中     | 此为已有问题，非本次改造引入；建议配合后续机器级互斥方案              |

## 六、后续优化建议

1. **动态调整机制**：根据队列积压深度自动临时提升并发上限（队列 > N 时自动 +1）
2. **机器级互斥**：多台机器同时跑时，通过 Redis/服务端做分布式并发控制
3. **紧急订单优先**：猎人的 `order_urgent` 字段（加急/特急/VIP）可跳过排队直接执行
4. **监控告警**：队列积压超过阈值时通过微信推送告警
