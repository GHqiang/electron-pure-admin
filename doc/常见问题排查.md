# 常见问题排查

## 1. 中标订单不出票

**现象**：平台已中标但一直没有出票，日志上看不到"发送新订单消息"相关日志。

**排查步骤**：

### 1.1 确认获取待出票队列是否在运行

```js
// 先开启控制台日志
window.isNeedLog = 1;
// 查看获取待出票队列运行状态
window.platFetchOrderQueueObj.lieren.isRunning;
```

返回 `true` 表示正常运行中。如果返回 `false`，去队列管理页面点击"一键全部启动"。

### 1.2 确认出票队列是否已启动监听

```js
window.isNeedLog = 1;
window.appTicketQueueObj.对应影线.isStart;
```

例如中影新（zhongyingxin）、SFC（sfc）、博纳（bona）：

```js
window.appTicketQueueObj.zhongyingxin.isStart;
window.appTicketQueueObj.sfc.isStart;
window.appTicketQueueObj.bona.isStart;
```

返回 `true` 表示已启动监听。如果返回 `false`，同样去队列管理页面启动。

### 1.3 确认事件监听器是否正常挂载

```js
window.isNeedLog = 1;
window.__ticketEventHandlers.has("newOrder_" + "zhongyingxin");
```

返回 `true` 表示该影线的出票监听器正常。没有的话可以刷新页面重试。

### 1.4 确认所有平台和影线队列一键启动

```js
window.isNeedLog = 1;
// 查看所有获取待出票队列
Object.entries(window.platFetchOrderQueueObj).map(([k, v]) => ({
  平台: k,
  运行中: v.isRunning
}));
// 查看所有出票队列
Object.entries(window.appTicketQueueObj).map(([k, v]) => ({
  影线: k,
  已启动: v.isStart,
  监听器: v._listenerAttached
}));
```

如果全部为 `false`，进入队列管理页面点击"一键全部启动"。

### 1.5 手动模拟发送测试订单（排查监听链路是否通）

在控制台执行：

```js
window.isNeedLog = 1;
window.appTicketQueueObj.zhongyingxin.testSendNewOrder();
```

如果控制台打印出"自动出票队列获取到新的待出票订单"说明监听链路正常，问题出在平台 API 返回空数据（即实际没有待出票订单）。

## 2. 某用户对某单「完全没有记录」

**现象**：同一角色、同一平台下，某订单在一个用户上有报价记录，在另一个用户上「未报价记录」、操作日志、明细日志都查不到，用户怀疑「程序没把单记到我名下」。

**先分清三种情况**（2026-10-19 起支持）：

1. **拉到了，入队前被丢弃**：该用户客户端确实拿到了这单，但在「能否登录/识别 → 是否重复 → 距截止是否足够」某一步被过滤，现在会写一条「未报价记录」并带原因。
2. **根本没拉到**：该用户客户端这一轮没有拿到这单（平台未返回、水位线错过、网络失败、客户端未运行），不会有「未报价记录」行；需要看拉单证据。
3. **无关订单**：影院 code 映射表没有 / 名称没匹配上（19）、系列或影院被禁用（18）、同角色所有用户都没有维护该影院登录（17 的子集）——按规则**不写库、不写 L1/L2**。这类单查不到是预期。

### 2.1 先看「未报价记录」页

打开「设置 → 未报价记录」，按订单号筛选，看「失败类型 / 失败原因 / 报价人」：

- 有 `入队前丢弃-*`：说明**已拉到、入队前丢弃**。失败原因列会写细分：
  - `距报价截止不足（剩余 Xms，阈值 Yms）`（16）
  - `无可用登录（缺 mobile 或 session_id / 登录不属于当前用户）`（17，且同角色有人有登录）
- 没有行：可能是没拉到，也可能是**无关订单**（19/18/同角色全无登录）——进入 2.2。

> 「未报价记录」只保留近 7 天（`offer_record_fail` 清理任务），超期查不到属正常。18/19 不会产生新行，**不要用“页面没有”推断“程序没记”**。

### 2.2 再打开「订单排查」页

「设置 → 订单排查」，输入订单号（日期会按订单号前 14 位自动带出），选择用户后点「排查」。页面会直接给结论：

| 结论 | 含义 |
|---|---|
| 目标用户已拉到，入队前丢弃 | 同 2.1，页面同时给出 `err_msg` 与报价人 |
| 目标用户已拉到并正常入队 | 该用户端处理过，后续报价成功/失败看「报价记录」/「未报价记录」 |
| 目标用户已拉到，但未发现丢弃/入队记录 | 异常缺口，提交开发按代码缺陷排查 |
| 同角色其他用户有记录，目标用户无记录：本机（当前页面）配置原因 | 对照记录里有 A 的 `cinema_code`，本机映射/登录/禁用状态显示 19/18/17；这是“为什么 A 有、B 没有”的首选答案 |
| 同角色其他用户有记录，目标用户无记录：本机配置正常，疑似未拉到 | 本机配置能报价、拉单循环正常，但没有该单的拉单返回；平台未返回或目标用户错过 |
| 未拉到：平台该轮未返回或属于无关订单 | 拉单循环正常、无失败；平台没返回，或该单是 19/18/同角色全无登录，按规则未记录 |
| 未拉到：客户端当时未正常拉单 | 该时段 `rounds=0`、拉单间隔过大或请求失败（网络/停机/水位线跳变） |
| 证据上传失败，无法判断 | 该时段 `trace_fail>0`，不能凭「无拉单返回」下结论 |
| 未拉到（无拉单摘要） | 超出 7 天保留期、该平台未接入拉单证据、客户端当时未运行，或该单属于无关订单 |

> 「订单排查」的「同角色记录」表**不按用户过滤**，会同时列出 A（有记录）和 B（无记录），并用「目标用户/其他用户」标注；下面的「本机配置对照」用 A 记录里的 `cinema_code`/名称，按**当前打开页面的这台机器**的映射/登录/禁用状态模拟“本机拉到会怎样”。查用户 B 请到 B 的客户端打开；本机配置对照只代表本机，不代表远端的 B。

> 一期只有 **lieren** 接入「拉单返回」证据；其他平台排查页会提示「该平台暂未接入拉单证据」，**不能**据此判「未拉到」。
> 无关订单（19/18/同角色全无登录）不会写 C1，所以“没有拉单返回”也可能是无关订单，不是平台没返回。

### 2.3 统计页（v6 已下线）

> 2026-10-19 按用户要求，统计页「拉单与入队前丢弃」模块及 `/discard`、`/pull` 接口**已全部下线**；逐单排查以 2.2「订单排查」页为准，不再提供聚合统计入口。

### 2.4 命令行兜底（开发用）

```bash
# L2 明细：拉单返回 / 订单丢弃 / 入队
node scripts/prod-query.js trace <订单号> --user-id <用户id> --date <YYYYMMDD>

# C2 拉单摘要（每 5 分钟一条）
node scripts/prod-query.js pull-summary --user-id <用户id> --date <YYYYMMDD>
```

注意：V3 后白名单系列的 L1 `opera_record` 只收 `errorSave`，正常链路明细只落 L2——**L1 为空是正常现象**；本方案的「拉单返回/订单丢弃」无论系列一律直传 L2，「拉单摘要」一律写 L1。无关订单（19/18/同角色全无登录）**不写 C1/B**，所以 trace 为空也可能是这类单。
